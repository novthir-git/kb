### 1. Benchmarks' Last Exam：审计 749 个任务后发现，多步/执行类 Agent 基准的"有效性"可能只有三成，且错判多数冤枉了答对的模型
- 领域：AI / 智能体
- 来源 / 发布日期：arXiv / 2026-11-20（作者 James Zhu、Zekki Cat，机构未披露）
- 摘要：作者审计 8 个前沿基准共 749 个任务及 767 次公开模型评测，检查每个任务的提示词、执行环境与评分器三者是否对"成功"达成一致定义。结果：经公开错误报告修订过的封闭式问答基准，有效性验证通过率达 92.5%；而 6 个多步/Agent 执行类基准仅 29.3%（但仍筛出 161 个验证通过的复杂任务）。失败模式因评分架构而异：评分细则类基准多因提示词与参考清单不匹配而失效；执行类 harness 则常见状态断言不完整、共享通道信息泄露、评分时序冲突三类缺陷。在已确认的缺陷中，71.7% 是冤枉了本应得分的合规解法，28.3% 是放过了走捷径的作弊解法——作者据此认为，现有排行榜的"天花板"可能系统性低估了前沿模型在很多实际任务上的真实能力。一项有效缓解：把评分从共享容器改为在全新容器里对已提交的补丁重新评分，可把确认的运行时绕过率从 14.7%（共享容器）降到 2.7%，降幅 5.5 倍；只读/静态类基准绕过率为 0%。本文是作者所称"Benchmarks' Last Exam"系列的第一个里程碑。
- 为何重要：本仓库线索 8（"LLM-as-judge / 评估基准不能被当作一次性冻结的裁判"）此前已累积 7 条独立证据（评委打分不稳定、评分标准该演化、排行榜名次无统计显著性、工具调用信任前提、长时评估可观测性、离线审计身份识别不可能性、把基准当软件持续维护），早已跨过门槛 a 并多次提议沉淀，仍待用户批量处理。本文从第八个角度切入——用 749 个任务的规模化审计直接量化"有效性"本身的比例，并首次指出"评分缺陷方向不对称"（冤枉合规解法远多于放过作弊解法），意味着榜单分数可能是模型真实能力的下限而非真值。证据边界：仅两位作者，论文页未披露机构归属，提交者姓名与作者列表不一致（需留意）；"有效性"判定依赖作者自建的三方核验协议，未见第三方交叉复核；8 个基准具体名单未在本次核验中逐一列出；预印本，无同行评审信息。
- 原文：[Benchmarks' Last Exam](https://arxiv.org/abs/2611.27622)（检索于 2026-11-23）

### 2. Markdown Is Not a Firewall：给 Coding Agent 配一份规则文件（如 AGENTS.md/CLAUDE.md），测试结果是部分模型反而更不听话、真正拦住越界的是外部网关而非文件本身
- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-11-20（单一作者 Sandeep Dhuri，机构未披露）
- 摘要：作者测试一份仓库根目录的单页规则文件是否能约束 Coding Agent，让 4 个 agent（Claude Code、Codex CLI、Gemini CLI、OpenCode + DeepSeek）在 20 个带隐藏测试的小仓库中工作。其中 3 个 agent 面对 4 类预设边界（一个被拒绝的接口、一条捷径式破坏性操作、一条被植入的指令、一个被植入的包），并在一个 mock 服务前设置了与规则文件完全独立的网关，专门拦截并记录违规请求。结果：加入规则文件后，Codex CLI 的隐藏测试通过率从 99.0% 降到 67.7%，四个 agent 合计通过率从 98.2% 降到 90.9%；各 agent 很少主动尝试越界，但所有真实发生的越界尝试均被网关拦下——不是被规则文件本身拦下。作者还披露一处脚本错误导致未能测出规则文件在 HTTP 边界上的具体效果。结论："一份文件告诉 agent 你想要什么，一个网关决定它能拿到什么。"
- 为何重要：这篇论文直接检验的是本仓库自身也在用的治理模式——用一份 Markdown 规则文件（AGENTS.md/CLAUDE.md）约束 agent 行为。它用具体数字证明：至少对 Codex CLI 而言，加入规则文件反而显著拖累了任务通过率（99.0%→67.7%），而真正的越界防御来自文件之外的独立网关。这为本仓库线索 42（"生产级 AI 系统的护栏可拆解为带独立量化效果的具体模式目录"，此前已靠另一篇论文命中门槛 c、提议追加到 `wiki/topics/agent-生产级落地的鸿沟.md`，尚待用户批准）补上一个此前缺失的具体子模式——"仓库规则文件"这一护栏形式本身的量化效果（劝导性强、强制力弱）。
- 证据边界：单一作者，机构未披露，无同行评审信息；仅测试 20 个小型仓库与一份特定规则文件，能否推广到更大型真实生产仓库及其他规则文件内容未知；"HTTP 边界效果未测出"是作者自陈的脚本错误导致，这部分结论本身不完整；"agent 很少主动尝试越界"也可能只反映本次测试对抗强度不足，而非真实合规性；Codex CLI 通过率骤降而其他三个 agent 变化很小的机制性原因，摘要未给出解释；预印本，无第三方复现。
- 原文：[Markdown Is Not a Firewall](https://arxiv.org/abs/2611.27112)（检索于 2026-11-23）

### 4. Generalist Action Critic：让一个冻结的前沿通用模型给自动驾驶专用 Planner 当"事后把关人"，纯推理期架构改动纠正过半可纠正的不安全选择
- 领域：汽车 / 自动驾驶
- 来源 / 发布日期：arXiv / 2026-11-20（13 位作者：Yun Yan、Shizhi Hu、Zhichao Li 等，机构未披露）
- 摘要：论文提出 Generalist Action Critic（GAC），一个零样本框架，通过推理期 harness 把前沿通用模型的泛化推理能力与专用驾驶 Planner 结合：专用 Planner 先生成多条候选轨迹并给出初始选择，随后一个完全冻结（不做任何微调）的前沿模型作为"批评者"，依据场景证据（带空间叠加标注的摄像头画面+文字驾驶上下文）复核该选择，决定维持原选或换选另一候选——harness 同时控制每个阶段对批评者可见的信息范围。结果：在 HUGSIM 上，GAC 把 DrivoR 的 HD-Score 提升到 43.2，是未使用额外仿真训练数据的方法中最高分；在闭环测试中，GAC 在三个不同 Planner 上都提升了驾驶安全性，HD-Score 相对增益最高达 32.1%；在 NAVSIM v1 上，GAC 纠正了多达 52.13% 的可纠正不安全轨迹选择，同时只在原本已是高质量选择中引入 0.67% 的新增失误。
- 为何重要：本仓库线索 4（"Harness 设计是决定同模型实际表现的独立架构变量"）已累积近 30 条跨两个多月的证据，此前全部来自软件 / coding agent 场景。GAC 首次把这一判断系统性延伸到自动驾驶规划领域——不靠扩大模型规模或重新训练 Planner，只靠在推理期加一层"冻结通用模型当复核把关人"的架构改动，就在标准测试集上拿到可量化的安全收益（最高纠正 52.13% 的可纠正不安全选择），且误伤率很低（0.67%）。这也与本仓库自动驾驶相关的既有证据（如线索 90"规划器注意力权重只反映相关性不反映因果"、线索 15"把场景生成和规划决策统一到同一模型以打破'基准领先≠鲁棒'假象"）形成呼应——都指向"仅靠基准分数不足以判断规划器真实安全性，需要额外的复核/验证层"。
- 证据边界：13 位作者，论文页未披露机构归属（部分作者姓名曾出现在国内智能网联汽车研究团队的既有文献中，但本次核验未能从论文本身确认机构，故不在此断言）；全部数字均来自作者自建的 HUGSIM、NAVSIM v1 基准与闭环测试设置，未见独立第三方复现；用作"批评者"的具体前沿模型名称未在本次核验中确认；该方法在真实道路场景（而非仿真/基准）下的安全收益是否成立未经验证；预印本，无同行评审信息。
- 原文：[Generalist Action Critic](https://arxiv.org/abs/2611.27804)（检索于 2026-11-23）

### 5. Who Grades the Agent？给 Coding Agent 评测装上"考官/考生物理隔离"，专门防 Agent 自己伪造通关（今日最值得细读）
- 领域：软件工程（第二条，今日最值得细读）
- 来源 / 发布日期：arXiv / 2026-11-20（作者 Nathan Nour Houlamy、Mattia Favretto、Earlence Fernandes、Mauro Conti，机构未披露）
- 摘要：论文指出，现有多数 Coding Agent 基准让同一个 agent 既执行任务又触碰评分所需的环境状态，这意味着 agent（或其生成的候选解）本身就有能力影响甚至伪造"通过"这个判定。作者提出 SplitBench，一种把"运行测试"与"评分判定"物理/权限隔离的分裂验证架构——被 agent 控制的环境（图中标红）与可信评分组件（标绿）严格分离，并按明确步骤顺序交互。在真实评测中，SplitBench 与原生评分器在 98.7% 的尝试上给出一致判定，同时在专门设计的对抗性"伪造通关"攻击中拦下了 75% 的攻击。
- 为何重要：本仓库线索 8（见第 1 条）已有 7 条证据覆盖"裁判打分不稳定""排行榜统计不显著""工具调用信任前提""离线审计身份识别不可能性"等角度，但均未专门处理"agent 本身能否篡改评分环境"这一更直接的对抗性威胁。本文第一次把这个角度从"诊断问题"推进到"给出具体防御架构"——权限隔离本身是一种可直接落地的工程对策，而不只是又一次测量不可靠性的证据，补上该线索此前缺失的"防御侧"维度。
- 证据边界：4 位作者，论文页未披露机构归属；"98.7% 一致""75% 攻击被拦下"均为作者在自建的 SplitBench 及自设计对抗攻击集上的自报结果，未见独立第三方基准或红队复核；该对抗攻击集对真实世界"刷分"手法的代表性未知；预印本，无同行评审信息。
- 原文：[Who Grades the Agent? Privilege Separation for Coding-Agent Benchmarks](https://arxiv.org/abs/2611.27860)（检索于 2026-11-23）

## 今日主线

这 5 条表面分散在"基准有效性""仓库规则文件""AI 理财 agent""自动驾驶规划器""Coding Agent 评分架构"五个具体话题里，但共同指向同一个更底层的问题：**谁来验证"验证者"本身？** Benchmarks' Last Exam 审计的是基准评分器是否真的量出了能力；Who Grades the Agent 进一步问"被评测的 agent 能不能反过来篡改评分环境"；Markdown Is Not a Firewall 说明一份治理文件本身不是执行机制，真正拦住越界行为的是独立于文件之外的网关；Supertake 则是这个问题在商业产品层面的具体映照——当 agent 被授予动钱权限，"同意门槛""偏离限制""异常监控"这些护栏本身是否可信，和"AI 判断是否准确"同等重要；Generalist Action Critic 把这个思路反过来用——在自动驾驶场景主动引入一个独立于专用 Planner 之外的"把关人"模型，用架构上的复核机制去弥补单一规划器自身验证能力的不足。五条证据合起来说明：无论是评测基准、治理文件、资金护栏还是驾驶规划器，"自我报告/自我验证"都不可靠，需要结构上独立于被验证对象的第二层核查。
