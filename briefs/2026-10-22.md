### 1. Agent S4：让 agent 自己进化它用的接口，开源权重反超 GPT-5.5 和 Claude Opus 4.8

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / 2026-10-21 公示（v1 于 2026-10-20 17:47:37 UTC 上传）
- 摘要：论文指出，计算机操作型（computer-use）agent 目前受限于人工预先设计的"接口"——一个 agent 可能逐格输入电子表格，而一行代码就能做到；也可能为找一个函数而把两千行文件整个打印到终端。作者主张"接口设计本身应该成为 agent 的能力"，提出 Agent S4：一个 meta-agent 在不提供成功标签的前提下研究任务 agent 在合成训练任务上的执行轨迹，据此构建并修订一个不断演化的"接口与使用知识仓库"；再用基于种群的演化机制，依据 meta-agent 从未见过的验证任务上的表现，挑选哪些仓库版本值得继续演化，偏好能泛化到未见任务的改动。论文明确把模型 M 与 harness H 保持固定，只演化接口层本身。在 OSWorld V2 上，搭配 Qwen3.8-27B 与演化出的接口仓库，Agent S4 刷新开源计算机操作 agent 的 SOTA：二元得分 21.3%，是同一模型固定接口版本的 3.8 倍，且高于 GPT-5.5（13.0%）与 Claude Opus 4.8（20.6%），成本约为二者的 4.3% 与 1.5%；在 ScienceBoard 上，同一模型的成功率从 41.4% 提升到 58.6%。代码已开源（github.com/simular-ai/agent-s）。
- 为何重要：这篇论文把本仓库持续追踪的"harness 独立于模型"判断，往前推了一层——它在实验设计上把"接口"明确从模型与 harness 中单独拆出来，证明"接口该怎么设计"本身也可以是一个靠经验自动演化、而非人工预先画死的独立变量，且在不改模型、不改 harness 的前提下带来 3.8 倍的提升，上限还超过了成本高得多的前沿闭源模型。证据边界：跨模型对比的得分与成本数字分别来自不同来源（本文自测 vs. 其他模型"各自报告的成本"），并非在同一硬件、同一时间窗口下的直接对照实验；两个基准均是桌面/科学计算场景的 computer-use 任务，能否推广到更一般的编码或业务 agent 场景未验证；接口演化依赖的训练轨迹来自合成任务且无成功标签，其质量上限尚不清楚；论文未披露投稿状态，暂无第三方复现；"接口"与团队此前已有的"harness"概念边界如何精确划分，论文本身也只是在方法设计层面做了区分，并未给出通用定义。
- 原文：[Evolving Agent Interfaces](https://arxiv.org/abs/2610.28601)
- 配图：![Agent S4 把任务经验转化为持续演化的接口与知识仓库](https://arxiv.org/html/2610.28601v1/agent_s4_method.png)
  图片来源：[Evolving Agent Interfaces 论文 Figure 3](https://arxiv.org/html/2610.28601v1)。

### 2. 63.2% 的 AI 生成 PR 改代码不改文档——文档漂移第一次被大规模量化

- 领域：软件工程
- 来源 / 发布日期：arXiv（APSEC 2026 Early Research Achievements 接收）/ 2026-10-21 公示（v1 于 2026-10-19 23:07:59 UTC 上传）
- 摘要：Monash University 两位作者分析了 AIDev 数据集中 2,585 个仓库的 29,669 条 AI 生成 Pull Request，衡量"文档协同变更"：代码文件改动是否在同一 PR 内伴随文档文件更新。结果：63.2% 的 AI PR 改了代码却完全没更新任何文档；该比例随任务类型大幅波动——功能类 PR 为 55.2%，重构类 PR 高达 77.5%。未同步文档的代码文件，在 30-90 天窗口内被同一文件的修复 PR 跟进的比例，比已同步文档的文件高 8.6-11.7 个百分点；但按 PR 原始规模直接比较会得出相反结论，因为已同步文档的 PR 平均规模是未同步的 3.9 倍、因而吸引更多修复——控制规模后结论才反转回来。已同步文档的改动合并更快（中位数 40 秒 vs. 184 秒），尽管其规模更大。更关键的是，漂移会自我累积：90 天内，一个未同步文档就改动的文件，之后被"补上文档"的比例只有已同步文档文件的一半（24% vs. 48%），说明文档债务更倾向于累积而非被回头偿还。
- 为何重要：这是本仓库持续追踪的"代码与文档漂移"论点迄今样本量最大（2,585 个仓库、近 3 万个 PR）的实证量化基线，第一次把"漂移会不会被偿还"这个问题直接测出数字——答案是：不太会，而且这个倾向本身会自我强化。它也提供了一个此前证据（gh-aw 工作流文件的实证维护模式）所缺的大规模、跨仓库对照数据。证据边界：该指标只衡量"是否有任何文档文件被改动"，不衡量更新是否必要、是否语义正确——一次无关的 CHANGELOG 编辑算"协同"，一次确实不需要文档的内部重构算"漂移"，且仅能看到仓库内文档文件，看不到行内注释、docstring 与仓库外文档（wiki、托管站点、API 门户），这会把 63.2% 这个比例推高；"修复更多"的归因是文件级、时间上的关联，并非因果——同文件修复未必源自原始改动本身；数据集时间窗为 2024 年 12 月至 2025 年 8 月，随 agent 快速演化可能已部分过时，且 agent 分布严重不均（Codex 占 65.8%，Claude Code 仅 1.4%），整体比例被向 Codex 风格工作流加权；人类 PR 数据缺乏文件级细节，论文本身也承认无法给出人类基线做直接对照。
- 原文：[Documentation Drift in AI-Generated Pull Requests](https://arxiv.org/abs/2610.27381)
- 配图：![按 agent 划分的文档漂移率，整体漂移率 63.2%](https://arxiv.org/html/2610.27381v1/figs/drift_rate_by_agent.png)
  图片来源：[Documentation Drift in AI-Generated Pull Requests 论文 Fig. 2](https://arxiv.org/html/2610.27381v1)。

### 5. 阿里内部数据：同一个模型，换三版 harness，交付率涨了 3.67 分（AI / 智能体，今日加选）

- 领域：AI / 智能体（Agent，今日加选）
- 来源 / 发布日期：arXiv / 2026-10-20 公示（v1 于 2026-10-19 13:39:42 UTC 上传）
- 摘要：浙江大学与阿里巴巴淘天集团合作的论文指出，现有评测多把 coding agent 的任务设定为"解决一个 issue"或"从零开发"，缺乏对"能否完整履行产品需求文档（PRD）、交付在哪里断裂"的洞察。作者构建 PACE-Bench：43 个源自真实企业内部研发平台的任务、750 个经专家审校的 Code Point，通过需求重建、验收标准构造与基于证据的评估来衡量 PRD 履行度，并把交付缺口追溯回具体 agent 行为。在 11 个模型—scaffold 组合上，多数得分落在 52.1 到 78.1 之间，表现最好的 GPT-5.6-Sol 完整交付率也只有 14.0%；"实现不完整"与"缺失集成"是主要瓶颈——做出各个零件并不等于交付完整功能。评估框架与专家共识的一致率达 95.2%，且跨评审记录的一致性比重复执行本身更稳定。论文披露的最关键证据是：作者把这套诊断方法应用到自家 coding-agent 平台的 harness 迭代上——**在同一个模型（Opus-4.5）、同一套冻结的 43 任务套件下，连续三版 harness 发布使平均得分从 59.37 升到 61.34 再到 63.04（累计提升 3.67 分）**，同期需求交付时间从 30.36 天压缩到 14.03 天（2 月至 8 月）。
- 为何重要：这是本仓库持续追踪的"harness 是独立于模型的架构变量"这一判断，迄今最直接的一次量化证实——模型完全不变，只是换了三版 harness，同一套冻结任务上的表现就能稳步上涨，且数据来自阿里真实内部研发平台的生产记录，而不是作者自建的合成基准。它和条目 2 共同把"这套系统到底可靠到什么程度"从定性讨论推进到具体数字：11 个组合里最高完整交付率只有 14%，意味着即便是当前最强的模型—scaffold 组合，距离"可信赖地完整交付一份企业级 PRD"仍有巨大差距，直接回应 `wiki/purpose.md` 关键问题 1（agent 能力落到生产要跨哪些具体门槛）。证据边界：任务来源单一，均出自阿里巴巴淘天集团一家公司的内部开发记录，作者明确说明未与"从 merge request 挖掘"等替代任务构造方式做对比，任务来源的代表性未知；"harness 三版迭代提升 3.67 分"的具体改动内容（检索修复、工具指引、完成度追踪等）由作者自行选择与排序，并非受控消融实验，无法单独拆解每一项改动的贡献；评审专家均为中国境内的公司员工，评审过程是否存在文化或业务领域偏向未讨论；基准规模为 43 个任务，样本量中等；论文未披露投稿状态，暂无第三方复现。
- 原文：[When Coding Agents Outpace Review: Evaluating PRD-Driven Development in Mature Enterprise Repositories](https://arxiv.org/abs/2610.26394)
- 配图：![PACE-Bench 把生产需求转化为冻结验收标准、证据支撑的判断与可追溯诊断](https://arxiv.org/html/2610.26394v1/pace_bench_overview_updated.png)

## 今日主线

今天 5 条的共同落点是：agent 系统的进步，越来越多地来自模型之外的那层——接口、harness、文档这些此前被当作"配套设施"的部分,正在变成可以被独立测量、独立改进、也可能独立失效的一等架构变量。条目 1 把"接口设计"从模型与 harness 中单独拆出来,证明它可以靠经验自动演化、不靠人工预先画死,还能在不动模型、不动 harness 的前提下把开源权重的计算机操作能力做到反超前沿闭源模型。条目 5 则从真实企业生产数据的角度,给"harness 独立于模型"这一本仓库持续追踪的判断,补上迄今最干净的对照——同一个模型,只换 harness,交付率就能稳步上涨;但它同时也诚实地报告,即便是当前最强组合,完整交付率也只有 14%,提醒这场"系统层改进"游戏远没有打完。条目 2 是同一枚硬币的另一面：文档,作为维持这整套系统"不漂移"的调和机制之一,在 AI 规模化生产代码时正系统性地被甩在后面,而且一旦被甩下就很难被追上。条目 3 提醒,除了接口、harness、文档这些"怎么用好已有模型"的轴,还有创业公司在赌一个更根本的问题——如果训练本身能不那么依赖海量数据,这些系统层改进的边界会不会整体位移。条目 4 则是最朴素的提醒：所有这些系统层投入,目前都要靠真金白银的利润去填——Tesla 这一季利润砍掉四成,公司自己承认账单主要来自 AI、Optimus 与自动驾驶,这场"模型之外怎么赢"的竞赛,正在真实地改变财报的样子。
