### 1. 把"该不该调用工具"钉在一个可因果操纵的内部向量上

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / 2026-10-08 公示（v1 于 2026-10-07 UTC 上传，已被 NeurIPS 2026 接收为 Main Poster）
- 摘要：作者用"换一个动词"的方式制造 500 组极小对照句对（覆盖 Python/Java/C++，300 组用于分析、200 组留作评测）——把句子里的执行动词（如"write"）换成分析动词（如"discuss"），模型是否调用工具的决策会随之稳定翻转。作者进一步定位出一个记为 μΔ 的内部向量，证明它对该决策因果上既必要又充分，并验证该向量能泛化到 τ²-Bench 的真实多轮交互轨迹，以及完全不含动词线索的请求上。机制分析显示：分析型动词会通过一组"工具非必要"的特征主动抑制这个向量所代表的"默认调用倾向"，而执行型动词基本不触碰它；下游的注意力头与 MLP 特征负责把这个状态读出来并付诸行动。该机制在 Qwen、Mistral、Granite 三个模型家族、共 7 个模型上复现。
- 为何重要：此前关于"怎么让 agent 别乱调用工具"的讨论大多停留在提示词工程层面，这篇论文第一次把这个决策钉在一个可被因果操纵的具体内部开关上，说明"语义上该不该动手"这件事在模型内部有专门的、可定位的抑制回路，而不只是靠经验调参凑出来的行为。证据边界：验证覆盖的 7 个模型均属中小型开源模型家族（Qwen/Mistral/Granite），未覆盖 GPT、Claude、Gemini 等闭源前沿模型；500 组极小对照句对为作者构造的合成数据，能否代表真实用户请求的语言多样性未验证；论文虽被 NeurIPS 2026 接收，但形式为海报而非口头报告。
- 原文：[How Do Agentic LLMs Decide to Call Tools? A Tool-Call Vector Shaped by Suppression](https://arxiv.org/abs/2610.09624)

### 2. 子 agent 自主决定何时并行执行，是把双刃剑

- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-10-08 公示（v1 于 2026-10-07 UTC 上传）
- 摘要：论文研究"动态并发"——coding agent 在执行过程中自主判断是否派生、以及如何派生并行子 agent 来处理长周期开发任务。作者在 Codex、Claude Code、Kimi Code 三款生产级 coding agent 上，分别开启与关闭该策略，覆盖 354 个任务、共 2,124 次执行，既评估端到端效果，也分析调度行为本身；通过配对轨迹分析，识别出 13 种并发特有的失效模式、28 种可观察的执行模式，并归纳出该策略真正带来帮助的具体条件。
- 为何重要：这把"harness 设计是独立于模型的架构变量"这一已反复验证的判断，从"该不该用子 agent"推进到更细一层的"子 agent 该不该自主决定何时并行"，首次给出三款主流生产级 harness 在这一具体编排决策上的横向对比与系统性失效分类，而不只是单一产品的案例报告。证据边界：摘要未给出端到端成功率提升或下降的精确数字，仅定性描述"有时有帮助、有时有害"；354 个任务是否存在偏向某一款 harness 的系统性基准选择未说明；论文未披露投稿状态，尚无第三方复现。
- 原文：[When Sub-Agents Work in Parallel: The Promises and Pitfalls of Dynamic Concurrency in Long-Horizon Coding Tasks](https://arxiv.org/abs/2610.10263)
- 配图：![Kimi Code AgentSwarm 在 seqtk 重建任务上的动态并发执行示意图](https://arxiv.org/html/2610.10263v1/illustrative_example_seqtk.png)
  图片来源：[论文配图](https://arxiv.org/html/2610.10263v1)。

### 5. agent 对工具失败的反应，是看"报错信号"而不是看"返回内容"

- 领域：AI / 智能体（Agent，今日加选）
- 来源 / 发布日期：arXiv / 2026-10-08 公示（v1 于 2026-10-07 UTC 上传）
- 摘要：作者给一个已有的 function-calling 基准的可执行环境包上一层故障注入层，在轨迹中受控位置注入四类典型故障（显式报错、看似合理但错误的返回值、超时、工具缺失/schema 漂移），记录 agent 是否察觉问题、是否改变计划、是否恢复、是否原地重复。实验覆盖 3 个模型家族共 6 个模型（一半为推理变体）、24 个多步任务、共 1,920 次试验。结果显示：显式报错下 91.3% 的试验 agent 能察觉问题，但面对"看似合理但错误"的返回值时察觉率骤降到 58.8%，且在 26.8% 完全没有故障的试验中 agent 也会"误报"问题。推理模型比对应的 instruct 版本更少察觉故障（低 9.3 个百分点，p<.001），但更倾向于改变计划（高 10.4 个百分点，p<.001），恢复率两者无显著差异（p=.512）。由于 agent 本身具有随机性，两次完全无故障的运行达到相同最终状态的比例也只有 63.3%——以此为基线，四类故障里只有"工具缺失"显著拉低恢复率（39.9%），超时、schema 漂移、返回值损坏都落在正常的运行间波动范围内。故障发生后，agent 连续三次以上调用同一工具的比例最高达 22.2%。提示 agent"逐项核查结果"并未提升其察觉率。作者原话："Agents respond to the error channel rather than to the content of what a tool returns."
- 为何重要：与条目 1 形成决策前后两端的互补对照——条目 1 关注"该不该调用工具"这一决策前端是否存在可操纵的内部开关，这篇论文关注"调用完之后 agent 能不能真的发现出了什么问题"这一决策后端；"agent 对报错信号本身反应、而非核验返回内容"这一结论，与此前多条证据（09-24 Trace Tampering 论文、"agent 工具执行的运行时授权治理"线索中"沙箱产物隐式信任"子维度）共同指向一个反复出现的模式——运行时的监控与故障处理机制，默认信任的往往是表层信号而非实质内容。证据边界：全文仅单一作者，所属单位为德克萨斯理工大学媒体与传播学院而非计算机科学/人工智能系所，学术背景与论文技术内容的匹配度存疑；1,920 次试验基于单一已有基准改造而成，6 个模型的具体名称未在摘要/简介层面完整披露；63.3% 的"运行间基线一致率"依赖 agent 自身的随机性设置（温度等超参数未说明），能否代表生产部署的真实波动范围未知；论文未披露投稿状态，无第三方复现。
- 原文：[Loud Failures, Quiet Failures: Fault Detection and Recovery in Tool-Using Language Model Agents](https://arxiv.org/abs/2610.10062)

## 今日主线

这五条共同拼出一张"agent 的自主性每往前推进一步，背后缺的那套验证机制是什么"的地图：条目 1 发现"该不该动手"这个决策在模型内部有一个可被因果操纵的具体开关；条目 5 发现"动手之后出没出错"这件事 agent 自己却经常看错方向——合在一起，决策前端有机制、后端缺核验。条目 2 把同样的张力带到编排层：子 agent 自主决定何时并行，本身也会带来一整类此前没被归类过的新失效模式。条目 3 显示资本仍在不计代价地押注"更好用的通用 agent 产品"，但该押注买到的主要是体验数据，不是独立验证的可靠性证据。条目 4 则提醒一旦 agent 真正接管物理世界的决策（自动驾驶），监管机构要求的"自证合规"本身也会变成一场关于时间表的博弈，而不是一次性过关的仪式。
