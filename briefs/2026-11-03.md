### 1. Verify–Backtrack Loop：给长时 Agent 一个可追溯的"计划状态"，而不是更长的自由文本反思（AI / 智能体）

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv 2610.41564 / v1 于 2026-10-30 10:58:17 UTC 上传，作者 Mingyang Liu、
  Qingcan Kang、Shixiong Kai、Tao Zhong、Mingxuan Yuan、Xin Li、Linqi Song（页面未披露机构
  归属）；主类 cs.AI，无交叉分类；Comments 字段未标注。
- 摘要：ReAct 及后续反思/自适应规划方法把"失败后怎么办"表达为自由文本反思，没有显式的控制状态
  把终极目标、当前活跃子目标与失败原因关联起来。作者提出 Verify–Backtrack Loop（VBL）：训练-free
  扩展 ReAct，维护一个有界的目标栈；当子目标被激活、执行失败或状态发生实质变化时，双重核验该
  子目标是否仍服务于终极目标、以及在当前状态下是否可行；结合失败归类，触发 Push（插入前置
  步骤）、Pop、重试或 BacktrackTo（回退到父目标）四种显式操作。在 Qwen3.5-9B、GPT-4o、
  DeepSeek-V3.2 三个模型底座上，分别在 AppWorld、ALFWorld、ScienceWorld 测试，VBL 在每一个
  "模型×基准"组合上都优于 ReAct 与基于反思的控制方法，在 AppWorld 上相对 ReAct 最高提升 22.07
  个百分点；消融显示去掉核验或归因任一环节都会掉分、部分情形甚至低于 ReAct 基线，证明两个机制
  互补。
- 为何重要：这条证据把"模型该怎么从失败中恢复"从自由文本反思改造成可审计的显式状态机，呼应
  「harness-vs-model」页已有的核心判断——同一组模型（Qwen3.5-9B/GPT-4o/DeepSeek-V3.2）仅替换
  控制结构就获得跨模型一致的提升，说明表现的决定因素里，harness/控制结构是独立于模型本身的
  变量；这是该线索目前候选池中第 26 条左右的新证据（该主题证据池已持续两月有余，多次建议批量
  批准沉淀，仍待处理）。证据边界：论文未披露作者机构归属；三个测试环境（AppWorld、ALFWorld、
  ScienceWorld）均为仿真/模拟型基准，不是真实生产工具调用日志；"训练-free"意味着不需要更新
  模型权重，但目标栈维护与双重核验本身会增加推理时的调用次数与延迟，论文未报告具体额外开销；
  仅测试三个模型，能否推广到 Claude、Gemini 等其他模型家族未知；未见第三方复现。

### 2. Stuck on Red？GitHub Actions 的"失败连续段"：五分之一超过一天的失败段，吃掉了大部分"失败时间"（软件工程，今日最值得细读）

- 领域：软件工程
- 来源 / 发布日期：arXiv 2610.41863 / v1 于 2026-10-30 15:17:30 UTC 上传，作者 Aref Talebzadeh
  Bardsiri、Tom Mens、Alexandre Decan（均 UMONS）、Thomas Degueule、Jean-Rémy Falleri（均
  LaBRI）；主类 cs.SE，无交叉分类；Comments 字段未标注。
- 摘要：作者在 238 天窗口内，对 4.3 万+ 个 GitHub 仓库、15.4 万+ 个 workflow、3,090 万+ 次运行
  做实证研究，定义"失败连续段"（failing streak）为 workflow 连续多次失败的运行序列，考察其如何
  开始、如何结束、期间发生了什么，并按运行的触发方式与关联 commit 分类，同时把所有 workflow 按
  用途（构建/测试/部署等）分类，并人工检查了一小部分失败连续段的日志。主要发现：失败运行大多
  成串出现——四分之三的失败运行紧跟着另一次失败运行，至少运行过 3 次的 workflow 里有一半出现过
  至少一次失败连续段；承担多种用途的 workflow 即便规模相同，也更容易出现失败连续段；大多数失败
  连续段在几小时内结束，但持续超过一天的那五分之一占掉了 workflow 处于失败状态的绝大部分时间；
  三分之一的失败连续段开始、五分之二结束时仓库本身并无任何改动；在 100 个失败连续段的抽样里，
  这类"无改动却开始/结束"的情形最常见的原因是网络问题或外部服务故障。作者据此建议：维护者不应
  默认失败来自最新一次 commit；GitHub 与工具开发者应标记"无仓库改动"的失败，并在 workflow 连续
  失败超过一天时提醒维护者。
- 为何重要：本仓库此前已跟踪"AI 把改代码打到接近零成本之后，瓶颈从代码质量转移到 CI 容量与人工
  评审带宽"这条线索（三个独立案例均聚焦"AI 生成的提交量暴增、压垮 CI 吞吐"这个具体机制）——这篇
  论文从另一个角度补了一块基础设施背景板：即便不考虑 AI，CI 管道本身的失败里三分之一到五分之二
  与代码改动无关（网络/外部服务抽风），且少数长尾（>1 天）的连续失败段占掉了大部分"失败时间"，
  意味着当 AI 把提交频率推高、CI 负载本就吃紧时，这类"假阳性失败"造成的人工排查成本可能被进一步
  放大，而维护者默认"失败来自最新 commit"这一直觉本身就站不住脚。证据边界：这是一般性 GitHub
  Actions 研究，样本未限定 AI 生成代码的仓库，论文未讨论 AI coding agent 对失败连续段频率/时长
  的直接影响，与本仓库"AI 驱动的 CI 容量瓶颈"线索是相邻而非直接证据；"无改动却失败"最常见原因
  （网络/外部服务）来自仅 100 个样本的人工抽样，占全部失败连续段的比例未知；238 天窗口与 4.3 万
  仓库的代表性（是否偏向活跃/知名仓库）未讨论；未见第三方复现。
- 原文：[Stuck on Red? 论文](https://arxiv.org/abs/2610.41863)

### 5. Ask on Demand：并行 Agent 之间"按需求助"优于预先共享/摘要，但收益在小模型上并不稳定（AI / 智能体，今日加选）

- 领域：AI / 智能体（Agent，今日加选）
- 来源 / 发布日期：arXiv 2610.41378 / v1 于 2026-10-30 07:43:03 UTC 上传，作者 Haofu Yang、
  Hongyang Yin（并列第一作者）、Ran Bi、Faguo Wu（通讯作者）、Peng Xue、Feng Zhou、Han Zhang
  （页面未披露机构归属）；主类 cs.AI，无交叉分类；Comments 字段标注"Equal contribution: Haofu
  Yang and Hongyang Yin. Corresponding authors: Ran Bi and Faguo Wu"。
- 摘要：并行探索多条路径的 LLM agent 系统里，有价值的发现往往被困在各自独立的执行历史中；现有
  共享方法（周期性共享、生命周期总结等）通常在"其他 agent 到底需要什么"还不明朗时就预先挑选或
  摘要信息，容易漏掉后来才变得重要的细节。作者提出 Ask on Demand（AOD）：当某个 agent 出现具体
  的信息缺口时，才主动向同伴发起有针对性的求助；请求被一个轻量级"门"模型批准后，AOD 从同伴的
  执行历史中检索相关证据、挑选合适的同伴、生成针对该请求定制的回复；门模型用"配对的团队后续
  走向"训练，监督信号来自最终团队结果与推理成本的权衡。在 AppWorld、WebShop 两个基准上，用
  Qwen3.5-35B-A3B 底座时，AOD 相对 Independent（无共享）在 AppWorld 上任务目标完成率从 53.89%
  升到 62.78%、子目标完成率从 30.00% 升到 38.33%，WebShop 上任务分从 67.45 升到 70.27、成功率
  从 42.50% 升到 45.50%，均优于 PeriodicShare、LTS（Adapted）、Agentfugue（Adapted）三个共享
  基线；但换成更小的 Qwen3.5-4B 底座，AOD 在 AppWorld 上的两项指标（31.11/10.83）反而不及
  LTS（Adapted）（31.39/12.50）。推理成本方面，作者报告 AOD 在四个"模型×基准"设置下用的 token
  数都少于 PeriodicShare 与 LTS（Adapted）两个共享基线，但相对完全不共享的 Independent 基线，
  AOD 消耗的 token 更多（如 Qwen3.5-35B-A3B 在 AppWorld 上的相对成本为 1.09 倍，WebShop 上
  为 0.92 倍）。
- 为何重要：这条证据给"agent 之间该怎么共享信息"这一具体协作设计问题提供了一个新思路——把共享
  的触发时机从"发送方预判"改为"接收方按需请求"，在 35B 模型上相对三个共享基线全面占优；但 4B
  小模型上的反例（AOD 不敌 LTS）提示这个设计的收益可能依赖模型本身有足够能力去判断"什么时候该
  问、该问谁"，而非对所有模型规模都成立——这与「harness-vs-model」页"表现由模型与控制结构共同
  决定"的判断相呼应，但补充了一个新变量：控制结构本身的收益可能是模型能力依赖的（capability-
  dependent），而非模型无关的普遍提升。证据边界：论文未披露作者机构归属；仅在 AppWorld、
  WebShop 两个仿真基准上测试，均非真实生产多 agent 协作场景；"推理成本更低"仅相对其他共享基线
  成立，相对完全不共享的 Independent 基线，AOD 在 AppWorld 上消耗的 token 反而更多（约 +9%），
  WebShop 上才更低（约 -8%），两基准方向不一致，论文摘要"lower inference cost"的说法需要结合
  这个限定条件理解；4B 模型上的反例未在论文摘要中提及，是否存在更系统性的"模型规模依赖"尚需
  更多模型规模点验证；未见第三方复现。

## 今日主线

今天 5 条的共同线索是"控制结构/协作机制独立于模型本身产生收益，但这种收益本身可能是有条件的"：
VBL 证明给长时 agent 一个显式的目标栈+双重核验，能在三个不同模型底座上一致提升长程恢复能力；
Ask on Demand 证明"按需求助"优于预先共享，但这一优势在小模型上反而消失，提示控制结构的收益
可能依赖模型自身的判断力。Stuck on Red 从一般性 CI 基础设施的角度补了一块背景板：当 AI 把提交
频率推高、CI 本就吃紧时，三分之一到五分之二与代码改动无关的"假阳性失败"会让人工排查成本被进一步
放大。创业/商业与汽车/自动驾驶两条则共同指向"AI 正在改变进入门槛和成本结构"这同一主题的两个
侧面：Grok Bot 的限流显示即便是增长最快的 AI 产品，服务成本相对收入也可能难以为继；Trucks VC
的路演数据显示基础模型正把自动驾驶软件栈的构建成本打低到一个量级，可能系统性降低这条此前被
认为资本/技术密集度极高赛道的准入门槛。
