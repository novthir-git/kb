### 1. Consistency Gap：同一个 agent 跑五次同一任务，全对的概率比单次通过率低 24 个百分点
- 领域：AI / 智能体（可靠性评估，运行时一致性）
- 来源 / 发布日期：arXiv，v1 于 2026-09-08 14:53:43 UTC 上传（检索于 2026-09-10）
- 摘要：论文指出一个此前被观察到但未被系统解决的现象：LLM agent 平均准确率高，但生产环境中并不可靠。在 AppWorld 基准上，一个基于 GPT-4.1 的 ReAct agent 单次任务通过率平均为 77%，但同一任务连续跑五次、五次全部成功的比例只有 53%——论文称这 24 个百分点的落差为"一致性缺口"（consistency gap），并主张解决它是 agent 可信部署的前提条件。作者提出一个自演化框架：用 Consistency Analyzer 定位轨迹中"容易翻车"的不稳定步骤，再用 Guideline Generator 把诊断转成具体准则，写入情景记忆、供后续同类任务调用。在 AppWorld/ReAct/GPT-4.1 上，该框架把"五次全对"的任务比例在同任务评测上提升 16 个百分点，在相似任务泛化评测上提升 13 个百分点。
- 为何重要：这把"agent 能力"从单次通过率这个常见指标，转向一个更贴近生产的追问——同一个任务重复执行是否稳定可靠，而不是平均分好看。证据边界：全部实验限于单一基准（AppWorld）和单一模型/框架组合（GPT-4.1 + ReAct），提升幅度是否能迁移到其他模型家族或开放式生产任务未知；情景记忆方案本身的维护成本、跨任务误用风险，以及一致性分析步骤带来的额外推理开销，论文摘要均未讨论。
- 原文：[Closing the Consistency Gap: Self-Evolving Agents That Learn to Stay on Course（arXiv 2609.08832）](https://arxiv.org/abs/2609.08832)

### 2. CapScope：给 coding agent 的每个子任务发"权限令牌"，把间接提示注入的成功率从六成压到 4%
- 领域：软件工程（Agent 安全，运行时授权架构）
- 来源 / 发布日期：arXiv（cs.SE），v1 于 2026-09-08 07:37:00 UTC 上传（检索于 2026-09-10）
- 摘要：论文指出 coding agent 调用系统级工具（读文件、执行命令、改代码）时普遍存在"环境权威"（ambient authority）问题——只要能叫出一个资源的名字就能对它动作，这正是间接提示注入的可乘之机：攻击指令可以藏在仓库文件或工具返回值里，诱导 agent 执行用户未授权的动作。作者提出 CapScope：在读取仓库内容或工具输出**之前**，先从可信输入推导出"任务级权限上限"，再给每个子 agent 分配一套存储在模型上下文之外的、独立的"类型化能力"（typed capabilities），每次工具调用都要核验发起方 agent 自身的能力集合，一个子 agent 的权限不会自动传给另一个。作者在 Pi coding agent 上实现 CapScope，测试场景为"编排器把子任务分给独立子 agent"的修复工作流，覆盖 5 个 Python 任务 × 5 种注入面 × 4 种授权条件 × 3 次重复。结果：基线（环境权威 / 全局静态策略）下注入攻击在 75 次运行中成功 33-47 次，CapScope 下仅成功 3 次；任务完成率基本持平（CapScope 完成 68/75，基线完成 68-72/75）。
- 为何重要：这为本 wiki 持续跟踪的"Agent 执行权限的授权/委托治理空白"这条线索（`briefs/memory.md` 跨天论点线索 2：2026-08-31 SARA、2026-09-03 Delegation Without Trust）补上第三个独立证据源，且首次给出一个**具体架构方案**（而非只诊断问题）与量化的攻击成功率对比（33-47/75 → 3/75），已达到该线索"≥3 条跨天证据"的沉淀门槛，详见文末沉淀候选。证据边界：评测规模小（仅 5 个 Python 任务、单一 coding agent 实现 Pi、300 次运行），未测试"知道 CapScope 边界"的自适应攻击者；"任务级权限上限"依赖的"可信输入"本身的信任链未在摘要中说明来源与校验方式。
- 原文：[Authority Is Not a String: A Capability-Scoped Harness for Prompt-Injection-Resistant Coding Agents（arXiv 2609.08371）](https://arxiv.org/abs/2609.08371)

### 4. PlannerForge：用 LLM agent 把自动驾驶"场景测试"的全流程串起来，而不是靠人工拼接工具链
- 领域：汽车 / 自动驾驶（规划器验证方法论，EMNLP 2026 主会）
- 来源 / 发布日期：arXiv，v1 于 2026-09-08 16:19:06 UTC 上传，EMNLP 2026 主会录用（检索于 2026-09-10）
- 摘要：论文指出当前自动驾驶系统的"场景化测试"（scenario-based testing）仍是碎片化的模块化流水线——场景生成、检索、修改、执行、结果分析分别由不同工具完成、彼此交互很少。PlannerForge 用统一的 LLM-agent 框架覆盖全部测试阶段（场景生成→选择→修改→模块路由→规划器测试），并新增两个阶段：ADS 增强与 ADS 基准测试。作者用 10 个现成 LLM、在 5 种 prompt 条件下评测各任务，各任务最佳得分在 0.88-1.00 之间，20-35B 参数的开源模型（如 Qwen3.6:35B）在三分之五的任务上追平商业 API；端到端串联全流程后，种子查询留存率商业模型/开源模型分别为 83%/78%。对比基线：自然语言生成上优于 Scenario Factory 2.0（200 条中 193 vs 144 条可执行）；rank-1 场景选择上优于 BM25（92.0% vs 67.5%）；物理有效编辑上优于 From-Words-to-Collisions（≥94% vs 31%）。在 N=400 的测试中，成本调优（cost-tuning）把规划器成功率从 50.4% 提升到 70.2%，碰撞率从 19.0% 降到 8.4%，且未做领域专属微调。
- 为何重要：这为"如何验证自动驾驶规划器"提供了另一个方法论候选——不是像本 wiki 已跟踪的"One Diffusion Model, Two Roles"（`briefs/memory.md` 跨天论点线索 15）那样让单一模型兼任规划器与对抗场景生成器，而是用 LLM agent 统一编排整条测试流水线的各个独立环节，思路互补但架构不同。证据边界：EMNLP 是 NLP 主会，其同行评审更侧重自然语言生成质量而非闭环驾驶安全本身；论文报告的各项得分是流水线内部任务的自动化指标（如生成文本可执行率、场景选择命中率），未见与真实道路数据或独立第三方安全评测的对照；对比基线（Scenario Factory 2.0、BM25、From-Words-to-Collisions）均由作者自行选定和实现。
- 原文：[PlannerForge: LLM Agents for Scenario-Based Testing of Motion Planners in Autonomous Driving（arXiv 2609.08965）](https://arxiv.org/abs/2609.08965)
- 配图：![PlannerForge 总览：LLM agent 自动化场景化测试全流程](https://arxiv.org/html/2609.08965v1/00_concept.png)
  图片来源：[论文 Figure 1](https://arxiv.org/html/2609.08965v1)。

### 5. 今日细读：agent 说"我快做完了"未必可信——进度自报的可靠性本身要分阶段测量
- 领域：AI / 智能体（任务进度自报可靠性，今日加选）
- 来源 / 发布日期：arXiv，v1 于 2026-09-08 11:25:31 UTC 上传（检索于 2026-09-10）
- 摘要：论文指出现有 agent 框架常依赖模型自己输出的"任务进度信号"来决定任务是继续还是终止，但"模型能否在任务全生命周期的每个阶段都可靠汇报进度"此前从未被系统研究过。作者在公开基准 τ²-bench 和自建的 StageIF（在任务生命周期中按检查点系统布点）上评测这一能力，均要求模型在多个任务阶段分别汇报进度。发现：汇报可靠性因任务所处阶段而异，几乎每个被测的已部署模型都是"在某些阶段可靠、在另一些阶段不可靠"，且失效模式因模型代际不同——多数已部署模型在任务进行中段准确率下降、任务完成后又恢复；最新一代模型修复了中段下降的问题，却在任务临近结束时变得过度保守（容易误判"还没完成"）。作者据此提出：agent 框架不应仅凭模型自身的状态汇报来控制任务流程。
- 为何重要：这与本期第 1 条（Consistency Gap）、第 2 条（CapScope）共享同一个工程判断——**agent 的自我报告（无论是完成信心、进度声明还是执行意图）不能被直接当作控制信号**，必须由 harness 层的外部机制（独立评测协议、情景记忆化准则、能力域授权）兜底，而不是把控制权交给模型自己的输出。证据边界：结论建立在 τ²-bench 与作者自建的 StageIF 测试床上，StageIF 的检查点划分由作者设计，存在选择偏向的可能；"最新一代模型"的判断基于有限的模型样本；论文未量化进度自报失真在真实生产系统里实际导致了多少次错误终止或误判。
- 原文：[The Unreliable Progress Bar: Can LLM Agents Reliably Report Task Progress Throughout Execution?（arXiv 2609.08589）](https://arxiv.org/abs/2609.08589)

## 今日主线

今天前三条（连同细读共四项 AI/SE 相关内容）反复出现同一个工程判断的不同切面：**agent 对自身状态的报告——无论是"这次任务算不算稳定成功"、"我能不能碰这个文件"，还是"我做到哪一步了"——都不能被直接信任，必须靠 harness 层的外部机制兜底**。Consistency Gap 把"平均通过率高"和"重复执行稳定"拆成两件事；CapScope 把"要不要执行一个动作"从模型上下文里搬到独立的能力令牌里核验，并首次让 SARA、Delegation Without Trust 这条线索凑齐三个独立证据源；Progress Bar 论文则说明连"做到哪一步了"这种最基础的自我认知信号也会系统性失真。PlannerForge 把类似的思路——不靠单一系统自证，而靠外部编排的验证流水线——搬到自动驾驶规划器测试上。与此同时，Cognition 一轮融资就把估值推到 480 亿美元、4 个月翻倍，形成鲜明对照：**独立研究还在一层层揭开 agent 自我报告与授权机制的具体缺口，资本与部署规模却已经跑在了前面**。
