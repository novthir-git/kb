### 1. CASEL：给 agent 的每一次工具调用算一道"值不值得自己拍板"的账，模拟环境里把有害轨迹砍了一半

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / v1 于 2026-10-27 03:19:41 UTC 上传，作者 Yanyan Zhang、Fei Shen、
  Ting Yan、Hao Zhang（页面未披露作者机构归属），已被 2026 年第五届云计算、大数据应用与软件工程
  国际会议（CBASE 2026）接收
- 摘要：论文指出，现有工具调用型 agent 的运行时安全阀多依赖笼统的不确定性分数或粗粒度启发规则，
  "该不该自己执行"这件事缺少按后果分级的系统方法。作者提出 CASEL，针对每一次待执行的工具调用，
  综合权衡校准后的失败概率、该状态下的后果严重度、动作可逆性、请求本身的歧义程度与证据新鲜度五个
  因子，在"直接执行、二次核验、沙箱执行、请求澄清、人工批准、直接拒绝"六种模式中选择期望代价最小
  的一种。在 20 个随机种子、每种子 12 万次测试动作、所有方案共享同一套干预菜单与计算开销的仿真
  环境中，CASEL 把有害副作用轨迹占比从"按不确定性排序的门禁"基线的 14.75% 压到 7.02%，平均归一化
  伤害从 0.184 降到 0.123；去掉"可逆性感知"这一项后，有害轨迹占比反弹到 15.53%（与基线相当甚至
  更差），说明收益主要来自对可逆性的显式建模，而不是五因子综合打分本身；另一种"失败概率×后果"
  排序的门禁能达到接近的伤害水平，但要多送 45% 的动作去人工批准；一种按轨迹整体风险预算控制的
  方案在同等开销下伤害反而更高（11.82%）。作者自己在文中提醒："干预措施本身是否真的有效，是本文
  假设而非实测的"——这套方法只是在模拟器的假设下给不同分配规则排名，并不等于证明了"二次核验"或
  "请求澄清"这些干预手段本身在真实环境里能挡住风险。
- 为何重要：这是本仓库持续追踪的"agent 工具执行的运行时授权治理"这条线索（此前已累计约 45 条
  跨天候选证据，核心主张是"权限边界需要按场景分级裁决，而非一次性批准/拒绝"）的又一条独立证据，
  且是该线索里少见的、给出完整消融实验拆解收益来源的工程化方案——此前的 SARA/CapScope/PACE 等
  方案多聚焦"怎么判断该不该拒绝"，CASEL 把判断结果进一步拆成六档可执行动作，并证明"可逆性"这个
  此前较少被单独量化的因子，是决定方案好坏的关键变量而非锦上添花。证据边界：论文未披露作者机构，
  仅发表于一个相对小众的会议（CBASE 2026），独立性与同行评审的严格程度存疑；全部数据来自作者
  自建的仿真环境（20 种子×12 万动作），并非真实工具调用日志，论文明确承认"干预有效性是假设不是
  测量"；五个因子如何在真实场景中被校准（尤其"校准后的失败概率"本身的准确性）未在摘要展开；未见
  第三方复现。
- 原文：[CASEL: Consequence-Aware Selective Execution for Reliable Long-Horizon Tool-Using Agents](https://arxiv.org/abs/2610.36570)

### 2. FeatureArc：让 agent 接着改自己刚写完的代码，功能完成率从 62.7% 一路跌到 28.5%

- 领域：软件工程
- 来源 / 发布日期：arXiv / v1 于 2026-10-27 15:45:50 UTC 上传，作者 Yunlong Wang、Alyssa Wu、
  Cuiyun Gao、Jia Feng、Songyuanyi Lu、Zhichao Hu（页面未披露作者机构，论文披露该评测流程已在
  腾讯内部使用，并为混元系列语言模型的开发提供反馈）
- 摘要：现有的"功能级"coding agent 基准大多只测"在一个固定代码库上完成一次请求"，但真实软件的
  功能是一层层在既有代码上接着加需求演化出来的。FeatureArc 改为测试 agent 在自己刚写完的代码上
  持续叠加后续需求：任务取自真实仓库的提交历史，拆成 2 到 10 个递进阶段，用可执行测试打分，覆盖
  四种编程语言，全程保持同一个会话、不给测试反馈、不允许回滚到更早版本。作者在 73 个经人工复核的
  任务上评测了 10 款 agent：按阶段汇总的成功率从第一阶段的 62.7% 一路跌到"整个功能在最终代码上
  整体测试"时的 28.5%；在后续阶段失败的案例里，72.9% 是因为继承了更早阶段留下的缺陷；而 agent
  自己大约 95% 的时间里都没有发现并修复这些被继承下来的早期错误，而是在这些错误之上继续叠加新代码。
  作者的结论是，没有人工在阶段之间介入检查的"自主功能演化"，对当前 coding agent 仍是一个实质性
  挑战。
- 为何重要：这是本仓库持续追踪的"Agent 长时任务的可靠性衰减是数学规律"这条线索（此前已累计 5 条
  跨天证据，对应已有页「agent-生产级落地的鸿沟」）的又一条独立证据，而且是该线索第一次把"长时任务"
  的衰减从"同一个任务做得越久越容易崩"这一维度，延伸到"同一段代码被反复要求往上加新功能"这个更贴近
  真实软件开发节奏的维度——62.7%→28.5% 的衰减曲线与此前《How Fast Do Agents Rot?》等论文证明的
  几何衰减律互相印证，而"72.9% 的后续失败来自继承的早期缺陷、95% 的时间没被发现"这组数字，第一次
  给出了衰减背后一个具体的、可归因的机制：不是能力随机漂移，而是早期错误被系统性地"捂住"、没有
  被自己发现。腾讯将该流程用于混元模型开发反馈这一点，也让这条线索第一次出现"头部实验室自报量化
  基线"之外的、来自另一家大厂内部真实研发流程的印证。证据边界：73 个任务、10 款 agent，样本规模
  中等；论文未披露具体是哪 10 款 agent、各自的供应商与版本，也未披露作者机构，仅说明流程已在腾讯
  内部使用，这句话本身来自作者自陈、无法独立核实其内部应用的具体规模与效果；任务"不给测试反馈、
  不允许回滚"是刻意设计的受控条件，与真实开发中 agent 通常能看到测试结果、能回滚的场景有系统性
  差异，衰减幅度可能被这一设计放大；未见第三方复现。
- 原文：[FeatureArc: Benchmarking Coding Agents on Evolving Features](https://arxiv.org/abs/2610.37434)

### 5. kw-bench：同一个开源模型，换一个商业 harness 分数能从 0 冲到 0.54——换成更强底座模型后两款又双双逼近满分（AI/智能体，今日加选，今日最值得细读）

- 领域：AI / 智能体（Agent，今日加选）
- 来源 / 发布日期：arXiv / v1 于 2026-10-26 23:40:10 UTC 上传，作者 George Juraj Salapa
  （页面未披露作者机构归属）
- 摘要：kw-bench 是一套"真实取证式调查任务"基准，首个任务族要求在不完整、互相矛盾的证据中，
  跨三代 SAP 系统、从原始系统导出数据重建连续五年的增值税记录，评分完全确定性、不用模型当裁判。
  作者让四款 harness——两款面向通用场景的开源/模型无关框架（Claude Code、OpenCode）与两款作者
  称为"实验室自带 harness"的方案——都搭配同一个底座模型 DeepSeek v4.1 Flash，跑满两小时：两款
  通用 harness 各拿到约 0.54 与 0.53 分，但两款"实验室自带 harness"均得 0.00 分；作者将其归因于
  难以在长会话里持续维持住大量微弱、零散的线索。换成 Claude Opus 5.5 这个更强的底座模型后，
  micro-cc 与 Claude Code 两款 harness 分别拿到 0.9986 与 1.000 分，且仅用 22 分钟与 25 分钟
  就完成。
- 为何重要：这是本仓库持续追踪的"Harness 设计是决定同模型实际表现的独立架构变量"这条线索（此前
  已累计 23 条跨天证据，对应已有页「harness-vs-model」）里反差最极端的一条独立证据——同一个底座
  模型，换一款 harness 分数可以从 0.00 直接跳到 0.54，而不是此前证据里常见的"提升几个百分点"
  量级；而把底座模型换成更强的 Opus 5.5 后，此前得零分的 harness（如 Claude Code）和得分最高的
  通用 harness（micro-cc）又双双逼近满分——这意味着"harness 不行"和"模型不行"在弱模型上几乎
  无法区分（harness 直接把模型能力压到 0），但强模型可以一定程度上掩盖/弥补 harness 的短板，
  这与此前「When Agents Fail: Model or Harness--Who's to Blame?》等论文证明的"harness 排名
  随模型配对系统性漂移、不存在普适最优解"互相印证，并给出了一个此前证据都没覆盖的极端边界案例：
  模型越弱，harness 设计失误造成的得分损失可能越接近"全军覆没"而非"打折扣"。证据边界：全文仅
  George Juraj Salapa 一名作者，未披露机构归属或投稿状态，论文规模（单一取证任务族、两小时时间

## 今日主线

今天的 5 条共同指向同一件事：能力和治理之间的分界线，正在从"要不要"变成"怎么分级、怎么定价、
怎么装进产品"。条目 1（CASEL）和条目 5（kw-bench）都在说"agent 到底该交给谁拍板、交给哪个
harness 执行"这件事远比一次性的批准/拒绝复杂——CASEL 证明把"可逆性"单独建模能把有害轨迹砍半，
kw-bench 则给出了迄今最极端的反例：同一个模型换一款 harness，分数可以从 0 直接冲到 0.54，弱
模型甚至完全无法掩盖 harness 的缺陷。条目 2（FeatureArc）从另一个角度印证了"长时任务会衰减"
这条规律背后的具体机制：不是能力随机漂移，而是早期错误 95% 的时间里都没被 agent 自己发现，
一直被新代码盖在下面。条目 3 和条目 4 则说明，"给 agent 发身份证"与"车也能装 agent"这两件事
正在变成真金白银的商业选择——Mintive 用两位基础设施老兵的背书把"agent 治理"做成了独立产品
品类，Rivian 则在畅想车机本身成为第三方 agent 的宿主平台。治理基础设施本身，正在从论文里的
受控实验，同时往两个方向落地：工程化的执行策略，和可以直接卖给企业的产品。
