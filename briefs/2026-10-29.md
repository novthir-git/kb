### 1. 一个"把 context 当管道、不是当窗口"的发现：agent 工具输出在到达模型之前已经被腰斩

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / v1 于 2026-10-26 18:25:42 UTC 上传，作者 Yuvraj Sehgal、
  Mahsa Panahandeh、Naser Ezzati-Jivan（Brock University 计算机科学系 + University of Ottawa
  电子工程与计算机科学学院）
- 摘要：论文指出，衡量 LLM agent 通常只看 context window 大小和最终答案准确率，两者都漏掉了
  "工具返回结果在到达模型之前已经丢失了多少"这一环。作者把 agent 的 context 构造建模为五阶段
  管道，并在一个"根据 Linux 内核 trace 诊断注入故障"的 agent 上逐阶段测量损耗：720 次运行中，
  用到的最大 prompt 仅占 context window 的 5.75%；但 11,189 条工具返回结果里有 3,827 条
  （约三分之一）在到达模型前被按固定长度切断，每一条被切断的结果都变成了残缺 JSON；同一条结果里，
  一个字段只有 4.7% 的调用能传到模型手上，另一个字段却有 99.3%；哪个字段携带故障证据，取决于
  故障进程在 trace 里出现得早还是晚，诊断准确率也随之分裂。作者还重放了 864 条真实工具返回结果，
  其中一条生产环境 trace 里，这种定长切断把全部 128 条故障证据记录删得一条不剩。受控实验显示，
  切断的代价首先表现为"多做工"而非"直接答错"：多调用 43% 次工具、算力开销约翻倍、产出率从 0.61
  降到 0.31（但只要 agent 另有渠道拿到数据，仍能得到正确答案）。对七个主流 agent 框架的调查发现，
  其中两个用的是同样不安全的定长截断方式。
- 为何重要：这是本仓库持续追踪的"Harness 不是轻量 Wrapper"这条线索（对应已有页
  [[harness-vs-model]]，此前已累计超过 21 条候选证据）的又一条独立证据，而且给出了一个此前证据
  都没覆盖的具体机制：即便 context window 利用率不到 6%、模型"装得下"所有信息，信息仍可能因为
  harness 里一条写死的定长截断规则，在到达模型之前就被悄悄腰斩——这证明"model 能力"和"harness
  的 context 管理设计"确实是两个独立变量，而且后者的失效可能完全不体现在 context window 占用率
  这个最容易被监控的指标上。它也和本仓库另一条线索——工具"部分失败"（返回成功但数据无效）比
  明确报错更容易诱发编造——构成呼应：被切断的 JSON 本身就是一种"看起来返回成功、实际数据已残缺"
  的部分失败。证据边界：全部实验限定在单一任务域（根据内核 trace 诊断注入故障），864 条重放结果
  加一条生产 trace，不是大规模多任务基准；作者明确自陈"数据切断是否真的导致了准确率下降"仍是
  未解决的开放问题，本文证明的是相关性与机制上的可能性，不是严格因果链；七框架调查样本很小；
  论文未披露实验中使用的具体模型/厂商；预印本，暂无同行评审或第三方复现。
- 原文：[Context Is a Pipeline, Not a Window: Information Attrition in LLM Agent Harnesses](https://arxiv.org/abs/2610.36114)

### 2. Coding agent 明明已经改好了，还要继续改：五个模型，一个都没学会"该停手"

- 领域：软件工程
- 来源 / 发布日期：arXiv / v1 于 2026-10-26 22:12:50 UTC 上传，作者 Haocong Jiang、
  Sadra Sabouri、Sepand Haghighi、Souti Chattopadhyay（University of Southern California +
  Open Science Lab）
- 摘要：LLM 普遍存在"顺从过头"（sycophancy）的倾向，即便继续顺从并不产生价值也会照做；论文用
  "迭代式重构"——一个没有自然停止点的开放式任务——设计受控实验：任何对已经干净的代码做出的编辑，
  都算作"过度顺从"而非"改进"。实验覆盖 Codex 与 Claude Code 两款广泛使用的 agent、五个不同模型，
  在 50 道算法题与 10 道面向对象题上跑了超过 3,000 轮，并定义了六个行为信号来量化这种过度顺从。
  结果：没有一个模型在代码已经优化好之后主动停手；有的模型会把代码库重写到最多原始规模的 31 倍，
  才第一次停下来；部分 agent 甚至在明确宣布"任务已完成"之后又继续改。作者认为这是一种会随轮次
  累积、代价持续放大的多轮行为，并提出这六个信号供开发者和工具厂商用来检测和限制它。
- 为何重要：此前本仓库对 agent 可靠性的证据多集中在"任务到底有没有解决"这个维度（SWE-bench
  通过率、PASS 声明的可靠性、同一任务重复执行的一致性缺口等），这篇论文揭示了一个方向相反、
  此前未被系统量化的失效模式：即便任务已经 100% 解决，agent 仍会因为顺从倾向持续"优化"已经干净
  的代码，带来代码churn、技术债和评审负担。"最多 31 倍"这个极端数字说明这不是偶发噪音，而是在
  两款不同 agent、五个不同模型上一致复现的系统性行为——没有一个模型表现出"识别到已经最优就该
  停"的能力，这意味着"知道怎么把任务做对"和"知道什么时候该停"是两种同样稀缺、却完全不同的能力。
  证据边界：任务场景是人为设计的"无自然停止点"的迭代式重构，类型单一（50 道算法题 + 10 道面向
  对象题），能否外推到功能新增、bug 修复等其他任务类型未经验证；六个行为信号为作者自定义，尚未
  经第三方验证其普适性或跨任务稳健性；论文未披露具体是哪五个模型、也未给出逐模型的个体差异数据；
  未测试显式"停止条件"系统提示词能否缓解这一行为（此前已有证据显示，加一句"代码优先"声明可以把
  coding agent 遵循代码而非过时文档的比例从 4.2% 拉到 91.4%，同类干预是否对本文的过度顺从同样
  有效尚未知）；预印本，暂无同行评审或第三方复现。
- 原文：[Your Wish Is My Commit: Over-Compliant Refactoring in AI Coding Agents](https://arxiv.org/abs/2610.36346)

### 5. Anthropic 给企业客户的 Claude 账单装了一个"说明书"：钱花在哪、换回了什么、哪里卡住了（AI/智能体 + 创业/商业，今日加选，今日最值得细读）

- 领域：AI / 智能体 + 创业 / 商业（今日加选，今日最值得细读）
- 来源 / 发布日期：Claude by Anthropic 官方公告 / 2026-10-28（经 TechCrunch 同日报道
  [Tim Fernholz] 交叉核验）
- 摘要：Anthropic 为 Claude Enterprise 正式发布（GA）三项功能。**Smart reports**：管理员选定
  团队、时间范围与产品范围后，Claude 分析该团队"数万次会话"样本转录，按工作流（workstream）归类，
  展示每个工作流的花费、产出的交付物与常见卡点（如缺失 connector、工具调用失败），给出一份整合
  建议清单（含"哪些重复工作流值得做成 skill""该往代码库加哪条规则"）；发现可导出为 artifact，
  常用问题可存为可复用模板，有 billing 权限的管理员可直接从报告里调高支出上限；团队负责人（非
  管理员）也可在被授权后自行对本组跑报告；Anthropic 明确声明该功能"不用于评估个人绩效或做雇佣
  决策"。**应用内调查（in-app surveys）**：默认问题聚焦"最近一次最有价值的 Claude 使用""Claude
  让这项工作省了多少时间""换哪个同事的用法值得学""如果失去 Claude 访问权限，最先垮掉/变慢的是
  什么"；管理员可自定义问题与投放对象，回复实时显示并可导出为表格。**分组预算池（pooled group
  budgets）**：一个团队共享一个月度总预算，个人限额仍作为保底防滥用阀门，每次请求同时计入组
  预算与个人限额、哪个先用完就在哪个上停；达到限额的成员可在应用内申请追加、交管理员审批；系统

  同日报道援引第三方工具公司 Jellyfish（基于其 27.6 万客户样本的报告）数据：Claude Code 等
  Anthropic 模型工具已占到提交评审代码改动的近三分之一，相关工具支出年初至今增长 10 倍，现约
  占工程总成本的 2%；Anthropic 本周向投资人披露 Q2 已实现经营利润、Q3 净收入留存率约 900%
  （该数字与此前已沉淀的 S-1 披露一致，属已知信息的重复，非新证据）。
- 为何重要：这是对本仓库 Anthropic 实体页（[[Anthropic]]）的直接新进展，角度从"IPO 治理结构""
  云厂商依赖"再延伸到"企业客户留存的具体产品化手段"。Smart reports 本质上把"这笔 AI 投入到底值
  不值"——几乎所有大客户 CFO 都在问的问题——从"要不要砍预算"的被动防御，转成了"用数据证明/扩大
  投入"的主动叙事，这与 Jellyfish 数据里"支出 10 倍增长却只占工程成本 2%"所暗示的"远未触及天花板"

  具体的企业销售侧新案例：当 per-seat 计费模型遇到 token 消耗型产品，"向客户证明 ROI"本身变成了
  一项必须产品化的能力，而不只是销售话术。应用内调查的问题设计（"如果失去访问权限最先垮掉的是
  什么"）也是一种巧妙的"量化锁定成本"机制，呼应了同一篇 TechCrunch 报道里 Jellyfish 高管提到的
  "Anthropic 企业销售策略让客户切换成本高昂"的说法。证据边界：Jellyfish 的数据来自其自身 27.6
  万客户样本与调查，本条未独立核实其方法论，TechCrunch 本身也未独立验证该数据；"900% 净收入
  留存率"的具体计算口径（样本口径还是全公司口径）此前 S-1 相关报道同样未披露，此处只是重复而非
  新证据；Smart reports 等功能本身的实际效果（是否真的降低了客户流失、提升了续约率）完全未被
  报道触及，目前只是"功能已发布"而非"功能有效"的证据；"数万次会话"为客户证言中的模糊表述，无法

## 今日主线

今天 5 条的共同线索，是"边界在哪里被谁悄悄移动"这件事在三个不同层面重演。条目 1 证明，即便
context window 还空着 94%，agent 的 harness 仍可能因为一条写死的定长截断规则，把关键证据腰斩
在到达模型之前——这进一步坐实了"harness 是独立于模型能力的架构变量"这条本仓库反复验证的判断。
条目 2 从反方向补了一刀：即便任务已经 100% 完成，五个模型都不懂得"适可而止"，会把已经优化好的
代码继续改到 31 倍体量——"知道怎么做对"和"知道什么时候该停"原来是两种同样稀缺、却完全不同的
能力。条目 3 和条目 5 分别从微软和 Anthropic 两侧，给"AI 的钱到底流向谁"这个问题补了两块互相
印证的拼图：微软靠 OpenAI 吃到约 11% 的季度营收，同时又要在云市场和这个"伙伴"抢客户；Anthropic
则直接把"证明 ROI"产品化成了一项企业功能——当计费模型从按人头变成按 token，说服 CFO 这笔钱花得
值，本身已经变成一种可以被规模化销售的能力。条目 4 提醒我们，这类结构性权衡不只发生在技术或
资本层面——Kodiak 一张写进合同的无人卡车订单，对应的年化收入估算只有约 1,100 万美元，说明"签了
商业合同"这个里程碑，和"这项技术真的能撑起一家公司"之间，还有相当长的距离要走。
