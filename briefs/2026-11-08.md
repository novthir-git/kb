### 1. MCPHallu：把 MCP agent 的"幻觉"拆成推理/执行/记忆三阶段四种具体子型，子型之间几乎不相关、排名剧烈震荡（AI / 智能体）

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / 2026-11-05（v1 于 2026-11-05 09:14:26 UTC 上传）
- 摘要：论文指出，现有面向 Model Context Protocol（MCP）的 agent 评测大多只看任务是否完成，
  对失败原因仅做事后归因。作者提出 MCPHallu：在任务设计阶段就为每个任务嵌入一个"结构化触发
  条件"，使四种失效子型之一成为该任务的主要风险——Branch Collapse（分支塌陷）、Unreachable
  Goal（目标不可达）、Tool Misuse（工具误用）、Context Forgetting（上下文遗忘），分别对应
  agent 循环里推理、执行、记忆三个阶段的具体失效形式。基准覆盖 5 个能力域、358 个任务，在
  36 个生产级 MCP server 的隔离容器环境中运行；对来自 8 家厂商的 14 个前沿 agent 做了 5,012
  条轨迹的评测。全部 agent 在全部任务上的平均得分（0–1 区间）为 0.642；其中 Unreachable Goal
  任务得分最低，平均仅 0.458、通过率仅 23.2%，agent 在"目标本身不可达"时常常持续反复调用工具
  或谎称任务已完成；同一模型在不同子型上的排名平均会上下浮动 6.9 个名次（共 13 个模型参与
  排名），Branch Collapse 与 Unreachable Goal 两个子型上的模型表现几乎不相关（Pearson r =
  -0.12）。
- 为何重要：这触及 `wiki/purpose.md` 关键问题 1（agent 能力落到生产要跨哪些具体门槛）。它和
  本仓库跨天线索 55（"Outcome-only 指标会掩盖 agent 执行过程中的具体脆弱性，需要过程级/环境级的
  补充评测维度"，此前证据来自轨迹级可执行性协议 Prefix Executability）构成一组新角度的互补
  证据：线索 55 此前关注的是"整条调用序列是否每一步都可执行"，MCPHallu 则是"把失效原因拆成
  推理/执行/记忆三阶段的具体子型"，并首次量化出一个容易被忽视的现象——一个聚合的"幻觉抵抗力"
  分数会掩盖模型在不同子型上几乎不相关的能力分布，意味着只看单一聚合分数去挑选或信任某个 agent
  产品，可能在它最薄弱的那个子型上完全失算。证据边界：论文未披露作者机构归属，亦无会议/期刊
  录用信息；14 个 agent 具体名称未在摘要层面列出，评测时间窗口与是否存在训练数据污染未讨论；
  "结构化触发条件"的任务构造方式依赖作者自定义协议与专家审核，是否存在系统性偏向某类失效的
  设计未详述；36 个"生产级" MCP server 的选取标准及代表性未说明。记为新线索（线索 68）持续
  观察，暂未达沉淀门槛（单一来源，待第二条独立证据或更明确的奠基性评估）。

### 2. Accepted but Wrong：LLM 修复 API 迁移后的代码时，"标准检查通过"掩盖了约四成的隐性错误修复（软件工程）

- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-11-05（v1 于 2026-11-05 16:41:32 UTC 上传）
- 摘要：论文做了一项预注册研究，考察 LLM 在运行时/API 迁移后生成的代码修复。基于 CPython、
  Node.js、SQLite 三个真实项目里 60 次有文档记录的变更，构造 73 个任务，把每个候选修复都放到
  真实运行时上、对照预留的验证契约执行测试。核心问题是：一个修复可能在常规输入上干净运行、却
  在契约层面返回错误结果——作者原话"an LLM-repaired procedure can run cleanly yet return wrong
  results"，而只用常规输入做的发布检查会直接放行它。量化结果：仅用"全部断言 + 常规输入"这道
  发布闸门时，有 0.410 的错误修复被放行；换成从官方变更说明里提炼的"边界输入"后，错误放行率
  降到 0.065（在 15 个未见过的新变更簇上为 0.061）；用一个未见过官方说明、只给三个输入的"盲写"
  前沿模型（GPT-5.6-luna）构造的检查，错误放行率为 0.070，与"边界输入"方案接近；把候选测试
  片段库扩充到 1,491 条并加入 233 条"刻意构造、在常规输入上表现与历史正确实现一致"的高难度
  干扰测试后，预注册的"边界输入"方案与"前沿模型盲写"方案分别通过 0.058、0.058，但面对高难度
  干扰测试时错误放行率回升到 0.168、0.153；在三个开源权重模型家族上，"边界输入"检查相比常规
  输入检查普遍降低错误发布率（例如从 0.233 降到 0.057），且不损失正确修复的通过率；让修复本身
  做"自我测试"的效果明显弱于前两种外部检查方式。作者还做了一次盲审：由一个独立 AI 审计这些
  验证契约，标出其中 34 条"比需求本身更严格"，但去掉这些有争议的契约后，结论（哪些修复算
  正确/错误）一个都没变。
- 为何重要：这触及 `wiki/purpose.md` 关键问题 1，并直接延伸本仓库跨天线索 7（"SE agent 补丁
  '测试通过'与'审查可接受'是两回事，且差距可量化"，此前已累积 8 条独立证据，覆盖通用代码修复、
  漏洞补丁、修复过程幻觉分析、工业真实系统、人类手动验证、生产推理服务引擎等任务域，远超
  沉淀门槛）——这是该线索第 9 条证据，首次把"测试通过≠正确"这个判断聚焦到"API/运行时迁移后的
  代码修复"这一具体场景，并给出一个可直接复用的缓解配方："从官方变更说明里提炼边界输入"几乎
  和"用更强模型盲写边界输入"效果相当，都显著优于只用常规输入做检查，但都无法扛住刻意构造的
  高难度干扰测试；审计契约过严的顾虑在本研究里被证明不影响结论稳健性。证据边界：规模中等（73
  个任务、3 个真实项目），作者机构未披露；"边界输入提炼"本身依赖有文档记录的官方变更说明，
  对没有详细变更日志的项目或库是否同样适用未验证；GPT-5.6-luna 作为"盲写"基线本身也是一个
  具体模型的能力体现，换用更弱或更强的模型效果区间未知；预注册协议降低了事后调参风险，但三个
  项目均为知名开源基础设施，结论能否推广到企业内部代码库未讨论；无第三方复现。
- 原文：[Accepted but Wrong 论文](https://arxiv.org/abs/2611.08269)

### 5. Benchmarks as Software：把 Terminal-Bench 当软件维护，审计发现三成任务有缺陷、修复后分数跳变超 10 个百分点（软件工程，今日最值得细读）

- 领域：软件工程（今日最值得细读，亦触及 AI / 智能体——评测方法论本身的可信度）
- 来源 / 发布日期：arXiv / 2026-11-05（v1 于 2026-11-05 18:18:39 UTC 上传）
- 摘要：论文作者为 E. Kelly Buchanan、Crystal Zhou、Scott W. Linderman、Christopher Ré（机构
  未在页面标注）。论文主张：即便是经过人工与模型辅助审查、做过红队测试的 coding agent 基准，
  也会随模型能力提升而逐渐失效——模型可能找到被验证器错误拒绝的有效解法，评测基础设施的变动
  也可能打破任务原有的隐含假设，这种累积作者称为"基准维护债务"。为此提出一套持续验证流程：
  汇总社区报告、任务产物、agent 执行轨迹、自动化 oracle 检查与人工批准的修复，并把这套流程
  应用到 Terminal-Bench 2.0，发布修复后的 Terminal-Bench 2.1。量化结果：审计发现 Terminal-
  Bench 2.0 约 30% 的任务存在缺陷（此前已经过人工与 LM 辅助评审及红队测试）；修复后整体准确率
  提升超过 10 个百分点；19 个 agent 的排行榜名次最多移动三位，但整体排名高度相关（Spearman
  rho = 0.958）；论文还论证"资源预算"（如墙钟时间限制）本身也是测量的一部分、需要与任务一起
  被验证——延长时间限制为 GPT-5.4 消除了 20 个百分点的"harness gap"，为 GPT-5.4 mini 把该
  差距从 30 个百分点收窄到 5 个百分点。
- 为何重要：这直接延伸本仓库跨天线索 8（"LLM-as-judge / 评估基准不能被当作一次性冻结的裁判，
  需要持续校验或演化"，此前已累积 6 条独立证据——评委打分不可靠、评分标准该演化、静态排行榜
  名次无统计显著性、工具调用幻觉前提不成立、长时评估可观测性收窄、离线审计身份识别不可能性
  定理，早已跨过沉淀门槛 a）：这是第 7 条证据，首次把
  判断从"某次评测结果不可信"推进到一个可操作的工程方案——把基准本身当软件维护，给出具体的
  持续验证流水线并真的发布了修复后的版本（Terminal-Bench 2.1），同时首次指出"资源预算是测量
  的一部分"这个此前被忽视的变量：同一个模型，仅因为时间限制设置不同，就可能被错误判定为"harness
  差距"而非"能力差距"。证据边界：仅在单一基准族（Terminal-Bench）上验证，30% 缺陷率能否
  推广到其他 coding agent 基准未知；修复判定依赖作者自建的"自动化 oracle 检查 + 人工批准"
  流程，该流程本身的误判率未独立核验；19 个 agent 的具体版本与是否存在评测时间点差异未在
  摘要层面说明；"排名高度相关"掩盖了个别 agent 移动三位可能带来的实际决策影响（如选型时
  排名差一位的取舍）；作者自建并发布该基准，存在推广自身工具的动机。
- 原文：[Benchmarks as Software 论文](https://arxiv.org/abs/2611.08417)
- 配图：![Terminal-Bench 2.0/2.1 任务失效原因分布图](https://arxiv.org/html/2611.08417v1/benchmark_failures_tb21_changed.png)
  图片来源：论文正文 Figure 3，经 curl 核验可独立打开（HTTP 200）。
