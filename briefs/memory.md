### 3. "不信任模型直接生成结构化产物/编辑"的确定性执行范式
- 2026-09-03：Don't Let the Model Write the YAML（arXiv 2609.00227）在 Kubernetes manifest 场景证明，无论是统一 diff 还是整文件重写都不适合无人值守自动化（宽容 patch 工具仍有 14%-20% 静默误改率），改用"agent 只给结构化字段意图 + 确定性流水线精确替换字符区间"的方案。
- 2026-09-05：When Models Edit Too Much（arXiv 2609.04061）在代码修复场景量化"过度编辑"问题（前沿模型含 GPT-4.5 普遍存在），"保持最小改动"指令与 RL 后训练均能改善编辑保真度，且证明其独立于修复正确性可测量。
- 2026-09-11：If It's Not Buggy, Don't Fix It（arXiv 2609.10123）把同一判断带到第三个独立场景——迭代式自动修复循环：LLM 在完全无 bug 的程序上仍反复"声称"发现 bug，且修复正确代码的破坏率高于修复真实 bug 的成功率，迭代过程常陷入"加了又撤"的循环；机制分析进一步发现一个控制"编辑倾向"的 steering vector，提示模型存在一个会被不当激活的"缺陷代码"内部表征。
- 状态：候选中 3 条，**已跨越"配置文件改写（YAML）→ 代码修复过度编辑量化 → 迭代 bug-fixing 循环 + 虚假 bug 声明的机制分析"三个场景，正式跨过门槛 a（≥3 条跨天证据）**。**已在本期简报提议沉淀**（新建 `wiki/topics/不信任模型直接编辑的确定性执行范式.md`，暂拟页名），尚待用户批准。

### 8. LLM-as-judge / 评估基准不能被当作一次性冻结的裁判，需要持续校验或演化

### 41. Agent 生成代码的"环境规范准确性"是独立于功能正确性的新质量轴，测试通过检测不出来
