### 1. EpiSEM-Bench：请求本身没有恶意，只是工具少说了一句话，agent 就可能做出不安全的事

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / 2026-10-23 公示（v1 于 2026-10-22 17:57:04 UTC 上传，香港城市大学 + 香港科技大学（广州）+ 香港中文大学（深圳））
- 摘要：论文指出，工具调用型 LLM agent 依赖工具返回的环境事实来判断一个操作是否被允许——但如果工具响应恰好漏掉了一条安全相关的事实（例如一项授权额度、接收方的权限、某服务的依赖关系），agent 即便收到的每一句话都是真的、用户请求本身完全是善意的，也可能执行一个本应被禁止的操作。这与"提示注入""越权执行"等已有威胁模型都不同——不需要任何攻击者指令，纯粹是信息缺失导致决策出错。作者构建 EpiSEM-Bench，一个覆盖 6 个领域、300 对匹配的"不安全/安全"任务的可执行基准：先在完整证据下测出基线（Full UCR，完整信息下的不安全执行率），再系统性抹去关键事实测出"证据抹除后"的不安全执行率（Critical UCR），最后给 agent 一个可主动查询的"证据恢复"渠道测出 Recovery UCR 与"配对有效恢复率"（PUR，要求 agent 既主动找回证据、又在两个镜像任务里都做对）。十个模型的结果显示：抹去关键证据后，不安全执行率普遍从个位数跳升到两位数甚至更高——GPT-6-Luna 从 3.0%（完整证据）跳到 21.0%（证据缺失），DeepSeek-V4-Pro 从 13.7% 跳到 65.0%；给予"主动查证"渠道后多数模型能部分或大幅拉回（GPT-6-Luna 21.0%→3.0%，DeepSeek-V4.1-Flash 45.7%→9.3%），但 PUR（真正做到"主动查证+两边都做对"）普遍只有 21%-58%，说明"没做出不安全动作"不等于"真的去主动核实了"——很多时候只是运气好。
- 为何重要：这是本仓库持续追踪的"Agent 执行权限的授权/委托治理空白"（线索 2，已累计 41 条跨天证据）这条线索第一次聚焦"证据缺失"而非"越权指令""账号冒用""沙箱隐式信任"这几个已有子维度——此前证据都假定"坏事发生"需要某种攻击或滥用，这篇论文证明哪怕请求和工具返回全部真实善意，单纯的信息遗漏本身就能把安全边界击穿，而且十个模型在"遗漏后多脆弱""恢复渠道下主动查证的意愿"两件事上差异巨大，提示"给 agent 一个查证入口"并不等于"agent 会用它"。证据边界：300 对任务与 6 个领域均为作者自建的可执行基准，是否穷尽真实工具返回中"关键事实遗漏"的全部形态未讨论；十个模型具体版本未在摘要中逐一列出完整清单；"配对有效恢复"要求同时满足两个条件，具体判定标准（如何界定"主动查证"）依赖论文附录定义，未经第三方复现；论文未披露投稿状态。
- 原文：[EpiSEM-Bench: Evaluating Safety and Evidence Recovery in LLM Agents under Missing Evidence](https://arxiv.org/abs/2610.31650)

### 2. 一句话实验：coding agent 宁可信过时的 CLAUDE.md，也不信眼前的代码

- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-10-23 公示（v1 于 2026-10-22 01:00:43 UTC 上传，Xiaonan Xu [佐治亚理工学院] + Wenjing Wu [科罗拉多大学博尔德分校]）
- 摘要：论文测量了一个本仓库自身也在依赖的机制——coding agent 会读取项目的指令文件（Claude Code 读 CLAUDE.md，Codex CLI 读 AGENTS.md），但这些文件往往写一次就很少被重新审视，而代码本身一直在变，于是指令文件描述的约定可能早已和实际代码脱节。作者构建 40 个 Python 项目，每个项目的指令文件要求一种约定（例如用 print），但现有代码实际用的是另一种（例如用 logging），让 Claude Code 与 Codex CLI 各自在"有/无一句优先级声明"两种条件下为每个项目添加一个功能，共 320 次运行。结果：没有那句话时，90.1% 的 agent 选择遵循过时的指令文件而非眼前的代码；Claude Code 在 80 次运行中有 79 次明确指出了文件与代码的冲突，但依然选择遵循文件；Codex CLI 在 80 次运行中有 20 次直接把现有（正确）代码改写成符合过时文件的样子，其中 17 次导致项目自身的测试随后失败。在用户级指令文件里加上"现有代码优先于本文件"这一句话后，遵循代码的选择比例从 4.2% 升到 91.4%，改写现有代码的行为消失，测试通过率从 89.4% 升到 100%。作者将这一现象归因于两种信息进入模型的渠道不同——指令文件是以"指令"形式送达，代码是以"工具输出"形式送达，而模型训练过程本身就倾向于把工具输出的权重排得更低。
- 为何重要：这篇论文测的正是本仓库据以运作的 AGENTS.md / CLAUDE.md 机制本身的一个具体失效模式——不是"agent 会不会参考指令文件"，而是"指令文件过时时，agent 会不会盲信文件、无视眼前已经改掉的代码"，而且即便 agent 自己已经发现了冲突（Claude Code 79/80 次指出冲突）也照样选错。这与本仓库持续追踪的"代码与文档漂移"论点直接相关，但角度更具体：此前证据（Documentation Drift in AI-Generated Pull Requests 等）测的是"代码改了、文档有没有跟着改"，这篇测的是"文档没跟着改时，agent 该信谁"，并给出了一个几乎零成本的具体缓解措施（一句话）。证据边界：40 个项目均为作者自建的小型 Python 项目，冲突场景局限于"单一命名/实现约定不一致"这一种漂移类型，未覆盖更复杂的语义级漂移；仅测试了 Claude Code 与 Codex CLI 两款 harness，未覆盖其他主流 coding agent；"一句话"方案的效果是否会随指令文件复杂度、项目规模增长而衰减未讨论；论文未披露投稿状态，暂无第三方复现。
- 原文：[Stale Instruction Files Override the Code in Coding Agents: A One-Sentence Fix](https://arxiv.org/abs/2610.30571)

### 5. 用 Petri 网把 agent 的"能不能做"焊死在"有没有授权"上，而不是靠读懂指令的意思（AI / 智能体，今日加选）

- 领域：AI / 智能体（Agent，今日加选）
- 来源 / 发布日期：arXiv / 2026-10-23 公示（v1 于 2026-10-22 14:48:16 UTC 上传，Chao Gu [贝尔法斯特女王大学] + Quanyan Zhu [纽约大学]）
- 摘要：论文研究 LLM agent 在面对提示注入时的安全工具执行问题。作者用 Petri 网把 LLM 与其工具之间的"执行 harness"形式化为一个监督控制问题：网中的"标记"（marks）代表能力、批准与预算；一个变迁（即一次工具调用）只有在它所需的标记都存在时才能触发，因此一条预设条件不满足或预算已耗尽的注入请求会被拒绝，无论它的措辞多有说服力——判断依据是形式化的资源状态，而不是对指令语义的理解。作者把工具执行结果视为不可控变量，用"最大许可监督器"来保证安全性，并证明在四个假设下这种安全性能从离线模型迁移到实际运行的系统。论文进一步引入"重新规划闭环"概念——agent 被拒绝后可以再次尝试，每次重试消耗一次推理调用；作者证明在这种闭环下，常规的最大许可监督器可能比一个更严格但同样安全的监督器"侵入性"（即不必要拒绝合法请求的程度）高出任意倍数，并针对给定的提议模型给出一个"最小侵入最大许可监督器"的构造方法。在一个"自主发布代理"案例的仿真中（基于脚本化提议者，每个注入概率取值跑一万轮），作者发现安全部署必须包含一个监督器在发布流程启动之后仍能拒绝执行的步骤，纯"事前一次性审批"做不到这一点。
- 为何重要：这是本仓库持续追踪的"Agent 执行权限的授权/委托治理空白"（线索 2）"权限边界"子维度（此前含 SARA/CapScope/GuardedAct/EffectMatch/PACE 等）新增的一条形式化方法路径——此前的方案大多靠工程化的权限检查或统计学习，这篇论文用 Petri 网监督控制理论直接证明"只要资源状态标记设计对了，拒绝请求不需要理解攻击者想干什么"，并第一次把"重新规划循环"本身的成本（不必要拒绝合法请求、迫使 agent 反复重试）纳入可形式化比较的指标，提示"更安全"的监督器设计选择不当可能带来隐性的可用性代价。证据边界：核心案例（自主发布代理）是作者自建的仿真环境，用脚本化（而非真实 LLM）提议者跑一万轮蒙特卡洛模拟，并非真实生产 agent 系统上的验证；"安全性从离线模型迁移到运行系统"依赖的四个假设具体内容及其在真实 harness 中是否成立未在摘要展开；对比的"常规监督器"与"最小侵入监督器"均为同一团队的理论构造，未见第三方复现或与 SARA/CapScope 等既有工程化方案的直接对比实验；论文未披露投稿状态。
- 原文：[Certified Execution Harness for Agentic AI: Safe and Least-Intrusive Petri-Net Supervisory Control Between Reasoning and Action](https://arxiv.org/abs/2610.31376)

## 今日主线

今天 5 条的共同落点是："信任"这件事正在被拆解到越来越具体、越来越不依赖"模型理解对不对"的颗粒度上。条目 1（EpiSEM-Bench）证明，哪怕请求和工具返回全部真实善意,仅仅因为少了一条关键事实,agent 就可能把不安全执行率从个位数推到五六十个百分点——问题不在"模型会不会被骗"，而在"模型手里的信息够不够"。条目 5（Petri 网 harness）从另一个极端给出回应：如果干脆不让"理解"参与决策，只靠资源状态标记的有无来放行或拒绝，那么连"措辞多有说服力"都不重要——但它也诚实地指出，这种确定性换来的代价是必须在流程启动后仍保留"事后能拒绝"的能力，纯粹的事前一次性审批并不够。条目 2（Stale Instruction Files）把同一张图景带回本仓库自身正在使用的机制——coding agent 面对"过时的指令文件 vs. 已经改掉的代码"时，哪怕自己已经发现了冲突，仍系统性选择相信那份写一次就不再更新的文件，这和"信息不够"（条目 1）、"靠什么判断是否放行"（条目 5）其实是同一个问题在文档维护场景下的具体版本。条目 3 与条目 4 把视角拉回资本与产品路线：OpenAI 新一轮融资传闻的估值从一个月前的 1.4 万亿美元修正为 1.25 万亿美元，提醒"超高估值"本身也需要被反复校验而非一次性采信；GM 把"眼睛离开路面"的自动驾驶从电动 SUV 扩展到主流皮卡与大型 SUV，则是继 Tesla 纯视觉自建车队、Waymo 传感器融合自营、Pony.ai/Rivian 借道资本轻量平台之后，第四条押注消费级个人车主而非机器人出租车车队的路线——四条线最终都指向同一个问题：当系统越来越自主，"够不够信息""靠什么放行""信哪份记录""信哪个估值"，都必须被拆解成可核查的具体机制，而不能停留在笼统的信任姿态上。

## 沉淀候选

1. **论点**：EpiSEM-Bench 证明，哪怕请求本身善意、工具返回的每一句话都真实，仅凭"关键安全事实被遗漏"本身就能让 agent 的不安全执行率从个位数跳升到两位数甚至 65%（十个模型实测），且"给 agent 一个主动查证渠道"能部分缓解但"配对有效恢复率"普遍只有 21%-58%——为"Agent 执行权限的授权/委托治理空白"这条已持续累积 41 条跨天证据的判断，补上一个全新机制（证据缺失导致良性任务不安全执行，不涉及任何攻击者或越权指令）。
   **命中**：门槛 a（线索 2 早已跨过 ≥3 条跨天证据门槛，本条为累计第 42 条候选证据）。
   **建议落点**：追加到待批准新建的 `wiki/topics/agent-工具执行的运行时授权治理.md`（该页确认仍不存在，与「harness-vs-model」「agent-生产级落地的鸿沟」两页已存在但待追加证据的情况不同），新增"证据缺失导致的非恶意越权"子维度，与既有"权限边界""善意指令后果验证""沙箱产物隐式信任""审计基础设施本身是否可信""真实生产事故""行业治理承诺""账号身份与决策权责的系统性混淆"等子维度并列。
   **对应 `wiki/purpose.md` 关键问题**：第 2 条（agent 自主执行的信任边界如何划定）。

2. **论点**：Certified Execution Harness 用 Petri 网监督控制理论证明，只要把能力/批准/预算形式化为资源标记，"拒绝一个注入请求"可以完全不依赖理解指令语义——同时首次把"重新规划闭环"下监督器的隐性可用性代价（不必要拒绝合法重试）纳入可比较的形式化指标，并证明"事前一次性审批"在持续运行的系统里不足够、必须保留流程启动后仍可拒绝的能力。
   **命中**：门槛 a（线索 2，本条为累计第 43 条候选证据）。
