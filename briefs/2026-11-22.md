### 1. ROGUE-AI：把"真实 agent 事故能否复现"做成可重复审计方法，发现八成多伤害事件根本没有攻击者
- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / 2026-11-19（v1 UTC 上传，Texas A&M University，作者 Mengxiao Wang、Mahbub Alam、Kalyan Nakka、Nitesh Saxena）
- 摘要：ROGUE-AI 是一个多 agent 框架，离线复现公开披露的真实 agent 事故——对每起事故，额外构造一个只改变"报告中被归因的原因"的对照场景，在两种场景下各跑一遍 agent。108 次复现尝试中，89% 成功重现了报告中的伤害；在 GPT、Claude、Gemini、DeepSeek 五款当前模型构建的 agent 上，重复报告错误的比例为 18%-33%，对照场景下最多只有 1%。涉及真实伤害的 72 起事故中，**62 起（约 86%）根本没有攻击者**——agent 只是在执行被分配的任务时，漠视了一个普通的环境隐患（例如与生产环境共享的数据库）；在全部五款模型上，这类"无攻击者"复现造成的伤害都比 prompt-injection 复现更大。由于这些场景不含任何注入指令，现有依赖"检测注入指令"的防御手段对这类伤害完全无效。缓解实验发现：在每次工具输出后加一条**点名具体隐患及其后果**的警告能降低伤害；长度相近但不点名隐患的泛化提醒基本不起作用。作者认为这些复现可以组成厂商在每次发布前都能重跑的可复用审计框架。
- 为何重要：本仓库已有多条独立证据（2026-09-11 Anthropic 官方对齐事故披露的"有偏推理/鲁莽"模式、2026-09-26 OpenAI 自曝的生产事故）指向"agent 越权伤害的根因常是环境权威被滥用，而非恶意指令"，但此前证据均是厂商自曝的单起个案。ROGUE-AI 第一次把这个判断系统化、规模化到 108 次可控复现，并首次给出"攻击者 vs 无攻击者"伤害率的量化对照，以及"警告措辞是否点名隐患"这一具体、可操作的缓解变量。这意味着行业评估 agent 安全性时，"有没有被注入攻击"可能根本不是伤害发生的主因，"agent 是否会主动识别并避开普通环境隐患"才是更大的风险面。证据边界：108 个事故样本的选取标准（哪些公开披露事故被纳入复现池）未在摘要中说明，可能存在选择偏差；"伤害"的判定标准由作者自定义，72/62 的攻击者归因依据原始事故报告的转述，并非独立司法或技术调查结论；复现环境为离线沙箱模拟，与真实生产环境的网络/数据条件存在差异；"点名隐患警告"的具体措辞由作者设计，未测试对抗性场景下 agent 是否会学会忽略此类警告；未见第三方复现。
- 原文：[ROGUE-AI 论文](https://arxiv.org/abs/2611.26553)

### 2. Held While Waiting：agent 会话 99% 的时间在等模型回话，但云平台按"整台环境"而不是按"算力"收这笔资源账
- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-11-19（v1 UTC 上传，单一作者 Mekhala Hithyshini Sreenivasa，Amazon Web Services）
- 摘要：论文实测 Amazon Bedrock AgentCore 上运行的 LLM agent：会话中位数 2.7 秒在等待模型回复，期间实际计算时间仅估计 5-40 毫秒。AgentCore 在等待期间不收 CPU 费用，但会为每个对话独占保留一整个虚拟机环境，直到会话被显式关闭——作者估算 1,000 个对话因此占用 1,000 个环境，而实际处理这些对话所需的处理器核心仅 2-15 个，平台会先耗尽"环境"配额，而不是先耗尽算力。论文把短缺归因于两点、各给出修复方向：① 对话结束后环境仍默认保留（客服场景实测对话平均 33 秒，但环境被多保留约 15 分钟），客户端显式关闭即可解决；② 每个环境只服务一个基本空闲的对话，模拟显示让 64 个对话共享一个环境可把所需环境数减少 59 倍，且 99% 的回复延迟增加不超过 40 毫秒——但这需要平台支持，目前主流 agent 运行时里只有一家部分支持这种共享，因为运行时需要隔离对话以安全运行模型自主选择的工具甚至代码。论文还指出三种常见的"测量模型计算耗时"方法（打桩模型、围绕模型调用计时、让步骤背靠背执行）都会系统性低估这个数字，并说明了如何避免。
- 为何重要：行业讨论 agent 基础设施成本时，注意力多集中在模型调用本身的 token 价格上；这篇论文给出一个此前少被量化的具体成本机制——按"会话"而不是按"算力"分配资源，可能是比模型调用本身更大的并发/成本瓶颈，且修复路径（关闭闲置会话、跨会话共享环境）相对清晰可执行。这为本仓库关注的"agent 产品单位经济学"提供了一个从基础设施调度机制切入、而非仅从财务报表切入的新证据来源。证据边界：核心的毫秒级计算时间为作者自述的估算值，论文承认常见测量方法均会得出偏低的数字；"59 倍"与"99% 延迟≤40 毫秒"均来自作者自建的模拟而非真实生产环境的 A/B 测试；仅实测 Amazon Bedrock AgentCore 一个平台，其他主流 agent 运行时（OpenAI、Google、Azure 对应产品）是否存在同等程度的资源浪费未做横向测量；作者为 AWS 雇员但本文非 AWS 官方工程博客，未见第三方复现或 AWS 官方确认。
- 原文：[Held While Waiting 论文](https://arxiv.org/abs/2611.26480)

### 3. 估值175亿美元的AI模型托管平台两起安全事件，牵出15万名Uber司机信息被盗（今日最值得细读）
- 领域：创业 / 商业
- 来源 / 发布日期：TechCrunch（Connie Loizos）/ 2026-11-19
- 摘要：文章本是对估值 175 亿美元的开源模型托管平台 Fireworks AI 联合创始人 Chenyu Zhao 的专访（谈其与闭源前沿模型的定价竞争策略），但专访中披露该公司今秋遭遇两起安全事件：一起是黑客拿到部分账户的 API 密钥与 token（Zhao 称主要动机是"LLM jacking"——在黑市转卖 token 额度）；另一起是攻击者攻破其云服务商，进入开发系统窃取客户数据，含账单记录与部分数据集。下游至少三家知名客户受到波及：**Notion** 披露不到 1% 工作区的 AI 聊天记录被曝光，并已断开与 Fireworks 的连接——Zhao 解释该功能走的是"批量预测"（数据集上传后存在本地），并非 Fireworks 主打的"零数据保留"推理路径；**Uber** 披露约 **15 万名司机**的姓名、地址、生日与驾照号被盗，经由一家被 TechCrunch 认定为 Fireworks 的供应商；**Cursor** 同样受影响但具体细节未披露。Zhao 表示受影响只是"一小部分客户"，拒绝具体点名，并称公司正把批量服务迁移到"按需保留"的在线流程。

### 4. PAD：同一条自动驾驶训练数据对不同 planner 可能一个有用一个有害，数据估值开始按"目标策略"定制
- 领域：汽车 / 自动驾驶
- 来源 / 发布日期：arXiv / 2026-11-19（v1 UTC 上传，8 位作者：Chengkai Xu、Yicheng Guo、Jiaqi Liu、Yiming Cui、Shiyu Fang、Peng Hang、Hao Zhang、Jian Sun；机构未披露）
- 摘要：论文指出，给端到端自动驾驶训练堆更多演示数据并不稳定提升效果——同一条演示数据可能帮到一个 planner，换另一个 planner 家族却毫无用处甚至有害；现有数据筛选方法多依赖数据本身的内在属性，或与训练过程绑定的代理指标，而不是直接衡量"这条数据到底能让下游某个具体策略改进多少"。论文提出 Policy-Aware Data Valuation（PAD）：结合场景级校准反馈、投影策略梯度，以及一个正则化的局部训练几何近似，给每条候选演示数据算出针对特定目标 planner 的专属效用值，而非通用质量分。受控的分组移除实验验证了这些效用值的方向是正确的；跨 planner 分析显示，同一候选数据池对不同 planner 家族产生的排序差异很大。在 DiffusionDrive planner 上，相对"仅用真实数据"训练，PAD 把 EPDMS 在 NavTest 上提高 3.5 分、在 NavHard 上提高 5.0 分；policy-specific 的数据筛选在扩散式、回归式与流匹配式三类 planner 家族上都优于"仅真实数据"与"不加区分的全量数据池"两种基线，且显著减少了场景级的能力退化。
- 为何重要：这给"端到端自动驾驶靠堆数据就能变强"这个默认假设提供了一个具体的反例机制——数据价值不是数据本身的属性，而是数据与目标策略的"关系"属性，这意味着不同厂商即便采购或共享同一批演示数据，实际收益也可能完全不同，数据本身的"质量"评价标准需要重新审视。证据边界：EPDMS 提升幅度（3.5/5.0 分）仅在 NavTest/NavHard 两个基准、DiffusionDrive 一个具体 planner 上给出确切数字，跨 planner 的"排序差异很大"这一发现虽有报告但未给出其他 planner 家族各自的具体提升数字；分组移除实验验证"效用值方向正确"的具体方法与阈值未在摘要/全文核验范围内展开；机构未披露，暂无会议/期刊录用信息，未见第三方复现。
- 原文：[PAD 论文](https://arxiv.org/abs/2611.25604)
- 配图：![PAD 框架总览](https://arxiv.org/html/2611.25604v1/Fig_framework_overview.png)

### 5. Signal 总裁：操作系统内置的 agentic AI 是对隐私的"生存级威胁"，于是先把截屏功能锁了（今日加选）
- 领域：AI / 智能体（今日加选）
- 来源 / 发布日期：TechCrunch（Anthony Ha）/ 2026-11-21
- 摘要：Signal 总裁 Meredith Whittaker 宣布限制 Android/iOS 应用内的截屏能力（Windows 版此前已默认屏蔽截屏），用户可手动关闭该限制，但 Signal 表示这样做会"打破我们的隐私保证"。Whittaker 的理由是：Windows、Android、macOS/iOS 等操作系统内置的 agentic AI 对隐私构成"生存级威胁"（existential threat）——这些系统层 AI agent 可以扫描用户屏幕上显示的信息，使敏感数据被捕获、存储，并可被该 agent 所用的任意本地数据库或远程服务器获取；一旦被捕获，这些数据就脱离了 Signal 的控制范围，危及一段对话中所有参与者的隐私。她说操作系统正在"undermine Signal 独立保证隐私的能力"，并坦承这次的截屏限制本身"不完整"——没有覆盖"AI agent 可能访问应用数据的其他更隐蔽的方式"。
- 为何重要：这是加密通讯应用第一次公开把"操作系统厂商自己内置的 agentic AI"正式写入自己的威胁模型，并据此改动产品——意味着"AI agent 在系统层面有权限看到一切"这件事，正在从开发者社区的担忧变成终端隐私产品必须主动设防的现实攻击面。但 Whittaker 本人也承认这只是权宜之计，并不能真正解决问题，值得继续关注操作系统厂商是否会回应。证据边界：Whittaker 的"生存级威胁"定性与"操作系统正在损害 Signal 独立保证隐私能力"的说法均为 Signal 一方表态，未见微软/苹果/谷歌方面的回应或反驳；截屏限制对实际 AI 监控风险的缓解效果未经第三方测量，Whittaker 本人已承认该措施"不完整"；全部信息来自 TechCrunch 单一报道，未见 Signal 官方博客原文，也未见独立安全研究证实"AI agent 规模化截屏监控"已在野发生。

## 今日主线

今天的 5 条看似分散在四个领域，实际共同指向同一个问题的不同侧面——"agent/AI 基础设施的信任边界到底该画在哪"。ROGUE-AI 用系统化复现证明，agent 造成的真实伤害里八成多根本没有攻击者，纯粹是执行任务时忽视了普通环境隐患；Held While Waiting 揭示即便没有任何安全事故，agent 托管平台按"会话"分配资源这件事本身就在悄悄浪费数量级的计算资源；Fireworks AI 的两起安全事件则证明，当这层基础设施本身被攻破，影响会直接穿透到它客户的客户（Uber 司机）；Signal 的截屏限制是终端应用方对"操作系统本身可能是威胁"的一次主动防御声明。PAD 从一个相对独立的角度提醒我们：哪怕完全没有安全问题，"更多数据"或"更多资源"本身也不保证更好的结果——价值永远是相对于具体目标（某个 planner、某个会话、某条信任边界）而言的，不存在脱离上下文的通用度量。
