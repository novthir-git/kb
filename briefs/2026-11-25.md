### 1. Anthropic 把"审批"也产品化：Claude Ship 让 agent 自己按团队写的政策文件决定哪些 PR 能合并，官方自曝合并数翻倍、回退率降四成以上
- 领域：AI / 智能体
- 来源 / 发布日期：Claude by Anthropic（官方博客）/ 2026-11-23；另见 TechCrunch（Sarah Perez）同日报道
- 摘要：Claude Ship 是 Anthropic 新发布的 PR 全生命周期自动化产品，由三部分组成：已正式可用的 Code Review（多角度审查 PR、对发现做对抗性复核后分类发布到 PR）；Beta 阶段的 PR Steward（持续修复失败的 CI 检查、合并冲突与评审反馈，每次推送后留言说明改动内容及如何回滚，但设计上不具备自行批准/合并的权限）；以及 Beta 阶段的 Claude Approvals——团队把批准策略写成仓库内的一份文件（自然语言），由其依据 Code Review 发现与自定义分类器信号自动批准符合条件的变更，或要求特定情形人工签字。Anthropic 建议先以"仅观察模式"运行 Claude Approvals，再逐步接入分支保护强制生效。官方给出的量化数据：在 Claude Code 团队内部，6 月到 9 月间合并的 PR 数量翻了一倍以上，同期被回退（revert）的 PR 比例下降超过 40%（Anthropic 强调 Claude 审查只是整体流程的一环，非唯一原因）。TELUS 工程总监 Vatsal Bhatt 与 Carvana 工程副总裁 Alex Devkar 的客户证言均强调"把人工精力留给真正需要人工的变更"。产品面向 GitHub 上的 Claude Team/Enterprise 计划开放，按 token 计费，符合条件的 Enterprise 客户可在 2027-01-15 前申领至少 1 万美元信用额度。
- 为何重要：本仓库线索 1（"头部实验室自报量化基线"，已累积 8 条候选证据，涵盖 Anthropic AI 研发自动化指数、湿实验室发现、Google FlowAgent、DoorDash 功能开关清理等）再添一个来自 Anthropic 自身内部团队的具体案例——"合并 PR 翻倍 + 回退率降四成"是继此前"渗透率/采纳率"类指标后，又一个"转化漏斗"式的自报基线。同时，Claude Approvals 的设计也构成一个值得关注的产业对照：本仓库线索 42 昨日新收录的《Markdown Is Not a Firewall》论文证明，仅靠自然语言规则文件（如 AGENTS.md/CLAUDE.md）约束 agent 行为强制力很弱，真正拦住越界的是独立于文件之外的确定性网关；而 Claude Approvals 把"批准关卡"本身也做成了自然语言策略文件 + AI（Claude 自己）判断的机制，而非独立于被评估对象之外的确定性网关——这恰好是论文所警示的那类"劝导性强、强制力弱"机制的一个具体工业落地案例，其是否会在真实生产环境中重演同样的局限性，值得后续追踪。
- 证据边界：全部效果数据来自 Anthropic 自身内部团队（Claude Code team）使用自家产品的自报结果，没有外部客户的汇总统计或独立审计；"6 月到 9 月"的具体基线定义、团队规模、PR 复杂度分布均未披露；TELUS、Carvana 的客户证言是公司挑选的案例而非随机抽样或独立调研；PR Steward 与 Claude Approvals 仍处 Beta，Anthropic 自己承认该产品"可能漏掉 bug、安全漏洞或其他问题"；不支持 Zero Data Retention/HIPAA/客户自管密钥的企业客户。

### 2. AgentBouncer：给软件工程 agent 的每一次系统调用都加一道 AI 仲裁，把攻击成功率从 99.41% 压到 10.59%，额外成本不到半美分
- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-11-23（Pascal Joos、Michael Pradel，机构未披露）
- 摘要：论文指出，软件工程 agent 要访问文件、执行命令、下载资源，这也让它们暴露在提示注入、恶意工具与供应链攻击之下；现有防御大多只检查最初的提示词与工具调用序列，而不检查真正执行的系统调用本身。AgentBouncer 在系统调用层面做运行时仲裁：每次调用先由一个 LLM 仲裁者依据"该调用对当前任务有多必要"和"有多安全"两个维度打分——调用看起来越不必要，仲裁者就需要越确定其安全才会放行；预置的策略规则与层级感知缓存减少仲裁者被触发的频率，以控制开销。作者在开发环境中用 4 类攻击向量共 340 次攻击、以及来自 SWE-bench Verified 的良性修复任务做测试：无防护时攻击成功率 99.41%，接入 AgentBouncer 后降到 10.59%，比现有同类防御方案再低 18.23 到 73.53 个百分点；良性工具调用仅 0.25% 被误拦，任务成功率基本保持；每个良性任务额外增加约 47 秒与 0.0036 美元的 LLM 开销，是现有最接近的同类运行时防御方案开销（4.5 倍时间、9.6 倍成本）的一个零头。
- 为何重要：本仓库线索 42（"生产级 AI 系统的护栏可拆解为带独立量化效果的具体模式目录"）此前已有断路器/输出质量门/组件隔离（10-05）与仓库规则文件（11-20，效果为负）两条候选证据，本文补上第三个具体模式——"系统调用级运行时仲裁"，且执行层次比昨日《Markdown Is Not a Firewall》论文里的独立网关更底层（网关拦在应用边界，系统调用仲裁拦在操作系统边界），为该护栏目录增加了一个此前缺失的、量化效果最强的具体工程模式。
- 证据边界：仅两位作者，论文未披露机构归属；340 次攻击集中在开发环境中自建的 4 类攻击向量，能否代表真实生产环境遭遇的攻击分布未知；LLM 仲裁者本身是否会被提示注入或对抗性输入绕过未在论文中讨论；预印本，无同行评审或第三方复现信息。
- 原文：[AgentBouncer: Defending Software Engineering Agents via Dynamic System-Call Mediation](https://arxiv.org/abs/2611.30621)（检索于 2026-11-24）
- 配图：![攻击成功率与任务成功率的权衡散点图，左上角最优](https://arxiv.org/html/2611.30621v1/asr_utility_scatter.png)
  图片来源：[AgentBouncer 论文 Figure 7](https://arxiv.org/html/2611.30621v1)。

### 4. ROSE-Drive：冻结所有驾驶模型权重，只靠运行时编排与失败驱动的离线修订，把闭环驾驶分数从 25 拉到 52
- 领域：汽车 / 自动驾驶
- 来源 / 发布日期：arXiv / 2026-11-23（Qihang Huang、Zhidong Wang、Zirui Li 等 9 位作者，机构未披露）
- 摘要：论文提出 ROSE-Drive，一个与具体模型无关的运行时编排框架，统一调度冻结的端到端驾驶模型、驾驶技能、感知工具与反馈控制器：一个蒸馏版视觉语言模型（VLM）每隔固定步数提出驾驶任务与场景关系建议；编排器维护共享物理状态与持续任务，融合模型与技能各自的输出、在它们之间移交任务责任，并依据执行反馈选择控制器、复用有效的运动参考、调度模型推理；离线阶段再用执行记录修订技能本身及其协同方式，供后续系统阶段继承，而模型、感知与 VLM 权重全程保持冻结不变。结果：在留出的 Longest6 基准上，AutoMoT 的闭环驾驶分数（DS）随系统阶段推进从 25 升到 52，SimLingo 从 22 升到 47；两套系统中，超过 71% 的控制步跳过了新一轮模型推理。
- 为何重要：本仓库线索 4（"Harness 设计是决定同模型实际表现的独立架构变量"）已累积 32 条候选证据，但长期几乎全部来自软件 / coding agent 场景，直到 11-20《Generalist Action Critic》首次把"模型权重冻结、只靠推理期架构改动"这一判断延伸到自动驾驶规划领域（单次事后复核）。ROSE-Drive 是该线索第二个自动驾驶领域证据，并把覆盖范围从"单次事后复核"推进到更完整的"持续运行时编排 + 技能调用 + 失败驱动的离线修订"这一系统级设计，首次在自动驾驶场景给出与软件 agent 领域量级相当的"harness/编排层决定表现"量化证据（DS 从 25 翻倍到 52，71% 的推理步骤被跳过）。
- 证据边界：全部数字来自作者自建的 Bench2Drive v0.0.3/v0.0.4、Fail2Drive 与留出的 Longest6 基准，未见独立第三方复现；作者机构未披露；论文与同日提交的另一篇论文《AgentMoT》作者高度重叠（可能是同一团队的并行产出），两者之间的对照关系论文本身未说明；蒸馏 VLM 的具体底座模型未具名；真实道路场景（而非仿真/基准）下的安全收益未经验证；预印本，无同行评审信息。
- 原文：[ROSE-Drive: Runtime Orchestration and System Evolution for Autonomous Driving](https://arxiv.org/abs/2611.30438)（检索于 2026-11-24）
- 配图：![ROSE-Drive 系统架构：能力组合、任务延续、自适应调度，VLM 每五步提出建议，三套协同执行的 harness 与安全过滤器](https://arxiv.org/html/2611.30438v1/fig2_framework.png)

### 5. ShellBench：1000 万条真实交互喂出的"日常生活"基准，顶尖模型三次重复同一任务里只有不到一半能全部做对（今日最值得细读）
- 领域：AI / 智能体（第二条，今日最值得细读）
- 来源 / 发布日期：OpenClaw Foundation 官方博客（联合 Parsewave、Hugging Face、Red Hat、UC Berkeley 等机构）/ 2026-11-24；另见 TechCrunch（Rebecca Bellan）同日报道
- 摘要：ShellBench 从超过 1000 万条匿名真实 AI agent 交互中提炼出 100 个"日常生活委托任务"：90 个按 721 项评分细则（含 381 项安全细则）打分，其中必须全部满足才算完成；10 个用代码直接测试。每个任务配一份含约 188 个文件（邮件、日历导出、表格、聊天记录、收据、网页存档、PDF）的工作区，并故意混入过期记录、相似账户、矛盾信息与潜在恶意指令。作者在 12 个模型（含 GPT-6 Astra、Claude Fable 5.2、Claude Opus 5.5、Gemini 4 Carbon、Muse Wonder Full 等）× 5 款 harness（Claude Code、Codex、Hermes、OpenClaw、Pi）上跑出 53,100 次评分运行，每个任务重复三次。结果：单次尝试平均通过率最高的模型是 GPT-6 Astra（62.5%，约 1.10 美元/次），其次 Claude Fable 5.2（61.9%，0.83 美元/次）；11 个模型的 harness 均值相差仅 2.36 个百分点（OpenClaw 45.23% 最高，Claude Code 42.87% 最低），说明整体上模型选择比 harness 选择影响更大，但在表现最好的五个模型之间，harness 造成的差距（9.9pp）反而接近甚至超过模型造成的差距（15.2pp）。可靠性方面，GPT-6 Astra 三次独立尝试里"至少成功一次"的比例是 75.1%，但"三次全部成功"只有 48.8%，相差 26.3 个百分点。安全方面，全部 53,100 次运行里 15.7% 未通过至少一项安全细则，即便在 26,151 次"正确完成任务"的运行里，仍有 9.9% 未通过安全细则——作者把安全失败归为钓鱼、欺诈性支付指令、敏感信息、不可逆操作四类，但未披露各类具体失败率。
- 为何重要：本仓库线索 16（"同一任务重复执行的一致性缺口，独立于平均通过率"）奠基于 09-10/09-11 两篇论文（GPT-4.1+ReAct 单次通过率 77% vs 连续五次全对 53%，24pp 落差），此后约两个半月未再出现专门针对"重复执行一致性"这一具体子维度的新证据（09 月中旬后的后续证据转向"进度自报/审查完整性/工具失败谎报"等相邻但不同的自我报告失真子问题）。ShellBench 给出一个独立团队、独立基准、独立模型（GPT-6 Astra，75.1% vs 48.8%，26.3pp 落差）下几乎同构的复现，强化"一致性缺口是跨基准、跨模型的普遍现象，而非某一篇论文的基准特有产物"这一判断，且首次把该判断的任务域从编码/交互式基准扩展到"个人生活委托任务"这一全新场景。同时，"模型选择整体上比 harness 选择影响更大、但头部模型之间 harness 更关键"这一发现，也为线索 4（harness 设计）已有的"harness 增益随模型能力增强而收缩"限定条件系列补上一个新任务域（日常生活 agent）的佐证；15.7% 的安全失败率、且其中近一成发生在"任务本身做对了"的运行里，提示"正确性"与"安全性"可以相互脱钩，与线索 42（护栏）、线索 59（outcome-only 指标掩盖过程脆弱性）方向相邻。
- 证据边界：博客引言与致谢部分列出的合作机构不一致（致谢额外提到 Paradigm、哥伦比亚大学、NVIDIA，引言未提及），存在披露不完整的可能；论文本身"待发表"，当前只有博客文章，未见可下载的数据集或代码仓库链接；评分依赖单次 LLM 裁判，作者自陈"部分差异可能来自裁判本身"而非模型/harness 真实差异；未在 Muse、Dots、Claude Duet 的原生产品 harness 下测试，结果未必代表普通消费者在这些产品中的真实体验；100 个任务规模中等，安全判据集中在作者自定义的四类风险，未必覆盖其他类型的个人生活风险。

## 今日主线

这 5 条表面分散在"PR 审批产品化""系统调用仲裁""企业 agent 定价模式""自动驾驶运行时编排""日常生活基准"五个话题里，但共同指向同一个问题：**当 agent 的产出已经足够多、足够快，谁来决定哪些产出"可以被接受"、以及这个判断本身有多可靠？** Claude Ship 把"批准"这个判断外包给一份自然语言策略文件 + AI 自己；AgentBouncer 把判断下沉到系统调用层面、由独立 LLM 仲裁者逐次裁决；ROSE-Drive 把判断外置到一个持续运行、与模型权重脱钩的编排层；Sierra 的 outcome-based 定价本质上是把"客户是否认可这个结果"作为付费判断的唯一依据，这要求"结果是否达标"本身必须可被稳定地判断；而 ShellBench 恰恰说明，即便是今天最强的模型，"同一个任务反复做"这件事本身的判断结果都不稳定——三次里有一次掉链子的情况接近一半。五条证据合起来提示：行业正在把越来越多的信任，压在"agent 产出是否合格"这个判断环节上，但无论是用 AI 做判断（Claude Approvals）、用独立机制做判断（AgentBouncer）、还是干脆把判断外包给商业结果（outcome-based 定价），这个判断环节本身的可靠性都还没有被证明足够稳固。
