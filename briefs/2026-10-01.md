### 1. Planning-as-Routing：Agent 声明的计划结构，只有 22%-45% 在执行中被真正遵守
- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / 2026-09-30（v1 于 2026-09-29 17:47 UTC 上传，ADIA Lab + 格拉纳达大学 + 卢森堡科技
  研究院）
- 摘要：论文把"agent 声明了什么计划"与"实际是否照此执行"拆成两个独立可测的维度，提出 Planning-as-Routing——
  LLM 从 Predefined / Sequential / Hierarchical / Search 四种模式中声明一种，再由确定性路由器分派给对应的
  模式专属执行器。在 4 个基准、3 个 LLM 上发现：通用的 Plan+ReAct 在更长的计划轨迹上普遍无法保持声明的计划
  结构，三个基准上仅 22%-45% 的轨迹保住结构，而模式专属执行器能强制维持；最大增益来自执行环节本身——在
  ALFWorld 上任务成功率从 0.48 提升到 0.92，在 SWE-bench Verified 上从 0.36 提升到 0.44；但当前 LLM 仍不能
  可靠地为每个任务选出最优模式，少样本示例只在部分基准-模型组合上有帮助。
- 为何重要：这把"agent 说自己在做什么"和"agent 实际做了什么"之间的落差，从模糊的"幻觉"问题精确到一个可
  拆解、可分别修复的具体机制——路由能大幅缩小执行缺口，但模式选择本身仍是开放问题。证据边界：论文未经同行
  评审（投稿信息未披露）；四个基准与三个模型的组合仍是有限的组合空间，"最强模式因模型而异"这一发现本身也
  暗示结论可能不能外推到未测试的模型；ADIA Lab 主要背景为量化金融研究，本文是否代表该机构的持续研究方向
  未知。
- 原文：[Do LLM Agents Execute the Plans They Declare? 论文](https://arxiv.org/abs/2609.38108)
- 配图：![Planning-as-Routing 的声明-路由-执行框架](https://arxiv.org/html/2609.38108v1/planning_routing.png)
  图片来源：[论文 Figure 1](https://arxiv.org/html/2609.38108v1)。

### 2. 71,677 份 Agent PR 里挑出的 1,262 个"性能修复"：合并不代表声称的收益是真的
- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-09-30（v1 于 2026-09-29 16:48 UTC 上传，亚利桑那大学等）
- 摘要：作者从 AIDev v4 数据集的 71,677 份 agent 发起的真实 PR 中，用文本过滤加人工+LLM 编码，筛出 6 个
  coding agent、582 个仓库中的 1,262 个性能相关 issue，并重新执行了 23 个被拒绝声明与 30 个已合并声明。
  发现：57% 的已关闭修复被合并，61% 的拒绝未给出理由，而在重新执行的 23 个被拒声明中只有 6 个在三轮试点
  测试下仍然成立；合并率更多跟随 agent 在该仓库的历史记录（31%-37% 升到 70%）与仓库对该 agent 其他 PR 的
  历史合并率（33% 升到 84%），而非代码质量本身；在 30 个已合并修复中，18 个达到作者设定的交付标准，3 个
  未达声称效果，9 个没有显著收益甚至退化，14 个在未测试的输入上改变了行为；仅 11% 的修复附带性能测试或
  基准。
- 为何重要：这是"agent 自我陈述与实际交付脱钩"这条判断第一次落在真实生产 PR（而非受控基准）上给出具体
  比例——"合并"本身正在被当成事实上的质量信号，但论文证明它主要反映的是团队与该 agent 的历史信任关系，
  跟性能声明是否兑现基本无关。证据边界：重新执行仅覆盖 23+30 个样本、且只做"三轮试点"，噪音影响未充分
  量化；issue 筛选与编码依赖 LLM 辅助标注，标注者间一致性未披露；六款 agent、582 个仓库是否代表更广泛的
  agent PR 生态尚未验证；论文未披露投稿状态、无同行评审。
- 原文：[Merged, Not Measured 论文](https://arxiv.org/abs/2609.37985)
- 配图：![研究流程：从 71,677 份 agent PR 到 1,262 个性能 issue 的五步筛选](https://arxiv.org/html/2609.37985v1/fig-workflow.svg)
  图片来源：[论文 Figure 2](https://arxiv.org/html/2609.37985v1)。

### 4. 生成式 AI 冲击 Stack Overflow：先侵蚀的是"简单、数据丰富"的问题，不是全面衰退（今日加选）
- 领域：软件工程（今日加选）
- 来源 / 发布日期：arXiv / 2026-09-30（v1 于 2026-09-28 18:21 UTC 上传，KAIST + 崇实大学）
- 摘要：作者把 ChatGPT-3.5 发布当作一次自然实验冲击，分析 2020-2025 年间 Stack Overflow 上超过 200 万条
  问题，沿"难度"与"数据可得性"两个维度追踪变化。发现简单问题数量急剧下降、困难问题占比上升（并有代码
  复杂度上升佐证）；数据丰富的主题/标签份额下降，数据稀缺的主题份额上升；两个维度还存在交互——"简单问题
  减少"这一现象集中发生在数据丰富的领域，而"困难问题增加"则不分数据可得性、普遍存在；这一模式在 Python
  之外的多种编程语言中同样成立，且越流行的语言变化幅度越大。
- 为何重要：此前"Gen AI 冲击知识社区"的证据多停留在"整体提问量下降"这一聚合层面，本文把冲击拆解到"哪类
  知识先被侵蚀"这一更细的机制层面——易得、标准化的知识最先被 AI 替代，复杂、长尾的知识仍需要人类社区。
  这为判断 AI 对知识密集型协作平台的结构性冲击提供了一个可能可复用的分析框架（难度 × 数据可得性两个维度），
  但目前仅是单一来源的首次观察，尚未形成跨天证据链，暂不提议沉淀，留待后续同类研究验证。证据边界：难度
  分类依赖作者自建的 AI 标注器（每天随机抽样 30 条问题），标注器本身的偏差未做独立人工核验；自然实验设计
  缓解但不能完全排除同期其他混杂因素（如整体开发者活跃度变化）；研究范围限定 Stack Overflow 一个平台，
  能否推广到其他知识社区未验证；数据截至 2025 年，未覆盖更晚近的模型能力跃升。
- 原文：[The Uneven Decline of Collective Knowledge Production 论文](https://arxiv.org/abs/2609.36069)
- 配图：![问题难度与代码复杂度随时间的变化](https://arxiv.org/html/2609.36069v1/Fig1.png)
  图片来源：[论文 Figure 1](https://arxiv.org/html/2609.36069v1)。

### 5. ToolFence：把"用户授权的值"和"不可信的工具观察"分开判权限，堵上工具内参数篡改（今日加选）
- 领域：AI / 智能体（Agent，今日加选）
- 来源 / 发布日期：arXiv / 2026-09-30（v1 于 2026-09-29 10:16 UTC 上传，香港理工大学 + 山东大学）
- 摘要：论文指出，工具调用型 agent 之所以仍易受间接 Prompt Injection 影响，根源是"可信指令"与"不可信
  工具观察"共享同一个上下文——已有的多路径共识防御只检查内容或聚合输出而非授权的"效果"本身，对"保留了
  预期工具、但篡改了其参数"的工具内攻击基本无效；而 CaMeL 一类数据流控制方案虽能提供更强保证，却带来
  显著的运行时延迟。ToolFence 在执行前编译一份带类型的授权蓝图，用确定性监视器强制执行，蓝图不完整时才
  请求 judge 授予新的能力（而非逐次裁决每个具体调用）。这让系统既能区分"用户授权的值"与"不可信的观察"
  （从而针对性解决工具内攻击），又能靠确定性快速路径与能力级别的运行时授权大幅减少昂贵的 judge 调用。
  在 AgentDojo 上用 Qwen3-max 测试，ToolFence 把整体攻击成功率压到接近零，干净任务效用只下降 3.80 个
  百分点，运行时开销"实际可行"。
- 为何重要：为本仓库长期追踪的"agent 工具执行运行时授权治理"线索的"权限边界"子维度（此前含 SARA/
  CapScope/GuardedAct/Agent Approval Laundering/EffectMatch/SEAD）新增一个聚焦"工具内参数篡改"这一具体
  攻击面的方案，且给出了与两类已知防御（多路径共识、数据流控制）的直接对比。证据边界：论文仅 9 页、评测
  仅覆盖 AgentDojo 一个基准与 Qwen3-max 一个模型，能否推广到其他基准/模型未知；"接近零"的攻击成功率与
  3.80 个百分点的效用损失均为作者自测，未见第三方复现；论文未披露投稿状态、无同行评审。
- 原文：[ToolFence 论文](https://arxiv.org/abs/2609.37196)
- 配图：![ToolFence 的授权蓝图-监视器-Judge 框架](https://arxiv.org/html/2609.37196v1/toolfence_framework.png)
  图片来源：[论文 Figure 1](https://arxiv.org/html/2609.37196v1)。

## 今日主线

今天的 5 条共同指向同一个问题："声明/声称"与"实际交付/实际执行"之间谁来验证。Agent 声明的计划结构在
执行中大量走样（Planning-as-Routing）；agent 提交的性能修复被合并本身并不能证明声称的收益成立（Merged,
Not Measured）；而在治理侧，ToolFence 提供了一种把"用户授权"和"工具观察"分开裁决的具体机制，Reco 的
5,500 万美元融资则说明资本已经在为这整条验证链条的缺口下注、一个原本还只是论文里的问题已经养出了 20 多家
竞品的独立赛道。Stack Overflow 的证据从旁佐证了同一张图景的另一面：AI 正在系统性地改变"什么知识值得被
公开验证和沉淀"这件事本身，且这种改变并不均匀。
