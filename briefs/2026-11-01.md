### 1. coding agent 的"队友"也能变成攻击者——跨团队运行时反馈里藏着 94.8% 成功率的注入攻击

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / v1 于 2026-10-28 20:04:20 UTC 上传，作者 Jie Fu、Shuang Wu、Ashish
  Kundu、Wendy Hui Wang、Yuan Hong（页面未披露机构归属）
- 摘要：coding agent 日益依赖由不同团队、不同服务拥有的组件（后端服务、测试 harness、CI 任务、
  部署服务）返回的运行时反馈来决定下一步动作。作者指出一种新的攻击面：这些组件能合法报告自身
  状态，却对受害 agent 的文件、凭据、shell、环境没有任何权限；一旦被恶意或被攻陷的同伴操纵，就
  能把诊断输出伪装成正常调试建议，诱导受害 agent 在未获授权的情况下采取行动。作者称之为"跨边界
  对抗性运行时注入"（CARI），构建了覆盖资源耗尽、信息泄露、开发状态篡改三类目标的十种具体攻击。
  在四种编程语言、五个代码能力模型上的 3,000 次试验中，CARI 成功 2,845 次（94.8%）；在产品级
  coding agent 上，Codex 的攻击成功率为 61.3%，Claude Code 为 58.7%。作者也测试了防御手段：泛泛
  的提示级警告基本无效，而显式策略能挡住攻击，但同时会过度拒绝合法操作。
- 为何重要：这条线索与本仓库长期追踪、已累计约 48 条跨天候选证据（仍待批准新建对应 topics 页）
  的"agent 执行权限的授权/委托治理空白"高度吻合，但补上一个此前未覆盖的具体场景——攻击者不是
  外部恶意用户，而是协作链路里另一个团队合法拥有、自身没有越权权限的基础设施组件，把"环境权威
  导致越权"的风险面从单一执行边界扩展到多方协作的信任边界本身。证据边界：论文未披露任何作者
  机构归属，是预印本、未见同行评审或第三方复现；94.8% 的总体成功率是作者自建十种攻击在受控环境
  下的汇总数字，具体攻击间的成功率分布、受害 agent 的具体版本与配置细节摘要页未完整展开；产品级
  Codex/Claude Code 的攻击成功率是否会被厂商已有的其他防护机制（沙箱、人工审查环节）进一步压低，
  论文未讨论。
- 原文：[CARI 论文](https://arxiv.org/abs/2610.38799)

### 2. Snyk 用 108 个真实漏洞测出：AI 安全 agent 与传统静态扫描谁都盖不全，harness 策略开关本身决定一半胜负

- 领域：软件工程
- 来源 / 发布日期：arXiv / v1 于 2026-10-28 10:38:43 UTC 上传，作者 Liran Tal、Chris Liu、
  Charlotte Fereday、Sebastian Roth、Brian Clark（Snyk 团队——基准、产品与评测均来自 Snyk 自身）
- 摘要：论文追问一个具体问题：AI coding agent 与 AI 安全 harness 能发现静态应用安全测试（SAST）
  漏掉什么，反过来 SAST 又能补上 AI 漏掉什么。作者构建 VulnBench 2.0——20 个开源 Go/JS·TS/
  Python/Java web 应用里人工标注的 108 个"攻击者可达"漏洞（62 个跨文件），判定一条发现成立要求
  同时命中攻击者可控的 source 与危险 sink（各容差两行）。九种生产级配置在同一盲测协议下评测：
  Snyk Code 静态分析器、Claude Code 的 /security-review（三档模型/算力设置，含一档接入 Snyk MCP
  服务器）、Codex Security（三种 GPT-5.6 变体）、DeepSec 扫描器（两种模型后端）。结果：Snyk Code
  宏召回率 82.4%（89/108），Claude Code（Opus 5，xhigh 算力）79.3%（85/108）；两者在 28 个漏洞上
  意见分歧（16 对 12），作者认为差距太小不足以分高下；二者合计可覆盖 101/108，这也是全部七个可比
  配置加总后的上限；AI 配置还额外报告了至少 7 个参考集之外、Snyk Code 未报告的真实漏洞。关键的
  架构发现：去掉 Claude Code 内置审查策略对特定漏洞类别的排除/限制后，同一模型在那些类别上的命中
  率从 9/20 升到 16/20——同一底座模型，仅因 harness 策略开关不同，表现产生显著差异。Codex Security
  在文件级定位到 80 个漏洞，精确到行级只剩 34 个。
- 为何重要：这是本仓库已沉淀页 [[harness-vs-model]]（对应论点"Harness 设计是决定同模型实际表现的
  独立架构变量"）的一条干净新证据——同一模型（Claude Code 所用的 Opus 5）仅因内置审查策略的开关，
  命中率就从 9/20 变到 16/20，证明"harness/策略"不是实现细节，而是独立于模型能力之外、可单独度量
  的变量。同时也为"确定性工具 vs AI 判断该如何分工"提供了迄今样本量较大（108 个人工标注、跨文件
  比例高）的头对头数据，呼应 [[Evals]] 页强调的"被评估的是模型 + harness + 工具 + 环境的整体"。
  证据边界：基准、评测代码与运行数据已公开（GitHub snyk-labs/snyk-vulnbench），但作者本身是 Snyk
  团队、Snyk Code 是其自家产品，存在厂商自评的潜在利益冲突，结果需要独立第三方复现验证；108 个
  漏洞覆盖 4 种语言 20 个应用，能否代表更广泛语言/框架生态仍未知；"source/sink 各两行容差"的判定
  标准偏宽松，可能高估部分配置的实际可用性；Codex Security 文件级到行级的大幅跌落（80→34）具体
  原因未展开分析。
- 原文：[Snyk VulnBench 2.0 论文](https://arxiv.org/abs/2610.38617)；
  [基准代码与数据](https://github.com/snyk-labs/snyk-vulnbench)

## 今日主线

这 4 条共同指向一个主题：AI 系统的风险与资本结构正在从"单点"扩散为"多方"。CARI 证明 agent
协作链路里连"自己团队没有越权权限"的合法组件也能成为攻击面；Snyk 的基准证明同一模型换一个
harness 策略开关就能让安全覆盖率产生两位数差异，工具与模型的边界本身需要被单独评估；OpenAI 下调
融资目标、Nvidia 可能为 Nscale 的建设风险做残值担保，则显示 AI 基础设施的资金链正从"一次性股权
豪赌"转向更复杂的多方风险转移结构——担保、债务、残值兜底开始与股权定价并存。
