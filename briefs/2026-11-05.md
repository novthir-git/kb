### 1. FlashProve：Anthropic 联合多家机构发布"可证明推理"开源原型，用零知识证明验证输出到底出自哪个模型（AI / 智能体，今日最值得细读）

- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：Anthropic 研究博客（Frontier Red Team，联合 EPFL、MIT、StarkWare、RESI、
  Succinct 的研究者）/ TechCrunch 报道于 2026-11-03 14:41 PST（作者 Russell Brandom），
  Anthropic 页面元数据标注 2026-11-02（见上文时间不一致说明）。
- 摘要：用户通常无法验证一次回复到底来自哪个模型——路由服务可能悄悄换成更便宜的模型省钱，
  攻击者也可能篡改 token 流。FlashProve 是面向 MoE 模型的开源软件原型，分离线/在线两阶段：
  离线阶段模型提供方为权重发布一次性"承诺"（约 6.5MB，一个承诺覆盖约 1,600 万次请求）；在线
  阶段对每次请求（prompt+输出 token）生成一份 zkSNARK 证明（约 19MB/千 token 请求），证明
  产出来自该承诺对应的确切权重，但不暴露权重本身（零知识）。验证只需 CPU，24 线程约 17 秒、
  单线程约 21 秒即可完成，不需 GPU 或权重。在 Llama 4 Maverick（400B MoE，4bit 量化）上实测
  约 110 token/秒（单 H100），证明开销约为 vLLM 直接推理 GPU 时间的 70-95 倍；离线阶段约需
  39 分钟。团队为完备性、合理性、零知识三项性质写了 Lean 形式化证明与交互式可视化审查工具，
  但明确声明：快速版 C++ 代码本身没有形式化保证，Lean/论文/代码三者可能不完全一致；系统假设
  整数化模型+贪心解码，浮点或采样输出可能导致证明失效；架构本身不被隐藏；侧信道（如证明耗时
  本身泄露信息）不在覆盖范围内；上下文仅覆盖 1,024 token，远短于真实对话长度；证明只能证明
  "该硬件确实在做推理"，不能排除背后存在秘密训练。代码、技术报告、协议规范（由 Claude 撰写）
  据称已在 GitHub 以 Apache 2.0 协议开源（github.com/anthropics/FlashProve），本次因自动化
  请求被拦截（HTTP 403）未能独立核验仓库是否存在/可访问；模型权重本身不包含在内，需用户自行
  从 Hugging Face 按 Meta 许可获取。研究者明确表态这是"中间进展分享"而非完整研究议程，希望
  他人在此基础上改进。
- 为何重要：这是 `wiki/purpose.md` 核心论断 1（"Agent 的瓶颈已从能力转到治理与验证"）的一个
  具体基础设施级实例——它第一次把"这段输出到底是不是某个特定模型产出的"这个问题，从"相信
  实验室的自我声明"变成"任何人拿着承诺、prompt 和回复就能独立核验的密码学证明"，直接服务于
  评测方（确认测的是真实在跑的模型）、路由服务客户（确认买到的是承诺的模型）、监管方（核验
  硬件是否真的只做推理而非秘密训练）、以及想证明"某项任务确实由某个特定模型完成"的第三方
  声明。本仓库目前没有任何页面直接覆盖"模型身份/推理可验证性"这一主题（已检索 `wiki/` 全库
  确认），这是一个全新话题；考虑到发布方的机构覆盖面（Anthropic Frontier Red Team + 四所
  学术/工程机构联合）与技术细节的完整度（形式化证明、开源代码、明确的局限性清单），**可能
  单独满足沉淀门槛 b（单个奠基性来源本身足以形成稳定判断）**——但其工程成熟度仍是"研究原型"
  级别（70-95 倍 GPU 开销、仅 1,024 token 上下文、无任何实验室宣布部署计划），这一点必须在
  沉淀时如实体现，不能写成"已可投产"。本条已作为新线索记入 `briefs/memory.md` 线索 60。证据边界：核心细节来自 Anthropic 官方页面与 TechCrunch
  报道的交叉比对，但 GitHub 仓库本身未能独立核验可访问；性能数字（110 token/秒、70-95 倍
  开销）均为作者自测，无第三方复现；系统目前只覆盖 MoE 架构与贪心解码，能否推广到稠密模型、
  采样解码、更长上下文均未知；"没有任何实验室计划部署"是研究者自陈的当前状态，不代表未来
  不会部署；Anthropic 与论文中提及的 StarkWare、Succinct 等机构在零知识证明基础设施领域
  本身也有商业利益，不能排除该研究同时具有生态位展示的动机。

### 2. 五个真实 Bug 定位基准平均 34.82% 的问题报告被错误标注，修正后六种方法的 MRR 全部显著下跌（软件工程）

- 领域：软件工程
- 来源 / 发布日期：arXiv 2611.05314 / v1 于 2026-11-03 18:22:34 UTC 上传，作者 Moumita Asad、
  Rafed Muhammad Yasir、Yirui He、Ziyao He、Sam Malek（页面未披露机构归属）；主类 cs.SE，
  CC BY 4.0 许可，Comments 字段无会议/期刊录用信息。
- 摘要：基于信息检索的 Bug 定位（IRBL）技术依赖"issue 报告 ↔ 实际缺陷文件"的标注数据做评测，
  但这些标注本身的质量此前缺乏系统性核查。作者分析五个常用基准数据集、合计超过 55,000 条
  issue 报告，发现平均约 34.82% 的 issue 被错误标注（如关联到错误的文件、遗漏实际涉及的
  文件）。在 Ye et al. 基准上，作者用传统方法、深度学习方法、LLM 方法共六种 IRBL 技术重新
  评测：剔除被错误标注的 issue 后，六种方法的平均倒数排名（MRR）全部显著下降，降幅在 4.68%
  到 21.74% 之间；错误标注不改变六种方法之间的相对排名顺序，但会改变它们之间性能差距的
  具体幅度。
- 为何重要：这篇论文指出的不是"某个 IRBL 方法不够好"，而是整个赛道的评测地基——标注数据
  本身——有超过三分之一是错的，而且这个噪声不是随机抵消的，它系统性地抬高了测得的 MRR
  数字（剔除噪声后全部方法都掉分）。这与本仓库线索 8（"LLM-as-judge / 评估基准不能被当作
  一次性冻结的裁判，需要持续校验或演化"，目前候选中 2 条、未达门槛 a）在"基准本身不可靠"
  这一大方向上相邻，但切入点不同——线索 8 关注的是裁判/评委随时间漂移或被针对性优化，本条
  关注的是基准的 **ground truth 标注本身从一开始就有系统性错误**，是评测可靠性问题里更
  上游的一层，暂判断角度独立，不直接合并，继续观察后续是否有同类"标注质量审计"工作出现在
  其他类型的 benchmark（如代码补丁正确性、漏洞检测）上。本条已作为新线索记入 `briefs/memory.md` 线索 61。证据边界：论文未披露作者机构归属，
  也未标注会议/期刊录用信息（暂为预印本）；"34.82%"是五个数据集的平均值，具体到每个数据集
  的错误率区间与错误类型分布未在摘要层面给出；重新评测仅在 Ye et al. 一个基准上进行，其他
  四个数据集是否会呈现同样幅度的 MRR 下跌未经验证；"错误标注"的判定标准与人工复核流程细节
  未知；未见第三方复现。
- 原文：[Noisy Issues, Noisy Results 论文](https://arxiv.org/abs/2611.05314)

### 3. Palantir 单季营收首破 23 亿美元、美国商业收入反超政府收入，但新签合同总额（TCV）环比下滑近三成（创业/商业）

  Palantir，其销售侵蚀的"合同质量"信号也值得单独追踪，暂无可直接挂靠的已有 wiki 页，继续

### 4. Waymo 确认将于 2028 年 1 月结束与 Uber 在奥斯汀、亚特兰大的独家合作，转为自建 App 直连乘客（汽车/自动驾驶）

- 来源 / 发布日期：TechCrunch（Sean O'Kane，In Brief）/ 2026-11-04 10:12 PST。
- 摘要：Waymo 将于 2028 年 1 月结束在奥斯汀、亚特兰大两市与 Uber 的独家合作安排，届时将像

  选择不在 Uber App 内增加直接预约机器人出租车的选项。此前《金融时报》报道称 Waymo 原本
  就想退出与 Uber 的这笔合作，该合作原定 2028 年 5 月到期。Waymo 联合 CEO Tekedra Mawakana
  向 Bloomberg 解释，公司最初选择与 Uber 合作是看中其规模，但乘客体验一直"不太可控"——
  乘客无法预先知道自己叫到的是机器人出租车还是真人司机，她称这"有点像赌博"，并表示"拥有
  和乘客的直接关系对我们很重要"。这一变化将让 Waymo 与 Uber 在这两个市场形成直接竞争，

  阵营的代表 Waymo 主动收回此前依赖规模换来的平台分销渠道、转向直连乘客"——方向与此前大多数
  扩张性证据相反，说明"自建 vs 联合"并非单向演化，领先者在规模达到一定程度后可能反而收缩
  对平台的依赖。本条仅记入 `briefs/memory.md` 作为该线索第 23 条候选证据，不再重复完整的

- 摘要：投机解码（speculative decoding）通常被当作纯粹的推理加速手段，本文认为它对长时
  Agent 推理准确率本身也有实质影响——数值噪声会在验证窗口内累积，草稿 token 被接受的过程
  在约 30 步之后可能让目标模型的输出分布发生偏移，进而影响推理正确性。作者的方法是训练一个
  草稿模型，使其在 Agent 执行轨迹中被识别出的"关键推理节点"上主动被拒绝——推理到这些节点时
  草稿与目标模型出现分歧、验证重启，关键 token 改由目标模型在噪声更低的条件下采样生成。
  作者报告该方法在不改变目标模型本身或其输出分布的前提下，提升了 agentic coding 基准上的
  端到端成功率，且只需训练宿主参数的 0.06%-0.28%。
- 为何重要：这是一个和本仓库线索 1（"Agent 长时任务的可靠性衰减是数学规律，不是工程疏忽"，
  已超过门槛 a、待批准追加到 `wiki/topics/agent-生产级落地的鸿沟.md`）相邻但机制不同的
  新角度——线索 1 现有证据链聚焦的是任务复杂度/步数增加导致的能力性衰减（早期错误被继承、
  未被自我发现），而本文指出的是一个纯推理工程层面、此前容易被忽视的变量：**解码策略
  本身的数值噪声积累，也可能是长时推理准确率下降的一个独立成因**，与模型能力、任务设计
  均无关——如果属实，意味着同一个模型在同一个任务上，仅因推理服务的解码配置不同，长时
  表现就可能不同，这对任何想"复现"或"对比"长时 Agent 评测结果的人都是一个容易被忽略的
  混杂变量。暂判断角度与线索 1 不同、不直接合并，继续观察是否有独立论文或产品团队复现
  "投机解码本身影响长时推理正确性"这一现象，若出现可考虑新建聚焦"推理服务工程选择 vs
  模型能力"这一维度的页面。本条已作为新线索记入 `briefs/memory.md` 线索 62。证据边界：论文未披露作者机构归属，暂无会议/期刊录用信息；
