### 1. Shirudo：OpenAI 与 Cisco 把"补丁要等天/周"的空窗期，交给 agent 用 eBPF 现场生成临时防护盾
- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：OpenAI 官方博客（Security 分类，标注 Partnerships/2026）/ 2026-11-23
- 摘要：Shirudo 是 OpenAI 与 Cisco 联合发布的开源 Linux 运行时，目标是填补"漏洞已知、永久补丁还要等天/周才能测试上线"这段空窗期——期间直接封堵触发漏洞的系统调用可能连带挡掉合法请求、导致服务下线。Shirudo 用 eBPF 在系统关键点插入轻量程序，生成临时性的"shield"：只拦截暴露漏洞的具体行为，放行合法请求；运营方可在强制生效前先测试 shield 对应用的影响，shield 本身经密码学签名与内核安全机制校验，TPM 记录何时加载/移除防护，供运营方核验合规。关键设计是"可以把调查漏洞、构建 shield、拿真实流量/漏洞验证 shield 效果这一整套流程交给可编程的 agent 去做"。文中给出一个受控示例（"Java4Shell"）：用 OpenAI 的 Codex 生成一个给 Java Base64 解码器加输入校验的 shield，挂载到一个正在运行的 Elasticsearch 进程上，成功拦截恶意输入且无需重启服务。项目在 GitHub 开源（核心 BSD 2-Clause，BPF 程序 BSD/GPL 双授权），12 月 15 日有配套技术网络研讨会。OpenAI 总裁 Greg Brockman 的原话："发现一个 bug 不代表你明天就能给每一套系统打上补丁。"
- 为何重要：本仓库线索 64（"AI 实验室开始规模化地把前沿模型能力用于防御"）此前只有 11-05 OpenAI Daybreak 一条候选证据（候选中 1 条，未达门槛 a/b），本条是该线索第二个独立证据点——同样来自 OpenAI，但从"用模型主动找漏洞/补漏洞"（Daybreak）换成"把漏洞响应流程本身的一段（调查+现场生成防护+验证）交给可编程 agent 执行，且用密码学签名+TPM 构成独立于 agent 判断之外的可核验记录"，呼应本仓库反复出现的"确定性机制优于单纯信任模型判断"这一设计哲学（与线索 3、线索 45 呼应）。证据边界：全文仅给出一个受控示例（Java4Shell/Elasticsearch），未提供规模化部署的量化效果数据；核心评测、效果数字均来自 OpenAI/Cisco 自身演示，未见第三方独立复现或生产环境验证；eBPF shield 本身的误拦截率、对合法流量的副作用规模未讨论；项目刚开源，长期维护与社区审计情况未知；"agent 可编程控制调查/生成/验证"具体由谁审批、出错后如何追责，博客未展开细节。

### 2. How Much Do Coding Agents Over-Edit, and Why?：微软用"逆转重跑测试"量出 agent 补丁里真正多余的代码只有一成左右
- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-11-25（v1 于 UTC 18:37 上传），Aakash Goel、Benjamin Steenhoek（并列一作）、Yu Hu，Microsoft
- 摘要：Agent 生成的补丁普遍比开发者补丁改动更多行，这常被简单读作"过度编辑"，但补丁体积本身不说明多出来的改动是否必要、是什么、来自哪一步。论文提出 Delta Residue Attribution（DRA）：回放 agent 执行轨迹，把最终补丁的每个代码块追溯到写下它的那一步，逐个还原后重跑任务测试，判断该块是否必要；并用同一方法对开发者补丁打分做对照基线。作者把 DRA 应用到 18 个前沿模型在 SWE-bench Verified（6,728 条）与 DeepSWE（932 条）上共 7,660 条已解决的 GitHub Copilot CLI 执行轨迹。核心发现：agent 补丁中位数改动行数是开发者补丁的 2.33 倍，但仅看代码单元本身的比例是 0.86（反而更少），仅看非测试文件是 1.09；SWE-bench Verified 上多出的编辑中 61% 是加测试、13% 是文档，DeepSWE 上 58% 是代码；agent 代码平均必要性不低于开发者（均值 NPcode 0.887 对 0.864，18 个模型中 11 个比开发者留下更少不必要代码）；平均只有 11% 的 agent 补丁代码单元确属不必要，其中 89% 一旦还原会改变程序行为；代码必要性与 SWE-bench Verified 解决率不相关（Spearman -0.10），但在 DeepSWE 上显著负相关（Spearman -0.59，p=0.01）；用 agent 自己能看到的测试做"DRA 剪枝"能去掉多数不必要代码但也会误删部分必要代码（67% 召回/46% 精确率），89% 剪枝后的补丁仍能通过任务；让 agent 自审自己的 diff 精确率更高但效果更弱（36% 召回/66% 精确率）。
- 为何重要：本仓库线索 7（"SE agent 补丁'测试通过'与'审查可接受'是两回事，且差距可量化"）此前已累积 9 条候选证据、早已跨过门槛 a，角度覆盖通用代码修复、漏洞补丁、修复过程幻觉、工业真实系统、人类手动验证、生产推理服务引擎、AI 自主开发全流程、API/运行时迁移场景，均待用户批量处理（追加到 `wiki/concepts/Evals.md`）。本文补上第十个独立角度——不是"补丁是否正确/能否通过审查"，而是用可复现的因果归因方法把"补丁体积大"与"补丁有不必要代码"两件事直接拆开量化，并发现两者关系很弱（11% 不必要代码对应 2.33 倍体积），对"agent 补丁臃肿=质量差"这一直觉判断给出一个有数据支撑的反驳，同时首次测出"自动剪枝 vs 自审"这组具体缓解手段各自的精确率-召回率权衡。按惯例本期不单独提议沉淀，继续记入该线索候选池（现为候选中 10 条）。对应 `wiki/purpose.md` 关键问题 5（如何用 evals 与反馈闭环驱动工程与产品演化）。
- 证据边界：全部实验基于 GitHub Copilot CLI 这一单一 harness 产生的轨迹，能否推广到其他 agent harness 未知；"DRA 剪枝"与"自审"均在 SWE-bench Verified 单一基准上验证，DeepSWE 上未重复该实验；强化后的测试 oracle（用于排除"测试本身标记虚高"）把开发者补丁的"不必要代码"比例从 33% 降到 3%，但对 agent 补丁是否存在同等幅度的高估未在摘要层单独量化；三位作者均为 Microsoft 雇员，未见第三方独立复现；预印本，无同行评审信息。
- 原文：[How Much Do Coding Agents Over-Edit, and Why?](https://arxiv.org/abs/2611.34875)（检索于 2026-11-26）

### 3. Maple：用 TEE 把"连公司自己都看不到你的数据"做成可验证的承诺，并把 agent 子任务接进 Claude/Codex
- 领域：创业 / 商业
- 来源 / 发布日期：TechCrunch（Sarah Perez）/ 2026-11-24
- 摘要：Maple 是一家四人团队的创业公司（Austin/San Francisco），核心主张是让用户数据对公司自身也保持私密：数据在用户设备上用只有用户知道的密码加密，只在一个硬件加密的可信执行环境（TEE，托管于美国数据中心）内解密处理，处理完再重新加密返回；代码开源、TEE attestation 可供用户自行核验，欧洲用户可走合作方提供的欧洲节点。产品分两块：Maple 聊天 App（可选 DeepSeek、Kimi、GLM、Thinking Machines 的 Inkling、Google Gemma、OpenAI GPT OSS 等开源模型，可在快速/强力模式间切换）；新上线的 Maple Work 桌面应用，带 agent 能力（可操控电脑、文件、应用与浏览器，内建 Gmail/日历等集成商店），并可在支持 Agent Client Protocol 的其他 AI 应用（如 Claude、Codex）内部运行子 agent。本轮为 530 万美元种子轮（超额认购），领投方 Epic Ventures，跟投 Draper Associates、Planetary VC、Epoch VC，此前已有一轮不到 100 万美元的天使轮；公司称过去三个月增长 60 倍（未披露具体用户/客户数），计划 2027 上半年启动 A 轮；企业版（含零数据留存版本）明年试点，SOC 2 合规审计在进行中；定价为 Pro 20 美元/月，Max、Max Plus 分别 100、200 美元/月。

### 5. Attack Policy Selection can Mislead Monitor Evaluators：同一个 OpenAI 安全监控器，换一种攻击生成方法，漏检率能从 0.5% 跳到 23%（今日最值得细读）
- 领域：AI / 智能体（第二条，今日最值得细读）
- 来源 / 发布日期：arXiv / 2026-11-25（v1 于 UTC 18:59 上传），Charlie Griffin、Oliver Makins、Asa Cooper Stickland、Alessandro Abate、Yarin Gal、Abby D'Cruz、Xander Davies（机构未在页面披露）
- 摘要：论文指出，用来标记 AI agent 危险行为的"监控器"（monitor）通常是用"攻击策略"生成的模拟记录来评估——攻击策略充当部署环境中真实危险行为的代理。作者以一个脱离生产环境的 OpenAI 监控器（GPT-5.4，xhigh 推理强度）为案例，在"基础设施即代码"（IaC，6 个子任务）与 LinuxArena 两类环境中测试：内部 agent 用 Qwen 3.8 27B 扮演，核心指标是监控器漏掉第一次危险动作的概率（FNR）。四种攻击生成方法全部只针对代理监控器（主要是 Qwen 系）做优化，GPT-5.4 从未被训练针对、只作为留出的目标监控器接受评估。IaC 环境下结果：基础提示词 0.2% FNR（async-control 基线 0.5%）；两轮人机协同优化提示词后升到 6.4%；强化学习（GRPO/DPPO 式训练）训练过程中从 0.5% 升到 20.8%（第一个检查点已到 5.1%）；演化式"转录编辑"方法在每个种子 100 次编辑预算下升到 23.0%。迁移到 LinuxArena 后，基础提示词与强化学习策略迁移效果弱（分别回落到 0.2%、0.7%），但专门针对 LinuxArena 优化的转录编辑方法在 150 次编辑预算下仍达 16.2%。作者认为，这说明监控器评估得出的漏检率高度依赖"选了哪种攻击生成方法、在该方法内优化到什么程度"，仅用基础提示词这类简单攻击做评估，可能让人误以为监控器很稳健；任何从代理攻击迁移来的 FNR 结论，都需要一个明确的"合法性论证"才能当作对真实部署表现的证据，而这类论证目前仍是未解决的问题。
- 为何重要：本仓库线索 8（"LLM-as-judge / 评估基准不能被当作一次性冻结的裁判，需要持续校验或演化"）已累积 10 条候选证据、早已跨过门槛 a，此前角度覆盖测量不稳定性、评分标准演化、排行榜统计显著性、工具调用信任前提、长时评估可观测性、离线审计身份识别不可能性、把基准当软件维护、基准有效性审计、评分权限隔离防御、人机评委偏差量化纠偏——本文补上第十一个独立角度，且是该线索第一次把"裁判不可信"的判断从"评测基准/LLM 评委"场景延伸到"AI 安全监控器本身的评估方法论"：同一个监控器，同一套能力，仅仅因为评估者选了哪种攻击方法、优化了多深，测出的"安全余量"可以相差近 50 倍（0.5% vs 23%），这意味着行业用来证明"我们的监控器很稳"的大量评估结果本身可能系统性偏乐观。按惯例本期不单独提议沉淀，继续记入该线索候选池（现为候选中 11 条）。对应 `wiki/purpose.md` 关键问题 5（如何用 evals 与反馈闭环驱动工程与产品演化）与核心论断 1（agent 瓶颈已从能力转向治理与验证）。
- 证据边界：全部实验基于单一脱离生产环境的 OpenAI 监控器与单一内部 agent 模型（Qwen 3.8 27B），能否推广到其他监控器/模型组合未知；攻击方法优化全程仅针对代理监控器而非 GPT-5.4 本身，论文承认"迁移到留出监控器"这一步骤本身的可靠性就是论文想质疑的东西，存在一定自我指涉的方法论张力；"按失败的旁路任务计入归咎"会把部分 FNR 数字拉低（如优化提示词从 6.4% 降到 5.4%），说明攻击行为本身是否易被识别也会影响测量结果，进一步复杂化了"合法性论证"该如何构建；7 位作者机构均未在页面披露；预印本，无同行评审信息，无第三方复现。

## 今日主线

这 5 条共同指向同一个问题：**当"信任"不能靠自我声明时，用什么来验证？** Shirudo 用密码学签名+TPM 让安全防护的加载/移除留下独立于 agent 判断之外的可核验记录；Over-Edit 不满足于"补丁改动大=质量差"的直觉，而是用逆转重跑测试把"必要"和"冗余"实证拆开；Attack Policy Selection 证明"监控器很安全"这个结论本身强烈依赖评估者选了哪种攻击方法——评估方法不透明，结论就不可信；Maple 把"我们不看你的数据"从政策承诺做成 TEE attestation 可供用户自行核验；Uber+Nuro 的无人驾驶测试资格，则是建立在加州 DMV 独立审核发出的许可之上，而不是公司自称"系统已经够安全"。五条证据在不同层面重复同一个判断：无论是代码、监控器、隐私承诺还是自动驾驶系统，"自己说安全/正确/隐私"正在越来越不够用，能留下独立证据链、能被第三方或密码学机制核验，才是今天行业默认要跨过的门槛。
