### 1. 重新打分八个 Agent 基准后发现：榜单前十名的名次差异可能小于测试本身的误差（今日最值得细读）
- 领域：AI / 智能体（Agent）
- 来源 / 发布日期：arXiv / 2026-11-10（v1 首次上传）
- 摘要：论文主张数据科学/机器学习工程类 Agent 基准（MLE-bench、ALE-Bench、SWE-fficiency、AlgoTune
  等共八个）失去区分顶尖模型的能力，主因是**测量方式太粗**而非任务本身被"打穿"。多数 Agent 基准把
  每次运行压缩成单一的通过/失败结果，作者重新打分已公开的运行记录，指出两类具体问题：① **粒度太粗**——
  在 SWE-bench Verified 上，榜单前十名相邻名次之间的差异小于该测试自身的误差范围；按误差范围修正后
  重新排序，名次变动幅度与"随机删除每个 Agent六分之一的通过记录"造成的变动幅度相当。② **封顶在参考
  答案处**——在 ALE-Bench 上，前十名 Agent 的比赛分数本身有差异，但若按"是否超过人类参照中位数"评分
  则全部打平；然而实际有接近一半的运行表现超过了这个人类中位数，意味着"二元是否超过中位数"这一常用
  评分方式把本可区分的差异抹平了。作者提出的修正方案是用"分级计分"取代"把基准做得更难"：引入带日期
  锚点的 clipped log-ratio 评分，并把成本作为独立维度单独报告，而不是和正确率混在一个数字里。在
  Terminal-Bench 的重新测试中，按通过/失败打平的模型，在"被二元指标丢弃的那个量"上实际相差超过 10 倍。
- 为何重要：这条证据直接补强本仓库「[[Evals]]」页已累积的多个独立维度（评委打分不可靠、评分标准该
  演化、排行榜名次缺乏统计显著性、离线审计的身份识别不可能性等），是该线索**第一次用"重新打分八个
  已发布基准的运行记录"这种大规模横向证据**，证明问题不是单一基准的设计缺陷，而是"通过/失败"这种
  压缩方式本身系统性地丢弃信息。它提醒：如果 Coding/Agent 产品只报"在 XX-bench 上超过 YY%"，这个
  数字本身可能已经无法区分模型优劣。证据边界：三位作者未披露机构归属；"重新打分"基于已公开的运行记录
  做事后再分析，并非独立重新运行模型；"相当于随机删除六分之一通过记录"是作者给出的类比量化，具体
  统计检验方法本条未展开核验；八个基准均偏数据科学/机器学习工程/终端操作任务，结论能否推广到网页
  Agent、多轮对话等其他任务类型未讨论；未见第三方复现或同行评审（预印本）。
- 原文：[Agent Benchmarks Stop Ranking Before They Run Out of Tasks](https://arxiv.org/abs/2611.13541) （检索于 2026-11-13）

### 2. JetBrains 实证：工程师的 AI token 消耗量衡量的是"用量"，不是"产出价值"
- 领域：软件工程
- 来源 / 发布日期：arXiv / 2026-11-10（v1 首次上传）
- 摘要：论文把 404 名 JetBrains 工程师五周的 coding agent token 用量与其提交记录逐一关联，并分析了
  412 名员工的问卷调查，检验企业常用"token 支出"来监控 AI 采用度、定预算、衡量生产力这一做法是否
  成立。核心结论：token 支出主要衡量的是工程师在**多大范围的工作类型**上使用了 Agent，而不是这些
  工作产出了多少成果或价值。具体数字：支出差异主要体现在工程师**之间**而非同一人随时间的波动，
  且高支出者在五周内基本保持稳定；在提交数相近的周里，第 90 百分位支出可以是第 10 百分位的 39 到
  240 倍；同一工程师内部，token 支出翻倍只对应约 10% 更多的提交数；可观测的工作量指标只能解释
  工程师间支出差异的 38%、同一工程师周内波动的 13%。问卷显示近九成技术岗受访者把 Agent 用于编码
  之外的分析、调研、规划类工作——这部分消耗记入 token 支出却不对应传统"写代码"产出。作者的核心
  结论是：token 支出至多只适合做资源核算，评估 Agent 辅助工作的实际价值仍需回到具体任务和结果证据。
- 为何重要：这条证据直接补强本仓库「[[生产力-体验悖论]]」页"从主观悖论到客观证据分层"一节已有的
  四层证据（PR 活动量提升、METR 实际完成时间反增、GitHub commits/LOC 逐级衰减、外围贡献者产出
  增加核心贡献者 review 负担上升）——本条补上了一个此前缺失的**企业内部计费/预算口径**层：
  token 支出这个被广泛用作"AI 采用度"代理指标的数字，本身与产出价值的相关性很弱（组间差异远大于
  组内，且可观测工作量只解释一小部分方差）。对正在用 token 消耗做团队 AI ROI 核算的组织，这是一条
  具体的度量学警示。证据边界：样本来自单一公司（JetBrains）的内部 coding agent 使用数据，可能受该
  公司自家工具生态特性影响，能否推广到其他企业/工具栈未讨论；观察窗口仅五周，长期趋势未知；"38%/13%"
  的解释力依赖作者选定的"可观测工作量指标"集合，换一组指标结果可能不同；问卷样本（412 人）与
  token 用量样本（404 人）是否完全重合未在摘要说明；未见第三方复现。
- 原文：[The AI Era's Lines of Code? A Case Study on What an Engineer's Token Spend Measures](https://arxiv.org/abs/2611.13396) （检索于 2026-11-13）

### 4. ForeseeDrive：用"预判未来场景"的 token 去指导轨迹生成，而非仅靠下游打分器挑选候选
- 领域：汽车 / 自动驾驶
- 来源 / 发布日期：arXiv / 2026-11-10（v1 首次上传）
- 摘要：生成式自动驾驶规划器能产生多条候选未来轨迹，但下游打分器只能从已采样出的候选里挑选——
  如果采样阶段本身就没覆盖到更优轨迹，打分器也无能为力。ForeseeDrive 把这一问题改写为"让预测的
  未来场景演化本身参与轨迹生成"：从记录的行车数据中提取按查询索引的 token，涵盖其他车辆的运动、
  占据空间的变化、与路线的交互、以及碰撞时间（TTC）余量，训练模型在部署时从当前上下文直接预测这些
  未来 token，再用这些 token 在候选轨迹生成之前就塑形轨迹的几何形态。为控制副作用，作者加入一条
  "零 token 门控残差路径"（不提供 token 时模块不产生任何效果）和一个"候选保持损失"抑制不必要的
  漂移，并针对从安全到危险的危险转换时刻设计了专门的 TTC 余量防护。关键数字：NAVSIM navtest 基准
  89.2 PDMS；nuScenes 验证集平均 L2 误差 0.41 米、碰撞率 0.05%；Bench2Drive 驾驶分数 76.50。作者
  另做了受控对照实验：零 token 时模块确实不产生效果（验证了设计意图）；token 与候选轨迹对齐时比
  打乱顺序时有小幅 PDM 优势；在"oracle 最优质量"这一指标上结果好坏不一；在 TTC 临界点附近仍存在
  局部失效案例。
- 为何重要：这是"端到端自动驾驶如何处理长时域风险/未来不确定性"方向的又一条具体技术路径，与
  11-11 收录的 When2Go（`briefs/2026-11-12.md` 条目 4，车间共享"意图"而非仅共享"感知"）、
  11-12 收录的 NegWAM（`briefs/memory.md` 线索 67，用失败轨迹做安全后训练排斥锚点）共同指向本仓库
  正在观察的"端到端驾驶模型如何补上风险/未来预测这一环"这一多路径并进的局面，但本条是三者中唯一
  给出跨三个标准基准（NAVSIM/nuScenes/Bench2Drive）具体数字且做了受控消融实验的。证据边界：
  作者机构未披露；全部数字均来自论文自身测试协议下的自评，作者在论文中承认基准数字出自"自己的
  测试规程"，未见第三方复现；"oracle 最优质量指标上结果好坏不一"与"TTC 临界点局部失效"两点是
  作者自陈的局限，具体失效比例未在摘要给出；代码据称在补充材料中，本条未独立核验是否可下载复现。
- 原文：[ForeseeDrive: Future-Token Conditioning for Anticipatory Generative Driving](https://arxiv.org/abs/2611.14286) （检索于 2026-11-13）

### 5. ReTrace：把 Agent 自己讲出来的"调用理由"蒸馏成不用模型打分的确定性工作流（今日加选）
- 领域：AI / 智能体（Agent，今日加选）
- 来源 / 发布日期：arXiv / 2026-11-10（v1 首次上传）
- 摘要：论文指出，生产环境里的工具调用型 Agent 为选出下一步该做什么，每一步都要调用一次模型，
  这在规模化部署时增加延迟与成本。ReTrace 提出：只要有一份标准操作流程（SOP）和少量已记录的 Agent
  执行轨迹，就可以把它们蒸馏成一个"由代码而非模型来选下一步"的可复用工作流——具体做法是从 Agent
  对每一步给出的解释中提取该步骤背后的判断条件，合并成一份规则文档，再把规则文档编译成可执行工作流。
  关键数字：在一个生产平台的 79 个流程上，ReTrace 工作流完成率 93.8%（对比原 Agent 96.8%），单任务
  成本降低 24%；在 τ²-Bench 上任务成功率 75.8%（对比 Agent 80.6%），但单任务耗时从 170 秒降到 1.3
  秒；针对训练集失败案例做三轮"修复"后，k=2 的工作流成功率从 66.7% 升到 81.2%；在 SOP-Bench 八个
  流程上，不做修复时 ReTrace（80.6%）略逊于少样本生成基线（83.6%），但做了基于标注训练失败案例的
  修复后达到 87.8%（单任务 0.40 秒），高于原 Agent 的 85.5%（单任务 46.6 秒）。论文的核心论点是：
  Agent 对每次工具调用给出的"理由"本身，而不只是调用动作序列，才是推导出工作流判断条件所需的关键
  信息。
- 为何重要：这条证据提供了一个具体、量化的"用确定性代码替代模型推理来降本"案例——完成率/成功率
  小幅下降（通常 3-5 个百分点）换来数量级的速度提升（170 秒→1.3 秒）和两位数的成本下降，为"Agent
  化之后价值捕获点从哪里移到哪里"这一本仓库关键问题提供了一个"从模型推理层下沉到确定性工作流层"
  的具体工程案例，但目前尚无可直接挂靠的已有 wiki 页，暂未达沉淀门槛，先计入观察（归入
  `briefs/memory.md` 新设观察线索，若后续出现同类"Agent 轨迹蒸馏为确定性工作流"独立案例再评估）。
  证据边界：作者机构未披露；生产平台的 79 个流程来自作者关联的商业场景，具体行业与任务性质未公开；
  "24% 成本降低"与"93.8% 完成率"均为作者自测，无第三方复现；SOP-Bench、τ²-Bench 为公开基准但
  具体任务是否被用于训练/调参阶段的边界未充分说明；"修复"依赖人工标注的训练集失败案例，标注成本
  本身未计入所报告的成本对比。
- 原文：[ReTrace: Distilling Tool-Using Agents into Planner-Free Workflows](https://arxiv.org/abs/2611.14492) （检索于 2026-11-13）

## 今日主线

这 5 条共同指向"衡量本身正在成为瓶颈"：条目 1 证明常用的 Agent/ML 工程基准因"通过/失败"这种
压缩计分方式系统性丢弃信息，顶尖模型的榜单名次可能还不如测试误差本身可信；条目 2 证明企业用来
衡量 AI 采用度的 token 支出指标衡量的是"用了多广"而非"产出了多少"；条目 5 则从反面给出一个具体
解法——把 Agent 的决策过程蒸馏成确定性代码后，可以用"结果小幅下降换数量级提速降本"的方式部分
绕开"每一步都要让模型打分/推理"这件事本身的成本。资本与硬件层面，Fractile 的 7.2 亿美元融资说明
推理芯片赛道仍在被国家级资本加码；自动驾驶领域，ForeseeDrive 代表了"把未来场景预测提前塞进轨迹
生成本身"这一条处理长时域风险的具体技术路径。

## 沉淀候选

1. **论点**：常用 Agent/ML 工程基准的"通过/失败"二元计分方式会系统性丢弃模型间的真实差异，
