### 1. CABAL：给"多智能体合谋"找了个真实的高利害场景——学术同行评审竞价
- 领域：AI / 智能体（多智能体模拟，检测与审计）
- 来源 / 发布日期：arXiv / 2026-09-07（公告日），v1 于 2026-09-04 14:55:33 UTC 上传
- 摘要：论文起因于 AAAI-27 审稿周期中真实出现的"审稿人协调竞价以换取互相分配"的报告。此前研究把竞价、分配、审稿操纵当作割裂的独立阶段处理，这篇论文用 LLM 驱动的审稿人 agent 同时模拟诚实与串通两种行为模式，覆盖竞价→分配→审稿结果的完整生命周期。关键数字：诚实场景下针对性分配率 18.3%–22.7%，串通后升至 62.4%–64.1%；目标论文捕获率从 28.0%–29.6% 升至 71.8%–76.9%（超两倍）；串通审稿人给目标论文的打分比诚实同行高约两分，被捕获目标论文相对匹配的诚实结果多获 0.84–0.89 分；会议整体平均分随串通比例从 0.2 升到 0.5，分别被抬高 0.13、0.38 分。但检测端明显滞后：现有正向竞价图检测器"几乎无法区分攻击痕迹"，集合检测器只能找回小部分串通者（如 15 人中 2 人、77 人中 42 人）。
- 为何重要：这为本 wiki 线索"透明多 agent 通信基础设施让作弊与吹哨自发涌现"（09-05 简报 DeepMind 100-agent 群体研究）补上第二个独立证据源，且把场景从抽象受控实验搬进真实、高利害的学术评审基础设施——首次给出"检测手段系统性落后于攻击能力"的量化证据（检出率从个位数到三成多）。证据边界：全部为 LLM 驱动的模拟 agent 行为，而非真实审稿人行为的直接观测，模拟对人类审稿人真实心理与操作约束的保真度未知；论文未标注作者机构；所用检测器基线是否代表当前会议系统实际部署的最优方法未说明。
- 原文：[CABAL: Multi-Agent Simulacra for Tracing the Effects of Collusive Bidding in Peer Review（arXiv 2609.05227）](https://arxiv.org/abs/2609.05227)

### 2. 两套真实生产系统、38 个崩溃 bug：LLM 修复"定位准了"不等于"改对了"
- 领域：软件工程（工业实证研究，故障定位与修复）
- 来源 / 发布日期：arXiv / 2026-09-07（公告日），v1 于 2026-09-03 21:04:40 UTC 上传
- 摘要：论文研究在两个大型 Java 企业系统的真实生产环境中，将"崩溃报告挖掘"（堆栈跟踪聚类 + 可疑文件/方法排序）与 LLM 结合，能否支持故障定位与修复。作者先对 5 个 LLM 在 4 种 prompt 配置下做回顾性评估，择优后在 38 个从两套企业系统收集的真实崩溃 bug 上运行，并对 LLM 生成解释的结构特征与模式做人工核验。结果：最优配置能定位高达 71% 的崩溃 bug，但只能正确修复其中 52%。
- 为何重要：这是本 wiki 已跟踪判断"SE agent 补丁'通过测试'与'审查/现实可接受'存在差距"（跨天线索：09-05 SWE-Gate、09-07 PatchBench、09-08 Defects4J 幻觉研究）之外的第四个独立证据源，但角度不同——它不是学术 benchmark，而是两套真实生产系统的工业案例研究，把"定位"和"修复"两个环节的成功率分开量化（71% vs 52%），说明即便有挖掘技术加持，从"找对位置"到"改对代码"仍有明显落差。证据边界：样本量小（仅 38 个 crash bug，来自 2 套系统），"最优配置"是从 5 个 LLM × 4 种 prompt 中事后择优，存在多重比较下的过拟合风险；"正确修复"的判定标准与人工复核覆盖率未在摘要中充分说明；未见其他行业系统的独立复现。
- 原文：[Integrating Crash Report Mining and LLMs for Bug Localization and Repair: An Industrial Report（arXiv 2609.04483）](https://arxiv.org/abs/2609.04483)

### 4. 一个扩散模型身兼两职：既当自动驾驶规划器，也当"找茬"的对抗场景生成器
- 领域：汽车 / 自动驾驶（轨迹规划与安全测试场景生成）
- 来源 / 发布日期：arXiv / 2026-09-07（公告日），v1 于 2026-09-04 09:22:54 UTC 上传，ECCV 2026 workshop 录用
- 摘要：论文证明单个预训练扩散交通模型可同时承担两个角色：作为自车运动规划器，以及作为可控生成"安全关键场景"的生成器，用于对规划器做压力测试。核心贡献包括 Single-Stream Dual-Stream（SSDS）扩散-transformer 解码器——用联合注意力（而非后期跨注意力）融合场景上下文，在 nuPlan 闭环仿真上提升表现；以及 Decoupled Annealing Posterior Sampling with Energy（DAPSE），一种无需重新训练、"在干净样本层面注入任意能量函数"的引导采样方法。用该模型生成的激进变道、前车急刹等长尾交互场景能暴露规划器的失效模式；论文明确指出"基准测试上的优越表现不必然转化为鲁棒性"。
- 为何重要：这为自动驾驶"如何验证规划器"提供了一个方法论候选——把"生成对抗场景"和"做规划决策"统一到同一个模型，而非分别维护两套系统；论文自己给出的警示（"benchmark 领先不等于鲁棒"）与本 wiki 长期关注的"evals 不是最终真相"主题相通，这次落在自动驾驶垂直领域。证据边界：仅在 nuPlan 闭环仿真验证，未见真实道路数据；论文是 ECCV workshop（非主会）录用，同行评审强度弱于主会；未说明生成的对抗场景本身是否代表真实事故分布，还是仅代表模型自身偏好的"困难案例"。
- 原文：[One Diffusion Model, Two Roles: Guided Trajectory Planning and Safety-Critical Scenario Generation in Closed-Loop Simulation（arXiv 2609.04921）](https://arxiv.org/abs/2609.04921)
- 配图：![SSDS架构：场景编码器共享给自车轨迹解码器与对抗agent轨迹解码器两路输出](https://arxiv.org/html/2609.04921v1/paper_pic_main_re.png)

### 5. 今日细读：agent 记忆不是"塞得越少越好"，合并规则和打包方式比检索算法更关键
- 领域：AI / 智能体（长时任务记忆架构，今日加选）
- 来源 / 发布日期：arXiv / 2026-09-07（公告日），v1 于 2026-09-04 09:19:00 UTC 上传
- 摘要：论文聚焦长时 agent 部署中 prompt 预算紧张（延迟、成本、上下文长度限制）场景下"什么记忆设计能取得最好的质量-token 权衡"，而非单纯追求召回率最大化。作者提出 RSM-full：一种在线聚类记忆流水线，结合"余弦门控的最大成员合并写入规则"与"atom 感知的分组上下文打包器"。在自建的 AMA-Bench 上，4k token 预算下达到全上下文质量的 83%，但只用 32% 的 token 成本；四种子平均下，在约 2.6k–5k token 区间比最接近的流式聚类基线（Online K-Means）高 3.5–6.0 个百分点（p<.001）。消融显示提升主要来自合并规则（+5.7pp）和分组打包器（+5.0pp）。在独立的长时人格记忆基准 RealMem 上复现了同样模式，相对 2025 年的 agentic-memory 基线 A-MEM 有 +1.65pp（p<.001）提升。
- 为何重要：这与本 wiki 线索"记忆存储格式的模型可迁移性"（09-08 简报，[[agent-记忆的模型可迁移性]] 候选中）是相邻但独立的问题——那条测的是"模型升级后记忆是否失真"，这条测的是"固定模型下，给定 token 预算，怎么合并、怎么打包"比"用什么检索算法"更重要，与已有页 [[Agent 记忆架构]] 的"存储不等于记忆"讨论直接相关。证据边界：核心指标依赖作者自建的 AMA-Bench，尚待第三方复现；p 值虽显著但效应量普遍在个位数百分点，实际生产收益是否可感知未讨论；论文自陈 RSM-full 在高于 5k token 的场景明确弱于全上下文基线，是"特定区间"的帕累托最优，不是全局最优方案。
- 原文：[Compact-Memory LLM Agents via Online Max-Member Clustering and Atom-Aware Packing（arXiv 2609.04915）](https://arxiv.org/abs/2609.04915)

## 今日主线

今天四条（连同细读共五项）共享一个追问：**验证机制本身的边界在哪里，谁来验证"验证是否可靠"？** CABAL 显示，现有审稿系统的串通检测器面对精心设计的合谋策略几乎失灵，检出率从个位数到三成多；工业 crash report 研究把"定位准确率"和"修复成功率"拆开算，揭示同一套流水线里两个环节的可靠性并不同步；扩散模型双角色论文更直接地把这一命题写进摘要——"基准测试上领先不等于鲁棒"，并让验证内生于系统设计（同一模型既当规划器又当对抗生成器）；RSM-full 则从记忆架构角度提供一个反例式提醒——一个在特定 token 预算区间统计显著跑赢基线的方法，离开那个区间就不再成立。四条放在一起呼应本 wiki 长期跟踪的判断：**agent 系统的瓶颈正从"能不能做"转向"我们拿什么去验证它做得对不对，以及这套验证机制本身有没有盲区"。**
