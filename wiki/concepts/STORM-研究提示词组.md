# STORM 研究提示词组（Claude 可执行版）

把 Stanford OVAL 的 STORM / Co-STORM 方法论移植成一组可直接用于 Claude 的分阶段提示词。
详细的系统分析（技术机制、停滞现状、局限、失真样本）见 [[STORM-知识策展系统分析]]。

## 设计前提：三样东西不能丢

STORM 的名字是 **S**ynthesis of **T**opic **O**utlines through **R**etrieval and
**M**ulti-perspective Question Asking——**R 是 Retrieval**。网上流传的"4 个 prompt 复现 STORM、
无需联网"的版本抽掉了检索，只留下固定角色扮演，却仍引用原论文的评估数字背书。
那种版本得到的"最强证据"是模型自己编的。这条失真链的完整取证（上游节点、证据点表、
分特征统计与反例）见 [[AI方法论的去机制化失真]]。

本提示词组刻意保留三个环节，缺一即退化为普通角色扮演：

1. **视角从检索材料里长出来**，不用固定角色表。STORM 的 `persona_generator` 是先检索同主题
   既有文章、再反推该主题特有的视角——所以研究"半导体制程"和"宋代科举"得到的视角不同。
   > 综合：这是 STORM 最值得单独拆用的一条原则——**用结构制造多样性，而不是用指令请求多样性**。
   > 在 prompt 里写"请提出多样化的问题"得到的问题总是同质的；让多个来源各异的视角并行提问才有效。
2. **每轮提问都真实检索**，答案 grounded 在检索结果上，不许用参数化知识补空。
3. **产物带引用可溯源**，否则违反本仓库铁律"论断必有出处"。

另外补了两个原版没有、但实践中很要命的检查：**共识独立性**（五个来源说同一件事，
可能只是同一个说法被转载了五次）和**反证检索**（替代不可靠的自我评分）。

## 使用前提

- Claude 需开启联网搜索。**没有检索能力就不要用这套**——退化后还不如直接提问。
- 完整流程适合值得投入的研究问题。一次性事实查询直接问即可。
- 阶段 1、2 是耗时主体（多视角 × 多轮 × 每轮检索）。

## 阶段 0：视角发现

```
研究主题：<TOPIC>

这是 STORM 流程第 0 步：视角发现。现在不要回答这个主题本身。

1. 联网检索该主题的既有高质量综述性材料 3-5 份。优先百科条目、行业综述、
   学术 survey、深度报道、官方文档。记录每份 URL 与发布/更新日期。

2. 通读后回答：围绕这个主题，现实中存在分歧或利益差异的群体有哪些？
   分歧轴必须从检索材料里读出来。不要套用"学者/从业者/怀疑者/经济学家/历史学家"
   这类通用角色清单——它对所有主题一视同仁，等于没有区分度。

3. 输出 4-6 个视角，每个包含：
   - 视角名称：用这个主题里真实存在的身份（如"矿场运营方""欧盟监管起草人"），
     不要用抽象角色
   - 溯源：该视角来自哪份材料的哪条线索，引用原文片段 + URL
   - 关切：它关心什么、明确不关心什么
   - 对立面：它最可能与哪个其他视角冲突，冲突在哪一点

4. 额外输出「初始盲区」：这几份材料共同没有覆盖的方面（阶段 2 会用到）。

输出格式：视角表 + 一段分歧轴说明。
```

## 阶段 1：分视角检索式提问

```
基于阶段 0 的视角列表，逐个视角进行检索式提问。

对每个视角执行 3-5 轮：
- 以该视角身份提出一个具体问题。要问该视角真正关心的细节，
  不要问"X 是什么"这类泛问
- 把问题转成 1-2 条搜索 query，实际执行检索
- 基于检索结果作答

硬约束：
- 回答中每个事实必须附 URL。检索不到就写「未检索到支持材料」。
  不允许用你已有的知识补空——这是本流程与角色扮演的根本区别。
- 连续两轮检索没带来新信息，该视角提前结束。
- 全程维护一份「检索残留」清单：检索结果里出现过、但没有被任何问题
  追问下去的信息点。逐条记录内容 + 出处。

输出：按视角分组的问答记录 + 检索残留清单。
```

> 检索残留清单是阶段 2 的唯一输入，不要省略。它是整套流程里最容易被跳过、
> 但价值最高的中间产物。

## 阶段 2：Moderator 介入（unknown unknowns）

```
切换到 Moderator 角色。这一步来自 Co-STORM，目的是发现"不知道自己不知道"的部分。

输入：阶段 1 的「检索残留」清单。

1. 从残留里挑出 2-3 条最反直觉、或最偏离主线叙事的信息点。
   判据是"意外"，不是"重要"——重要的东西前面已经问过了。
2. 针对每条提出一个前面所有视角都没问过的问题。
3. 对这些问题执行检索并作答，引用要求同前。
4. 明确判断：这些回答是否动摇了前面形成的主线判断？动摇了哪一条？

自检：这一步做完如果没有产生"这个角度我原本根本不会想到"的感觉，
说明阶段 1 检索广度不够。回到阶段 1 扩大 query 范围重做，不要硬往下走。
```

> 机制出处：Co-STORM 的 Moderator agent 被定义为"基于检索到了、但前面轮次没用上的信息提出问题"。
> 原系统还有一条防收敛规则——连续 3 轮只回答不提新问题就强制插入 Moderator
> （`moderator_override_N_consecutive_answering_turn` 默认 3）。手工执行时，
> 阶段 1 每个视角跑完就切一次阶段 2 效果更好。

## 阶段 3：矛盾与共识地图

```
汇总前面所有轮次的材料，输出三张清单。这一步不做综合、不下结论。

1. 冲突清单
   格式：论断 A（URL）↔ 论断 B（URL）| 冲突性质 | 哪方证据更强、为什么
   证据强弱只看：一手 vs 二手、样本与方法、发布时间、利益相关性。
   不看措辞的自信程度。

2. 共识清单 —— 必须附独立性检查
   对每条"所有来源都同意"的论断，追查这些来源是否真正独立：
   - 是否都引用同一份原始研究/报告？
   - 是否存在 A 引 B、B 引 C、C 引 A 的循环引用？
   标注为：真共识（多个独立一手来源）/ 疑似同源传播（写明共同源头）
   五个来源说同一件事，可能只是同一个说法被转载了五次。

3. 空白清单
   哪些关键问题所有检索都没能回答？区分三类：
   - 尚无研究（真空白）
   - 有研究但检索没覆盖到（检索缺陷 → 补检索）
   - 数据被刻意不公开（信息不对称本身就是信号）
```

## 阶段 4：综合成文

```
现在综合成文。

1. 核心结论：3-5 句，直接回答最初的研究问题
2. 分歧所在：哪些是真争议，各方位置与证据强度
3. 已确立的事实：只放通过独立性检查的真共识
4. 关键未知：空白清单里最影响结论的 2-3 条
5. 证伪条件：要推翻当前结论，需要出现什么证据

引用规则：
- 每个事实性论断后附 URL
- 来源事实与你的推断必须区分，推断句以「推断：」开头
- 不确定的判断标注置信度（高/中/低）+ 依据
```

## 阶段 5：独立校验（不是自评）

```
这一步不给自己打分。模型评审自己的输出存在已知的自我偏好偏差，
且评审时的盲区与生成时的盲区高度相关——自评会把未验证内容包装成已验证内容，
比不做更糟。改为执行三项可证伪的检查。

1. 引用抽验
   抽取 5 条带引用的论断，重新访问 URL，确认：
   (a) 页面存在 (b) 确实包含该论断 (c) 语境未被截断而改变原意
   逐条报告：核实通过 / 引用不支持该论断 / 链接失效

2. 反证检索
   对最核心的 3 条结论主动检索反面证据，query 按
   「<结论> 反驳 / 批评 / 局限 / 失败案例」构造。
   报告找到了什么，以及原结论是否需要修正。

3. 来源结构检查
   统计全部引用的构成：一手 vs 二手比例；是否过度集中于单一机构、
   媒体或立场；时间分布是否全挤在某个窗口。
   STORM 论文承认的 source bias transfer 就发生在这里——
   检索到什么立场的源，报告就带什么立场。

输出：三项检查结果 + 需修正的具体条目。不要给总分。
```

## 快速版（单轮，用于时间不够时）

完整流程跑不动时用这个，但要清楚它牺牲了什么：视角数量减半、无残留清单、
Moderator 与校验合并——**unknown unknowns 的发现能力基本丧失**。

```
研究主题：<TOPIC>

按以下步骤执行，每步都要实际联网检索：
1. 检索 3 份该主题的综述材料，从中提炼 3 个真实存在、且相互对立的视角（附溯源 URL）
2. 每个视角提 2 个具体问题，逐个检索作答，事实附 URL，检索不到就说没有
3. 列出：来源之间的直接冲突 / 真正的共识（标注是否同源传播）/ 没人回答的空白
4. 综合成 5 句结论，区分事实与推断，标注置信度
5. 对最核心的 1 条结论做反证检索，报告结果
```

## 已知边界

- **不能产出发表级内容。** STORM 论文自述定位是只在 pre-writing 阶段有帮助，
  Wikipedia 编辑评价为需要大量编辑。这套提示词继承同样的边界。
- **source bias transfer 无法根除**，阶段 5 第 3 项只能让它可见，不能消除。
- **over-association**：把不相关事实强行关联是长文本生成通病，阶段 4 综合时易发。
- **手工执行没有并行。** 原系统多个 persona 走 `ThreadPoolExecutor` 并行，
  手工串行跑成本高得多。若在 [[Claude Code]] 中执行，可以用多个 subagent 分头跑阶段 1
  再汇总，这是最接近原系统的执行方式。

## 关联

- [[llm-wiki-方法论]]：STORM 强在**发现**、llm-wiki 强在**沉淀**，两者互补——
  STORM 每次研究跑完即弃、不积累知识，本 wiki 恰好接住它的产物。反过来，
  本 wiki 的 research 环节原本是单线程提问，阶段 0-1 的多视角分裂正好补这个短板。
- [[building-effective-agents]]：本流程对应 **prompt chaining + parallelization**
  两个 workflow 模式，是预定义代码路径而非自主 agent。原系统亦然。
- [[Evals]]：阶段 5 拒绝自我评分的依据——LLM-as-judge 存在自我偏好偏差，
  且评判错误与生成错误相关。
