# Evals（AI 系统评估）

**Eval** 是针对 AI 系统的可重复测试：给定任务与环境，运行一次或多次 trial，再用 grader 判断输出、
过程或最终状态是否满足成功标准。对 agent 来说，被评估的是**模型 + agent harness + 工具 + 环境**的整体，
而不只是单轮回答。（Anthropic，2026-01-09）

## 基本组成

- **Task / test case**：输入、环境、约束和成功标准。
- **Trial**：同一任务的一次运行；因模型非确定性，通常要多次运行。
- **Grader**：评分逻辑，可组合代码检查、模型评分和人工评审。
- **Transcript / trace**：工具调用、推理与中间结果的完整轨迹。
- **Outcome**：任务结束后的真实状态；例如“系统里是否真的产生了预订”，而非 agent 是否声称成功。
- **Suite / harness**：批量运行、记录、评分和汇总任务的基础设施。

## 两类常用 eval

- **Capability eval**：测试 agent 目前能做到什么，题目应保留足够难度，给能力提升留下爬坡空间。
- **Regression eval**：保护已经会做的事情，目标接近稳定全通过，防止模型、prompt、工具或代码变更造成倒退。

Agent 的多轮、工具调用和状态修改会让错误传播，单次通过也不代表稳定。可按场景区分：

- `pass@k`：k 次中至少成功一次，适合“多试几次只需一次成功”的探索场景。
- `pass^k`：k 次全部成功，适合用户每次都期待可靠结果的生产场景。

## Evals 不是最终真相

> 综合：evals 是**符合性证据**，不是意图或现实的最终裁判。任务可能有歧义，grader 可能奖励错误代理指标，
> suite 也会随产品和用户分布变化而漂移。应与生产监控、A/B 测试、用户反馈和人工 trace 复核组合使用。

这与 [[代码与文档漂移的本质]] 的分层一致：规格定义预期，evals 提供实现是否符合预期的证据，
生产数据验证真实效果。

模型 grader（LLM-as-judge）自身有两类实证偏差：评审模型会识别并偏袒自己生成的输出
（自我偏好偏差：https://arxiv.org/abs/2404.13076 ，检索于 2026-07-17）；多个评审模型的错误
高度相关，越强的模型错误越趋同（跨厂商亦然），九个相关评审的有效票数约等于两票
（https://arxiv.org/abs/2506.07962 、https://arxiv.org/html/2605.29800 ，均检索于 2026-07-17）。
因此模型 grader 应尽量与被测系统异源，其结论按证据而非裁决使用；
agent 自产自审的完整实证边界见 [[论代码与文档漂移解决方案]]。

## 从最终答案到全轨迹审计

[[2026-08-07-A2E-Agent-Auditing-Engine-源摘要|A²E]] 将 agent eval 拆成三个互补范围：用 outcome 验证任务终态，用 process 评估计划、工具、记忆与错误恢复，用 lifecycle 指标评估成本、延迟与安全。其 855 条完整轨迹显示，harness 的平均 correctness 只跨 0.568–0.663，而可观测 harness 的平均 token 使用差 3.5 倍；终点分接近不代表过程、成本和风险接近。

综合：**outcome 是成功主证据，trace 是归因与审计证据**。过程分不应覆盖 outcome；指标、judge 和轨迹应分开版本化，以便在不重跑 agent 的情况下重评历史轨迹。完整的四类契约与最小实现见 [[Agent 全轨迹评测与审计]]。

## 设计检查表

- 从需求或真实失败案例派生任务，成功标准对被测 agent 清晰可见。
- 优先验证 outcome，同时保留 trace 以诊断“为什么失败”。
- 正反例平衡，避免只测“应该做”而不测“不应该做”。
- 为任务准备可通过的 reference solution，先证明 grader 与环境没有坏。
- 多次运行并报告分布，不用一次成功率掩盖非确定性。
- 定期阅读失败与成功 trace，校准模型 grader，并为 suite 指定 owner 与更新条件。

## 产品级 eval：能力、行为与事故回灌

[[2026-07-21-Simon-Willison-Claude-Code团队访谈-源摘要|Claude Code 团队访谈]]展示了一套持续增长的
产品级 eval：新模型进入产品前跑完整套件；能力项检查能否正确修复 bug、通过测试，行为项检查是否过早停下、
只完成部分任务就把继续与否抛给用户。用户反馈和生产事故按优先级变成新用例，事故致因 PR 还会进入 code
reviewer 的回归集。

Cat 同时承认，团队对提示词修改没有完全置信度，行为覆盖也不是 100%。她认为客户侧主要瓶颈往往不是缺少
评测工具，而是缺少构建高质量 eval 的方法、技能和时间。综合：eval 的复利来自**把真实失败持续编译进套件**，
而不是一次性搭好 harness；工具可降低运行成本，不能代替问题定义与失败分类。

## 生产运行：评估系统也需要被评估

[[Anthropic-AI原生SDLC治理循环]] 提供了一个组织级运行案例：新 reviewer 先以 shadow mode 运行，
自动批准结果接受抽样复核，模型和权限变化接受红队测试；批准、工具调用和 agent 间消息统一进入 SIEM。
这支持把 eval 从“发布前跑一次的分数”扩展为持续校准的治理系统，但仍只是公司实践证据，不能替代逃逸缺陷率、
事故率等结果指标。多专职 agents 可提升覆盖面，不应被视为相互独立的 grader。

## Agent 配置也要做回归测试（2026-08-27 新增）

综合：本页上一节说“评估系统也需要被评估”，但没有回答**由什么触发**。Anthropic 的 AI-native SDLC
playbook（[[2026-08-21-Anthropic-AI原生SDLC-playbook-源摘要]]）给出了一个直接可抄的答案：
把 **agent 配置当代码**，让它接受代码那样的回归测试。本节要点与各处英文引文均出自该源摘要及其存档原文。

- **触发条件**：eval 套件在 CI 中定时运行，**以及在 `CLAUDE.md`、skills、hooks 任何变更时运行**。
  理由是这些文件在操纵 agent 的行为，“deserves the regression testing that code gets”。
- **门禁**：pass rate 下降的配置变更必须先经 review 才能合并。也就是说 eval 结果不是仪表盘上的
  一个数字，而是一道**合并条件**。
- **套件来源**：从近期真实工作中收集 20–50 个任务，每个写成 prompt + 定义“可接受”的检查
  （测试通过、lint 干净、行为不变、政策被遵守）。
- **事故转回归**：每个生产事故由**事故归属团队**写成一条 eval，常驻套件。
- **套件本身会失效**：“As models improve, cases that once discriminated stop doing so and new ones
  must be added.” 即 eval 套件需要自己的保鲜机制，否则通过率虚高。

> 综合：这条实践之所以重要，是因为它把本 wiki 反复出现的一个隐患机制化了——
> [[Anthropic-AI原生SDLC治理循环]] 的“把经验编译进控制面”和 [[论代码与文档漂移解决方案]] 的
> “自然语言规则成为 Agent 的控制面”都依赖一个前提：**控制面本身不漂移**。
> 而 `CLAUDE.md` / skills / REVIEW.md 都是自然语言文件，它们和普通文档一样会过期、会与真实政策
> 脱节——playbook 自己也承认这一点（若 PR 中引用某政策的 findings 不下降，“either the skill isn't
> triggering or its text has drifted from the official policy”）。配置变更触发 eval，
> 是目前唯一给控制面装上反馈约束的可操作做法。

需要注意它的边界：eval 通过率是**证据不是裁决**（本页“Evals 不是最终真相”一节），
而且 playbook 没有给出任何实施数据——没有误报率、没有套件规模与维护成本的实测。
把它当设计模式采用，不要当已验证的效果。

## 任务从哪来，以及记分卡的第二根轴（2026-08-31 新增）

上两节回答了"eval 由什么触发"，没有回答**任务集从哪来**。Uber 的做法给出一个与"事故回灌"互补的
答案：**benchmark 直接由该 agent 的真实工作构成**——uReview（全量 PR 的 AI code review）的套件
由**已知含 bug 的真实 PR** 组成并分难/中/易；另有跨大型 monorepo、数千真实 PR 的 Uber SWE Benchmark
用于跨任务类型的选型（[[2026-08-27-Uber-软件工厂成本效率-源摘要]]）。

更值得抄的是**记分卡有两根轴**：precision / recall / F1 **加上**每次 review 的成本、时延、超时与噪声，
选型在这个二维空间的 Pareto 前沿上做。

> 综合：单轴质量记分卡会让"更准但贵三倍"自动获胜，而生产系统里它常常不该获胜。
> 把成本并入 eval 记分卡，等于承认 **eval 的对象是"配置"而不是"模型"**——同一模型换个 reasoning
> effort、换个子 agent 模型、换个上下文策略就是另一个被评对象。这与上节"agent 配置也要做回归测试"
> 是同一件事的两面：配置既要过质量门禁，也要在成本轴上被比较。
> 托管 agent 侧 Uber 进一步用**结果计价**指标（每合并 PR / 每 review / 每告警成本）配质量信号
> （revert 率、F1、MTTR）——但需注意其正文只公布了成本数字，**质量侧的实际值没有公开**。
