# Agent 工具上下文膨胀

**一句话定义**：把工具接入 agent 的方式，决定了它在收到第一句用户输入**之前**就必须携带的固定
上下文；由于每一轮都重发全部历史，这份固定成本是**乘以轮次的税**，不是一次性开销。

这是 [[MCP]] 类统一工具接口在规模化后暴露的结构性代价，也是 [[Uber-软件工厂的成本工程]]
中 tokens/request 一项的主要治理对象。

## 一、三个叠加的成本面

1. **schema 预加载**：标准 MCP 把所有 server 的全部工具 schema 塞进每个 session 的初始提示，
   不管这次会不会用到。Uber 实测：装了 100+ 工具时，开场约 **50K–70K token** 的纯 schema 开销。
2. **每轮重发**：这份开销随对话历史一起在每一轮重新计费。缓存能把读价降到 0.1×，
   但缓存过期（长间断）后要按全价重建前缀——所以"膨胀 × 缓存失效"是复合放大。
3. **选择准确率下降**：工具库越大，模型在其中选对的难度越高。这一面不体现在账单上，
   体现在错误轮次里，最终仍回到成本。

第三方 SaaS 尤其糟糕，原因是**结构性的**：厂商无法预知客户用哪部分，只能暴露完整能力面。
Uber 举例：某办公套件单 server 打包 49 个工具、约 **22K token** schema；IM 34 个、项目管理 46 个。
挂两三家厂商的 server，**agent 开场背的 schema 比它要编辑的那个文件还大**。

## 二、三条解法及其代价

| 解法 | 机制 | 代价 / 前提 |
|---|---|---|
| **按需检索（tool search）** | 启动只带目录，模型按需检索并加载所需工具 | 依赖检索准确率；多一次往返；工具描述必须写得可检索 |
| **CLI 投影** | 工具映射为 shell 命令，网关在调用时动态解析，schema **完全离开** session 上下文 | 需要统一网关做认证与策略；命令必须自描述（`--help` 可用）；模型要会用 shell |
| **code-mode** | 工具即命令后可在一个脚本里批量调用，中间轮询留在子进程，只有摘要回到上下文 | 需要可执行沙箱；把"多轮推理"换成"一次写对脚本"，失败模式改变 |

三条解法可叠加：Uber 同时用了三者，并对最常访问的 MCP server 预写了 **25+ 个 code-mode skill**，
让常见流程**默认走最省的那条路**——这一步是关键，否则解法存在但无人用。

### code-mode 省的是什么

Uber 同 session 内的 5 条 SQL 双路实测显示：**即使结果集只有 1 行也省 55%**。
省的不是数据体积，而是 schema 初始化、多轮轮询与冗余的逐步推理。批量流程可省 >90%，
因为"N 个模型轮次"被压成"1 个脚本"。

> 综合：因此 code-mode 的适用判据不是"数据量大不大"，而是**协议啰不啰嗦**——
> 需要"提交 → 轮询 2–5 次 → 取结果"的工具，收益最大；一次调用一次返回的工具，收益有限。

## 三、这不是 MCP 的缺陷，是分层的必然副作用

[[MCP]] 把集成复杂度从 M×N 降到 M+N，代价是每个 server 独立设计、彼此不知道对方存在，
**聚合成本被推给了客户端**。协议解决了"接得上"，没有解决"同时接一百个还便宜"。

协议侧已有回应：MCP 规范 2026-07-28 版把能力协商改为逐请求、并引入需双方显式启用的 Extensions
（Tasks / Skills over MCP / MCP Apps）。但这些解决的是状态与分发，**schema 预加载本身仍在协议默认路径上**。
目前的有效解法都在**客户端与网关侧**，不在协议侧。

## 四、Agent Skills 早就内建了这个解法

> 综合：[[Agent Skills]] 的 **progressive disclosure 三级加载**（启动只加载名称与描述 →
> 命中后加载 `SKILL.md` → 脚本与参考按需读取）与 tool search 是**同一个设计原则的两次独立实现**。
> 区别在于 Skills 从格式第一天就把它写进了规范，而 MCP tools 的默认路径是全量预加载。
>
> 这条对比有实践含义：**当一段能力既可以做成 MCP tool 也可以做成 Skill 时，
> "上下文占用"应当进入选型考量**——Skills 天然按需，工具默认常驻。

## 五、可确定性检测的反模式

工具上下文膨胀的好处是它**几乎全部可以从 trace 元数据里确定性地检出**，不需要判断任务做得好不好
（对照 [[Agent 全轨迹评测与审计]] 的 trace 归因证据、[[控制带]] 的确定性检测端）。Uber 的反模式清单里属于本类的有：

- 用户输入前先加载 10 万 token 的系统指令与工具定义；
- 大工具响应（如 40KB 的 MCP 返回）赖在上下文里，被后续每一轮重复计费；
- 长间断后恢复 session，过期缓存导致按全价重建前缀。

> 综合：第二条值得单独强调——它不是"接入方式"问题而是"**返回值治理**"问题。
> 工具的**输出**同样需要预算：一个不分页、不截断、不摘要的工具，会在被调用一次之后持续收税。
> 设计工具时"返回多少"与"声明多少"同等重要。

## 六、本仓库的实例

综合（可直接观察）：Claude Code 的 **deferred tools + ToolSearch** 机制正是"按需检索"解法的产品化——
大部分工具只以名称出现在提示里，schema 要显式检索后才加载。本 wiki 的维护会话即运行在该机制上。
这说明该解法已从"大厂内部工程"下沉为**通用 harness 的默认能力**，小团队无需自建网关即可获得其中一部分。
