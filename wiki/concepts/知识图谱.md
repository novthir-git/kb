# 知识图谱

知识图谱用实体（或资源）及其有类型的关系表示一个领域中的知识。RDF 常用
`subject–predicate–object` 三元组表达；Neo4j 等属性图则使用节点、关系、标签和键值属性。
两者都把“关系”提升为可查询的一等对象。

## 不要混淆三个概念

| 概念 | 是什么 | 不是什么 |
|---|---|---|
| 知识图谱 | 对实体、关系和语义约束的知识表示 | 一张可视化关系图 |
| 图数据库 | 存储和查询图结构的软件 | 知识正确性的保证 |
| 图检索 / GraphRAG | 利用图结构取证或构造回答的方法 | 知识图谱本身 |

Obsidian 双链与 [[Open Knowledge Format|OKF]] 的标准 Markdown 链接都能形成轻量语义网络，
但若链接没有类型、关系属性、统一实体标识与约束，它们不等同于可执行复杂图查询的属性图或 RDF 图谱。
OKF 规范也明确把 Concept 间链接视为有向但无类型的边，具体关系依靠周围正文解释。

## 适合的问题

- 需要沿显式关系做多跳查询；
- 多个来源需要围绕同一实体对齐；
- 需要展示可解释的关系路径；
- 关系本身带角色、时间或证据属性；
- 数据模型会扩展，但仍能维持稳定的身份与约束。

若问题主要是“找到与这段话语义相近的原文”，向量或全文检索通常更直接。是否建图应从查询需求出发，
而不是因为图形看起来更高级。

## 生产级构建流程

```text
目标问题与权威源
→ Schema / ontology 与稳定实体 ID
→ 解析及候选实体关系抽取
→ 实体消歧、去重与对齐
→ 规则或人工验证
→ 写入来源、时间、置信度和权限
→ 发布图谱或索引
→ 查询、监控、纠错与退役
```

LLM 可以加速“候选抽取”，但不会消除后续治理。低 temperature 只降低生成波动，
不能证明实体存在、关系成立或时间仍有效。

## 每条关键事实至少应携带什么

| 字段 | 用途 |
|---|---|
| 稳定实体 ID | 避免同名异物和一物多名 |
| 来源与证据定位 | 回到原文或权威系统核验 |
| 提取/确认方式 | 区分模型候选、规则导入和人工确认 |
| `valid_from` / `valid_to` | 处理随时间变化的关系 |
| 版本与状态 | 支持替代、下架和重建 |
| 权限标签 | 防止索引侧越权召回 |
| 置信度 | 供人工队列和检索降权使用，不能替代证据 |

## Agent 场景下的成本论证（2026-08-31 新增）

过去论证图谱投资的理由是能力侧的——"能回答关系型问题"。Agent 场景给出了第二条、且更易批预算的理由：
**减少检索次数**。在大型代码库与数据生态里，agent 的多数轮次花在**定位信息**而非生成结果；
每一轮都重发全部上下文，因此"多找几个地方"是乘以轮次的开销。
Uber 据此建了 AI Context Graph（2,400 万节点 / 8,000 万边 / 86 类节点 / 117 类边 / 30+ 内部系统，
支持自然语言查询），并给出一句可复用的判断：**"没接地的 agent 不是便宜地失败，而是缓慢地失败"**
（[[2026-08-27-Uber-软件工厂成本效率-源摘要]]）。

> 综合：这不改变下节的 System of Record 边界——图谱仍是可重建派生视图。它改变的是**投资论证方式**：
> 图谱不是检索的替代品，而是**减少检索次数**的前置条件，收益可直接换算成 token 账单。
> 证据边界：其 38 秒 vs 20 分钟的对照是精选单例，且属于图谱最擅长的"哪张表被谁在用"类问题；
> 对"这段代码为什么这么写"一类问题未必有同等杠杆。完整语境见 [[Uber-软件工厂的成本工程]]。

## System of Record 边界

综合：在从文档或业务系统自动构建 Agent 知识的场景中，知识图谱通常应视为**可重建派生视图**，
而不是新的权威事实源。事实修正应回到原始业务源，再由变更事件或扫描重建图谱。
只有当图谱本身有明确 Owner、正式录入流程、版本和治理责任时，它才可能成为某些事实的权威源。
这一边界详见 [[基于IT4IT的Agent知识治理]]。

同理，OKF Bundle 即使通过格式合规检查，也只是可携带知识制品；它是否能成为权威源，仍取决于 Owner、
正式写入流程、来源、核验、权限和生命周期治理，而不是 Markdown 文件本身。
