# 控制带（control bands）

**控制带**是一种给自主 agent 分级授权的机制：用**确定性**的统计检测监视一个生产指标，
按偏离基线的程度分层决定 agent 被允许做什么。核心特征是**检测端不含模型**——
模型只在带被突破之后才被调用，且带的层级决定它的权限上限。

出处：Anthropic 的 AI-native SDLC playbook（Stage 6 "Closing the loop"，
[[2026-08-21-Anthropic-AI原生SDLC-playbook-源摘要]]）。

## 机制

```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```

- **检测**：滚动窗口上的均值与标准差，配合 Western Electric 一类规则，使**缓慢漂移**和**尖峰**
  都能被捕捉。脚本进版本控制并有单元测试。原文措辞：
  "detection stays entirely deterministic, with no model involved."
- **1σ**：只记录，不调用模型。
- **2σ**：以**只读**权限调用 agent 诊断（工具面被显式限定为 Read / Grep / 特定只读命令）。
- **3σ**：agent 可以行动，但**路由被穷举**——只能开 PR 进入审查门禁，或触发**预先批准**的 runbook。
- **输出格式固定**：agent 把诊断写成与 Plan 阶段同格式的 `intent.md`（异常与证据、建议结果、
  受影响系统、开放问题），因此发现物以与其它任何变更相同的方式重新进入流水线。
- **分诊与调参**：服务 owner 或 on-call 分诊队列（Fix now / schedule / dismiss），
  **dismissal 用于调整带宽并降噪**——这是闭环里唯一需要人持续投入的部分。

## 为什么这个设计成立

综合：控制带把三条已被本 wiki 分别论证过的原则压进了一个可版本化的配置文件里。

1. **"AI 负责理解和调和，程序负责证明和约束"**（[[论代码与文档漂移解决方案]] §七）。
   检测是程序的，诊断是模型的，授权是配置的。模型从不决定自己该有多大权限。
2. **权限是可穷举的路由，不是自由动作**。3σ 层给的不是"可以改生产"，而是两条具名通道
   （PR / 预批准 runbook）。这与该页 §九 "自动删除的授权只能来自可确定性验证的条件" 同构。
3. **假阳性有泄压阀**。dismissal 直接反馈到带宽，对应
   [[论代码与文档漂移解决方案]] §十一 的"假阳性预算"——组织不缺加检查的能力，缺删检查的机制。

## 与 T0–T4 风险分级的关系（本 wiki 的补充）

综合：[[论代码与文档漂移解决方案]] §九 的 T0–T4 按**产物风险**分级，控制带按**信号强度**分级。
两者**正交**，可组合成一张授权矩阵：

| | 1σ（记录） | 2σ（只读诊断） | 3σ（受限行动） |
|---|---|---|---|
| T0–T1 生成物、断链 | 记录 | 诊断 | **自动修复 + 自动合并** |
| T2 有完整替代的普通产物 | 记录 | 诊断 | 开 PR，确定性条件满足才自动 |
| T3 Spec / PRD / 架构 | 记录 | 诊断 | **只能开 PR**，人工批准 |
| T4 ADR / 法务 / 安全 / 公开契约 | 记录 | 诊断（只读） | **不授予行动权**，仅升级给人 |

单看信号强度会在高风险产物上授权过度；单看产物风险则无法区分"轻微抖动"与"系统性失控"，
只能用一个静态阈值应对两者。两个维度都要，是因为它们回答的是不同问题：
**产物风险问"做错了后果多大"，信号强度问"现在有多确定出事了"。**

## 适用边界

- **需要一个有稳定滚动基线的指标。** 原文举的三个都满足：CI 测试失败率、部署后 5xx 率、
  PR cycle time。没有稳定基线的指标（新服务、季节性强的业务指标）用不了这个机制。
- **不适用于符合性判断。** 控制带监视的是可量化的运行信号，即 [[代码与文档漂移的本质]] 分类里的
  **运行漂移**——它可治理正是因为 desired/actual 同构可 diff。"实现是否符合意图"没有这种同构，
  不能靠控制带发现。
- **回滚必须先被演练过。** 原文明确要求 rollback 是"流水线里被演练得最多的路径"，
  并在 staging 定期执行——因为 3σ 层会调用它。**授权一条自动路由的前提是这条路由已被证明可靠。**
- **它不解决检测本身的漂移。** 带宽是配置，配置也会过期；原文靠 dismissal 反馈调参，
  但没有回答"谁拥有关掉一个坏检测的权力"。这正是 [[论代码与文档漂移解决方案]] §十一 第 7 条
  （假阳性预算需要有人拥有下线检查的权力）指出的空白。

## 证据状态

原文**没有给出任何实施结果数据**——没有误报率、没有 3σ 触发频率、没有自动修复的成功率。
它给了度量指标（从带突破到 intent.md 进入分诊队列的时间、findings 变成已合并修复的占比、
同类事故重复率），但没给测量值。因此当前应视为**设计模式**，不是经验证的效果。
证据性质与 [[SDD 收益主张的实证赤字]] 记录的问题同源。
