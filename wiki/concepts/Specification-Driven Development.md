# Specification-Driven Development

**Specification-Driven Development（SDD，规格驱动开发）**是一种把规格从一次性说明文档提升为
开发契约的工程范式：先明确系统要满足的行为与约束，再派生设计、任务、代码和验证证据；需求变化时，
规格与实现一起演化。GitHub Spec Kit 将其概括为“规格定义 what，再逐步细化 how”，并强调多轮澄清，
而不是从一条 prompt 一次生成完整代码
（[GitHub Spec Kit](https://github.github.com/spec-kit/concepts/sdd.html)，检索于 2026-07-16）。

## 核心闭环

流程：意图 → 规格 → 设计 → 任务 → 实现 → 测试 / [[Evals|evals]] → 证据 → 规格回写。

- **规格**回答“系统必须做什么、什么不能改变”。
- **设计**回答“如何满足规格，以及为何选择这条路径”。
- **任务**把设计拆成有依赖、有完成条件的可执行单元。
- **测试/[[Evals|evals]]**把自然语言规格硬化为机器可检查的约束。
- **证据与回写**防止实现完成后规格立即失真。

> 综合：SDD 的本质不是“写更多文档”，而是为人和 coding agent 建立一个可版本化、可验证、可演化的
> 意图接口。若规格不能约束实现、测试不能追溯规格、变更后不回写，流程只是传统文档前置，不构成完整 SDD。

Margaret-Anne Storey 将这类缺失进一步命名为 **intent debt**：目标、约束与设计理由没有被外化到人和 agent
都能使用的制品中，代码即使通过测试，也可能持续偏离“本来要构建什么”。SDD 因而不仅是生成效率工具，还是
意图债的偿还机制；但它不能单独偿还团队失去系统理解形成的 cognitive debt，见 [[AI编码技术债的三层治理]]。

代码与文档为什么会系统性失同步、漂移的四种类型（表达/符合性/运行/生命周期），
以及“代码作为唯一真相源”的能力边界，见 [[代码与文档漂移的本质]]。

## 两个必须分开的选择

### 规格保留多久

| 模型 | 做法 | 适用边界 |
|---|---|---|
| Spec-first | 编码前写规格，完成后可丢弃 | 一次性原型、低风险探索 |
| Spec-anchored | 实现后继续维护规格，后续变更以它为锚 | 大多数长期维护的软件 |
| Spec-as-source | 只人工编辑规格，代码等产物由它再生成 | 生成链和验证链足够确定的特定领域 |

这三个层级来自 2026 年 SDD 实践综述，并被 GitHub Spec Kit 的持久化文档采用
（[arXiv 2602.00180](https://arxiv.org/abs/2602.00180)，检索于 2026-07-16）。

### 需求变化时改什么

GitHub Spec Kit 另区分三种 artifact mutation model
（[Spec Persistence Models](https://github.github.com/spec-kit/concepts/spec-persistence.html)，检索于 2026-07-16）：

- **Flow-back**：规格、设计、任务、代码都可先发生变化，之后人工重新对齐；快，但易静默漂移。
- **Flow-forward**：已完成的变更包保持不可变，新需求新建变更包；审计强，但上下文可能碎片化。
- **Living spec**：先更新规格，再重新派生设计和任务；契约清晰，但必须保留重要的技术理由。

> 综合：多数存量项目适合“Spec-anchored + Living current spec + Flow-forward change history”：
> 当前规格描述系统应有行为，每次变更以 delta 提案，验证后合并回当前规格。Flow-forward 要求已完成记录
> **不可被静默改写**，不等于所有过程文件必须永久留在工作树：长期理由蒸馏到 ADR / current spec，
> 有审计或复现义务的包归档，其余按保留策略退出并由 Git 历史恢复。
> OpenSpec 的 `specs/`（当前真相）与 `changes/`（提议差异）就是该组合的实现
> （[OpenSpec](https://openspec.dev/)，检索于 2026-07-16）。

该生命周期规则与 [[论代码与文档漂移解决方案]] 的 Reconcile & Retire 状态机一致；可执行门禁见
[[SDD 开发规范研究]] 的 G5。

## 与 TDD、BDD、Loop Engineering 的关系

- **SDD**管理“意图、约束与跨产物追溯”。
- **BDD**用 Given/When/Then 表达可观察行为，可作为 SDD 的需求表达层。
- **TDD**用失败测试驱动局部实现，可作为 SDD 的执行与验证层。
- [[Loop Engineering]] 管理规格、[[Evals|evals]]、coding agent 与人类反馈的运行循环；SDD 把其中的规格接口和
  checkpoint 固化成版本化工程资产。
- [[Claude Tag 驱动的团队研发流程]] 补出团队协作边界：Slack 等频道可以作为事件入口和多人协调面，
  但不能成为规格真相源；讨论结论必须回写成 spec delta、验收标准、测试 / eval、PR 与审批证据。

三者不是替代关系。没有测试的 SDD 仍可能得到“文档一致、运行错误”的系统；没有规格的 TDD 只能证明代码
满足测试，不能证明测试覆盖了真实意图。

## 证据边界

2026 年 Orchid 基准覆盖 1,304 个函数级任务，发现词汇、句法、语义与模糊性歧义都会降低受测 LLM 的
代码生成表现；模型还经常对同一模糊需求生成行为不同的实现，且不能可靠地自行发现或消解歧义
（[arXiv 2604.21505](https://arxiv.org/abs/2604.21505)，检索于 2026-07-16）。这直接支持 SDD 的
“澄清后再实现”，但尚不能证明任何一套完整 SDD 工具必然提升组织生产率。

**且现有最大样本的证据指向反面**（2026-08-27 补）：119 个开源仓库、100,247 个 PR 的 within-author
分析显示，规格与更高返工显著相关（+5.0pp, p<0.001），与更高缺陷率的关联方向为正但仅边缘显著
（+1.4pp, p=0.056，严格说不显著），规格质量对返工零效应（p=0.997）。因此应把 SDD 的成分与打包主张分开
——“澄清歧义后再实现”“可追溯”各有独立支持，“写规格 ⇒ 缺陷与返工下降”没有。
证据表、限定条件与结构性解释见 [[SDD 收益主张的实证赤字]]。

> 综合：为什么规格的净收益难以显现，可以从本库的漂移框架直接推出——规格与代码之间同样没有
> 共同形式表示，所以 SDD 并未消除符合性漂移，而是把它**向上位移一层**（从代码偏离意图变成
> 规格偏离意图），并把它部分转化为表达漂移与生命周期漂移。这笔交换只有在配套建了调和机制时
> 才划算。论证见 [[代码与文档漂移的本质]]“SDD 与漂移的转化关系”。

可执行的团队规范见 [[SDD 开发规范研究]]；相关 agent 设计原则见 [[building-effective-agents]]，
人的监督成本见 [[生产力-体验悖论]]，生产环境约束见 [[agent-生产级落地的鸿沟]]。
