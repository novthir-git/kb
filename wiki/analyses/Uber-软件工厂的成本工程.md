# Uber 软件工厂的成本工程

**核心论断**：当 agent 用量按倍数增长，成本问题的正确形态不是"选更便宜的模型"或"限制使用"，
而是**把花销拆成可乘的若干项，逐项定义浪费、逐项建指标、逐项上杠杆**。
Uber 2026-08-27 的公开实践给出了目前最完整的一份该类方法论
（[[2026-08-27-Uber-软件工厂成本效率-源摘要|源摘要]]）。

数据全部为公司自报，口径边界见源摘要末节；本页只取其中**可复用的判断**。

## 一、"浪费"第一次有了可操作定义

原文把成本方程的中间三项定义为**"agent 在工程师真正提出的那个请求之上，替它自己多干的活"**，
并把优化火力集中在这里。

> 综合：这是本 wiki 见过的第一个**可操作**的 agent 浪费定义。此前的讨论要么停在"token 贵"
> （无法指导行动），要么停在"少用点"（等于放弃收益）。把"用户要的活"与"agent 为完成它而自己
> 生成的活"分开之后，"降本"不再与"降能力"耦合——原文的结论句正是这个意思：
> 消除零价值 token，而不是靠更低单价或降级工具。

这条区分同时解释了为什么**总支出持平也算成功**：分子被砍掉的部分，恰好被用量增长填回去了。
把"单位成本"和"总支出"混为一谈会读错这篇文章。

## 二、成本方程（六项相乘）

原文只在图片里给出六项名称。综合（推断，非原文明文）：

```
总支出 = 用户数 × 会话/用户 × 轮次/会话 × 请求/轮 × token/请求 × 单价/token
         └── 采用与参与 ──┘   └────── agent 自己多干的活 ──────┘   └ 厂商定价 ┘
```

依据：原文称"前两项代表采用与参与""中间三项是优化机会"，而三节优化标题恰为
Price/Token、Tokens/Request、Requests/Turn。四层用量结构（越专用越可控）同理只在图片中。

**方向是反直觉的**：前两项要**做大**（采用与参与是价值来源，不是成本问题），
中间三项要**做小**，最后一项靠选型而非议价。把六项混成一个"总花费"数字，就同时失去了
"该增长的"和"该压缩的"这两个方向。

## 三、驱动因素分解：不留未解释残差

度量表里最硬的一行是 **driver decomposition**——把成本变化**顺序分解**为采用、参与、
输入负载、输出负载四个因子，要求"为什么变了，说得精确，不留未解释残差"。

> 综合：这是财务分析（量价拆分）的做法，不是工程博客常见的做法。它的价值在于**排除争论**：
> 账单涨了，是人变多、用得更狠、上下文变胖，还是模型想得更久——四选一，且四项之和等于全部变化。
> 没有这一步，任何"优化"都无法与"用量自然波动"分离，团队会持续争论功劳与责任。
> 对照 [[Evals]] 的同源要求：outcome 证明成功，归因需要单独的分解证据。

## 四、控制单元从"人"上移到"托管 agent 队伍"

原文的战略主张：从交互式开发者工作流转向**完全托管的 agent**，因为托管环境才完整掌握
模型路由、执行 harness 与运营开销；优化一支各配 benchmark 与 Pareto 模型的专用 agent 队伍，
比优化几千名工程师各自的终端 session 更划算。

> 综合：这与本 wiki 已记录的两次"控制单元上移"是**同一个运动的不同侧面**：
> [[Anthropic-AI原生SDLC治理循环]] 把安全控制点从"逐项审查代码"上移到身份、委托与风险门禁；
> [[控制带]] 把授权决策从"人逐次判断"上移到可版本化的分级配置。
> Uber 这里把**成本**控制点从"教育每个工程师省钱"上移到"托管少数几个 agent 的配置"。
> 三者共享同一条逻辑：**当被治理对象的数量爆炸时，治理必须迁移到数量少、可配置、可测量的那一层。**

但要注意这是**主张，不是实测**：原文未给交互 session 与托管 agent 在同类任务上的对照成本。
机制可信（控制点少、可测、可换模型），论证尚缺。

## 五、选型是持续过程，且 benchmark 必须来自自己的真实工作

四步法里最关键的不是"选 Pareto 最优"，而是两条约束：

1. **benchmark 由该 agent 的真实工作构成**——uReview 用**已知含 bug 的真实 PR** 打 F1，
   而不是公开 benchmark；另有跨 monorepo 数千真实 PR 的 Uber SWE Benchmark。
2. **harness 固定、模型可换**——"一个接口后面接任意模型（前沿或开源权重）"。

> 综合：这两条正是 [[harness-vs-model]] 的工程化推论。既然同模型在不同 harness 上成功率、
> 轨迹与成本都会变，那么想比较**模型**就必须把 harness 钉死；想比较 **harness** 就必须把模型钉死
> （原文测自身优化收益时正是固定模型）。Uber 两个方向都做了，这是方法上的自洽。
> 而"用真实工作造 benchmark"回答了 [[Evals]] 长期悬着的一个问题——生产级 eval 的任务从哪来：
> 从生产事故与真实缺陷里来，不是从榜单里来。

同时它把 [[Evals]] 的评分维度从质量单轴扩成**质量 × 成本双轴**：uReview 的记分卡是
precision / recall / F1 **加上**每 PR 成本、时延、超时、噪声。Pareto 前沿是这个二维空间里的概念——
"更准但贵三倍"不再自动获胜。

**子 agent 默认弱模型**被原文称为交互侧最有效的单一杠杆，机制清晰：主模型做拆解与评估，
子 agent 执行定义良好的子任务，前沿级推理在后者上是溢价而非必需。这条与 [[building-effective-agents]]
的编排分层直接对应——**编排层与执行层的能力需求本就不同，用同一个模型跑两者是默认值的懒惰，不是设计。**

## 六、接地取代搜索：requests/turn 的唯一大杠杆

原文最锋利的一句：**"没接地的 agent 不是便宜地失败，而是缓慢地失败"**——它会带着不断膨胀的
上下文再去找一个地方。因此在大型代码库里，agent 的多数轮次花在**定位信息**而非生成代码。

Uber 的答案是 AI Context Graph（2,400 万节点 / 8,000 万边 / 86 类节点 / 117 类边 / 30+ 内部系统），
支持任意 agent 自然语言查询。对照实验（单例）：接地 38 秒答对，未接地 20 分钟答错。

> 综合：这是 [[知识图谱]] 在 agent 场景下的**成本论证**，而非能力论证——过去论证图谱的理由是
> "能回答关系型问题"，这里的理由是"能把 requests/turn 砍下来"。两者指向同一投资，但后者可以直接
> 换算成账单，因而更容易被批预算。它同时坐实了 [[从知识图谱到 Agent 编排]] 里"权威事实层"的位置：
> 图谱不是检索的替代品，是**减少检索次数**的前置条件。
>
> 需要打折：38 秒 vs 20 分钟是精选单例，且选的正是图谱最擅长的"哪张表被谁在用"类问题。
> 对"这段代码为什么这么写"一类问题，图谱未必有同等杠杆。

## 七、成本治理照搬了控制带的形状

可见性那一节的机制是：实时可见（status line）+ 分级软额度（共享池、50/80/100% 提醒、
经理快速审批升档）+ 自动反模式检测（16 种，各配金额影响与整改动作）。

> 综合：这是 [[控制带]] 在**成本**维度上的同构实现——确定性检测（花了多少、命中哪种反模式）
> 在前，分级处置（提醒 / 需审批 / 升档）在后，检测端不含模型判断。
> 两处差异值得记下：
> - **Uber 明确不设硬上限**（"to avoid imposing strict caps"）。硬闸会把成本风险变成交付风险，
>   而软额度把决策权留给最了解任务 ROI 的人。这与控制带"1σ 只记录"的设计动机相同：
>   **低强度信号不该触发行动，只该触发可见性。**
> - **反模式清单是可执行的知识资产**。16 条里被点名的四类（该用弱模型的跑在强模型上、
>   大 MCP 响应赖在上下文里逐轮计费、缓存过期后全价重建前缀、用户输入前先加载 10 万 token 指令）
>   全部是**可确定性检测**的——它们不需要判断"这个任务做得好不好"，只需要比对 trace 元数据。
>   这正是 [[Agent 全轨迹评测与审计]] 说的 trace 归因证据的用法。

## 八、一个未被原文承认的张力：可计价者被优化，不可计价者被牺牲

托管 agent 的指标是**结果计价**的——每合并 PR 成本、每次 review 成本、每条告警成本。
交互式 session 没有这样的分母：一次探索、一次读代码理解系统、一次最终没走通的尝试，
产出无法计价，但在同一套单位经济学仪表盘上只会显示为"贵"。

> 综合（本 wiki 的判断，原文未讨论）：这套度量体系有一个内建偏向——**它能精确地为可计价的工作
> 定价，因而优化压力会持续流向可计价的部分**。风险不是省错了钱，而是长期把工程师的探索性使用
> 挤向"看起来便宜"的行为（少读上下文、少开子 agent、更早收敛），而这类损失不会出现在任何一行指标上。
> 这与 [[生产力-体验悖论]] 记录的背离是同一类问题的成本侧版本：
> **活动量、实际速度、体验与价值可以各自朝不同方向走；现在要再加一个维度——单位成本。**
> 原文的软额度设计（不设硬闸、把 ROI 判断留给工程师）恰是对这个风险的部分对冲，
> 但它靠的是人的自觉，没有指标兜底。

## 九、对"生产级落地鸿沟"的意义

这是 [[agent-生产级落地的鸿沟]] 上一条**罕见的正向证据**：一家非 AI 实验室的大型工程组织，
公开报告了规模化生产使用（>70% PR 归因、3,600 skills、30K 次/日执行）。

> 综合：但它**印证**而非推翻该页的核心论点。清点 Uber 用到的东西——统一 harness 包装、
> MCP 网关、CLI 投影、code-mode skill、上下文图谱、真实工作 benchmark、五层度量、
> 反模式检测、额度分层——**没有任何一项依赖"模型更强"**。它们全部是 harness 层与组织层的工程。
> 这恰恰是该页反复论证的：跨过鸿沟靠的是工程栈，不是能力曲线。
> 换句话说，Uber 不是"鸿沟不存在"的证据，而是"鸿沟可以靠工程填平、代价是这么多工程"的证据。

## 十、可迁移到本仓库 / 小团队的部分

不是所有条目都需要 Uber 的规模。按投入排序：

| 杠杆 | 规模门槛 | 小团队可直接用吗 |
|---|---|---|
| 缓存 TTL 与 session 空闲习惯匹配 | 无 | 可以，纯配置 |
| 子 agent 默认弱模型 | 无 | 可以，纯配置 |
| reasoning effort / 压缩阈值默认值 | 无 | 可以，纯配置 |
| 工具 schema 瘦身（按需加载、CLI 投影） | 低 | 可以，见 [[Agent 工具上下文膨胀]] |
| code-mode 批处理常用工具链 | 中 | 值得，对"多轮轮询"型工具收益最大 |
| 用真实工作造 benchmark + 双轴记分卡 | 中 | 值得，是 [[Evals]] 的落地形态 |
| 驱动因素分解 | 中（需要成本数据管道） | 有账单明细即可做 |
| 上下文图谱 | 高 | 大代码库才回本；小库靠文件组织与 `CLAUDE.md` 即可 |
| 托管 agent 队伍 + 结果计价 | 高 | 需要先有稳定的 agent 产出单位 |
