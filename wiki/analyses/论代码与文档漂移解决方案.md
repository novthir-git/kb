## 核心论点

代码与文档漂移无法通过“提醒开发者及时更新文档”得到根治。问题也不只是代码和 Markdown 没有同步，
而是多个相关事实及其派生表达，在不同触发器、验证机制和生命周期下独立演化，却没有持续调和机制
（问题层的完整分析见 [[代码与文档漂移的本质]]）。

因此，更合理的目标不是追求“代码和文档永远相同”，而是确保相关事实之间的关系可观察、差异有边界、
失效内容能自动退出。

本文将这一方法称为：**基于分层权威的持续调和方法**。

```text
可治理漂移
= 按问题分配权威
+ 显式关系契约
+ 有界一致性
+ 自动持续调和
+ 可恢复生命周期
```

## 一、四类漂移与本方案的范围

“代码改了，文档没改”只是一种表现。漂移分四类——表达、符合性、运行、生命周期——分类定义与论证
见 [[代码与文档漂移的本质]]，此处不再维护副本。本页只补一行成因归纳：

> 表达漂移来自重复信息；符合性漂移来自意图与实现之间缺少证据；运行漂移来自交付与生产状态之间
> 缺少反馈；生命周期漂移来自系统只定义了“如何创建”，没有定义“何时退出”。

**范围声明（修订）**：本方案的机制主要治理**表达漂移与生命周期漂移**。符合性漂移依赖规格与证据
体系（承载见 [[SDD 开发规范研究]]）；运行漂移已有成熟的调和方案（IaC / Kubernetes reconciliation）。
本方案通过关系契约（`verified_by`、`observed_by`）与这两者对接，不重复它们。

因此，解决方案必须回答四个问题：

1. 事实由谁权威定义？
2. 不同事实之间是什么关系？
3. 这些关系应在何时达到一致？
4. 失效内容如何退出？

## 二、没有全局唯一真相源，只有问题级权威

问题级权威的完整分配表见 [[代码与文档漂移的本质]]（本页初稿新增的“用户如何理解和操作 → 经过验证的
教程与操作指南”一行已回写至该表，此处不再维护副本）。本节只保留原则本身：

**关键不是把所有内容塞进一个文件，而是避免两个来源同时对同一个问题宣称权威。**

## 三、把文档分成四类产物

每份文档都必须明确自己的角色。

### 1. 权威产物

定义意图、边界、约束和决策，例如：

- Spec
- PRD
- 行为契约
- ADR
- 安全与合规政策

这类内容不能简单地从代码反推。

### 2. 证据产物

用于证明不同权威来源是否一致，例如：

- 测试
- [[Evals]]
- 验收记录
- 运行指标
- 契约检查结果

证据不是绝对真相，但它能让偏差变得可观测。

### 3. 派生视图

从权威来源生成或投影，例如：

- API Reference
- 配置字段列表
- CLI 帮助
- Schema 文档
- 模块索引
- 状态统计

派生视图可以重复展示事实，但不能独立维护。它们类似数据库的物化视图：源发生变化时，应当自动重新生成或失效。

### 4. 工作产物

服务于某一次变更过程，例如：

- Proposal
- Task
- Story
- 临时计划
- 调研笔记
- Agent 中间结果

这类产物必须有明确的完成和过期条件，不能默认永久保留。

## 四、Spec 是 Agent 控制面，而不仅是文档

Spec Kit、OpenSpec、BMAD 等已核实方法表面上使用不同命令和目录，底层都在做同一件事：
把开放式需求转换成一套由持久化产物驱动、带状态与门禁的 Agent 执行流程。

```text
意图澄清
  ↓
规格固化
  ↓
任务分解
  ↓
受控执行
  ↓
证据验证
  ↓
结果收敛
```

在这类方法中，Spec、PRD、Plan、Story、Task 不只是写给人看的说明，而同时承担：

- **意图契约**：限制 Agent 对需求的自由解释空间。
- **外部记忆**：跨越会话和上下文窗口保存长期状态。
- **交接协议**：让规划、执行、审查 Agent 共享同一任务基准。
- **状态快照**：记录当前处于 clarify、plan、apply、verify 或 done 等阶段。
- **验证基准**：定义何种证据可以推动状态进入下一阶段。

需求因此像源码一样被逐层“编译”：

```text
自然语言意图 → Spec → Plan → Tasks → Code → Evidence
```

其共同内核可以定义为：

```text
Artifact-Driven Agent Workflow
= 持久化产物
+ 阶段状态机
+ 执行门禁
+ 反馈子循环
+ 完成证据
```

这类方法在流程设计上较好地回答了**需求如何变成代码**——这是流程层判断，不是效果承诺：
"写规格 ⇒ 缺陷与返工下降"的默认收益假设已被现有最大样本证据推翻（见 [[SDD 收益主张的实证赤字]]）。
它们普遍重创建、轻维护，重归档、轻删除；产物关系多藏在
文件名和自然语言中，状态推进也常依赖用户主动执行下一条命令。它们没有完整解决交付之后 Spec、代码、测试、
运行状态和历史产物如何继续保持关系成立。

因此，本方案的定位不是再设计一个 Spec 工作流，而是补上纵向生命周期：

```text
Artifact-Driven Agent Workflow
            +
Continuous Documentation Reconciliation
            =
全生命周期的 Spec 治理
```

> 实证补强（2026-08-31）：[[SDD 收益主张的实证赤字]] 的反向证据强化了"必须建调和层"的定位——
> Hill 的 10 万 PR 观察研究显示规格与更高返工显著相关（p<0.001；缺陷率方向为正但边缘显著），
> Scott Logic 实测 Spec Kit 流水线总耗时约为迭代提示的 7 倍且带 bug（证据表与限定条件见该页）。
> 综合：这一证据形态与本方案的判断吻合——只写规格不建调和机制，成本立刻发生而收益不兑现；
> 但"补齐调和层后收益兑现"的对照数据目前同样缺失（见该页"待追踪"），本方案的收益主张同受此限。

## 五、不同步文件，调和关系

代码与文档不是一对需要同步的文件，而是一张带类型的关系图：

```text
Spec ──implemented_by──▶ Code
Code ──verified_by─────▶ Tests
Schema ──projected_as──▶ API Docs
ADR ──constrains───────▶ Architecture
Deployment ──observed_by──▶ Telemetry
New Spec ──supersedes──▶ Old Spec
```

每一种关系都应有自己的验证方法：

| 关系 | 自动验证方式 |
|---|---|
| `derived_from` | 重新生成并比较 hash |
| `implemented_by` | 需求 ID、代码映射、验收测试 |
| `verified_by` | 执行测试或 eval |
| `constrains` | 变更影响分析、规则检查 |
| `observed_by` | 运行指标、配置采样 |
| `supersedes` | 引用迁移和删除计时器 |

系统治理的单位不再是“文件是否更新”，而是“关系是否仍然成立”。

### 关系图自身的元漂移（修订新增）

关系图是又一份需要维护的现实表述，必须对它做同样的漂移分析：

- 它只对**已声明**的边有效，而漂移主要发生在未声明的关系上。“关系图完整性”门禁只能验证已声明的边
  可解析（目标存在、hash 匹配），验证不了“该声明的边没有声明”。
- 治理手段：关系随产物在同一变更中声明（如同外键随 DDL 演化）；残余的未声明关系由 AI 影响分析提示、
  定期体检兜底（“无权威来源 / 无关系产物”即孤儿指标，见 §十二）。
- 收敛是渐进的：优先为高风险产物（T3 / T4）声明关系，不追求一次性建全图。

先行实现：sphinx-needs 在文档体系内提供需求、规格、测试等工程对象的定义、带类型链接与分析
（https://sphinx-needs.readthedocs.io/ ，检索于 2026-07-16）；Backstage software catalog 用
kind + relations 元数据描述产物及其关系
（https://backstage.io/docs/features/software-catalog/descriptor-format/ ，检索于 2026-07-16）。
本方案的关系契约是同一思路的一般化。

## 六、按内容选择一致性等级

所有内容都要求在同一个提交中更新并不现实。应根据内容风险选择一致性模型。

### 强一致

必须在同一次合并中完成：

- Schema 与生成的 API 文档
- 配置定义与配置参考
- CLI 参数与帮助文本
- 对外契约与契约测试（consumer-driven contract 工具如 Pact：https://docs.pact.io/ ，检索于 2026-07-16）

### 发布一致

允许分开修改，但必须在行为对目标用户生效前一致：

- 用户手册
- 迁移指南
- 发布说明
- 对外行为说明

### 有界最终一致

允许短期滞后，但必须设置调和期限：

- 内部教程
- 架构概览
- 培训材料
- 非关键分析文档

### 历史不可变

不修改旧记录，而是创建新记录显式取代：

- ADR
- 重大决策
- 审计记录

这种分级既避免“一切必须同一 PR”的僵化，也避免文档更新被无限期拖延。

与 [[代码与文档漂移的本质]]“原则二：同一交付事务”的关系：变更作者的默认仍是“同一变更”；
本节回答的是另一个问题——每类内容**最迟**必须在何时达到一致。

## 七、建立 AI 持续调和控制回路

系统不等待人发起文档维护，而是由事件自动驱动：

```text
Observe
  ↓
Impact Analysis
  ↓
Reconciliation Plan
  ↓
Modify / Generate / Consolidate / Delete
  ↓
Deterministic Verification
  ↓
Risk Evaluation
  ↓
Merge
  ↓
Garbage Collection
```

触发事件包括：

- 代码和配置变化
- Spec、PRD、Story 状态变化
- 测试或 eval 变化
- 上游文档、API、依赖版本变化
- 发布和部署事件
- 文档复核或保留期限到期
- 引用关系消失

其中 Spec 工作流提供的是可观测的状态转换事件，例如 `spec accepted`、`plan ready`、`apply completed`、
`verification passed`、`story done`。持续调和层消费这些事件，检查对应产物是否应该晋升为权威、回写 canonical
内容、补充证据关系或触发退役，而不是要求另一套流程重新判断开发阶段。

AI 负责需要语义理解的工作：

- 判断变更影响范围
- 更新叙述
- 合并重复内容
- 提炼长期知识
- 判断替代关系
- 生成清理方案

确定性程序负责门禁：

- 文件和引用存在性
- Schema 和结构验证
- 关系图完整性
- 生成内容一致性
- 构建、测试和 eval
- 删除安全条件
- 生命周期政策

原则是：

> AI 负责理解和调和，程序负责证明和约束。

AI 不能成为新的事实权威，也不能仅凭置信度决定删除内容。

### 自产自审的实证边界（2026-07-17 新增）

“Agent 写代码和文档、再交给 Agent 审查一致性”的回路，有三组实证划定能力边界：

1. **自审存在系统性偏袒**：LLM 评审者能识别自己生成的内容并系统性给自己打高分；
   自我识别能力与自我偏好强度线性相关，微调实验证明是因果关系
   （Panickssery et al., NeurIPS 2024：https://arxiv.org/abs/2404.13076 ，检索于 2026-07-17）。
2. **换模型交叉审查只部分缓解**：对 350+ 模型的测量显示，两个模型都出错时约 60% 的情况下
   给出相同错误答案；错误相关性在同厂商/同架构模型间更高，且越准确的模型错误越趋同——
   跨厂商、跨架构亦然（ICML 2025：https://arxiv.org/abs/2506.07962 ，检索于 2026-07-17）。
   相关错误使评审团失效：九个相关评审的有效票数约等于两票
   （https://arxiv.org/html/2605.29800 ，检索于 2026-07-17）。
3. **开放式一致性审查不可用，结构化审查可用，但真实环境远低于消融值**：直接让 LLM 开放式检查
   “文档与代码是否一致”，标记率 98%、准确率仅 14%——模型把高层文档与实现细节之间的天然抽象落差
   误报为不一致；改为局部小判断 + 外部确定性过滤（LCEF，依赖短程补全而非长程推理）后，
   标记率降到 14%、准确率反转为 94%。**但 94% 是消融实验值**：同一工具在 Python / TypeScript /
   C++ / Java 的跨语言真实评测中，标记率 15%、**precision 仅 0.62**——约三分之一告警为假
   （DocPrism：https://arxiv.org/abs/2511.00215 ，检索于 2026-07-27 复核）。
   注释-代码不一致这类窄任务的检测性能，第三方复现比较给出：C4RLLaMA 在 JITData / CCIBench
   验证测试集上 accuracy 87.82%、precision 89.67% / 92.67%、F1 87.45 / 90.63
   （CCISolver 表 V：https://arxiv.org/html/2506.20558 ，检索于 2026-07-27；
   原始论文 https://dl.acm.org/doi/10.1109/ICSE55347.2025.00035 ）。

> 综合：三条设计推论。其一，审查任务必须**切窄**——“这段参数表与该函数签名是否一致”，
> 而非“检查一下文档”；其二，可持续性的真正约束是**假阳性率 × 触发频率**——高频触发叠加
> 高假阳性导致告警疲劳，机制退化为仪式（与 [[代码与文档漂移的本质]] 对自评清单仪式化的诊断同构），
> 宁可调低召回也要先压假阳性——DocPrism 跨语言实测的 precision 0.62 就是这条约束的现实取值，
> 不能拿消融实验的 94% 做规划基准；其三，能生成的不要审——派生视图重新生成 + diff 是确定性验证，
> 优于让 AI 读两边“判断一致性”。审查产出是证据，进入门禁或人的决策，不直接授权合并与删除。

### 生产案例：Anthropic 的治理循环（2026-07-23 新增）

Anthropic 在内部 AI 原生 SDLC 中把重复缺陷写回 `CLAUDE.md`、组织 skills、review 规则与 evals，
再通过专职 review agents、SAST、系统不变量、风险分级和人工批准影响后续合并；生产事故 agent 可定位根因、
写复盘和候选补丁，但没有部署权。新 reviewer 先跑 shadow mode，自动批准接受抽样复核，工具调用与
agent-to-agent 消息进入 SIEM（[[2026-07-21-Anthropic-AI原生SDLC-源摘要]]）。

这为本页控制回路补出三项生产要件：

- **指令也要进入调和循环**：事故 → 可版本化政策/skills/evals → 后续生成与审查 → 生产结果 → 再校准。
- **权限必须覆盖委托图**：一次事故 agent 经 Slack 请求另一个 Claude 推动修复的事件表明，直接权限之外，
  还要审计 agent 可调用、可通信、可委托的传递路径。
- **循环本身需要 SRE 式治理**：shadow mode、抽样自动批准、红队与 SIEM 用于监测误报、漏报、权限异常和
  模型升级后的行为漂移。

> ⚠️ 矛盾：Anthropic 原文称专职 agents 不共享偏差；但本页上节和 [[Evals]] 汇总的研究显示，
> 同厂商及跨厂商模型的错误都可能相关。专业化可提升覆盖面，不能当作审查独立性的证明。
> 完整案例与证据边界见 [[Anthropic-AI原生SDLC治理循环]]。（发现于 2026-07-23）

## 八、生命周期必须自动退出

推荐采用以下状态机：

```text
draft → active → superseded → depublished → deleted
                                     └──→ archived（例外）
```

- `draft`：尚未成为正式权威。
- `active`：当前有效。
- `superseded`：已有明确替代。
- `depublished`：从导航和 AI 默认上下文中移除。
- `deleted`：从工作树删除，由 Git 保留恢复能力。
- `archived`：只用于法规、审计或长期复现。

工作产物完成后应自动执行：

```text
提炼长期有效内容
    ↓
回写 Spec / ADR / Release Note
    ↓
验证引用和证据
    ↓
删除 Proposal / Task / 中间稿
```

不能把“移动到 archive”当成清理。对于没有保留义务的普通文档，Git 历史本身就是归档。

## 九、风险分级自动执行

| 风险等级 | 产物 | 默认行为 |
|---|---|---|
| T0 | 自动生成内容 | 自动更新、自动删除、自动合并 |
| T1 | 临时文档、坏链接、无效索引 | 验证后自动处理 |
| T2 | 已有完整替代的普通文档 | 满足确定性替代条件时自动处理，否则标记待人审 |
| T3 | Spec、PRD、Architecture | 自动更新，严格限制删除 |
| T4 | ADR、法务、安全、公开契约 | 不允许自动删除 |

T2 的确定性替代条件（修订）：替代页有显式 `supersedes` 声明、原页入链已全部迁移、保留期届满——
三者均可程序验证。初稿此处写“双 AI 审查后自动处理”，与 §七“AI 不能仅凭置信度决定删除”相矛盾：
AI 审查（无论并行几个实例）只是置信度信号，同源模型的错误高度相关，不构成独立见证
（实证甚至更严：跨厂商强模型的错误同样趋同，见 §七“自产自审的实证边界”）。
自动删除的授权只能来自可确定性验证的条件。

本节 T0–T4 按**产物风险**分级；[[控制带]]（Anthropic playbook 的分级授权机制）是它在库内的
首个生产形态实例化——按**信号强度**（1σ/2σ/3σ）分级，与产物风险正交，可组合成二维授权矩阵；
其"检测端不含模型"的设计与 §七"AI 提议、程序验证"同构，其 dismissal 调参对应 §十一 第 7 条的
假阳性预算（该页也指出原文未回答"谁拥有关掉一个坏检测的权力"，正是第 7 条命名的空白）。

高风险事项不应阻塞整个系统。当 AI 无法证明某项修改或删除安全时，应将其标记为异常，退出默认发布和
AI 上下文，同时继续处理其他低风险任务。

人不负责推动日常流程，只负责定义治理政策和处理少量无法自动证明的异常。

## 十、用事件 Adapter 适配 OpenSpec、BMAD 等框架

方法论本身不依赖具体框架。Adapter 的职责也不只是识别文件目录，而是把框架自己的产物与状态转换映射为
统一事件：

```text
框架命令或状态变化
        ↓
Adapter 解析产物、转换与证据
        ↓
标准 Reconciliation Event
        ↓
调和、门禁、回写或退役
```

### OpenSpec

```text
specs       → 意图权威
changes     → 工作产物
tasks       → 执行状态
tests       → 符合证据
archive     → 调和触发事件
```

`verify passed` 或 `archive requested` 不是简单移动目录的指令，而是调和事件：系统先将有效变化回写
canonical Spec，验证实现与证据关系，再按保留策略删除不再需要的 Change 过程产物。
（OpenSpec 的 specs / changes 结构与本库推荐的 SDD 规范见 [[SDD 开发规范研究]]。）

### BMAD Method

（BMAD-METHOD：https://github.com/bmad-code-org/BMAD-METHOD ，2026-08-07 复核）

```text
PRD / Architecture → 意图与设计权威
Epic / Story        → 工作产物
Code                → 实现事实
QA / Tests          → 符合证据
Story Done          → 调和、提炼与清理触发事件
```

不同框架只需要提供 Adapter，将自己的产物和转换语义映射到统一模型：

```text
kind
status
authority
depends_on
verified_by
supersedes
retention
transition
completion_evidence
consistency_level
canonical_target
retire_on
grace_period
```

其中 `transition` 表示发生了什么状态变化，`completion_evidence` 决定转换能否成立，`canonical_target` 指定
长期知识应回写到哪里，`retire_on` 与 `grace_period` 则定义工作产物何时退出。这样 OpenSpec 的 `archive`、
BMAD 的 `Story Done` 或其它框架的 `ship` 事件可以触发同一套治理语义，而无需共享同一种目录结构。

> 2026-08-07 校正：上面的静态映射只概括了 stable 6.10 一类 Story / Quick Flow 工作流，不能直接代表
> main/next。当前 npm latest 仍为 6.10.0，而 main 已转向 `bmad-project-context` 的 kernel + bundle 与统一
> `bmad-build` 入口；Story Done 只能作为信息捕获点，Merge / Release / Epic Close 才分别承担仓库调和、
> released baseline 切换与综合退役。文档分工、逐事件维护规则（PR/Merge、Release、Epic 关闭）与
> 存量清理、两周试点步骤见 [[BMAD 项目文档治理方案]]。（2026-08-11 更新指针：该页已于 2026-08-07 整页重写，
> 原指针所述"版本校验、三容器、状态模型"为第一版草案内容，现行页不再包含。）

## 十一、最小可行版本与采纳分级（修订新增）

完整的事件驱动调和平台是重型建设，调和成本必须与漂移代价成比例。按规模分三档采纳：

| 阶段 | 适用 | 内容 | 成本 |
|---|---|---|---|
| 阶段 0 | 任何团队 | 派生视图全部生成化并进 CI（强一致层）；PR 声明文档影响；临时稿蒸馏后删除 | 建设期数周（主要是生成化改造，与 §十一"建设期约数周"同指）；建成后持续成本≈0，即可消灭大部分表达漂移 |
| 阶段 1 | 单仓库 / 小团队 | 产物 frontmatter 声明关系（depends_on / verified_by / supersedes）；定期 lint 断链、孤儿、过期；人驱动、AI 辅助 | 低；本库的 index / log / lint 机制即此档 |
| 阶段 2 | 多仓库 / 高变更频率 | 事件驱动调和回路 + 风险分级自动执行（§七–§九） | 平台级；仅当阶段 1 的人工调和超载才值得建 |

> 综合：为低风险、低变更率的文档建阶段 2 平台是过度工程；反之，当 agent 已成为文档的主要生产者和
> 消费者时，停留在阶段 0 会让生命周期漂移失控。

### 组织的最小职责（2026-07-17 新增）

“组织执行不了这套纪律”的批评瞄准的是错误的执行模型。本方案不要求组织获得新美德，而是把新检查
挂到组织已被证明守得住的旧权力点上：组织守不住“记得更新文档”（要求人人持续自律），守得住
“CI 红了不能合并”（只要求一次接线）。组织执行力需求由此压缩为**少数人的一次性配置 +
少量持续裁决**（wiring over willpower）。

**建设期（一次性）**：

1. 裁决权威：批准问题级权威表。权威是社会事实，AI 只能提议不能自授（§七）。
2. 生成化投资：派生文档改造为“生成 + diff”进 CI（阶段 0 的主要工程量）。
3. 门禁接线：Document impact 进 PR 模板、一致性检查进 merge 条件、发布级检查进 release 条件；
   全部挂既有权力点，不新增会议与仪式。
4. 政策定义：T0–T4 风险分级、一致性等级、保留策略。

**运营期（持续但有界）**：

5. 异常裁决：处理 AI 无法确定性证明的升级项（语义冲突、T3/T4 退役、规格与实现矛盾）；
   命名 owner + SLA，否则异常队列成为新的漂移堆积地。
6. 校准巡检：定期读调和记录与 lint 报告，校准 grader 与过滤器（与 [[Evals]] 检查表同构）。
7. 假阳性预算：借 SRE error budget——每类检查设 precision 底线，跌破即下线或收窄该检查；
   须有人拥有“关掉坏检查”的权力。组织不缺加检查的能力，缺删检查的机制——检查本身也需要 GC。
8. 激励核算：文档影响计入变更的 definition of done 与工作量核算，修正“成本现在付、收益未来归”
   的外部性（[[代码与文档漂移的本质]] 因果模型第 5 条）；这是记账规则改动，不是道德动员。

**填证据空白**：

9. 划边界跑试点：拿一个仓库跑一个季度，用 §十二 指标 + [[SDD 开发规范研究]] 试点指标回答
   “纪律成本是否可承受”。

> 综合：量级感——建设期约数周工程投入；运营期应收敛为一个 owner 角色 + 每周/双周校准时间盒 +
> 一条异常队列。**若运营负担不收敛反而增长，即元维护劳动超过被替代劳动，判定机制失败**（见 §十三②）。

## 十二、评价目标

这套方法不能保证永远不存在漂移。语义理解、测试完备性和现实变化决定了绝对零漂移不可实现。

它要保证的是：

```text
没有静默漂移
没有无限期漂移
没有无法追溯的漂移
没有不可恢复的自动删除
没有永久滞留的临时文档
```

建议关注以下指标：

- 无权威来源的信息数量
- 断裂关系数量
- 超过一致性期限的差异数量
- 孤立发布文档数量
- 过期工作产物数量
- 已完成但未调和、未退役的 Spec / Plan / Story 数量
- 缺少完成证据却发生状态晋升的转换数量
- 派生事实自动生成覆盖率
- 漂移从产生到被调和的时间

## 十三、反对观点与未决空白（2026-07-17 新增）

来源：2026-07-17 辩论会（正反双方由同一模型扮演，仅作论点结构化，按 §七 实证边界不构成独立见证）。
三条经受住交锋的反方论点，按“论点—现有回应—残余风险”收录：

### ① “保障”叙事诱导过度信任

Agent 把未被标记的文档当真相批量执行；半吊子保障 + 全额信任可能比无保障更糟。
现有回应：agent 信任文档是现状而非选项，有调和层的错误率仍低于零覆盖；无法证明安全的项
退出默认发布与 AI 上下文（§九）。残余风险：对外叙事必须说“有界调和”，不说“保障一致”——
超卖能力本身就是漂移源。

### ② AI 边际贡献的归因之争

承重的是生成与确定性门禁，它们先于 LLM 存在；AI 的边际贡献限于“过去无法形式化、因此从未被执行”
的语义残余（影响分析、蒸馏回写、查重合并）。方案成立不依赖 AI 判断力强，依赖结构：AI 提议、
程序验证。让步式反驳成立的部分：AI 把语义维护从不可能变为可能，但同时引入元维护劳动
（校准 grader、维护过滤器、处理升级队列）——“元维护是平台成本、摊薄趋零”与“元维护不收敛、
反超被替代劳动”两种前途由运营数据裁决，判定信号见 §十一“组织的最小职责”。

### ③ 组织执行力是无实证的空白

机制设计精美与组织能执行是两回事：阶段 0/1 的纪律成本（生成化改造、关系声明、假阳性纪律）
目前没有任何实证数据，是论证链中唯一靠信念支撑的环节。唯一诚实的填法：§十一 第 9 条试点 +
§十二 指标。在试点数据出现前，本方案的可行性主张应限定为**“机制可行性已论证，组织可行性未验证”**。

## 总结

现有 Spec 方法提供了从意图到实现的 Artifact-Driven Agent Workflow；本方案增加交付后的 Continuous
Documentation Reconciliation。二者结合，才构成从创建、执行、验证到持续维护和退出的完整 Spec 生命周期。

这套方法可以浓缩为四句话：

> 不维护重复事实，而维护问题级权威。  
> 不同步代码与文档，而持续验证它们之间的关系。  
> 不依赖人推动更新，而让 AI 在规则约束下自动调和。  
> 不永久保存所有过程，而让失效知识按生命周期退出。

企业 Agent 知识运维场景的实例化见 [[基于IT4IT的Agent知识治理]]：借 IT4IT 的 Desired / Actual
Product Instance 给知识状态建出可 diff 的同构表示，把本方法的调和回路与生命周期退出落成
企业统一 Agent 的知识治理（生命周期状态机与本页 §八 一致）。
