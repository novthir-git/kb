# AI 编码技术债的三层治理：意图、证据与责任

## 核心判断

AI 没有消灭软件工程的苦工，而是把苦工从**生成代码**迁移到**验证代码、维护系统理解和保存设计意图**。
Sonar 的调查把前一段称为 “great toil shift”：53% 的受访开发者报告 AI 会产生看似正确却不可靠的代码，
而频繁使用者的 toil 更多落在技术债管理和改写 AI 代码上。该数字来自自报调查，不等于 53% 的 AI 代码有缺陷，
但足以说明验证吞吐已成为新的瓶颈。

综合：个人或团队最小可行的治理模型不是把 Automated、Assistance、Control 当成三种等价工具，而是建立三层
不可互相替代的责任链：

```text
意图层（Intent）       人决定要什么、为何这样做、哪些边界不能破
        ↓
证据层（Evidence）     确定性门禁证明底线；AI review 提供概率型补充
        ↓
责任层（Accountability）人按风险批准、解释、处置异常，并把事故回灌规则
        └──────────────────────────────↺
```

这与 [[Specification-Driven Development]] 的意图接口、[[Evals]] 的“评分是证据而非裁决”、
[[Anthropic-AI原生SDLC治理循环]] 的风险分级与事故回灌，以及 [[论代码与文档漂移解决方案]] 的持续调和同构。

## 为什么不能只治理“代码债”

Margaret-Anne Storey 在 ACM Queue 提出三类相互强化的债：

| 债务 | 存在位置 | 典型症状 | 主要偿还方式 |
|---|---|---|---|
| Technical debt | 代码与结构 | 变更昂贵、重复、复杂、脆弱 | 测试、重构、静态分析、架构治理 |
| Cognitive debt | 团队的分布式理解 | 改动结果出乎预期、入职慢、bus factor 低 | walkthrough、pairing、teach-back、复盘、知识转移 |
| Intent debt | 规格、约束、理由等非代码制品 | 代码能跑但偏离目标；agent 反复澄清或“做对了错误的事” | intent-first workflow、ADR、BDD/验收标准、领域模型、活规格 |

AI 可能用自动重构和测试降低部分技术债，同时更快累积后两种债：代码生成速度超过团队形成心智模型和记录理由的
速度。于是“代码质量绿灯”仍不足以证明系统健康——测试可以通过，产品行为仍可能偏离真实意图。

技术债一行的偿还方式（测试、重构、静态分析）还有一个 agent 特有的问题：它们在 agent 吞吐下**不会自然发生**。
Agent 会复制仓库里现成的坏模式，却很少主动发起重构，见 [[Agent 不会自发偿还结构债]]。

> 综合：认知债不是多写 AI 文档就能还清。自动生成解释可能制造“已经理解”的外观，反而遮蔽理解缺口。
> 团队至少要保留让人复述不变量、失败模式和架构理由的真实摩擦。

## 两篇论文的关系：一篇解释风险，一篇给出工作法

Storey 的《From Technical Debt to Cognitive and Intent Debt》回答的是 **“为什么代码质量绿灯仍可能掩盖系统
腐化”**：AI 加快实现后，团队理解与设计理由可能跟不上，形成 cognitive debt 与 intent debt。它是概念框架，
不是验证三类债规模或治理效果的实证研究。

Bridgeford 等的《Twelve quick tips for AI-assisted coding in science》回答的是 **“个人如何组织一次 AI 辅助编码”**：
先补背景知识与定义问题，再选择交互方式、拆计划、管理上下文；用测试约束并验证 AI，持续监控、审查、增量重构
和记录文档。它是 PLOS Computational Biology 同行评审的 Education 文章，基于作者经验与文献综合，也不是干预试验。
（版本说明：其预印本为 arXiv 2510.22254《Ten Simple Rules…》，即用户草稿所引论文——同一工作的先后两版，
不是两篇独立文献；见 [[2026-08-07-AI编码技术债三层治理-用户研究草稿-源摘要]] 的核验行。）

综合：十二条建议可落入本页三层，但这不是论文原文提出的分类：

| 治理层 | 对应建议 | 作用 |
|---|---|---|
| 意图 | 背景知识、问题定义、计划拆分、上下文管理、测试规格、文档 | 让目标、约束与理由先于实现并可追溯 |
| 证据 | 核验 AI 生成的测试、用测试约束代码、扩展覆盖、监控进度、审查和小步重构 | 防止 AI 同时生成代码与“证明自己正确”的假证据 |
| 责任 | 选择交互模式、判断何时重启、批判性 review、决定是否发布 | 保留人对风险、停止条件和最终合入的判断权 |

## 研究并不一致：效果取决于任务和测量层

[[2026-08-07-AI编码治理高质量证据包-源摘要]] 汇总了随机试验、生产遥测、维护负担与安全研究。关键结论不是
选一个“最权威数字”，而是识别它们各自回答的问题：

| 场景 | 观察结果 | 证据边界 |
|---|---|---|
| 三家企业、4,867 人的随机现场试验 | 完成任务 / PR 数提高 26.08%，经验较少者收益更大 | 主要是活动产出，不是长期维护质量 |
| Google 96 人、单个复杂任务的 RCT | 完成时间约缩短 21% | 单企业、单任务，未评估代码质量 |
| METR 16 名资深维护者、246 个成熟仓库任务的 RCT | 允许 AI 后实际慢 19%，参与者却仍感觉快 20% | 高上下文成熟仓库；不能外推到新手和绿地项目 |
| 超 10 万 GitHub 开发者的事件研究 | commits / LOC 大增，但到 projects、releases、用户采用明显衰减 | 大规模观察证据，不是随机试验 |
| 两项安全用户研究 | 一项发现多数任务更不安全且信心更高；另一项未发现严重缺陷显著上升 | 任务、模型、界面与被试不同，安全效果尚无统一结论 |

> ⚠️ 矛盾：企业 RCT 的短期加速与 METR 的成熟仓库减速同时成立；两项安全研究也得出不同结果。
> 因此不能说“AI 必然提效”或“AI 必然降低安全性”。更合理的调节变量是任务成熟度、隐性上下文、开发者经验、
> 模型 / 界面，以及测量停在代码、PR、release 还是生产价值。（发现于 2026-08-07）

## 第一层：意图前置，但不要迷信提示词

### 使用当前工具真正读取的文件

- 跨 agent 的项目约定：`AGENTS.md`。
- Claude Code：`CLAUDE.md`，可导入分拆的领域、测试和工作流文件；自 v2.1.277（2026-09-18）起，项目中没有
  `CLAUDE.md` 时改读 `AGENTS.md`（Bedrock / Vertex / Foundry 上暂不支持）——`AGENTS.md` 作为跨工具入口的地位
  因此更强。
- Cursor：`.cursor/rules/*.mdc`；根目录 `.cursorrules` 已是 legacy。
- `.claudeprotocol` 不是已核验的 Claude Code 官方约定，不应写进模板。

规则文件应该承载**项目特定、可执行、会影响决策**的内容，而不是把 DDD、SOLID 全文塞进上下文。建议最小结构：

```markdown
# 领域与边界
- 权威领域词汇及数据所有者
- 不允许跨越的模块/租户/权限边界

# 变更协议
- 先读取哪些 spec / ADR / 接口契约
- 允许修改的范围；范围外先报告
- 先给验收标准和测试计划，再实现

# 验证协议
- 必须运行的 test / typecheck / lint / security 命令
- 不得删除、弱化或改写失败测试来“证明成功”
- 输出实际命令、结果、未验证项与风险
```

**规则文件的效果有了第一批测量（2026-09-23 补）**，结论与上面的"只写项目特定内容"一致，但对"写了就有益"泼了冷水：

- Gloaguen 等（ETH，arXiv 2602.11988v2）在 Claude Code、Codex（两个模型）、Qwen Code 共 4 个 agent–模型配置上测试：LLM 生成的上下文
  文件使解决率平均变化 −0.5%（SWE-bench）和 −2%（自建 CTXbench），均不显著（p=87%、37%）；步数增加、成本平均上升
  20% 和 23%（p<0.001）；
  开发者手写的文件平均提升 2.4%（p=21%，不显著），且对 Claude Code 没有提升。文件里的指令**会被很好地遵循**——
  这正是成本上升的原因（更多探索、测试与推理）；而模型厂商推荐的**仓库概览没有帮助**。作者结论：上下文文件适合
  写非标准的编码约定，任何"提升表现"的尝试都应先评测再部署。
- Lulla 等（arXiv 2601.20404，5 页短文）在 Codex 上用 10 个仓库、124 个 PR 对比有无根目录 `AGENTS.md`：中位运行时间
  −28.64%、输出 token −16.58%，任务完成行为相当；未评估正确性。

> ⚠️ 矛盾：Lulla 等 2601.20404 称根目录 `AGENTS.md` 与更短运行时间、更少输出 token 相关，但 Gloaguen 等 2602.11988 称
> 上下文文件使推理成本平均增加 20% 以上且不提升成功率。可能的差异来源：前者只用 Codex、只挑小 PR、只测效率；
> 后者跨多个 agent 与模型并测了成功率。（发现于 2026-09-23）

另有两篇单作者预印本补了两个维度：

- McMillan（arXiv 2605.10039，2026-05）在 1,650 个 Claude Code 会话上做析因实验，操纵文件大小（25 / 100 / 250 / 500 行）、
  指令位置、文件架构、相邻文件冲突四个变量：**四者对指令遵循都没有可检出的影响**（大小与冲突两项有贝叶斯因子
  支持"无效应"）；影响最大的是会话内的长度——每多生成一个函数，遵循几率约降 5.6%。测的遵循对象是一个简单标注。
- Khatri（arXiv 2607.27250，2026-07）在 Claude Code 与 Codex、3 个真实仓库 17 个任务上做消融：上下文注入策略对
  正确率没有可测影响（等价检验界定在 10–15 个百分点内）；失败来自实现能力（功能设计、模式选择、接线），不是缺少
  上下文文件能提供的仓库知识。

> ⚠️ 矛盾：Claude Code 官方最佳实践称 `CLAUDE.md` 膨胀会导致 Claude 忽略其中的指令，但 McMillan 2605.10039 在
> 25–500 行范围内未测到文件大小对指令遵循的影响（贝叶斯因子支持无效应）。差异可能来自遵循对象（后者只测一个简单
> 标注）与更长文件未覆盖。（发现于 2026-09-23）

> 综合：现有测量都不支持"规则文件越详尽越好"，也不支持"写得长 agent 就不听"。能从代码推断的内容（目录结构、
> 组件清单）写进常驻文件主要是**成本**问题；推断不出的约定才值得写——这与 Claude Code 官方的修剪判据
> "删掉这一行会不会出错"一致。

规则只能提高遵循概率，不能保证“不合规代码不被输出”。真正的禁止条件必须落到权限、沙箱和 CI 门禁。
Matt Pocock 的 `/to-spec` 可把已讨论的决策综合为 spec，并要求结合领域词汇、ADR 与测试 seam；它是意图外化工具，
不是自动证明实现正确的控制器。

## 第二层：机器卡点要区分确定性与概率性

### 可作为硬门禁的证据

1. 编译、类型检查、lint 和格式检查；
2. 单元、集成、契约与端到端测试，重点覆盖变更行为和失败路径；
3. SAST、依赖漏洞、secret、license 与 IaC 扫描；
4. SonarQube 等静态分析的 new-code quality gate；
5. 变更范围、迁移兼容、生成物一致性和可回滚性检查。

Sonar way 的可复用默认线是：新代码不引入 issue、全部新 Security Hotspots 经人工复核、新代码覆盖率至少 80%、
新代码重复率不高于 3%。这些是起点，不是跨语言、跨系统的自然定律。

原草稿的“圈复杂度 >15”混淆了两个概念。15 通常是多数语言**单函数 Cognitive Complexity**规则的默认值；
C、C++、Objective-C 常用 25。不要对代码库总复杂度设置一个会随规模单调增长的硬阈值，应对新代码启用单函数
规则，并按语言、风险和现有基线校准。

### AI review 是辅助证据，不是独立裁决

CodeRabbit 等工具可以在配置 `Request Changes` 后阻止合并，也能用自然语言定义 pre-merge checks；但其判断仍是
概率型的，不能替代编译器、测试、静态分析或 owner 的高风险批准。更稳妥的证据顺序是：

```text
确定性失败 → 直接阻断
概率型高风险信号 → 请求修改或升级人工
全部通过 → 仍按代码路径和影响面决定是否需要人工批准
```

`/improve-codebase-architecture` 也应放在这一层的“发现”侧：它扫描热点并输出重构候选，之后由人选择再进入设计；
它不会替团队自动完成架构判断。

Anthropic 的 AI-native SDLC playbook 把本层的一条底线机制化了：修复任务期间用 hook 阻断 agent 编辑
测试文件（"an agent fixing code must not be able to weaken the check on that code"），先提交失败测试、
再在不能改测试的前提下修复——即证据层“防止 AI 同时生成代码与‘证明自己正确’的假证据”与意图层
“不得删除、弱化或改写失败测试”两条规则，从建议性文本升级为确定性卡点
（[[2026-08-21-Anthropic-AI原生SDLC-playbook-源摘要]]）。

### 门禁在 agent 面前的两种失效（2026-09-23 补）

Böckeler 的可维护性 sensor 实验（[[2026-05-27-Boeckeler-可维护性传感器-源摘要]]）暴露了确定性门禁面对 agent 时的
两种特有失效：

1. **阈值会被当成优化目标。**允许 agent 在"认为重构不必要"时略微上调阈值后，圈复杂度成了 agent 唯一频繁
   上调阈值的规则类别，而作者事后发现这条规则恰好没配修正指引。对策：规则消息改写成自纠正指引；上调可以有，但要可见、不能永久豁免，恶化时规则仍会触发。
2. **覆盖率不是测试质量。**AI 写的测试里，一个语句覆盖 100% 的文件没有任何单元测试，变异测试报出 13 个存活
   变异体——覆盖来自一个断言稀疏的大验收测试。
   > 综合：上文 Sonar way 的"新代码覆盖率至少 80%"在这种情况下可以被满足而不提供保护。测试也由 AI 生成时，
   > 覆盖率门禁要配变异测试（可按变更增量运行以控制成本），否则就是本层要防止的"证明自己正确的假证据"的
   > 另一种形态。

同一实验还划出了确定性门禁的**适用边界**：它在文件与函数层面可靠，跨文件的模块化与耦合问题则要靠推理型评审，
而推理型评审非确定、值得多跑（Böckeler 的术语是 computational vs inferential sensors，见 [[Harness Engineering]]）。
综合：这与本页"确定性门禁 vs 概率型 AI review"的分层同向，但补了一条——在跨文件模块化这类问题上，推理型评审
不只是"补充"，而是主要手段；它仍非确定，所以结论只能作候选、由人裁决。

## 第三层：人工控制不是逐行重写，而是保留判断权

“AI 代码第一责任人”容易把治理误导为来源标签。更准确的制度是：**任何合入代码都必须有明确的人类 owner，
无论最初由人还是 AI 生成**。owner 不必机械地给每个函数做提炼，但必须能回答：

- 这次变更满足哪条用户意图和验收标准？
- 关键不变量、权限边界和失败模式是什么？
- 哪些证据已运行，哪些仍未验证？
- 出错时如何发现、回滚和追责？
- 这段实现为何符合当前架构；若偏离，理由记录在哪里？

建议按风险分层，而不是所有 PR 一刀切：

| 风险 | 典型变更 | 合入策略 |
|---|---|---|
| 低 | 文案、局部 UI、无状态样板代码 | 确定性门禁通过后可自动合入或抽样复核 |
| 中 | 常规业务逻辑、数据读取、内部接口 | 一名了解领域的 reviewer；检查验收标准与回滚 |
| 高 | 身份权限、支付、PII、加密、原始查询、生产 IaC、不可逆迁移 | senior owner 强制批准；威胁模型、回滚演练和必要的双人复核 |

如果 reviewer 无法解释核心逻辑，应拒绝合入；但补救方式不只有“人工重写”，也可以缩小 diff、补充规格与测试、
要求 agent 解释并由人 teach-back，或回退后重新实现。控制目标是恢复理解和可证明性，不是保存手工编码仪式。

## 把事故变成下一轮约束

三层治理只有形成反馈循环才会复利：

1. 生产事故、回滚、审查漏检或重复返工被归因到具体失败模式；
2. 能确定表达的，写成测试、静态规则、权限或 CI 门禁；
3. 需要语境判断的，写成 spec、ADR、review checklist 或 eval；
4. 新 reviewer / agent 先跑 shadow mode，用误报、漏报和人工覆盖率校准；
5. 只有证据稳定后，才扩大自动批准的文件范围与风险等级。

这与 [[Anthropic-AI原生SDLC治理循环]] 已公开的事故回灌、shadow mode 和按风险逐步放权一致。重点不是建立一次性的
“AI 代码规范”，而是让失败持续改变下一轮生成、验证和批准方式。

## 最小实操文档

个人项目只需维护三页活文档，避免治理本身变成文档债：

1. `INTENT.md`：目标、非目标、领域词汇、架构不变量、高风险路径、关键 ADR 链接；
2. `VERIFICATION.md`：本地与 CI 必跑命令、quality gate、测试分层、证据输出格式；
3. `OWNERSHIP.md`：风险分类、谁能批准什么、升级条件、回滚与事故回灌流程。

Agent 入口文件只引用这三页并给出执行顺序，不复制全文。否则相同规则散落在 `AGENTS.md`、`CLAUDE.md`、
`.cursor/rules` 和 CI 配置中，会重新制造 [[代码与文档漂移的本质|表达漂移]]。

## 高质量实践资料的采用顺序

不要从某篇博客复制一套阈值。更稳妥的顺序是：

1. **NIST SSDF 1.1** 定安全 SDLC 底线：组织准备、软件保护、安全生产、漏洞响应；它与代码由谁生成无关。
2. **DORA 2025 AI Capabilities Model** 检查组织是否具备小批量、强版本控制、内部平台、可访问数据和清晰 AI
   立场。DORA 将 AI 视为系统放大器，而不是脱离交付系统的单点工具。
3. **OpenSSF AI Code Assistant Instructions Guide** 把输入校验、鉴权、secret、依赖与 IaC 等安全约束写入
   agent 指令，但仍保留 review、测试、静态分析与版本控制。
4. **工具官方 Responsible Use** 定义能力边界。例如 GitHub 明确 Copilot review 可能漏报或产生错误，只提交
   Comment，不满足 required approval，也不会自行阻止合并。
5. **PLOS 十二条建议与 Anthropic / Claude Code 团队案例** 用于设计具体工作流；前者是同行评审实践文章，
   后者是公司自述案例，均需用本地缺陷、返工和交付指标验证。

## 应跟踪的结果指标

不要用生成代码量或 AI PR 数量证明治理有效。更接近结果的指标是：

- 新代码逃逸缺陷率、变更失败率、回滚率和平均恢复时间；
- review lead time、人工升级率、AI review 误报 / 漏报率；
- 同一失败模式的复发率、AI 产出返工时间占比；
- 从代码 / commit → PR → project → release → 用户采用的逐层转化率，避免把上游活动量当成价值；
- 核心维护者与外围贡献者各自的产出、review 与 rework 变化，识别苦工是否只被转移；
- 感知节省时间与实际完成时间的差距，防止“感觉更快”替代真实测量；
- onboarding 到独立改动的时间、关键知识集中度；
- spec / ADR / 验收标准与生产行为的漂移事件数；
- 工程师心流、认知负荷和控制感，关联 [[生产力-体验悖论]]。

这组指标同时回应 [[agent-生产级落地的鸿沟]]"待追踪"里「生产级落地的可量化指标是什么」的悬而未决问题
——本页是编码场景下的成型答案；跨场景的落地节奏证据与"分层放权、shadow mode、事故回灌"的同一治理
循环见该页证据点表。

[[2026-08-21-Anthropic-AI原生SDLC-playbook-源摘要|Anthropic 的 AI-native SDLC playbook]] 为六阶段的
每个 play 都给出 leading / lagging indicator，可作本节按三层挑选指标时的框架补充；但其全文零实测数据，
是度量框架而非效果证据，采用前仍需用本地缺陷、返工与交付基线验证。

## 证据边界

- Sonar 是厂商主导的自报调查，能证明开发者感知与 toil 迁移，不能直接推出真实缺陷率。
- Storey 的三债模型是 ACM Queue 概念文章，解释力强，但认知债和意图债的量化方法仍在形成。
- 《Twelve quick tips》是面向科学软件的 PLOS 同行评审实践指南，不能直接外推为所有企业 SDLC 的效果证明。
- Cui 与 Google 的 RCT 支持特定企业任务的短期收益；METR 的 RCT 显示成熟仓库中的反向效果。样本、任务和
  工具不同，不应做简单平均。
- NBER 与 Xu 等研究把观察窗口延伸到项目、release、维护者 review 和返工，但属于观察 / 准实验设计，仍有
  选择偏差和处理组识别边界。
- Perry 与 Sandoval 的安全结果互相约束：现有证据支持“必须独立验证安全”，不支持单向的普遍结论。
- NIST SSDF 是权威安全开发基线，但不是 AI 代码专用效果研究；OpenSSF 指南也明确属于专家建议。
- Janea、Medium 和开源 skills 是实践线索，不是独立对照研究；其阈值与流程必须在本地基线上验证。

因此，目前最稳妥的结论不是“AI 代码必然制造更多技术债”，而是：**AI 往往先放大局部生成与活动吞吐，是否
转化为更快、更安全、更可维护的软件取决于任务上下文和交付系统。当生成吞吐超过验证、理解和意图维护吞吐时，
债务会从可见代码层迁移到更难察觉的认知与意图层；治理必须同时约束三层。**
