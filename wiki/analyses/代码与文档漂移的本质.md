# 代码与文档漂移的本质

> v2（2026-07-16）：经两轮评审重写。v1 只处理“代码—文档”一种漂移；本版扩展为四类漂移的统一模型，
> 并修正三处：测试由“裁判”降为“证据”、“同一变更”放宽为“同一交付事务”、“完成后归档”改为“蒸馏后删除”。

## 核心命题

> 综合：漂移的一般定义——**多个相关事实及其派生表达，在不同的触发器、验证机制和生命周期下
> 独立演化，却没有持续调和机制。**

代码与文档之间的漂移是其中最常见的实例，“文档没有跟上”只是表象。它的具体因果机制是：
**同一事实被代码和文档重复表达，却依赖人在两条独立的修改路径之间手工同步；
同时，代码进入了交付闭环，文档没有。**

因此，漂移首先是信息与流程设计问题，其次才是个人执行问题。把它归因于“开发者不够自律”，
只会得到更多提醒和文档任务，不会消除漂移机制。

## 四类漂移

即使完全消除重复文档，漂移仍会以其他形态发生。按“什么与什么失同步”可分四类：

| 类型 | 含义 | 典型例子 | 可治理程度 |
|---|---|---|---|
| 表达漂移 | 同一事实存在多个独立维护的副本 | README 配置说明落后于代码 | 高：派生生成可基本消除 |
| 符合性漂移 | 实现偏离预期与意图 | bug、遗漏需求、测试迁就实现 | 低：只能持续取证，不能证明 |
| 运行漂移 | 生产状态偏离声明状态 | 手改线上配置、基础设施漂移 | 高：reconciliation loop 是成熟解 |
| 生命周期漂移 | 失效产物未退出，仍声称有效 | 过时设计文档、孤儿页、僵尸计划稿 | 中：需要 GC 机制与所有权 |

> 综合：四类的可治理程度悬殊，原因是**调和的前提是两侧有共同的形式表示**。
> 运行漂移可解，因为声明态与实际态同构、可 diff——Kubernetes controller 就是“持续把 current state
> 拉向 desired state”的调和循环（https://kubernetes.io/docs/concepts/architecture/controller/ ，
> 检索于 2026-07-16）。意图与实现之间没有这种同构，测试与 [[Evals|evals]] 只是有损的桥，
> 所以符合性漂移只能持续取证、不能一次性消除。反向应用：为难治理的漂移**人为建出**
> desired/actual 同构表示，即可把它改造成运行漂移——企业 Agent 知识治理借 IT4IT 的
> Desired/Actual Product Instance 实现这一转化（见 [[基于IT4IT的Agent知识治理]]）。

> 综合：表达漂移不止发生在一个代码库内部，也发生在**公共知识的传播链**上——
> [[AI方法论的去机制化失真]] 记录了同一标识符（某研究系统的名字）指向两个实质不同产物、
> 而权威性仍挂在原产物上的形态。差别在于治理手段失效：仓库内可用派生生成消除副本，
> 跨主体传播既没有共同事实源，也没有任何调和机制，只能靠**接收端的识别方法**兜底。

## 表达漂移为什么必然发生（因果模型）

### 1. 两种产物受到的约束不对称

代码不改，功能无法交付；代码改错，编译、测试、运行或用户会很快反馈。文档没有更新通常不影响
构建、合并和上线，错误可能几周或几个月后才被发现。

> 综合：当时间紧张时，优先修改代码不是意外，而是当前激励和门禁下的理性选择。

### 2. 人工文档常在复制高频变化的代码事实

接口字段、配置默认值、类与函数结构、模块依赖和具体执行流程，本来就存在于代码中。再手写一份，
等于维护两个可独立修改的数据库，却没有事务、约束和冲突检测。这正是 DRY 原则在文档维度的违例——
每一项知识在系统中应有单一、无歧义、权威的表示（Hunt & Thomas《The Pragmatic Programmer》）。

可以用一个非定量的因果模型概括：

`漂移风险 ∝ 重复信息量 × 变更频率 × 同步延迟 × 检测缺口`

注意该式混合了发生因素（前三项）与暴露因素（检测缺口）：检测不改变漂移是否发生，
只决定错误存活多久。按启发式使用，不作定量模型。

### 3. 代码有依赖图，文档缺少影响分析

开发者通常知道要修改哪些代码文件，却很难知道某次变更同时影响了哪些 README、用户手册、设计文档和
运维指南。文档越分散、内容越重复，这个问题越严重。

### 4. 实际设计会在编码中继续发生

开发前的文档表达的常是预期方案。真正实现时，团队才发现隐藏约束、性能问题、兼容性边界和新的取舍。
如果流程没有安排一个明确的“决策回写”时刻，代码会保留最终结果，文档则停在最初假设。

### 5. 成本和收益落在不同的人与时间点

更新文档的成本由当前开发者支付；它的价值通常由未来的维护者、新成员、运维人员或其他团队获得。如果交付流程
不把未来的理解和维护成本计入当前变更，文档债务就会累积。这一条在 agent 时代被部分削弱——
回写可以自动化，见下文“Agent 时代的漂移经济学”。

## “代码是唯一真相源”解决了什么

它取消了代码与描述性文档的形式冲突：无论实现发生什么，代码都自动成为当前答案。这对于低风险、容易重写、
行为可从测试和类型中明确推导的小工具，可以是合理选择。

但它没有解决“实现是否符合意图”，而是取消了判断这件事的独立尺度：

- bug 可能被重新定义为规格；
- 遗漏功能与有意的非目标无法区分；
- 历史偶然行为可能被当作兼容性承诺——即 Hyrum's Law：API 用户足够多时，无论契约承诺什么，
  系统的一切可观察行为都会被某人依赖（https://www.hyrumslaw.com ，检索于 2026-07-16）；
- 维护者只能通过代码考古推测“为什么”。

> 综合：代码唯一真相源可以消除“两份描述不一致”（表达漂移），但也可能把“实现偏离意图”
> （符合性漂移）变成不可观测。这是隐藏漂移，而不是消除漂移。

## SDD 与漂移的转化关系（2026-08-27 新增）

同一套分析可以施加到 [[Specification-Driven Development|SDD]] 上，结论与"代码唯一真相源"对称。

SDD 想治的正是符合性漂移：把意图写成规格，让规格成为可对照的一侧。但**规格是自然语言，
它与代码之间依然没有同构**。所以 SDD 并没有创造出上文所说的"共同形式表示"，
只是把对照的一侧从"人脑里的意图"挪到了"文档里的意图"。

这里可以直接延伸本页下文的那条修正——**测试只是证据，不是裁判**，因为测试本身是预期行为的
又一份表达，同样处在漂移机制之内。**同样的论证完整适用于规格**：规格也是意图的又一份表达，
规格也会漂，而且**规格漂移比代码漂移更隐蔽**——代码写错了编译器、测试和用户会反馈，
规格写错了没有任何东西会反馈（即本页因果模型第 1 条的"约束不对称"，在规格上表现得更极端）。

综合：由此得到三条推论：

1. **符合性漂移没有被消除，而是向上位移了一层。** 从"代码偏离意图"变成"规格偏离意图"，
   同时因为代码与规格一致，还获得了一层**虚假的合规证据**。由此可推演一种失败模式：
   写了完整规格、代码完全符合规格、最后东西是错的。此为本框架的推断，库内暂无直接匹配
   该模式的外部报告；最接近的 Scott Logic 实测（见 [[SDD 收益主张的实证赤字]]）是代码带
   明显 bug，属"实现不符规格"，并非同一形态。
2. **把规格写得更好并不解决这个问题**，因为好规格和坏规格都会漂。
   这与 Hill 的 10 万 PR 观察研究中"规格质量对返工零效应（p=0.997）"一致
   （见 [[SDD 收益主张的实证赤字]]）。
3. **SDD 把符合性漂移部分转化成了表达漂移与生命周期漂移**——规格是需要独立维护的新副本
   （表达漂移的新来源），过期规格比没有规格更糟因为它是误导性 context（生命周期漂移的新来源）。

> 综合：对照本页四类漂移表，这是一笔**可治理度上的置换**：被换出的符合性漂移可治理度**低**，
> 换入的表达漂移可治理度**高**、生命周期漂移为**中**——两者都高于符合性漂移，但并非同等好治。
> 所以 SDD 的价值主张应重述为**"把难治的漂移换成可治理度更高的漂移"**，
> 而不是"消除符合性漂移"。这个重述有两个后果：
> 其一，SDD 的成本核算必须算上新增两类漂移的治理开销；其二，**这笔交换只有在真的建了调和机制时
> 才划算**——生成化、同步门禁、回归测试、GC，即 [[论代码与文档漂移解决方案]] 描述的那一整套。
> 只写规格不建调和机制，等于付了转化的成本却没兑现转化的收益。

## 按问题分配权威——但裁判也在漂移

不必追求一个“全局唯一文件”，而应让每类产物只对一类问题权威：

| 问题 | 权威来源 |
|---|---|
| 系统当前实际如何实现 | 代码、配置和部署产物 |
| 系统应该满足什么 | 需求、行为契约或精简规格 |
| 实现是否符合预期 | 无单一裁判：测试、[[Evals|evals]]、CI 提供符合证据；生产数据提供最终验证 |
| 为什么选择这个方案 | ADR 与必要的代码注释（Nygard 2011 开创的决策记录传统，https://adr.github.io ，检索于 2026-07-16） |
| 生产环境实际发生了什么 | 日志、指标、追踪和业务数据 |
| 用户如何理解和操作 | 经过验证的教程与操作指南（示例可执行、随发布重验证） |

这不是相互竞争的多个真相源，因为它们回答的问题不同。[[SDD 开发规范研究]] 采用了同构的
“预期行为—实现状态—符合证据—决策历史”分层。

v2 修正：**测试只是证据，不是最终裁判。** 测试本身是预期行为的又一份表达，同样处在漂移机制之内：
覆盖不足、错误编码旧行为、实现出 bug 后反过来修改测试迁就实现（snapshot 测试尤甚）——
“bug 被重新定义为规格”同样会发生在测试层。正确的分工是：**规格定义预期，测试提供符合证据，
生产数据验证真实效果**；测试通过不等于符合意图。

## 防止漂移的设计原则

### 原则一：可以重复展示，不能独立维护第二事实源

- 低成本、无歧义可从代码推导的实现事实：由工具生成或不写（API 文档、Schema、类型、CLI 帮助、配置列表）。
- 推导成本高、或目标读者不应去读实现代码的内容（模块能力概览、API 使用示例、新成员入门路径、
  关键调用流程）：做成**派生视图**——可以重复展示，但标注 canonical source 与版本，不做第二份独立维护。
- 人工原创只保留无法从代码恢复的意图、边界、风险和决策理由；代码注释解释“为什么”和非显然约束。

### 原则二：同一交付事务

默认形态：必要的代码、测试和文档修改处在**同一个变更**中，而不是上线后再建“补文档”任务。
当发布工程迫使分离（分阶段发布、feature flag、多仓库、文档随功能上线才公开、API 与客户端独立版本）时，
放宽为：**同属一个交付事务，受同一发布门禁约束，在行为对目标用户生效前达到一致。**
事务化是带门禁的例外通道，不是延后的许可。

门禁应尽量自动化：示例可执行、生成物 CI 校验、契约测试、链接检查。自评清单
（是否改变对外行为？权威文档是否已同步？否则记录 `Document impact: none` 及理由）只兜底
无法自动判定的部分——否则清单会仪式化，整个机制退回“靠自律”，与本页开头的诊断自相矛盾。

### 原则三：按变化率匹配载体，临时产物蒸馏后删除

| 内容 | 推荐载体 |
|---|---|
| 高频变化的实现细节 | 代码、类型、Schema、自动生成内容 |
| 可观察行为和边界 | 测试、契约测试、可执行示例 |
| 中频变化的产品意图 | 精简规格或需求契约 |
| 低频变化的架构原则和取舍 | ADR、架构概览 |
| 临时计划和任务过程 | 蒸馏后删除：长期有效的结论回写进规格 / ADR / Release Note，过程稿删除，Git 历史负责恢复 |

归档不是清理，只是把过时声明换了个目录。只有审计、法规与可复现性要求的产物才值得长期归档。

### 原则四：生命周期与垃圾回收

前三条防新漂移；还必须让失效产物退出，否则生命周期漂移持续累积：

- 每类文档有 owner 与失效判定条件：被替代、零引用、超过 review 周期未确认。
- 被替代的文档：有效信息回写后删除，或留一行 stub 指向新位置；不做无限归档。
- 定期体检：孤儿、重复、断链与过时论断检测（本库的 [[llm-wiki-方法论|Lint]] 操作即此机制）。
- 生成新文档前先查重：优先更新已有页面，其次才新建。

## Agent 时代的漂移经济学

- **Agent 作为文档消费者**：coding agent 把 CLAUDE.md / AGENTS.md / README / 规格当作 ground truth
  并据此批量行动。过时文档的危害从“误导人”（人会怀疑）升级为“驱动错误行动”（agent 默认信任、
  按规模执行）。文档从辅助材料变成运行时输入。
- **Agent 作为文档生产者**：回写与同步的边际成本大幅下降，因果模型第 5 条的外部性被削弱——
  “决策回写”可以交给 agent；但文档生成成本同时趋零，缺少查重与 GC 闸门时，
  表达漂移和生命周期漂移会以更快速度累积。
- 综合：CLAUDE.md / AGENTS.md 是“文档进入交付闭环”的罕见实例——agent 每次会话都读取并执行它，
  写错会立即表现为错误行为，从而获得与代码对称的反馈约束。

## 判断一段信息是否需要写文档

> 回答“为什么、应该、必须、不得”的信息，应当留下记录；
> 实现事实不做第二份独立维护——低成本可推导的省略或生成，
> 高推导成本或读者不宜读代码的，做成标注来源的派生视图。

- 让代码成为实现事实的真相源。
- 让规格或契约成为预期行为的真相源。
- 让测试和运行证据成为两者是否一致的**证据机制**（不是裁判）。
- 让生命周期机制保证失效产物退出。

> 综合：权威分层 + 派生而非手工复制 + 关系可追溯 + 交付时持续验证 + 生命周期自动退出 = **可控漂移**。
> 目标不是零漂移，而是让每类漂移都有对应的调和或取证机制。

相关的规格持久化和追溯模型见 [[Specification-Driven Development]]；
“预期行为—实现状态—符合证据—决策历史”的分层实践与门禁见 [[SDD 开发规范研究]]；
解决方案层的治理架构（关系契约、一致性分级、调和回路、生命周期 GC）见 [[论代码与文档漂移解决方案]]。
