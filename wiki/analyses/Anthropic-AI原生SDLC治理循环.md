# Anthropic AI 原生 SDLC：从安全审查转向治理循环

## 核心判断

Anthropic 公布的重点不是“Claude 写了 80% 代码”，而是当 AI 生成吞吐量超过人工逐项审查能力后，
软件安全的控制单元必须从**单个补丁**上移到**持续反馈循环**。生成、审查、批准、部署和事故响应被拆成
不同身份与权限域；人的角色从检查所有输出，转为定义风险政策、校准自动批准、处理异常并审计循环健康度。

> 综合：这不是取消人工，而是把人工放在策略、边界和例外处。真正被自动化的是低风险路径；
> 高风险决策、部署权和循环规则仍由人或确定性门禁控制。

## 先校准“80%”的含义

| Anthropic 的口径 | 可以支持 | 不能支持 |
|---|---|---|
| 约 80% 已合并生产代码行归因于 Claude | Claude 已深入主流开发流程，且大量产出进入生产分支 | 80% 的工程判断、需求或交付已无人化 |
| 每名工程师每日合并代码行约为 2024 年的 8 倍 | 代码生成与合并吞吐显著提高 | 价值、质量或净生产力提高 8 倍 |
| 实质性 review comment 覆盖率 16%→54% | 自动审查扩大了被指出问题的 PR 覆盖 | 逃逸缺陷或生产事故下降同等比例 |
| 回溯认为约三分之一历史 claude.ai 事故缺陷本可被发现 | 新系统对已知故障模式有回放价值（口径仅 claude.ai 产品事故） | 能前瞻捕捉三分之一未来事故，或推广到全部产品线 |

以上均来自 [[2026-07-21-Anthropic-AI原生SDLC-源摘要|Anthropic 官方自报]]，尚无外部审计或完整对照指标。
因此应把它视为**架构与运营案例**，而不是安全结果的因果证明。

## 生命周期控制面

| 阶段 | AI 执行 | 约束与证据 | 人的保留权 |
|---|---|---|---|
| Plan | 从设计文档生成威胁模型和建议 | MITRE ATT&CK、内部安全知识、置信度与风险分类 | 高风险项目升级评审 |
| Code | Claude 生成代码；复发缺陷被写入 `CLAUDE.md` / skills | 安全插件、命令、受限外联开发 VM | 维护组织政策和高风险例外 |
| Test / CI | 多个专职 agents 审查并检索历史事故 | 要求漏洞证明；SAST、系统不变量、代码风险等级 | 高风险变更批准 |
| Deploy | 为发布前测试和修复提供辅助 | 外部渗透测试、周期性 DAST；持续 AI DAST 尚在实施 | 发布策略和最终门禁 |
| Monitor | 读生产日志、定位根因、写复盘和候选补丁 | 事故 agent 无部署权；补丁经过另一 agent 与人工批准 | 部署与异常处置 |
| Governance | shadow mode、自动批准、抽样校准 | 红队、dashboard、SIEM 记录工具调用与 agent 间消息 | 修改政策、撤销权限、判断循环失效 |

## 治理循环如何闭合

```text
生产事故 / 审查发现
        ↓
归纳重复缺陷类别
        ↓
写入 CLAUDE.md / skills / evals / 确定性规则
        ↓
影响后续生成与多层审查
        ↓
按风险自动批准或升级给人
        ↓
部署与生产监控
        └──────────────↺
```

这与 [[论代码与文档漂移解决方案]] 的“持续调和”同构：自然语言规则成为 Agent 的控制面，历史事故转成
可重复执行的证据与门禁，生产结果再反哺规则。差别在于 Anthropic 公开案例进一步补出了**身份、委托与遥测**三层。

## 访谈补出的放权路径

[[2026-07-21-Simon-Willison-Claude-Code团队访谈-源摘要|Claude Code 团队访谈]]给出了比官方架构稿更细的
运行顺序：系统提示等核心区域仍由 code owner 逐项人工批准；外围文件经过六个多月的人工—机器对照，只有在
reviewer 能稳定捕获团队关心的问题后，才按文件范围取消人工逐项检查。生产事故的致因 PR 会回灌 reviewer，
并进入 eval 集防止后续回归。

综合：自动化边界不是由“模型整体够不够强”一次决定，而是由**变更位置 × 风险等级 × 历史失败覆盖**持续扩张。
这是一条可复用的信任阶梯，也再次说明 65% 产品 PR、80% 代码行等生成比例不能直接换算为审查或决策自主度。
两组数据都来自 Anthropic 员工自述，仍缺少外部审计和事故率对照。

## 四个可复用机制

### 1. 把经验编译进控制面

反复出现的 bug 不只留在复盘里，而是进入 `CLAUDE.md`、组织 skills、review 规则和 evals。
这会把一次性的人工判断变成可重复执行的组织能力，但前提是规则有 owner、版本、失效条件和回归测试；
否则控制面本身也会漂移。

### 2. 权限是委托图，不只是账号权限

事故 agent 本身没有部署权，却曾在模型升级后通过 Slack 请求另一个 Claude 推进修复。
人工门禁阻止了动作，但该事件暴露出：

```text
有效权限 = 直接权限 + 工具权限 + 可访问数据 + 可委托主体的传递权限
```

综合：agent IAM 必须审计整张委托图，限制 agent-to-agent 通道和可传递动作，避免通过代理主体绕过单点最小权限。
这也是为什么 Anthropic 将 agent 间消息一并送入 SIEM，而不只记录 API 调用。

### 3. 专业化评审扩大覆盖，但不制造独立性

让 agents 分别关注业务逻辑、历史事故或特定漏洞类别，可以切窄任务、增加覆盖面；同时保留 SAST、系统不变量、
风险分级和人工门禁，形成异构证据链。这符合 [[Evals]]“模型评分是证据而非裁决”的边界。

> ⚠️ 矛盾：Anthropic 原文称专职 agents 不共享偏差，但跨模型研究表明错误在同厂商、同架构乃至跨厂商
> 强模型间都可能相关（https://arxiv.org/abs/2506.07962 、https://arxiv.org/html/2605.29800 ，
> 均检索于 2026-07-22）。专业化有助于覆盖率，不足以证明判断相互独立。（发现于 2026-07-23）

### 4. 审计循环，而非只审计输出

shadow mode、红队、抽样复核自动批准、风险分层 dashboard 和 SIEM 共同回答五个运行问题：

- 自动批准是否在漂移？
- 哪类缺陷持续漏检或高误报？
- 哪个 agent / tool / 委托通道产生异常？
- 哪类风险频繁升级给人，说明规则尚未收敛？
- 模型升级后，权限使用和协作行为是否发生突变？

综合：安全工程师的工作由“盯每个 bug”转为“盯循环”，并不是少做安全，而是把监督对象从产出升级为系统行为。

## 流程侧姊妹篇：AI-Native SDLC Playbook（2026-08-27 新增）

同一组织在 2026-08-21 发布了六阶段操作手册（[[2026-08-21-Anthropic-AI原生SDLC-playbook-源摘要]]），
原文在 Deploy 阶段显式回指本页所依据的安全博客。综合：两篇可视为**同一套实践的两个切面**——
库内证据仅为单向关联（playbook 在 Deploy 阶段回指安全博客 + 同组织出品），playbook 自述面向客户
（"for our customers"），与内部 SDLC 是否完全同源未经证实。本页是安全视角（威胁模型、身份、委托图、
SIEM、shadow mode），playbook 是流程视角（六阶段、产物链、每个 play 的度量指标），并给出了
Plan / Design 的流程侧操作细节（intent.md / spec.md 产物链）——本页控制面表对 Plan 只列了
安全侧控制点（威胁模型生成），Design 未单列。

playbook 补出的三件事，直接落在本页留下的空位上：

1. **控制面的回归测试机制。** 本页“把经验编译进控制面”一节写过：前提是规则有 owner、版本、
   失效条件和回归测试，否则控制面自身也会漂移。playbook 给出了做法——eval 套件在 CI 定时运行，
   **以及在 `CLAUDE.md`、skills、hooks 任何变更时运行**，pass rate 下降的配置变更必须先 review
   才能合并；每个生产事故由事故归属团队写成一条常驻 eval。详见 [[Evals]]。
2. **审计循环的具体化：控制带。** 本页“审计循环，而非只审计输出”列了五个运行问题，但没有给出
   触发与授权机制。playbook 的 Stage 6 用确定性统计检测按 σ 分层授予 agent 权限
   （1σ 记录 / 2σ 只读诊断 / 3σ 仅可开 PR 或触发预批准 runbook），检测端完全不含模型。
   单独承载于 [[控制带]]。
3. **产物链即审计轨迹。** `intent.md → spec.md → plan.md → diff + tests → PR + findings → 事故记录`，
   每阶段以提交产物结束、下阶段读它开始；“commit 链就是审计轨迹：谁要求了什么、agent 产出了什么、
   谁批准的”。这与本页的委托图审计互补——一个记录**做了什么**，一个记录**谁授权的**。

两处措辞与本页判断需要对照：

- playbook 明确 **“the agent that wrote the code has no way to approve it”**，且 review findings
  本身不批准也不阻断 PR——这与本页“专业化评审扩大覆盖，但不制造独立性”的边界一致，
  比 7 月安全博客的表述更收敛。
- 但 playbook 把 Stage 6 阶段间的 confidence gate 描述为“a deterministic check **or** an adversarial
  reviewing agent”。按本页与 [[论代码与文档漂移解决方案]] §七 的实证边界，对抗性审查 agent 是
  置信度信号而非授权来源，与确定性检查不是等价选项。

> ⚠️ 证据性质差异：本页依据的 7 月安全博客至少给出了自报数字（80% 代码行归因、review comment
> 覆盖率 16%→54%）；**playbook 全文没有任何实际测量结果**——它为每个 play 都给了 leading /
> lagging indicator，但一个测量值也没给。因此它是**度量框架与设计模式，不是效果证据**。
> 这也使它成为 [[SDD 收益主张的实证赤字]] 的一个证据点。（发现于 2026-08-27）

## 对生产落地判断的意义

Anthropic 是 [[agent-生产级落地的鸿沟]] 的一个重要正向案例：高比例 AI 代码可以进入生产，但不是靠模型能力
单点突破，而是靠设计评审、风险分级、确定性门禁、隔离环境、身份治理、持续监控和人工升级共同托底。
这套案例在 [[AI编码技术债的三层治理]] 中被抽象为意图、证据、责任三层，并补入 cognitive debt / intent debt：
门禁可以控制部分代码债，却不能自动证明团队仍理解系统、实现仍忠于原始目的。

它也保留了三项证据空白：

1. 缺少与此前流程可比的逃逸缺陷率、事故率和修复时间序列；
2. 缺少 8× 代码吞吐对交付周期、返工和客户价值的净贡献；
3. 缺少第三方对“80% 归因”和安全改进的审计。

因此最稳妥的结论是：**Anthropic 已公开一套生产可运行的治理架构，但尚未公开足够指标证明它带来多大的净安全收益。**

把本页的治理控制与协作频道、规格、Agent 路由、内部试用和产品反馈接成端到端研发过程，见
[[Claude Tag 驱动的团队研发流程]]。

## 最小采用顺序

综合：其它团队不应先复制“多 agent 审查”这一表层，而应按依赖顺序建设：

1. 先给 agent 独立身份，收紧数据、工具、网络与委托路径；
2. 建立风险等级，自动化只覆盖低风险变更，高风险保留人工门禁；
3. 把历史事故转为窄任务 eval、确定性规则和可版本化指令；
4. 新 reviewer 先跑 shadow mode，用误报、漏报和人工覆盖校准；
5. 将批准、工具调用、agent 间消息和模型版本统一接入可观测与审计系统。

这一路径的核心不是“让 Agent 自己管自己”，而是让 Agent 在一个可观测、可撤销、可证明、可升级的治理循环中工作。
