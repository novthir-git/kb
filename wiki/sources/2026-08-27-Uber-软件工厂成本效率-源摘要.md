**原文**：Uber 工程博客，2026-08-27，作者 Uday Kiran Medisetty（Distinguished Engineer）。

## 一句话

一篇 **agent 成本工程**方法论：把 agentic session 的花销拆成六项相乘的方程，逐项建指标、逐项上杠杆，
在用量涨 7 倍的同时压低各项单位成本。

## 自报数据（全部为 Uber 内部口径，无第三方审计）

| 指标 | 值 | 原文口径 |
|---|---|---|
| PR 归因于本地或云端 agent | >70% | "attributed to"；未定义归因规则，未说明人工审查比例 |
| 已建 agent skills | >3,600 | 覆盖整个 SDLC |
| agent skill 日执行 | >30K/天 | |
| 周活用户 | 7×（2026-02 → 08 中） | 全员口径，含非工程师；跨工具去重 |
| 周 agentic 请求 | 9.4×（同期） | |
| 总 AI 支出 | 自 4 月起"相对稳定" | **持平，不是下降** |
| 每千次模型请求成本 | 较峰值 −34%（2–7 月） | **固定同一模型**测得 |
| 每 session 成本 | 较 6 月峰值 −52% | 同上；数据始于 5 月末 |

原文明确说明"固定一个模型"是为了把自身优化收益从模型换代与厂商调价里分离出来，
并自述"具体降幅取决于你的代码库、团队规模和工作流，方法论才是通用的"。

## 结构：四层 + 六项成本方程

- **四层 agent 用量**：从最专用到最通用；越往上对成本、质量与选型的控制力越强。
  （四层的具体名称只出现在 Figure 3 图片里，正文未写出。）
- **六项相乘的成本方程**：前两项是采用与参与（要持续增长），
  **中间三项是优化空间——"agent 在工程师真正提出的那个请求之上，替它自己多干的活"**，
  这是大部分投入的去处（帮 agent 更快规划、减少多余轮次与错误、压缩输入 token）。
  （六项名称同样只在 Figure 4 图片里。）

## 五层度量表（原文完整列出）

| 层 | 指标 | 回答什么 |
|---|---|---|
| Portfolio | 总归因成本、去重归因用户、各工具/agent 的成本与份额 | 钱花在哪、哪个工具动了 |
| 单位经济学（按工具） | 每用户成本、每用户请求数、每千请求成本、每请求输入/输出/总 token、每百万 token 成本、每千 session 成本、每活跃 session 小时成本、prompt 缓存命中率 | 是工具真的变便宜了，还是用量在挪位置 |
| 模型经济学 | 每个模型的成本与份额、请求与份额、每千请求成本、每百万 token 成本 | 哪次模型发布真正改变了账单 |
| 驱动因素分解 | 把成本变化**顺序分解**为采用（用户数）、参与（每用户请求）、输入负载（每请求输入 token）、输出负载（每请求输出 token） | 为什么变了，**不留未解释残差** |
| 托管 agent 结果 | 结果计价成本（每合并 PR / 每次 review / 每条告警 / 每次清理）、质量信号（revert 率、F1、MTTR）、体量（合入 diff、发出 review、分诊告警） | 每单位价值是否更便宜，模型迁移后质量是否守住 |

## 杠杆逐条

### Price / Token（选型）

- 四步法：**用 agent 的真实工作造 benchmark** → 跑在"一个接口后接任意模型（前沿或开源权重）"的 harness 上
  → 迁到 Pareto 最优并**持续迁**（"前沿每几周就移动一次"）→ 用托管 agent 的聚合洞察试验模型路由策略。
  Pareto 效率定义为：每完成任务成本 × 输出质量 × 模型可靠性。
- **uReview**（全量 PR 的 AI code review）：benchmark 由**已知含 bug 的真实 PR** 构成、分难/中/易，
  打 precision / recall / F1 + 每 PR 成本 + 时延 + 超时 + 噪声。换模型后 F1 上升且每 PR 成本大降
  （具体数值只在 Figure 5）。
- 另有 **Uber SWE Benchmark**：跨大型 monorepo 的数千真实 PR，跑前沿与开源权重模型、覆盖不同任务类型。
- **默认子 agent 用弱模型**：原文称这是交互侧**最有效的单一杠杆**且重要性还在上升——
  主模型负责任务拆解与评估，子 agent 执行定义良好的子任务，通常不需要前沿级推理；允许手动覆盖。

### Tokens / Request（载荷）

- **400K 触发自动压缩**，即便模型有 1M 上下文——权衡模型表现 vs 缓存爆发与重复输入费。
- **reasoning effort 默认 Medium**：输出（含内部推理）token 单价是输入的数倍。
- **缓存 TTL**：读为标准输入价的 **0.1×**；写溢价 5 分钟 **1.25×**、1 小时 **2×**；
  Anthropic 提供 5 分钟与 1 小时，OpenAI 提供 30 分钟。交互 session 因工程师常挂机 >5 分钟而改用 1 小时；
  **子 agent 保持 5 分钟**（生命周期短）。
- **MCP schema 膨胀**：>100 个工具 → 开场约 **50K–70K token** 的 schema 开销，且每轮重发。
  两条解法：**CLI tool resolution**（1K+ 内部 MCP 工具全部投影为 CLI 命令，schema 完全离开上下文）
  与 **tool search**（按需检索加载）。全部 MCP 走统一网关，覆盖 **1,000+ server**，集中认证与策略。
- **Code-mode**：工具即 shell 命令后可在一个脚本里批量调用；同 session 内 5 条 SQL 双路实测：

  | 查询 | LLM tool-use | Code-mode | 省 |
  |---|---|---|---|
  | SELECT 1（1 行） | 903 | 402 | 55% |
  | COUNT(*)（1 行） | 954 | 403 | 58% |
  | GROUP BY LIMIT 20（20 行） | 1,600 | 457 | 71% |
  | SHOW COLUMNS（175 行） | 2,200 | 900 | 59% |
  | SELECT * 宽表（50 行） | 1,431,594 | 900 | ~100% |

  原文强调**前三行才是主要发现**：结果集极小也省一半以上，省的不是数据体积，
  而是 schema 初始化、多轮轮询与冗余逐步推理。批量流程可省 >90%。已部署 **25+ 个 code-mode skill**。
- **SaaS MCP 更糟**：某办公套件单 server 打包 49 个工具 / 约 **22K token** schema，IM 34 个、项目管理 46 个；
  挂两三家厂商的 server，agent 开场背的 schema 比它要编辑的文件还大。解法同上（网关 + CLI 投影 + 自写 code-mode skill）。

### Requests / Turn（接地）

- 论断原文："An ungrounded agent fails slowly rather than cheaply."
- **AI Context Graph**：2,400 万节点 / 8,000 万边，86 类节点、117 类边，整合 **30+ 内部系统**
  （服务、工程团队、事故日志、PR、架构设计文档、部署、数据集、历史表使用查询），支持任意 agent 自然语言查询。
- 同 prompt 同模型对照（单例）：接地方 **38 秒**给出答案（查历史用量，定位到 50+ 分析师在用的表）；
  未接地方花 **20 分钟**、开 2 个子 agent、撞 3 次错误，最后**错误地**判定该数据集不可查。

### 可见性与教育

- **status line 实时花费计数器**：显示本 harness 及跨 harness 累计。
- **不设硬上限**：交互类 harness 共享一个额度池（非按工具分预算），托管 agent 单独分池；
  50/80/100% Slack 提醒；经理审批快速升档；`cost check` skill + 状态栏即时提示。
- **session 分析看板**：内建于 runtime，零配置零 opt-in；`cost dashboard` skill 分析该用户
  跨本地与云沙箱、跨所有 harness 的全部 session trace，**识别 16 种反模式**并各配金额影响与整改建议。
  原文举出四类：模型路由不当（简单多轮跑在 Opus 上）、上下文膨胀（40KB 的 MCP 响应赖在上下文里逐轮计费）、
  缓存过期（长间断后按全价重建前缀）、初始化开销（用户输入前先加载 10 万 token 系统指令与工具定义）。

## What's Next（原文列出的在建项）

扩大托管 agent 队伍（每个新 agent 都走"定结果指标 → 建 benchmark → 找 Pareto 模型"同一路线）；
动态模型路由（扩 benchmark 覆盖到更多语言/仓库/agent 形态）；深化上下文图谱接入；
把 session 分析从批量检测演进为实时逐 trace 指导；**持续 skill 改进**——自动记录 skill 执行中的
papercut 并从 trace 自动生成 skill 更新。

## 结论段的战略主张（原文）

> 核心转变是从交互式开发者工作流转向**完全托管的 agent**。把 SDLC 负载迁进托管环境即完整掌握
> 模型路由、执行 harness 与运营开销；优化一支各配专属评测 benchmark 与 Pareto 模型的专用托管 agent 队伍，
> 本质上比优化几千名工程师各自的终端 session 更划算、更可扩展。

## 口径与证据边界

1. **全部为公司自报，无第三方审计。** "70% PR 归因于 agent"未给归因规则，与 Anthropic 的"80% 代码行归因"
   属同类口径问题——归因 ≠ 自主完成 ≠ 净生产力（对照 [[Anthropic-AI原生SDLC治理循环]]）。
2. **分母被换过。** 34% / 52% 是**单位成本**；总支出只是"稳定"。这是"用量爆炸时守住预算"，不是"降本"。
3. **code-mode 表 N=1。** 同一 session 各跑一次，无重复无方差；末行 ~100% 是"别把宽表 dump 进上下文"的极端化，
   与前三行不是同一量级的现象。
4. **"托管 agent 天然更划算"是主张不是实测。** 原文未给交互 session 与托管 agent 在同类任务上的对照成本。
5. **接地对照是精选单例**，且选的正是图谱最擅长的"哪张表被谁用"类问题。
6. **四层与六项方程的具体名称只在图片里**，本 wiki 的重建见 [[Uber-软件工厂的成本工程]]，
   已标注为综合推断。
7. 原文自述定价与厂商指标"基于公开信息"，效率收益来自"在标准分级定价内更聪明地路由内部负载"——
   即不含企业折扣议价这一维度。
