# AI 编码治理高质量证据包

## 筛选口径

本证据包只保留以下四类材料：同行评审论文；有清晰设计和样本的工作论文 / 预印本；政府或行业标准；工具方关于
自身控制边界的一手文档。Medium、厂商营销稿和无方法说明的经验数字可作为线索，但不进入核心证据表。

“权威”不能只看发表场所：随机试验擅长回答特定任务上的短期因果效果，遥测研究擅长观察大规模生产链条，安全
用户研究依赖任务、模型与被试，而标准回答的是最低治理要求。它们的结论不能互相替代。

## 实证证据地图

| 来源 | 设计与样本 | 主要结果 | 能证明什么 | 不能证明什么 |
|---|---|---|---|---|
| Cui 等，*Management Science* | Microsoft、Accenture 与一家 Fortune 100 企业的 3 个随机现场试验；合计 4,867 名开发者 | AI 助手使完成任务 / PR 数提高 26.08%；经验较少者收益更大 | 代码补全在若干企业环境中能提高短期活动产出 | 长期可维护性、缺陷率和生产价值 |
| Paradis 等，Google RCT | 96 名 Google 全职工程师；单个复杂企业任务 | 完成时间约缩短 21%，置信区间较宽 | 特定内部工具和任务上的速度收益 | 多任务、跨企业效果与代码质量 |
| Becker 等，METR RCT | 16 名资深开源维护者、246 个真实任务；平均熟悉仓库 5 年 | 允许使用 2025 年初 AI 工具后，实际完成时间增加 19%；参与者事前预计快 24%，事后仍感觉快 20% | 成熟仓库、隐性上下文丰富时，感知加速可与实际减速并存 | 新手、绿地项目或更新模型的平均效果 |
| Demirer 等，NBER Working Paper 35275 | 超过 10 万名 GitHub 开发者与 AI 工具遥测；匹配事件研究 | commits 增幅从 40% 到 180% 不等，但到 projects / releases 明显衰减；同步 agent 的 LOC +741%、PR +65%、release 仅 +20% | “写出更多代码”不会等比例传导为可发布价值 | 严格随机因果、企业内部软件质量 |
| Xu 等，arXiv:2510.10165 | 开源仓库的 Difference-in-Differences；37,334 名贡献者 | 核心贡献者 commits -19%、review +6.5%；外围贡献者 commits +43.5%、PR +17.7%，返工上升 | 与“产出转移为资深者维护负担”一致的生产数据 | 无条件的因果结论；处理组识别依赖语言与 Copilot 暴露假设 |
| Perry 等，ACM CCS 2023 | 47 人、Python / JavaScript / C 的 5 个安全任务 | AI 组多数任务的代码更不安全，却更有信心 | AI 辅助可能放大安全误判和过度自信 | 所有模型、所有开发者和真实生产系统的安全效果 |
| Sandoval 等，USENIX Security 2023 | 58 名学生、随机分组、一个低层 C 链表任务 | 功能正确性提高；未得到严重安全缺陷显著上升的结论 | AI 安全影响受任务、模型和交互方式影响 | “AI 必然更安全”或“必然更不安全” |
| DORA《Impact of Generative AI in Software Development》 | 基于 2024 DORA 调查的统计建模，主要为自报数据 | AI 采用与 flow、满意度、感知生产力、代码质量正相关，却与 valuable work、交付吞吐和稳定性负相关 | AI 可能放大交付系统的强弱，并出现局部收益 / 系统结果背离 | 单独使用 AI 导致这些结果的因果关系 |

> ⚠️ 矛盾：企业随机试验显示约 21%–26% 的短期速度 / 活动收益，但 METR 在成熟开源仓库中测得 19% 的减速；
> Perry 在多种安全任务上观察到更不安全的代码，Sandoval 在单一 C 任务上没有得到严重缺陷显著上升的结论。
> 差异来自任务、开发者经验、仓库成熟度、模型、界面和结果指标，不能用任一研究覆盖全部场景。（发现于 2026-08-07）

## 实践与标准材料

### 第一层：治理基线

- **NIST SSDF 1.1（SP 800-218）**：政府标准级的安全 SDLC 基线，覆盖组织准备、软件保护、生产安全软件、
  漏洞响应。它不专门评价 AI 代码，但适用于任何代码来源。SP 800-218A 面向生成式 AI 模型 / 系统生产者，
  不应误当作“AI 生成应用代码”的专用规范。
- **DORA 2025 State of AI-assisted Software Development + AI Capabilities Model**：把 AI 定位为组织系统的放大器；
  七项基础能力包括用户中心、强版本控制、AI 可访问的内部数据、小批量、清晰 AI 立场、高质量内部平台和健康
  数据生态。适合用于组织能力诊断，不是代码规则清单。
- **OpenSSF Security-Focused Guide for AI Code Assistant Instructions**：给出面向输入校验、鉴权、secret、依赖、
  IaC、OWASP / ASVS / CWE 的指令模板，同时明确这些内容是专家建议，开发者仍须执行 review、测试、静态分析
  和版本控制。

### 第二层：工具边界与工程控制

- **GitHub Copilot 官方 Responsible Use / Code Review 文档**：明确 AI review 可能漏报或产生错误；Copilot review
  只提交 Comment，不会 Approve / Request changes，也不满足 required approval，更不会自动阻止合并。这是把它定位
  为辅助证据而非裁决者的直接依据。
- **《Twelve quick tips for AI-assisted coding in science》**：PLOS Computational Biology 同行评审的 Education
  文章，覆盖背景知识、问题定义、交互模式、计划拆分、上下文、测试验证、测试约束、覆盖率、进度监控、代码
  审查、增量重构与文档。它来自作者经验与文献综合，不是流程效果试验。其预印本为 arXiv 2510.22254
  《Ten Simple Rules…》（同一作者团队；2026-07-27 正式刊出时 10 条扩为 12 条并改题）——统计证据数量时
  与用户草稿所引 arXiv 版按**同一工作**计。
- **Anthropic / Claude Code 团队实践**：可作为高比例 AI 编码下的身份隔离、风险分级、shadow mode、事故回灌、
  文件化上下文和 eval 驱动放权案例；属于公司自述的一手架构材料，不能独立证明安全或效率效果。

## 综合判断

综合：现有高质量材料不支持“AI 编码必然提效”或“必然制造更多技术债”这类无条件命题。更稳健的判断是：

1. AI 往往先提高局部代码 / PR 活动，但收益会沿任务完成、项目推进、release 和用户采用逐层衰减；
2. 仓库越成熟、隐性上下文越多，审查、返工和维护越可能成为瓶颈，负担也可能从外围贡献者转向核心维护者；
3. 安全结果具有明显场景依赖，因此不能让概率型 AI review 替代测试、静态分析和责任人批准；
4. 治理应同时保存意图、机器可验证证据和人类责任，并按风险与任务类型校准，而不是设置一组跨项目通用阈值。
