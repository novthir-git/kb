# 2026-05-19 Sonar《Does Code Cleanliness Affect Coding Agents?》源摘要

**原文**：Priyansh Trivedi、Olivier Schmitt（SonarSource），arXiv 2605.20049 v1，2026-05-19，预印本。
**存档**：`raw/sources/articles/2026-05-19-Sonar-代码整洁度最小对实验.md`（要点式中文摘录；Table 1–4 照录）。

判断与跨源综合见 [[全AI代码库的治理决策]]；它对"结构债按 token 计价"的修正见 [[Agentic SE 时代的系统重构]] §二。
本页只做忠实摘录与口径标注。

## 一句话

**第一份固定 agent 与任务、只改变代码库整洁度的受控实验**：6 对行为等价的仓库、33 个任务、660 次 Claude Code 运行。
整洁度不改变通过率（−0.9 pp），但整洁侧输入 token −7.1%、输出 token −8.5%、对已编辑文件的重读 −33.8%。

## 设计要点

- 最小对：架构、依赖、测试、外部行为相同，只在 SonarQube 规则违规数与认知复杂度上不同。双向构造：
  降质流水线（Slopify）往整洁仓库里内联 helper、复制逻辑、**塞死代码**、合并模块；清理流水线（Vibeclean）对混乱仓库
  删注释掉的代码、删死分支、拆上帝结构。
- 三个仓库公开、三个为 SonarSource 私有（防记忆）；三个主要为 Java、三个主要为 Python。
- 任务描述只给外部行为、不点名文件；隐藏测试只走公开接口。分三轨：认知热点 13、跨模块 14、校准 6。
- 单一配置：Claude Code + Claude Sonnet 4.6，每任务每侧 10 次；Haiku 4.5 通过率过低被排除。

## 关键数据

| 范围 | 通过率 | 输入 token | 重读 |
|---|---|---|---|
| 数据集（33 任务） | −0.9 pp | −7.1% | −33.8% |
| 跨模块轨（14） | −2.6 pp | −10.7% | −50.8% |
| 认知热点轨（13） | +0.1 pp | +1.8% | −20.2% |
| 校准轨（6） | 0.0 pp | +3.8% | −75.0%（三次重读，micro-average 放大） |

数值为 (cleaner − messier) / messier，通过率为绝对百分点差。全部 10 项指标与分仓库数据见 raw。

## 作者的发现

- **收益集中在跨模块任务**：读文件数基本不变，整洁侧改完就走，混乱侧反复回到已改文件。
- **热点拆分基本不省 token**：清理只是把复杂度分散到更多方法，agent 打开更多文件、每文件改更少行。
  个案分化明显：commons-bcel 把数百行 switch 换成具名 helper 后输入 token −35%（可 grep 定位）；
  genie 在核心逻辑周围加结构却未改核心，输入 token +8%。
- **注释不是驱动因素**：注释量消融后整洁侧优势仍在，sonar-caas-poc 从 +1.2% 变为 −18.0%（控制读文件 LOC 后 −13.0%）。
- 作者定位：反驳"可维护性原则只为人类读者校准"的一小块证据；长期是否复利是开放问题。

## 口径与证据边界

- **利益相关**：作者受雇于 SonarSource，"整洁"以 SonarQube 规则违规数为代理。
- **方差很大**：同一任务同一侧 10 次运行，最贵与最便宜的输入 token 通常相差约 2.5 倍；作者明言单任务约 10% 的差值可能是噪声。
  27 个真实任务中 16 个整洁侧更省、11 个更费，中位数 −4.5%。
- **只用隐藏测试评分**：不检查 agent 是否破坏仓库原有的其他测试。所以"通过率不变"不覆盖回归。
- **降质是捆绑注入**：死代码、重复、内联、模块合并、命名劣化一起变化，未分离单个变量的效应。
- 单模型、单 harness、短程单任务；作者自己说可迁移性是推测。
- 由作者端到端策划仓库、配对与任务，选择偏差会直接传到结论。
