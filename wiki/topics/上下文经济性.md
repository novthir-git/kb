# 上下文经济性

## 论点

**上下文经济性**指 agent 做一次变更要读进多少上下文、读进来的上下文能被利用得多好。代码库的结构决定它：
小而内聚、边界清楚的代码让 agent 只读所需的那一小块（[[Agentic SE 时代的系统重构]] §九）。

用户 2026-10-08 的判断（调研稿续篇 §6）把它拆成两个维度，两者的寿命不同：

- **质量维度**：上下文越满，单位信息的利用质量越低。证据充分，但退化起点随模型代际后移——**在收窄，未消失**。
- **经济维度**：读进来的每个 token 都要计费、都增加 prefill 延迟。窄读取的相对优势与模型能力无关——**不会被更强
  的模型抹平**，但倍数取决于读取体量比与缓存条件（用户原文"永远便宜一个数量级以上、≈25×"偏强，见下文）。

用户原稿把证据分三层、强度递减，并称第三层"代码库结构 → agent 成功率"的受控实验**基本缺失**。核验后第三层要改写：
受控实验**有，但少而新、多为厂商所做**；它们的结果形态恰好对上两维判断——

> 综合：强模型上，代码整洁度对**成功率**的影响不显著；对**成本与效率**的影响方向一致为正；中等规模的开源模型上，
> 质量维度仍显著。所以"为 agent 重构"在前沿模型上主要该按**成本**论证（[[Agentic SE 时代的系统重构]] §二的按 token
> 计价），而不是按"能不能做成"论证。置信度：中低（研究少、单配置、厂商所做，且强模型组的零效应可能是检验功效不足）。

**什么证据会让本页改口**：

- 强模型上出现有足够检验功效的整洁度对照，成功率差异显著 → "质量维度已收窄"要撤回；
- 缓存与定价让多轮、跨会话的全量读取与窄读取成本持平 → 经济维度的"长存"要降级；
- 第三方测量中 1M 多事实检索的退化消失 → 质量维度在长度轴上被抹平。

## 证据三层（核验后）

逐项核验见 [[2026-10-08-agentic-se-refactoring-methodology-补充研究-源摘要]]。

### 第一层：长上下文退化本身——充分，跨代际复现

- **RULER**（Hsieh 等，NVIDIA，COLM 2024）区分声称长度与有效长度：17 个声称 32K 以上的模型里只有一半在 32K 保持
  合格表现，所有模型的有效长度都短于声称长度（如 GPT-4 声称 128K、有效 64K）。原文只测到 128K。
- **NoLiMa**（Modarressi 等，ICML 2025）去掉问题与"针"之间的字面匹配后，32K 时 13 个模型中有 11 个跌破各自短上下文
  基线的 50%（v3；v1 为 12 个中 10 个）。
- **Chroma "Context Rot"**（2025-07-14，18 个模型）：即使是简单任务，表现也随输入长度显著变化，且长度越长越不均匀。
- **200K 以上**：用户原文"截至 2026 年仍有 30–60 分退化、没有前沿实验室公布过经第三方验证的 500K+ 多事实检索分数"，
  出自一篇营销博客（genai.club，2026-05-22），30–60 没有数据链接。第三方榜 Context Arena（MRCR v2 8-needle，2026-10-08
  取数，高推理档）：前沿模型从 8K 的近满分到 (128K,256K] 区间跌约 11–53 分、到 (256K,512K] 区间跌约 22–69 分——退化
  确实在，但范围比 30–60 宽。(512K,1M] 区间有 Google 模型的第三方数据：Gemini 3.1 Pro 25.9%（Google 自报 26.3%），
  Gemini 3.7 Flash 63.5%，所以"无第三方验证"**失准**；Anthropic 与 OpenAI 的 1M 自报分数（如 Opus 4.6 的 76%）尚无
  第三方复现。
- **收窄的直接迹象**：同一区间 (128K,256K]，Gemini 3.1 Pro（2026-04 测）跌约 53 分，Gemini 3.7 Flash（2026-08 测）
  跌约 11 分。
- **机制**：部分解释，不是定论。Softmax 输出的最大元素随输入长度趋于零（Nakanishi 2025，预印本，称 attention fading）；
  Anthropic 的 context engineering 文章说 n 个 token 有 n² 个成对关系、模型有"注意力预算"，但同文也归因于训练分布
  （短序列更常见）；Lost in the Middle 是位置效应的实证。综合：softmax 稀释是有力的假说，没有被证明是前沿模型退化的
  主因。

### 第二层：对 coding agent——方向大体一致，但有反例

- **《The Limits of Long-Context Reasoning in Automated Bug Fixing》**（Raju 等，SambaNova，arXiv 2602.16069，ICLR 2026
  ICBINB workshop）：SWE-bench Verified 100 题，mini-SWE-agent 下 GPT-5-nano 解决 31%、DeepSeek-R1 30.3%、Qwen3-32B
  15.2%；把 gold patch 涉及的全部文件塞进 64K 单次上下文（召回率 100%），Qwen3-Coder-30B-A3B 7%、GPT-5-nano 0%。
  成功的 agent 轨迹通常在 2–3 万 token 以内；v1 表中失败轨迹的平均 token 是成功轨迹的 1.8–2.0 倍（两个模型）。作者结论：
  agent 的成功主要来自把任务拆成短上下文步骤，而非有效的长上下文推理。**边界**：模型偏小，只有 GPT-5-nano 两种设置都跑
  了（31% vs 0%），"约 30%"不是所有模型；workshop 论文，结论由 token 分布推断，不是因果实验。
- **SWE-Pruner**（arXiv 2601.16746）：SWE-bench Verified 全 500 题上，裁剪上下文使 token 降 23–38%，解决率 Claude
  Sonnet 4.5 70.6% → 72.0%、GLM-4.6 55.4% → 56.6%。+1.2–1.4 个百分点在噪声内，准确说法是**少读四分之一到三分之一而不伤
  成功率**，不是"裁剪反而提升表现"。
- **LoCoBench**（Salesforce，2025-09）：单轮 LLM 评测，难度上升时表现下降，但难度按上下文长度定义，长度与难度混在一起。
- **反例：LoCoBench-Agent**（2025-11）：同一团队的 agent 版本发现"agents exhibit remarkable long-context robustness"。
  综合：一个说得通的解释是 harness 的上下文压缩与记忆管理吸收了退化——这正是 [[AI工程方法论的耐久度]] 所说"context
  engineering 的机制层正被 harness 内建"。所以第二层"方向一致"要限定为"裸模型方向一致，带 harness 的 agent 不一定"。

### 第三层：代码库结构 → agent 表现——有受控实验，成功率零效应、成本正效应

| 研究 | 设计 | 成功率 | 成本 / 效率 |
|---|---|---|---|
| Trivedi & Schmitt（SonarSource，arXiv 2605.20049，2026-05-19） | 6 对"架构、依赖、外部行为相同，只差静态分析违规与认知复杂度"的仓库（Java/Python，2.6 万–13.7 万行），33 个任务、660 次试验，Claude Code + Sonnet 4.6 | 0.913（整洁）vs 0.921（杂乱），**无差异** | 整洁侧输入 token −7.1%、输出 −8.5%，回头重改已编辑文件 −33.8% |
| Borg 等（CodeScene，arXiv 2601.02200，FORGE 2026） | 5,000 个竞赛题 Python 文件（60–120 行），LLM 重构后测试是否仍通过，按 Code Health 分健康 / 不健康 | 五个中等规模开源模型在不健康代码上破坏语义多 8.6–15.1 个百分点（p<0.001）；**Sonnet 4.5（−2.7pp）与 Claude agent（−1.4pp）无显著差异**（p=0.439，只跑了 1,000 个文件，作者自承可能是功效不足） | 未测 |
| Patel 等（CodeThread，arXiv 2606.21804，2026-06-19） | 4 个前沿 coding agent、4 个基准：在 agent 写的代码上继续开发 vs 在人写的代码上继续开发 | 在 agent 代码上解决率最多低 13.1%；**传统可维护性指标解释不了这个差距**，更明显的信号是输入校验、错误处理等行为层差异 | 未测 |
| Thoughtworks（2026-07-30） | 同一变更在 15 步重构前后各重放一次 | 未测 | 输入 token −83%（约 5.8×），输出 token 与耗时未降；n=1 |

用户原文称 AGENTS.md 是"少数有实证研究的实践"——成立，但三项研究互相矛盾（ETH 测得成本 +20% 且不提升成功率，Lulla 等
测得 Codex 运行时间 −28.64%，McMillan 在 25–500 行内未测到文件大小效应；⚠️ 矛盾标注见 [[AI编码技术债的三层治理]]）。

> 综合：第三层的四项研究拼出的形态与"质量收窄、经济长存"一致——前沿模型对代码整洁度的**成功率**敏感性已经很低（SonarSource、
> CodeScene 的 Claude 组），开源中等模型仍然敏感（CodeScene），而**成本与效率**一侧每项测了的都是正向（7% 到 83%，幅度取决于
> 基线有多糟）。CodeThread 另提一个警告：决定后续 agent 成败的，可能不是"整洁"这类传统指标，而是 agent 代码在行为层的缺口；
> 用传统可维护性指标去衡量"为 agent 重构"的收益，可能量错了对象。

## 会被更强的模型抹平吗

| 维度 | 判断 | 依据与修正 |
|---|---|---|
| 质量 | 在收窄，未消失 | 收窄：同区间跌幅一年内从约 53 分降到约 11 分（Context Arena）；CodeScene 中强模型对代码健康度不敏感。未消失：(256K,512K] 区间仍跌 22–69 分 |
| 经济 | 相对优势长存，倍数不固定 | 用户原文"窄读取永远比全量读取便宜一个数量级以上（读 2k 行 vs 50k 行 ≈ 25×）"**失准**：25× 只是 token 数之比；缓存读价通常为基础价的 0.1×（部分新模型 0.05× 甚至 0.025×），多轮复用全量上下文时每轮边际成本差压到约 2.5× 或更低；本库仅有的实测是 7%（SonarSource）与约 5.8×（Thoughtworks），都不到一个数量级。另：50k 行约合 50 万 token，可能直接超出上下文窗口 |

综合：经济维度真正不受缓存影响的部分在**跨会话**——agent 每次变更从零开始读（Thoughtworks 的实验正是利用了"agent 不会
学习"），缓存的生存期只有 5 分钟到 1 小时，跨变更、跨会话的重复读取多数吃不到折扣。所以站得住的说法是：**每次变更的首轮
读取体量，决定了窄读取相对全量读取的成本优势；这个优势与模型能力无关，但倍数取决于读取比与缓存命中。**

用户原文另列的两条不随模型变强而消失：多 agent 并行依赖可分解的窄变更；人类 review 与 CI 的窄范围需求。这两条是判断，
没有单独测量；在本库中它们分别对应 [[AI工程方法论的耐久度]] 的"任务可分解性"与"验证优先"两条保值项。

## 待追踪 / 悬而未决

- 强模型上整洁度 × 成功率的**有足够功效**的对照；以及长视野（多次变更累积）下成本节省是否复利（SonarSource 自己提出的问题）。
- CodeThread 的行为层差异能否转成可计算的 sensor，替代或补充传统可维护性指标（接 [[Harness Engineering]]）。
- Anthropic、OpenAI 1M 自报分数的第三方复现。
- 拆大文件（Thoughtworks，−83%）与清理违规（SonarSource，−7%）的收益差一个量级：哪类重构动作贡献了大部分读取节省？
