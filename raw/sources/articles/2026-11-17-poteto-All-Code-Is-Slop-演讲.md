## 推文正文（verbatim）

一个月上线 3000 个 PR，大部分代码还能由 AI Agent 自己合并。🤯

GrokBot 工程师 Lauren Tan 在 AI Engineer Code Summit 上展示了自己的开发工作流。

每次 Agent 犯错，不是往提示词里加规则，而是把错误转成 Lint 检查规则。Agent 还会通过视频、截图和测试验证自己的工作。

她表示，这套方法让代码库保持整洁，也让 Agent 能自主合并大部分 PR。

### [00:00] 开场：人人都能成为 coding machine

All right, so again, my name is poteto. I work on Grok Bot at SpaceX SI. And can I ask you a quick show of hands? How many of you have ever looked at code that somebody else wrote and you thought, that's all slop? Well, I have too. But today I'm going to convince you that you can turn that slop into gold. And so, I did something crazy last month and I shipped 3,000 pull requests to production. Now, before agents, we never really cared about volume, except for the outliers. And at my previous company, we called these people coding machines. People like Bret Taylor, who famously rewrote all of Google Maps in a weekend. Just an insanely productive engineer. And well, with agents, anyone can now be a coding machine. And my thesis is that the job of the software engineer, the meta of being a software engineer, is figuring out how to maintain or even improve the quality of your code while massively increasing your productivity. To get there, some people like to call this a software factory. But I like to keep it simple. And I think of it as all about trust. Not blind trust, but investing in your agent's environment so you can trust that your agents are going to do the right thing. Now, it takes quite a lot of effort to get there. And it took me six months to get to a point where I could ship thousands of pull requests, a lot of them, in my sleep. But it's certainly possible. And it will take you much less time than I did. So, let's start by talking about how we move from a low trust environment to a

### [01:47] poteto 金字塔

high trust one. So, this inverse pyramid is how I think about where to spend time on your agent's environment. The first two layers are deterministic. So, using your code itself. So, things like good API design, architecture, refactoring, or using lint rules, type systems, compilers, or, you know, different kinds of testing. And you can use both of these layers together to constrain what agents can do and force them to do the right thing by default. Verification, both runtime and formal, are great tools to layer on to find bugs and check properties and the invariants in your system that you want to hold true. And also, help you check whether or not the agent understood your goals and your intent. And then, finally, you want to layer with a little bit of prose. So, things like rules, skills, agents.md, things that require judgment.

### [02:45] 代码库是花园：有机架构

But let's start with your codebase. Agents generate their outputs based on their inputs. And so, the quality of the input really matters. And it just so happens that your codebase is one of the largest inputs. So, whenever you're correcting your agent, think about how you can make that a deterministic check instead of adding another line to your rules or your agents.md. Because it's far more reproducible when it's in code and it lets you trust it more. And the analogy that I like to use is that your codebase is kind of like a garden. You know, code used to arrive a few pull requests at a time. And I remember going into work in 2024 and reviewing the three pull requests that my colleagues wrote. And today, that number is more like 300. So, you know, every engineer is now a team of hundreds or even thousands of agents. And code is arriving so rapidly that it almost feels like a continuous stream. And it almost feels organic, like a living thing. And in this analogy, your codebase, the constraints that you impose, the guardrails that you put up are the concrete foundations that the new code that your agents write grow around. Just like the building in this picture. And so, in many ways, the job of being a software engineer is kind of becoming like gardening. Because code is the biggest input for agents, it means that any workarounds, anti-patterns, deprecated code, it's now likely to be just copied by the next agent since it looks like the established pattern in your codebase. And it's like you have some weeds or pests growing in your garden and then they spread everywhere before you know it. So, you want to make your codebase as pristine as possible so that agents are always copying the good stuff. All right. Let's look at some real examples.

### [04:47] Dune 与反模式的类别性消除

So, Dune is a client framework that we created for Grok Bot to implement this idea for organic architecture. It's not really that interesting technically. You can kind of think of Dune as kind of like Next.js for Electron apps. But the interesting part of Dune is that it has a lot of constraints and lint rules that we've encoded a lot of the lessons that we've learned building desktop applications. And one such lesson is that anything that requires nuance to use well often leads to slop. You know, your classic example is useEffect in React. Right? It has its use cases, but it's often misused. Some people joke that you need a PhD to use useEffect. And in other words, it really requires a lot of nuance to use well. And agents are not good at using it. So, our solution has been to just ban it in product code. And it's really only allowed in some places inside of Dune APIs. And effectively, this problem has now been categorically eliminated and we never need to catch that during code review again. Another interesting pattern that we use is context through directory structure. So, one anti pattern that we saw with Cursor, which is an Electron app, is that agents would often import main thread code into the render thread, which would cause long tasks and jank. So, in Grok Bot and in Dune apps, we've made this very, very conventional. We have these two top level directories literally called electron-renderer and electron-main. And imports between them are forbidden or banned by our dependency graph analyzer and some lint rules. And again, these are simple lint rules to set up. But it means one less thing that we need to review and think about during code review. And then one more surprising thing that I've seen is agents using markdown. So, things like documentation, code comments, rules or skills. And they use this as a place to write down their justifications for not doing the right thing. Or I don't know if you've ever seen this, but they'll over rotate on some small correction that you made and they treat it like a hard rule that can never be broken ever again. And here's another example from Cursor. So, agents really loved using imperative timers. So, things like setTimeout, requestAnimationFrame, requestIdleCallback. And they were using these as quick fixes because they were really patching over an architecture clash between VS Code's imperative style and React's declarative style. So, our choice of architecture actually made both the client and the agent performance much worse. And if you've ever done any performance work in JavaScript, you'll know that when you have tons of timers being rapidly created and destroyed, causes a lot of major garbage collection, which causes a lot of lag and jank. But the worst part is that agents wrote a lot of code comments like you can see in red here, explaining why this quick fix was justified. And before you know it, we had timers spreading everywhere and the performance of the app really suffered. Now, in Grok Bot, we learned our lesson there and we decided to just ban 99% of comments because they go stale easily. Humans just really don't bother reading the comments a lot anyway. And again, it gives an agent an escape hatch to justify not doing the right thing because it's hard. And the worst part about comments, though, is that they're not enforceable. So, what seems well intentioned, you know, like I'm going to tell the next agent not to do something, never ends up actually being anything that you can trust. So, in Grok Bot and in Dune, we now have lint rules that give good and very helpful error messages telling the agent to fix the root cause, the real problem, rather than just patch around it. And so, our general principle is that every time we correct our agents, it turns into one of these deterministic checks where we think about how to categorically eliminate that problem in the code through better API design, through better architecture. And if you do this enough times, you'll find that you have just less things to look out for in code review. And at some point, you realize there's nothing left to review and you can just let agents merge most of their own pull requests.

### [09:27] 验证

All right. Moving on, verification is also a really big part of how we make our agents more autonomous and also increase our confidence and trust in their work. And our code review process has now really shrunk into looking at verification artifacts instead. So, things like videos, screenshots, diagrams, formal verification. And the most basic example of this is runtime verification, which is just a fancy way of saying giving your agent a way to run the code for itself and use debugging tools that human developers use as well, like the Chrome DevTools protocol. In our runtime verification skills, we have this thing that we call a feature map. And that's basically kind of like a site map of all of the features that are available in your application from the user's point of view. And so, with this, agents don't need to guess when you say, you know, the thingy in the left side bar. It gives you some shared vocabulary. And we also make use of custom CLIs inside these skills so that agents can reuse the CLI and the driver every time, which cuts down on token usage and is also testable. And then recently, we've also started looking at formal verification. So, we now use TLA+ to do some model checking of major user flows, such as notifications across multiple devices and platforms. We use Lean as well for proving certain algorithms. For example, we have our own we wrote our own custom virtualization library and we use Lean there to check that we don't have flickering or jittering problems. And we're still experimenting with this approach overall. It seems very promising. We've already found quite a few bugs with formal verification. But it's certainly not a silver bullet and we're treating it as another tool, another layer in our agents' environment. And then this is a very fast video. But another thing that we just started looking at is property-based testing as well for UIs. So, we use this library called Bombadil. And this has also caught a few UI bugs for us already.
