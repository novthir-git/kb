# Does Code Cleanliness Affect Coding Agents? A Controlled Minimal-Pair Study（中文结构化研究摘录）

- 原文：https://arxiv.org/abs/2605.20049 （全文 HTML：https://arxiv.org/html/2605.20049v1 ）
- 作者：Priyansh Trivedi、Olivier Schmitt（均为 SonarSource）
- 发布日期：2026-05-19（arXiv v1，cs.SE；截至检索日只有 v1，未见同行评审信息）
- 配套博客：https://www.sonarsource.com/blog/a-cleaner-codebase-results-in-less-token-usage/
- 检索与入库日期：2026-11-05（curl 直连 arXiv abs 与 HTML 全文）
- 存档说明：要点式中文摘录，非翻译或镜像；Table 1–4 的测量值按原文照录（事实数据）；参考文献未收录。
- 证据性质：作者自建的受控最小对实验，单一配置（Claude Code + Claude Sonnet 4.6），Python 与 Java 仓库；
  作者受雇于 SonarSource，"整洁"用 SonarQube 规则违规数定义，存在利益相关。

## 研究问题

- RQ1：代码整洁度是否影响 coding agent 完成任务的能力？
- RQ2：是否改变 agent 的运行足迹（输入/输出 token、推理、对话长度、读文件数、重读次数、改动行数）？
- RQ3：效应是否随任务拓扑变化，尤其是"集中在单个高密度代码区"与"跨多个模块边界"之间？
- 作者称：据其所知，此前没有工作在固定 agent 与任务的前提下改变代码库本身。

## 实验设计

- **最小对（minimal pair）**：架构、依赖、测试、外部行为相同，只在 SonarQube 规则违规数与认知复杂度上不同的两个仓库。
  "整洁"没有形式化定义，以 SonarQube Cloud Enterprise 的 "default quality gate" 规则集违规数为代理。
- **双向构造**：
  - Slopify（降质）：从整洁仓库出发，三阶段 agent 流水线（Build → Explore → Transform）引入精选 SonarQube 规则的违规，
    每轮重跑测试，破坏测试的轮次被拒绝。变换包括把 helper 内联进调用方、跨路径复制逻辑、**往文件里塞死代码**、
    偶尔把多个模块合并成单文件。
  - Vibeclean（清理）：从自然生长的混乱仓库出发，按分析器问题清单逐条修复：去重字符串字面量、**删除注释掉的代码**、
    替换旧集合写法、**删除死分支**；对真正的上帝结构做结构性改写（如把 200 多行的分发 switch 换成具名 helper、
    从 2,800 行的类里抽出持久化 helper）。抽取只是把复杂度分散到更多方法，几个最大的上帝结构被标为 wontfix。
- 6 对仓库：3 个主要为 Java、3 个主要为 Python；3 个公开、3 个 SonarSource 私有（私有仓库用于防止模型记忆训练数据）。
- **任务**：33 个，三条轨道。
  - Cognitive-hotspot（13 个）：经过单方法/单类高复杂度区域。
  - Multi-module（14 个）：需要跨两个及以上模块修改。
  - Calibration（6 个）：刻意选在两侧完全相同的区域（如在 CLI 入口加一行日志），作为对照。
  - 任务描述只给外部可观察的输入输出，不点名任何文件或函数；隐藏测试只通过应用的公开接口交互。
  - 两道自动检查：参考实现必须在两侧都通过隐藏测试；未改动的仓库必须不通过。
- **运行**：Claude Code 默认工具集，agent 只读任务描述，不知道自己在哪一侧。所有报告数字来自 Claude Sonnet 4.6；
  另跑过 Claude Haiku 4.5，其通过率过低、无法读出足迹差异，被排除。每个任务每侧 10 次，共 660 次。
- **统计**：同一（任务，侧）内偏离 10 次中位数 50% 以上的运行被剔除（实际剔除 9.7%）；数据集级数字按 33 个任务
  micro-average；通过率报告绝对百分点差，其余报告 (cleaner − messier) / messier。

- 校准轨道 −75% 重读只是六个任务中一个任务的三次重读，因 micro-average 显得很大。

## 方差

- 同一任务同一侧 10 次运行中，最贵一次的输入 token 通常是最便宜一次的约 2.5 倍；约 72% 的组超过 2 倍。
  最极端例：ckan/organization-list-exclude-empty 整洁侧 1.4M–10.6M、混乱侧 1.8M–14.3M。
- 原文："A single per-task delta of around 10% may therefore be agent noise rather than signal"；数据集级结论成立是因为汇集了数百次运行。
- 27 个真实轨道任务的输入 token 差从 −47% 到 +44%，中位数 −4.5%；16 个任务整洁侧更省，11 个更费，"更接近 60/40"。
  读文件数则 10 个任务整洁侧更少、17 个更多。

## 案例

- 整洁侧胜（commons-bcel/stack-effect-annotation-in-disassembly）：混乱侧两个数百行的 JVM 操作码 switch 上帝方法，
  清理后变为几十行的薄分发器 + 约十个具名 helper。整洁侧输入 token −35%、读文件 −25%、改动行 −31%、对话轮次 −32%。
  文件本身并没变小；原因是 agent 能用 grep 精确定位要改的地方。
- 混乱侧胜（genie/cluster-active-job-limit）：清理在核心启动逻辑周围抽了 helper 但保留原逻辑，整洁侧输入 token +8%，
  其余指标在几个百分点内。作者解读：增加了结构表面积却没有带来可导航性收益。

## 作者自列局限（第 6 节）

- 端到端由作者策划：仓库选择、配对构造、任务编写都由作者完成，选择偏差会直接传到结论。
- 单一配置：只有 Claude Sonnet 4.6 + Claude Code；未测 GPT、Gemini 系列与其他 harness；机制可迁移是推测。
- 只算 token 不算美元：美元成本取决于模型、供应商、缓存与排队，且与 token 非线性。
- **只用隐藏测试**：不检查 agent 是否破坏了仓库原有的其他测试。
- 未对 agent 的输出做整洁度扫描，不能回答整洁度会自我强化还是自我侵蚀。
- "cleaner / messier" 只是对内标签，不是对原仓库的评价。
- **短程**：值得下一步测的是这些每任务节省会不会复利，或代码库是否会漂移到抵消它们；作者点名 SlopCodeBench 的迭代评测方法。

## 结论原话要点

- "cleaner code did not change whether the agent finished its task, but it reduced the footprint the agent left doing it."
- 最清楚的行为标记是重读：整洁侧重开已编辑文件的次数约少三分之一。
- 作者把它定位为反驳"可维护性原则只为人类读者校准、agent 时代不再重要"这一说法的一小块证据；
  长期演化中是否复利仍是开放问题。
