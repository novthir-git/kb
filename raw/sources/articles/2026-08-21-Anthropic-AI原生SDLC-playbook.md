## 一、Code is no longer the bottleneck

传统 SDLC 六阶段（plan / design / build / test / deploy / maintain），每阶段是由不同角色拥有的离散
阶段，工作通过文档、工单和签核在阶段间流动。原文核心前提：

> "the traditional SDLC was designed to maximize efficiency in an era where the most time-consuming
> and expensive stage was writing and implementing code, which is no longer the case."

当 build 不再是约束，三件事成立（原文列举）：

1. "The bottleneck moves to the steps to the left and right of the build phase. This is mainly plan,
   review/test, and deploy, which still run at human speed."
2. "The controls stop matching reality and become intractable. Reviewing each line by hand made sense
   when a person had written it, but it can't keep up once agents write most of the diff."
3. "Governance costs increase because exceptions still route through meetings and committees that meet
   weekly or monthly."

安全瓶颈作为示例：安全团队按人的产出规模配置，agent 放大代码产出后，"either the review queue builds
or code ships under-reviewed. A regulated organization can't accept either outcome."

## 二、What is an AI-native SDLC?

> "The AI-native SDLC is a reimagined process that combines the old control objectives with new
> enforcement. Instead of a linear flow, the process becomes a loop, and AI is embedded at each point."

原文注明别名："the agentic SDLC, the AI SDLC, or simply agentic software development — the labels
differ, but they describe the same thing."

### 六阶段对照表（原文表格）

| Stage | Traditional SDLC | AI-native SDLC |
|---|---|---|
| Plan | Requirements gathered by committee, distilled through workshops and sign-offs, written up by hand | Claude synthesizes pain points straight from the sources and captures them within intent.md which is human readable and machine actionable |
| Design | Spec written by analysts, parsed by designers | Requirements and design compressed into one working session with an agent, guided by standards encoded as skills, versioned in git |
| Build | Tests and code are handwritten and documentation is written after the main development happens | Tests and code are generated by AI and institutional knowledge is maintained as versioned machine-readable CLAUDE.md files and skills |
| Test | QA gates at stage boundaries | Continuous evals woven through implementation |
| Deploy | Humans review every line of code and governance occurs in review cycles, often inconsistently | Layers of agentic review with human review reserved for regulated and critical code. Governance is enforced as the AI acts, with hooks as approval gates |
| Maintain | Humans watch production for bugs | Agents monitor live deployments. Any breached control band is diagnosed and written back into the loop as a new intent.md |

### 贯穿主线：committed artifact

> "The thread running through the right-hand column is the committed artifact. Each stage ends by
> writing one to version control (including intent.md, spec.md, plan.md, the diff and its tests, the PR
> with its review findings, and the incident record) and the next stage begins by reading it. ...
> The chain of commits is also the audit trail: who asked for what, what the agent produced, and who
> approved it."

> "Humans remain accountable for every decision that requires judgment. In the agentic SDLC world, the
> human attention shifts along with the artifacts that must be reviewed."

### Plays 的统一结构

每个 play 覆盖：What changes；Getting started（Prerequisites / Infrastructure）；Concrete steps；
Governance considerations；How to measure it（leading + lagging indicator）。

> "A stage ends by committing an artifact with the commit initiating the next stage. An accepted
> intent.md triggers the requirements and design pass, an approved spec.md triggers plan mode, a merged
> PR triggers the pipeline, and a breached control band in production writes the next intent.md and so
> the loop continues."

原文强调 plays 是模块化、非线性的，依赖关系由每个 play 的 "Prerequisites" 与依赖图给出。

## 三、Stage 1 — Plan

### Play: Capture as intent.md

intent.md 的三种入口：人有想法、工单被提交、告警触发事故（见 Stage 6）。

- Traditional："An idea passes through backlog entries, user stories, story points, and refinement
  meetings before anyone can act on it. Ownership transfers at each handoff, so what reaches
  engineering is several steps removed from what the originator meant."
- AI-native："The originator brainstorms with Claude and writes the result down as intent.md, a
  proto-spec in the originator's own terms."

Prerequisites：None。
Infrastructure：非工程人员的 Claude 访问（claude.ai 或 Cowork）；约定的 intent.md 模板；产品负责人
监看的、版本控制的共享位置。单产品最简形态是产品 repo 里的 `intent/` 目录；跨多仓库时才值得建独立
intent repo。无 git 经验的贡献者通过 GitHub 连接器由 Claude 代为提交。

执行步骤（原文）：
1. 发起人用自己的话向 Claude 描述问题，无需正式语言。
2. 头脑风暴至想法具体化。"Claude asks the questions an analyst would ask: scope, users, constraints,
   and what success looks like."
3. 让 Claude 按组织模板写成 intent.md（模板可编码为 skill，由技术成员搭建、lead 签核）。
4. 发起人纠正 Claude 误解的地方。
5. 提交到共享位置，作者与时间戳进入记录。

示例产物：

```md
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.

## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.

## Proposed outcome
Customers see claim status, next step and expected date in the portal.

## Affected users and systems
Claims handlers, portal team, claims-core API.

## Constraints
No new PII in the portal session. Existing authentication only.

## Open questions
Do third-party loss adjusters need access too?
```

Governance：证据是被提交的 intent.md，含作者、时间戳与完整修订历史，记在 intent home 的 git 历史里。
产品负责人批准，接受/拒绝的决定记录为 merge 或 closing review。

度量：
- Leading — 从第一次对话到 intent.md 被提交的时间（读 git 历史）。"The expectation is to fall from a
  multi-week elicitation and refinement cycle to hours."
- Lagging — survival rate：产品负责人接受进入 Design 的 intent.md 占比；以及同一变更首次 spec.md 提交
  之后 intent.md 的修改次数。

## 四、Stage 2 — Design

### Play: Requirements and design

> "Claude takes the accepted intent.md and produces a requirements and design spec. This is guided by
> the organization's skills for brand, security, compliance, and UX."
> "The product owner reviews that spec, but doesn't write it."

- Traditional："Requirements and design are separate phases run by separate teams. ... The separation
  exists for accountability, but it is slow and lossy."
- AI-native："Both phases happen in a single prompted session ... constrained by the organization's
  skills, with areas of concern flagged."

前端工作路径：产品负责人从 intent.md 在 Claude Design (beta) 中做 mock，迭代后导出到 Claude Code 构建。

Prerequisites：intent.md 文件，加上写成 skills 的 brand / security / compliance / UX 政策。
Infrastructure：一位有 Claude 访问权的产品负责人。"No engineering skill is required."

执行步骤要点：
- 先手工运行 prompt，再固化为组织级 slash command；最终以 intent.md 在 intent home 的合并为触发器，
  由非交互式作业运行、把 spec.md 作为 PR 提交。"From that point the product owner's first involvement
  is the review."
- "Work through the flagged concerns first as they are the points an analyst would have escalated."
  产品负责人在工程看到 spec 之前，与各政策 owner 逐条解决。
- spec.md 与 intent.md 并置提交。"The file pair records what was asked for and what was decided."
- 是否进入 build 由人决定，高风险咨询技术 lead。"A human team mate always makes this call."

示例 prompt：

```text
Read the attached intent.md and produce a requirements and design spec for integrating it into our
existing codebase. Apply the skills available to you so the plan conforms to our brand guidelines,
security policies and UX standards. Document the spec fully as spec.md, ready to hand to the
engineering team. Describe clearly any areas of concern, especially where you cannot satisfy
contradicting policies.
```

Governance："Instead of being discovered in a review weeks later, the live policy is read and applied
while the spec is written." spec、产生它的 prompt、以及生效的 skill 版本全部记入版本控制。

度量：
- Leading — 同一变更 intent.md 提交到 spec.md 提交的间隔（两个 git 时间戳）。
- Lagging — build 开始后的需求返工：统计同一变更首次 plan.md 提交之后的 spec.md 提交数。

## 五、Stage 3 — Build

> "Nothing is implemented without an accepted plan. Institutional knowledge becomes files the agent
> reads, and the guardrails run as code rather than as habits."

### Play: Claude Code plan mode as the default starting point

- Traditional："How the change will be made, down to which files and which tests, stays in the
  engineer's head or at best a ticket comment. Nobody else can review it."
- AI-native："Work starts with a written plan that Claude produces in plan mode, where it can read the
  codebase without changing anything."

执行步骤要点：
- 给 Claude intent.md 与 spec.md，要求实现计划点名"哪些文件会变、工作顺序、以及证明它的测试"。
- "Interrogate the plan by asking what the change could break, which step is most risky, and what other
  options Claude chose not to do."
- "Iterate until an engineer who has never seen the conversation could implement the change from the
  plan alone."
- 提交为 plan.md，PR review play 会拿最终 diff 与它比对。
- **"When implementation departs from the plan, update plan.md in the same commit. Consider using a
  hook to enforce synchronization between the two."**

示例产物：

```md
# Plan: claims status self-service (from intent.md 2026-06-02)

## Files that change
portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py,
claims-api/tests/test_status.py

## Order of work
1. Add the status endpoint behind existing auth.
2. Panel against the endpoint.
3. Wire into the portal nav.

## Risks
The claims-core API rate-limits at 50 rps; the panel must cache.

## Proof
test_status.py covers the four claim states; screenshot matches the
approved mock.
```

Governance："Plan mode enforces this itself, since Claude cannot edit files until the engineer accepts
the plan."

度量：Leading — 首次实现即合并的变更占比、计划批准到 PR 合并的时间；Lagging — 每次变更的返工轮数、
合并 diff 与 plan.md 仍然吻合的频率。

### Play: Claude Code on auto mode

随后续 play 的护栏成熟（调好的 CLAUDE.md、编码政策的 skills、阻断不安全动作的 hooks、Claude 可运行的
测试套件），auto-accept 成为常规工作的默认："a tight spec.md, a small blast radius, and code the tests
already cover."

> "The shift is now away from the user watching the agent make the edits and reviewing actions, towards
> the review of artifacts after longer autonomous sessions."

### Sidebar: Legacy systems and the source of truth

适用于流程产出的每一个产物。既有系统（Jira、需求工具、Figma、变更委员会）难以取代，因为审计与监管
已经接受它们。三种配置：

- **The repo as the source of truth** — markdown 产物是权威记录，legacy 系统引用 commit 内的文件。
  "one of the cleanest configurations for engineering-led organizations, as all records live in one
  tool with one timestamp authority."
- **The legacy system as the source of truth** — Jira/ServiceNow/需求工具持有权威记录，markdown 是
  工作副本；Claude 会话开始时读取记录，结束时通过 MCP 连接器写回。
- **Linkage as the minimum bar** — 所有产物记录 record ID，所有 legacy 记录含 markdown 文件的 commit
  SHA。"Linkage is a good place to start when transitioning to the AI-native SDLC, **accepting that
  there are two sources of truth**."

> "Both the legacy system and the markdown-first system can coexist, so long as there is a link between
> the two or one is declared the source of truth."

### Play: The CLAUDE.md

> "CLAUDE.md gives Claude the context a new joiner would need, covering conventions, commands,
> architecture, and the mistakes the team sees most often."

执行步骤要点：`/init` 生成初稿 → 裁剪到"新人第一天需要的"→ 签入 git repo 根 → **"When Claude makes a
mistake twice, the correction goes into CLAUDE.md."** → "Keep it under a page, because Claude reads all
of it at the start of a session and anything stale is taking up context for no benefit."

示例产物：

```md
# Payments service

## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (runs in CI; fix before pushing)

## Conventions
- Java 21, Spring Boot 3. No new Lombok.
- Money is always BigDecimal, never double.
- Every endpoint needs an integration test in src/itest.

## Architecture
- api/ holds REST controllers, core/ holds domain logic,
  adapters/ talks to external systems.
- Kafka events are defined in schemas/; never edit generated classes.

## Things Claude gets wrong
- Do not bump dependency versions; the platform team owns them.
- The legacy v1/ package is frozen; changes go in v2/.
```

度量：Leading — Claude 重复犯 CLAUDE.md 本应拦住的错误的频率；Lagging — 新成员首次合并 PR 的时间。

### Play: Skills as institutional knowledge

> "The rule of thumb: write a skill for institutional knowledge that must be applied consistently;
> don't write a skill for components that belong in CLAUDE.md or a prompt."

Infrastructure："One policy with a named owner and a written source of truth."

示例产物：

```md
---
name: secure-api-review
description: Apply the API security standard. Use whenever creating or
  modifying an external-facing endpoint, reviewing API code, or
  generating an OpenAPI spec.
---
# Secure API review

When you create or change an API endpoint:
1. Authentication: every endpoint requires the gateway JWT;
   no anonymous routes outside /health.
2. Input validation: validate request bodies against the OpenAPI
   schema and reject unknown fields.
3. Audit: every state-changing endpoint emits an audit event with
   actor, action, entity and timestamp.
4. Data classification: fields tagged pii in the schema must never
   appear in logs or error messages.

Run scripts/check-endpoints.sh and include its output in your summary.
```

**Governance（关键论断）：**

> "A skill is a control, though an advisory one. It makes Claude likely to apply the policy while the
> code is written, and nothing forces a session to comply with it. A policy that must always hold needs
> something deterministic behind the skill, such as a hook that blocks the action or a review pass that
> re-checks the policy at the PR. **The skill makes violations rare and the hook makes them close to
> impossible.**"

度量：Leading — 政策 owner 批准变更到 skill 合并的时间；Lagging — 引用该政策的 PR review 发现数，
应趋近于零。"Where the findings don't fall towards zero, either the skill isn't triggering or its text
has drifted from the official policy."

### Play: Hooks as build-time guardrails

> "A skill is an advisory control while a hook is the deterministic layer behind it."

build 阶段 hook 可以：阻断对受保护路径（生成类、冻结包）的编辑；在文件编辑后运行 formatter 与 linter
"so drift never accumulates"；把凭据挡在 diff 之外。

"A hook that asks a human for approval belongs with the gates in Stage 5: Deploy, because an approval
prompt during the build puts a person back on the critical path of all the sessions running in parallel."

### Play: Parallel sessions and subagents

- 并行 session = 另一个完整 Claude Code 实例，在自己的 git worktree 中做独立任务。
- subagent = 单个 session 内的受限助手，有自己的上下文窗口与工具限制。

执行要点："Two or three sessions is a sensible starting point. The practical ceiling is how many streams
one person can review properly, so add sessions only while review is keeping up."

subagent 示例：code simplifier、verifier、researcher。示例产物：

```md
---
name: verifier
description: Runs the app and checks the change works before the session
  reports done
tools: Bash, Read
---
Start the app with make run. Exercise the changed behavior and the two
nearest neighboring flows. Report what you ran, what you saw, and any
behavior that does not match plan.md. Do not fix anything; report only.
```

度量：Leading — 在 review 质量保持的前提下每位工程师的并发 session 数（读 OpenTelemetry 导出）、
一天中用于 steering 而非等待的比例；Lagging — 每位工程师每周合并的变更数，与返工率并读。

## 六、Stage 4 — Test

> "Every session checks its own work before a human sees it, and the configuration that steers the agent
> gets regression-tested like the code it writes."

### Play: Give Claude a feedback loop

区分（原文明确）："The feedback loop runs through the whole task as many times as the work. The verifier
subagent, on the other hand, is one way to package the final check by running a fresh context window
once the session believes the work is done. This way the verdict is not colored by the assumptions that
produced the code."

执行步骤要点：
- 把检查包成单一命令（`make test` / `npm test`），失败时非零退出；在 CLAUDE.md 的 Commands 节列出每条
  命令并给出健康输出示例。
- 目标要可量化，让 Claude 无需询问即可自检。
- 修 bug 时先写失败测试："Ask Claude to reproduce the bug as a test, run it, and confirm it fails for the
  reason you expect. Commit that test. Only then ask Claude to make it pass without editing the test...
  A test that existed before the fix, and that the agent couldn't rewrite, is proof the bug is gone."
- UI 工作用视觉检查闭环（浏览器或截图工具 + mock，实现→截图→比对→调整，两三轮为常态）。
- **"the loop itself needs protecting, because an agent fixing code must not be able to weaken the check
  on that code. A hook that blocks edits to test files during a fix task does this."**

示例产物：

```md
## Verifying your work

- Build: make build (must finish with "Build succeeded")
- Test: make test (all green; never skip or delete a failing test)
- Lint: make lint (zero warnings)

Run all three before reporting any task complete, and paste the output.
If a test fails, fix the code, not the test.
```

Governance 四问：
- What is enforced — 报告完成前必须验证；修复任务期间阻断 agent 编辑测试文件（需要保证时实现为 hooks）。
- What the evidence is — `make test` 的字面输出、构建日志或截图 diff，"so the evidence comes from the
  toolchain."
- Where it is logged — session transcript（经 OpenTelemetry 导出到组织可观测栈）与 PR 的 check run。
- Who approves — 审 PR 的 code owner，"who can concentrate on intent and risk because the mechanical
  evidence is already attached."

度量：Leading — agent 所写变更的首次 CI 通过率；Lagging — 每个 PR 的 review 时长、变更失败率。

### Play: Continuous evals in CI

> "Evals are the AI-native equivalent of stage-gate QA. In practice that means a suite that runs whenever
> the agent's configuration changes. When a new model is swapped in or a prompt is rewritten, the eval
> suite says whether the agent still does the work to the same standard."

> "The evals should be seen as a live suite. As models improve, cases that once discriminated stop doing
> so and new ones must be added that arise from ongoing monitoring."

执行步骤：
- 平台工程师从近期工作中收集 20–50 个真实任务及其预期/可接受结果。
- 每个任务写成 eval = prompt + 定义"可接受"的检查（测试通过、lint 干净、行为不变、政策被遵守）。
- **"The suite runs non-interactively in CI on a schedule and on any change to CLAUDE.md, skills or
  hooks, since that configuration steers the agent and deserves the regression testing that code gets."**
- **"Gate configuration changes on the results. A skill change that drops the pass rate gets reviewed
  before it merges."**
- **"Each production incident gets an eval, written by the team that owned the incident, and stays in the
  suite as a regression test."**

示例产物：

```yaml
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
```

度量：Leading — eval 通过率随时间的变化、生产事故变成常驻 eval 所需的时间；
Lagging — CI 捕获的回归数 vs 生产中发现的回归数。

## 七、Stage 5 — Deploy

> "Review runs in both directions, and governance is enforced as the agent acts. **The agent does
> everything up to the production gate and nothing past it.**"

### Play: AI in the PR review loop

Claude 既给 review 也收 review。"This allows engineers to focus on behavior in their PR review, which
boils down to judging intent and risk."

执行步骤要点：
- 托管 Code Review 服务（research preview）是最快起点；需要控制流水线或走自有云协议时用
  claude-code-action 在自有 CI 运行（模型调用可经 AWS Bedrock、Google Vertex 或 Microsoft Foundry）。
- 技术 lead 把 review 政策写成 repo 根的 REVIEW.md，划分为组织关心的 passes；REVIEW.md 同时定义什么算
  Important、什么算 Nit、什么跳过。
- **"The tech lead sets the human threshold. Findings do not approve or block a PR on their own, and
  branch protection still requires approval from a code owner."**
- @claude 标记可让 Claude 处理评论并推送修复；对 Claude 自己开的 PR 可"babysit the PR to merge"。
- **"Review findings feed back into CLAUDE.md. When a review flags a mistake for the second time, the
  correction goes into CLAUDE.md as part of that review... Review also flags when a change has made
  CLAUDE.md outdated."**
- 每月由技术 lead 调优：给 findings 评分、在 REVIEW.md 里限制 Nit 数量、排除生成路径与 CI 已强制的项。

示例产物：

```md
# Review instructions

## Passes
Run three passes and tag each finding with its pass:
- Bugs: logic errors, broken edge cases, subtle regressions
- Security: injection risks, authentication gaps, PII in logs
- Compliance: the change matches spec.md, plan.md and our design principles

## What Important means here
Reserve Important for findings that would break behavior, leak data
or breach a policy. Style and naming are nits.

## Cap the nits
Report at most five nits per review; summarize the rest as a count.

## Do not report
Generated files under src/gen/ and anything CI already enforces.
```

Governance："Separation of duties is preserved, because **the agent that wrote the code has no way to
approve it**." 原文在此处交叉引用："For how these controls compose at production scale, see securing an
AI-native SDLC at Anthropic."（即 2026-07-21 的安全博客）

度量：Leading — 首次 review 时间（应降到分钟级）、无需人工触碰分支即解决的 review 评论占比；
Lagging — 合并前捕获的缺陷与漏洞 vs 逃逸到生产的。

### Play: Hooks as approval gates

> "The build phase used hooks as guardrails, allowing or blocking actions with no human involved. A hook
> can also **ask**, pausing the action until a specific person approves, which is what release gating
> needs."

"hooks are not deploy-specific: they run wherever Claude acts."

执行步骤：工程领导层会同变更管理与合规，列出必须存活的人工审批门禁；平台工程师把每个门禁表达为 hook
（allow / ask / block）。"Team hooks go in .claude/settings.json in git, and non-negotiable hooks go in
managed settings owned by the platform or IT admin, where individual engineers cannot switch them off."
"A block should explain itself."

示例产物：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh" }
        ]
      }
    ]
  }
}
```

```bash
#!/bin/bash
# Production deploys require a named release authorization
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "Production deploys need a release authorization." >&2
    exit 2  # exit 2 blocks the action; the message goes to Claude
  fi
fi
exit 0
```

### Worked example: Managed settings for a regulated enterprise

由平台团队经 MDM 或管理控制台下发，工程师不可编辑或覆盖：

```json
{
  "permissions": {
    "deny": [
      "Read(.env*)", "Read(./secrets/**)",
      "WebFetch", "Bash(curl *)", "Bash(wget *)"
    ],
    "allow": [
      "Bash(git *)", "Bash(make build)",
      "Bash(make test)", "Bash(make lint)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": { "allowedDomains": ["git.internal.example.com",
                                    "registry.npmjs.org"] },
    "credentials": {
      "files": [
        { "path": "~/.ssh", "mode": "deny" },
        { "path": "~/.aws/credentials", "mode": "deny" }
      ],
      "envVars": [ { "name": "GITHUB_TOKEN", "mode": "deny" } ]
    }
  },
  "allowManagedHooksOnly": true,
  "disableSideloadFlags": true,
  "allowManagedMcpServersOnly": true,
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "example-corp/approved-plugins" }
  ],
  "requiredMinimumVersion": "2.1.193"
}
```

每一行买到的控制（原文逐条解释）：
- `permissions.deny` 把 secrets 挡在 agent 上下文外并阻断经工具的任意网络出口；`permissions.allow`
  预批准安全内循环，"so the deny list doesn't turn into prompt fatigue."
- `disableBypassPermissionsMode` + `allowManagedPermissionRulesOnly`：没有工程师、项目文件或命令行 flag
  能放宽规则。
- `sandbox` 补 permissions 补不上的缺口："A tool-level deny on WebFetch doesn't stop a shell command
  reaching the network; the OS-level domain allowlist blocks egress outright."
- `failIfUnavailable` + `allowUnsandboxedCommands`：sandbox 无法初始化时 Claude Code 拒绝启动；
  sandbox 内失败的命令不能拿到外面重试。
- `credentials`：deny 规则只管 Claude 的文件工具，sandboxed shell 命令仍可能读 `~/.ssh` 或
  `~/.aws/credentials`；此块拒绝这些读取并从每个 sandboxed 命令的环境中剥离指定 secret。
- `allowManagedHooksOnly`：审批门禁是唯一运行的 hooks。
- `disableSideloadFlags` + `strictKnownMarketplaces`：每个 skill、agent、hook 与 MCP server 都来自组织
  批准的 plugin marketplace，而非来自 home 目录。
- `allowManagedMcpServersOnly`：agent 的工具面成为平台团队拥有的 allowlist。
- `requiredMinimumVersion`：低于批准下限的版本拒绝启动。

> "Consider the above a starting point to tailor, rather than a recommendation to copy. Every deny trades
> against capability, and the right balance depends on the data classification of the repo."

度量（针对 hooks 本身）：Leading — 每个审批门禁上的等待时间（每次 hook 决定含时间戳与 allow/block 判定
写入 OpenTelemetry 导出）；Lagging — hooks 前后到达生产的门禁违规数。

### Play: CI/CD integration and deployment

执行步骤要点：
- 从只读判断步骤起步（`claude -p` 在流水线作业中分诊失败构建、总结 flaky test、起草 changelog）。
- 写操作步骤放在既有门禁之后。"Anything the agent writes arrives as a PR through branch protection, and
  the agent has no route to push to main."
- 执行沙箱化："Agent jobs run in containers under a network policy with short-lived scoped tokens, and
  hold no production credentials by default."
- 通过 MCP 暴露部署："Deploy, status, and rollback become tools, scoped per environment, so the agent's
  deployment powers are an allowlist rather than a shell script with credentials."
- 按环境分层自主权："In development, the agent deploys freely. In production, the agent prepares the
  release and the release manager authorizes it, and a hook enforces the production gate."
- **"Rollback should be the most rehearsed path in the pipeline, a single command that the agent can run
  and that is exercised regularly in staging."**

示例产物：

```yaml
- name: Triage failed build
  if: failure()
  run: >
    claude -p "Read the build log at out/build.log. Identify the most
    likely cause, say whether the failure looks flaky or real, and write a
    three-line summary for the PR thread." >> triage.md
```

Governance 原则："The governing principle is that **the agent may act up to the production gate and
cannot pass it**." 三项控制：branch protection；production deploy hook；per-environment permission tiers。
"Each non-interactive run acts under the agent's own identity, so the pipeline log separates what the
agent did from what the engineer who triggered it did."

度量：Leading — 无需呼叫人工即完成分诊的流水线失败占比；Lagging — DORA 指标。

## 八、Stage 6 — Maintain

> "The loop closes. A trigger invokes Claude with no person in the invocation path, and what it finds
> re-enters the pipeline as intent.md."

> "Stage 6: Maintenance runs headless, with an independent confidence gate between stages, a
> deterministic check or an adversarial reviewing agent, deciding whether the previous stage's output
> continues or is escalated to a human."

### Play: Closing the loop（控制带）

> "A deterministic script watches production and invokes Claude when a control band is breached."

Prerequisites：intent.md（给循环一个结构化输出以重启流程）、Claude 加速的 PR review、作为动作边界的
hooks、CI/CD 的 rollback 路径（最高自主层会调用它）。

执行步骤：
- 服务 owner 或平台工程师挑一个有稳定滚动基线的指标：CI 测试失败率、部署后 5xx 率、PR cycle time。
- 编写检测脚本，"typically mean and standard deviation over a rolling window with rules (Western Electric
  or similar) so the bands catch slow drift as well as spikes. The script is version controlled and unit
  tested, and **detection stays entirely deterministic, with no model involved**."
- 响应层级定义在版本控制的配置里："At 1σ the script only logs, at 2σ it invokes Claude read-only to
  diagnose, and at 3σ Claude may act, though **only by opening a PR into the review gate or triggering a
  pre-approved runbook**."
- 触发层可以是 GitHub/GitLab 的定时 workflow、既有监控栈的 webhook，或网络内的 Cron Job。
  "Claude runs stateless... Because the run is stateless and non-interactive, a loop can begin and end
  without anyone starting it."
- agent 把诊断写成 Stage 1 格式的 intent.md（异常与证据、建议结果、受影响系统、开放问题）。
- 服务 owner 或 on-call 工程师分诊队列：Fix now、schedule、dismiss。"Dismissals tune the bands and help
  to reduce noise."
- 修复上线后为该事故补一条 eval。

示例产物：

```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```

Governance："The tier boundaries are enforced from version-controlled config, with permissions and
managed settings denying production access. ... the runbooks the agent may trigger were approved in
advance."

度量：Leading — 从带被突破到 intent.md 进入分诊队列的时间，对比旧的"事故到复盘行动"时间；
Lagging — findings 变成已合并修复的占比、同类事故的重复率。

原文给的三个例子：
- CI 测试失败率突破 3σ → agent 隔离 flaky test 或开 revert PR，由 review gate 决定。
- 部署后 5xx 率突破 3σ 且窗口内有部署 → agent 触发既有 rollback 流水线。
- PR cycle time 触发漂移规则 → agent 为工程领导层写报告，"which shows the harness works for process
  metrics as well as production ones."

> "Detection stays deterministic. Claude is invoked once a band is breached, and the tier sets what it
> may do."

### Play: Recurring codebase scans

> "A security scan is a point-in-time statement about a codebase under a particular model, and both
> halves go stale: the code changes every week, and each model generation finds vulnerabilities the
> previous one missed."

Claude Security 是托管形态：连接 GitHub 仓库，扫描在 Anthropic 基础设施上以 Claude Mythos 5 运行，
"with each finding validated before it is reported and a confidence rating attached."

执行步骤要点：按 repo/service/team 组织成 projects 使 findings 归属清晰；首次全量扫描当作基线
（"The first scan will likely surface findings in code that was considered clean."）；活跃服务默认每周
一次；带着 confidence rating 分诊，dismiss 时给理由以免同一 finding 下次以新问题重现；有界 finding 走
PR review gate（"The agent that proposed the fix has no route to approve it."）；超出一个 patch 的写成
intent.md 回到 Stage 1；修复上线后为该漏洞类别补 eval；可导出 CSV/Markdown 或用 webhook 让既有 tracker
保持 system of record 地位。

Infrastructure（原文列出的商业条件）：Claude Enterprise 组织的 public beta；需安装 Anthropic GitHub App
（cloud-hosted github.com）、启用 Claude Code on the Web、开启 Extra Usage 并设置支出上限、为执行扫描的
人员配 premium seats、由 admin 在 claude.ai/admin-settings/claude-code 开启。
"Scans are billed on consumption at Mythos 5 rates."

Governance："Claude Security augments existing static analysis and dependency scanning. The deterministic
checks stay in CI, and the model-driven scan covers the context-dependent vulnerabilities those checks
are not built to find."

### Play: Claude on call with Claude Tag

Claude Tag（public beta，Slack）让 Claude 以自己的身份成为频道成员，"so each new incident gets a first
responder and the response itself becomes part of the loop and memory for future incidents."
经 MCP 访问，Claude 验证指标回到基线并在 thread 中确认，把复盘写入版本控制的 lessons 文件。

> "The channel is the audit trail: request, diagnosis, human authorization and fix all stay where the
> incident was handled."

小而有界的修复以 PR 走 review gate，更大的写成 intent.md 回到 Stage 1。
