01 · Why

为什么要重构：目标函数变了

代码库是 agent 的运行环境

OpenAI 零手写代码实验的第一条结论是瓶颈在环境而非模型：早期进展慢，是因为缺工具、抽象与内部结构；卡住时要问“缺什么能力，怎样让它对 agent 可读且可强制执行”。自述

Böckeler 把代码库可被约束的程度称为 harnessability：强类型、清晰的模块边界、能替 agent 屏蔽细节的框架，决定了能给 agent 套上多完备的 harness。

对人好维护，对 agent 也好维护，但 agent 更在乎上下文成本

两者高度重合，但 agent 对上下文成本敏感得多：它每次变更都要把相关代码从零读进上下文，也没有人带着的那套隐性 harness——约定、对复杂度的痛感、问责、组织记忆（Böckeler）。推断 · 置信度中 由此多出三条重构理由：

重构的传统理由（对人）agent 时代新增的理由
降低理解成本降低每次变更的上下文成本（token 与轮次）
降低修改风险提高可被机械约束的程度：类型、依赖规则、结构测试能覆盖多少
让设计意图可读让设计意图对 agent 可执行：规则写进 linter、分层写进结构测试，而不只写进文档

结构债可以按 token 计价 测量 · 单实验 · 单开发者 · greenfield

Thoughtworks（Giles Edwards-Alexander，2026-07-30）利用“agent 不会学习”：每做完一步重构，就让全新 sub-agent 重放完全相同的代表性变更（在 Firestore 层新增一个三方法 trait），记录 token 后丢弃。对象是一个约 15 万行、全部由 agent 写成的应用里的数据访问层——单个 17,155 行的 Rust 文件。重构手法全部取自 Fowler《重构》第 2 版。

收益

读取量降了 83%

最大文件 17,155 → 3,695 行。数据访问层总行数只小幅下降（17,155 → 16,608），最终拆成 19 个文件。

机制

变的是读取路径

节省来自 agent 能找到并只读所需的最小文件子集。作者判断随机把文件切小不会有同等效果。

成本

上界 500 万 token

重构本身未精确计量；上界含两次制定计划与实验设计。全程约 8 小时，基本无人值守。

证据冲突：作者结论与数据不符作者称实验显示了重构“in time and money”的价值，但结果表中同一变更的耗时由 342 秒变为 454 秒，并未下降；时间上的价值在表中找不到支撑。

回本与选题 推断 · 置信度低，仅到量级

≈38次

5,000,000 ÷ 132,204。分子是作者账户在时间窗内的总消耗（含非重构工作），分母是按文件字符估算的读取量，两者口径不同，输出 token 又更贵——只能说量级是“几十次”同类变更。

推断 · 置信度中 · 选题判据优先重构被 agent 频繁改动、且单次变更要读进大量无关代码的热点：改动频率决定复利次数，无关代码的体量决定单次收益。

引入时间点提前

OpenAI 的另一个判断把时间点也改了：人类团队常推迟到数百名工程师规模才引入的严格分层架构，对 agent 是早期前提。

推断 · 置信度中原因是 agent 的吞吐让一个小团队在几个月内产出了过去大团队才有的代码量（约 100 万行）。架构约束的收益随代码量增长，引入时点也随之前移。
02 · Target state

改成什么样：agent 友好代码库的目标形态

总目标用 Salomon 的判据：好的代码库，能让一个不熟悉它的 agent 找到正确的上下文、做窄范围的变更并完成验证，而不必把整个系统装进工作记忆。下面五条是达到这个判据的手段。

上下文经济性

让 agent 只读它需要的

实践者观点收益有单实验测量
  • 小而内聚的文件；目录浅而可预测、按领域命名（领域在顶层、用例切片在下一层）；避免缩写与重名——Marmelab 称之为“代码 SEO”。
  • Salomon 的五项特征：局部性（Locality）、影响半径（Blast radius）、边界完整（Boundary integrity）、可导航（Navigability）、窄的重新构建与测试范围（Rebuild/test scope）。
  • 上下文是有限资源，性能随长度逐渐下降（context rot）。Anthropic 推荐混合策略：少量内容常驻，其余按需检索；长任务靠压缩、外置笔记和子 agent 回传摘要。
  • 第一部分 Thoughtworks 的 −83%，就是这一条的收益。

显式契约

让规则能被机器检查

实践者观点
  • 强类型让接口自带文档；显式边界防止 agent 推断出错误的契约。
  • 消除全局状态、时序耦合、语义耦合（Salomon 列了六类有害耦合）；抵制过早抽象。
  • 在 ARCHITECTURE.md 里点名众所周知的架构模式，agent 就不必逐行读实现。这是实践者的经验之谈，未见实证；这份文件本身也应保持简短。

给 agent 读的文档

入口极简，深层按需

厂商与实践者效果证据冲突
  • 三方做法同向：OpenAI 用约 100 行的 AGENTS.md 当地图，指向结构化的 docs/；Anthropic 让 CLAUDE.md 只写删掉就会出错的内容，按场景才需要的知识放进按需加载的 skills；Marmelab 用短入口文件，加上就近嵌入代码库的文档。
  • 统一的命令入口（如 Makefile）、自带说明的 CLI、架构决策记录（ADR），也都是给 agent 的接口。
  • AGENTS.md 与 CLAUDE.md 并存：在 2,586 个有上下文文件的仓库里，CLAUDE.md（45.9%）仍比 AGENTS.md（39.5%）常见；Claude Code 自 2026-09-18 起，在没有 CLAUDE.md 时读取 AGENTS.md。
  • 这类文件到底有没有用，证据相互冲突（见第八部分）。

为 agent 设计接口

工具和报错也是 UX

基准测量
  • SWE-agent（NeurIPS 2024）提出 agent-computer interface（ACI）：把 agent 当作一类新的终端用户来设计工具。四条原则：动作简单、动作紧凑、反馈充分而简洁、用护栏阻断错误扩散。
  • 在它的基准上，专门设计的接口比直接给 shell 高 10.7 个百分点。
  • “反馈充分而简洁”与第三部分“检查信号要写明怎么改”是同一条原则。

prompt 也是架构制品

代码评审之外，再加一层架构评审

立场论文
  • 开发者用自然语言描述需求，agent 几秒内就做出框架选择、基础设施和集成决策——这些是架构决策，却没人评审（arXiv 2604.04990 称之为 vibe architecting）。
  • 示意：只改 prompt，同一个聊天机器人的代码从 141 行涨到 827 行（5.9 倍），依赖图和故障模式随之改变。三个 prompt 各跑一次，作者自称是示意而非实验证明。
  • 主张：把 prompt 规范和 agent 做出的架构决策纳入评审。这是在代码评审之外新增的一层，不是替代。
推断 · 置信度中五条形态对应第一部分的三条新理由：降低上下文成本 → 上下文经济性；让规则能被机器检查 → 显式契约；让设计意图对 agent 可执行 → 给 agent 读的文档、为 agent 设计接口、prompt 评审。它们大多是老原则，新的是 agent 对上下文成本敏感得多。也要先打基础再上工具：Anthropic 把“基础没做好就先接 MCP”列为常见错误。

信号要带修正指引

否则 agent 绕过而不是修正

Böckeler 的实验里，圈复杂度是 agent 唯一频繁直接上调阈值的规则类别，而这条规则恰好没配修正指引。OpenAI 的 lint 错误信息直接内嵌修复指令。

推断 · 置信度中 阈值变成了可被优化的目标——古德哈特定律在 agent 身上的形态。

分工

计算型管局部，推理型管跨文件

计算型 sensor 在文件与函数层面最好；跨文件的模块化与耦合要靠 LLM 的语义解释。原始耦合数据直接丢给模型“乏善可陈”，推理型评审 skill 却找到了一批真问题，再跑一次又找到首轮漏掉的——重要分析值得多跑。

04 · Prerequisite

前提：验证网先行

执行重构

让 agent 能安全地改

Thoughtworks 的每一步都可单独测试、也都单独测过（原文称这比多数人类工程师的做法更严格）。

推断 · 置信度中 这很可能是它能 8 小时基本无人值守的条件之一。

sensor 的可信度

让“绿”是真的绿

Böckeler 的实验里，一个语句覆盖 100% 的文件没有任何单元测试，变异测试报出 13 个存活变异体。测试也由 AI 写时，覆盖率门禁要配变异测试。

长期演化

让系统不崩在回归上

失败集中在防回归，错误沿依赖链滚雪球。适度而有纪律的测试验证得分最高，验证过度同样偏低；频繁改同一文件却很少跑测试的盲目试错最差。

两条约束，防止“验证优先”走样

约束结果，不规定过程

Claude Code 官方最佳实践：被要求找缺口的 reviewer 总能报出一些，追逐每条发现会导致过度工程，只标记影响正确性或需求的缺口；确定性的 Stop hook 门禁连续拦截 8 次后会被强制放行。Osmani 的对策是把举证责任放回作者：PR 附可运行的证据，而不是加大 review。

05 · Legacy

遗留系统：最需要 harness 的地方，最难建 harness

没有测试、边界模糊、弱类型的代码库，恰恰最难给 agent 套上约束（Böckeler）。而且企业代码里满是没写下来的领域知识，agent 拿不到，所以不会自己完成现代化（Harrer）——不存在按一下按钮就完成的现代化。

来源说明：下面的方法框架主要来自 Markus Harrer（INNOQ）在 iSAQB 博客的访谈（2026-05-18），是一位实践者的框架，不是多方共识；Osmani、Google、AWS 与 Thoughtworks 提供部分独立佐证。
方法做法出处与证据
先缩小范围能用标准软件替代、外包或删掉的，先不现代化——“The less you do, the more of it you can do”Harrer 转引 Hanselman观点Thoughtworks 与 AWS 都有先识别死代码、未用作业再决定退役的环节
先铺 characterization tests用代表性输入录下现有系统的输出，改完再比对；“丑陋”的现有行为也要锁住，业务可能正依赖它Harrer；Osmani（2026-09-14）独立主张同一做法观点 · 两源

06 · Sequence

落地顺序：六步，每步有门槛

推断 · 置信度中：方向有多个来源支持，顺序本身未经实证检验

先度量、再铺验证网、再建 agent 接口层、再做边界重构、再批量执行，最后把偿还变成常态。“验证网先行”与 Harrer（characterization tests 先行）一致，“批量放在最后”与 Osmani（“Parallelize last”）一致。每两步之间是进入下一步的门槛。

  1. 0

    度量与缩范围

    选几个代表性变更，记录输入 token 与改动文件数；先砍掉不必现代化的部分。

    依据：Thoughtworks 的计价法 · Böckeler 的“小改动要改的文件数” · Harrer 的缩范围

    门槛知道热点在哪、基线是多少

  2. 1

    验证网

    characterization tests、CI 门禁；AI 写测试时配变异测试。

    依据：Harrer · Osmani · Böckeler · SWE-Milestone

    门槛热点区域的行为被锁住

  3. 2

    agent 接口层

    短入口文件做地图（只写推断不出的约定），深层文档按需加载；统一命令入口；依赖与分层规则写成 linter。

    依据：OpenAI（约 100 行的入口文件，指向结构化 docs/） · ETH 的对照评测（仓库概览类内容无益，成本 +20% 以上） · Claude Code 官方建议（规则文件只写删掉就会出错的内容）

    门槛规则能机械执行，而不只是写在文档里

  4. 3

    边界重构

    人画区域图、划 seam；按 agent 的读取路径拆热点大文件、去重。

    依据：Osmani 的区域 · Harrer 的 seam · Thoughtworks 的 −83%

    门槛代表性变更的 token 与文件数下降

  5. 4

    批量 campaign

    小而定向、每单元可独立测试；机械变更优先走确定性转换。

    依据：/batch · Bun · Google · Harrer 的 recipe

    门槛既有测试全绿、人审每个变更

  6. 5

    持续偿还

    定期 GC 任务、周期性推理型评审、阈值上调可见。

    依据：OpenAI · Böckeler

    不结束：与传统“重构项目”的根本区别
推断 · 置信度中在 agent 吞吐下结构债持续产生，而 agent 不会自发偿还，所以重构不能是一次性项目，必须是 harness 里一个一直在跑的职能。
07 · Background

背景：分歧在范式，收敛在实践

“AI 写代码之后，代码还重要吗？”大致有两种立场：一端认为意图（prompt 或 spec）会成为一等公民，代码降为可以再生成的中间产物；另一端认为代码与工程判断仍是责任落点。把每位代表的范式判断和工程实践分开看：

代表范式判断工程实践：人在哪里
意图优先：prompt / spec 成为一等公民
KarpathySoftware 3.0 · 2025-06程序从代码（1.0）、神经网络权重（2.0）扩展到用自然语言写给 LLM 的 prompt（3.0）；三者并存，3.0 正在“吃掉”软件栈。“最热门的新编程语言是英语”“keep the AI on the leash”：小步增量，人类验证者是瓶颈；这是“agent 的十年”而不是“agent 之年”。他自己做 MenuGen 时，“the code was actually the easy part”，认证、支付、部署花了一周
Spec 即源代码spec-as-source · Tessl 2025人只维护规格，代码由规格再生成、不再手改（三个层级见下）旗手 Tessl 到 2026-09 已转型为 agent enablement 平台；Böckeler 2025-09 试用时判断，Spec Kit 与 Kiro 的实际形态是 spec-first

“spec 是新的源代码”指什么

规格驱动开发（SDD）是先写规格、再让 agent 实现。Böckeler 2025-10 把它分成三个层级，区别在于规格活多久、人维护的是什么：

  1. spec-first规格先行

    编码前写规格，完成后可以丢弃；之后维护的是代码。

    适合：一次性原型、低风险探索
  2. spec-anchored规格为锚

    实现后继续维护规格，后续变更以它为锚；规格与代码一起维护。

    适合：大多数长期维护的软件
  3. spec-as-source规格即源代码

    人只编辑规格，代码由规格再生成、不再手改。2025 年 Tessl 生成的文件上标着 “GENERATED FROM SPEC - DO NOT EDIT”。

    适合：生成链和验证链足够确定的特定领域
规格用完即弃，人维护代码人只维护规格，代码再生成

“spec 是新的源代码”说的就是第三层：规格取代代码，成为人维护的那份源文件。Böckeler 推测这一层会同时继承模型驱动开发（MDD）的僵化和 LLM 的非确定性，并以 MDD 在业务应用领域从未流行起来为参照。“适合”一行参考 Piskala（arXiv 2602.00180）的建议。

Agent-native 的五条原则

Every 的《Agent-native Architectures》（Dan Shipper 与 Claude 合著，2026-01）讨论的是怎么构建应用，不是怎么维护代码库。它的出发点是：功能不是你写的代码，而是你描述的结果，由 agent 带着工具在循环里完成，直到达成。五条原则：

  1. Parity对等用户能在界面上完成的事，agent 都能通过工具完成。这是地基，没有它其余都不成立。
  2. Granularity粒度工具是原子原语，判断留给 agent。检验标准：想改变行为时，你改的是 prompt，还是要重构代码？
  3. Composability可组合有了原子工具和对等，新功能只需写一段新 prompt。比如“每周回顾”就是一段 prompt：读本周改过的文件、总结变化、建议下周的三个优先事项。
  4. Emergent capability涌现能力agent 能完成没被专门设计过的任务。观察用户实际在要什么，再把高频模式固化成专用工具或 prompt。
  5. Improvement over time随时间改进应用靠积累的上下文和 prompt 迭代变好，不必发布新代码。

指南自己注明：一部分模式经过 Dan 验证，另一部分是 Claude 在构建过程中的贡献、尚待验证。第二条的检验标准正好关系到重构：在 agent-native 应用里，改行为靠改 prompt，而不是重构代码。

为什么说实践已经收敛

  • 意图优先一端的代表，在工程实践上都保留了人的验证角色（见上表“工程实践”一列）；spec-as-source 的旗手已经转型。
  • Karpathy 审 10,000 行 diff 时说 “I'm still the bottleneck”。
  • Osmani（2026-01）：瓶颈从“写代码”移到了“证明代码能用”，对策是让作者在 PR 里附可运行的证据，而不是加大 review。
  • Sonar 2026 开发者调查（n=1,149，自报）：96% 不完全信任 AI 代码的功能正确性，但完全同意“提交前总是检查”的只有 48%。
  • Anthropic 2025-08 对 132 名内部工程师与研究员的调查：超过一半的人能完全委派给 Claude 的工作只占 0–20%。
  • SWE-Milestone：agent 在长期演化中缺的是不引入回归的能力（见“验证网先行”）。
推断 · 置信度中分歧仍在范式层：长期看代码会不会被 prompt 或 spec 取代，没有定论。但工程实践已经收敛到“验证是瓶颈”。真正待解的是：在 agent 的吞吐下，由谁、用什么来验证。本文的回答：确定性 sensor 管局部，推理型评审管跨文件，人管选题与高风险区。

还没定论的问题与证据强度

问题现状
spec 是否是新的源代码即上文的 spec-as-source。旗手是 2025 年的 Tessl（已转型）；GitHub Spec Kit 的方法论文档在理念上接近这一层（代码是“持续再生成的输出”），但工具的实际形态是 spec-first；Böckeler 担心这一层兼有 MDD 的僵化与 LLM 的非确定性
规则 / 上下文文件写多详尽形态已收敛为“常驻入口极简 ＋ 深层按需加载”；效果证据相互矛盾：ETH 的对照评测（arXiv 2602.11988）测得成本 +20% 以上且不提升成功率，Lulla 等（arXiv 2601.20404）测得 Codex 运行时间 −28.64%；McMillan（arXiv 2605.10039）在 25–500 行内没测到文件长度影响指令遵循，与 Claude Code 官方文档“文件膨胀会导致规则被忽略”的说法相左证据冲突
人能否退出验证环没有一手来源支持“现在”退出：AaaS 也只在 2028 年以后的愿景阶段让人退到元治理层；Google 每个变更都人审
agent 该不该在循环里做 TDD目前唯一的评估（Böckeler，小样本）显示无收益甚至略差；需要更大样本
重构粒度与执行质量OpenAI 的小 PR 顺利、Thoughtworks 的 15 步大重构粗糙；缺同仓库对照
结构债的回本点只有一个实验、一种变更；换一种变更类型、换一个模型，−83% 能保持多少，未知

这些结论有多可靠

  • 一手实验都是单点：Thoughtworks（单实验、单开发者、greenfield、每步只测一次）、Böckeler（单人单应用、无对照）、OpenAI（公司自述、无对照，且被 Böckeler 指出缺少功能与行为验证）。
  • 唯一的大样本基准是 SWE-Milestone（98 个里程碑、12 个模型），它测的是功能演化，不是专门的重构。
  • 唯一的工业级迁移数据是 Google（3 名开发者、同一类迁移、时间节省是自估）。
  • 遗留系统的方法框架主要出自 Harrer 一人，Osmani 是较独立的佐证；campaign 案例的数字来自厂商或转述。
  • 标为“推断”的是本文的判断：回本量级置信度低，其余推断置信度中。首页机制图把三条回路画在一起是归纳；“agent 对上下文经济性远比人敏感”只有机制层面的支撑，程度没有测量。

什么证据会推翻“agent 不会自发偿还结构债”：agent 在无显式重构指令时，自行识别并完成有度量收益的结构性重构（如降低后续变更的 token 或改动文件数），且在多仓库上可复现。
