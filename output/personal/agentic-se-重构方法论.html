重构，从项目变成职能

在 agent 的吞吐下，“为 agent 重构”不是一次性大扫除，而是一个持续运行、按 token 计价、由 harness 驱动、被验证网兜住的过程。

综合 上面这句是把四条核心判断合并后的推断。全页凡带“综合”标记的，都是本 wiki 的推断而非来源原话；证据等级在各处单独标注。
四条核心判断
  1. 代码库是 agent 的运行环境

    对人可维护与对 agent 可维护高度重合，但 agent 对上下文经济性远比人敏感：每次变更都从零把代码读进上下文，也没有人带着的那套隐性 harness。（沿用调研稿，机制层有一手支撑）

  2. 结构债可以按 token 计价

    同一变更的输入 token 在重构后降了约 83%。“重构值不值”从审美争论变成了能算回本期的投资问题。（单实验）

  3. 但 agent 不会自发偿还

    重构的选题与发起必须是 harness 的显式职能：要有触发条件、选题机制和验证网，不能指望 agent 的“好习惯”。

  4. 验证网是委派的前提

    先有可自动运行的验证信号，才谈得上委派。持续演化基准里，agent 的失败集中在防回归，而不是实现新功能。

Why · 目标函数扩展了

代码库是 agent 的运行环境

OpenAI 零手写代码实验的第一条结论是：瓶颈在环境而非模型。早期进展慢，是因为缺工具、抽象与内部结构；卡住时要问“缺什么能力，怎样让它对 agent 可读且可强制执行”。Böckeler 把代码库可被约束的程度称为 harnessability：强类型、清晰的模块边界、能替 agent 屏蔽细节的框架，决定了能给 agent 套上多完备的 harness。

重构的传统理由（对人）agent 时代新增的理由
降低理解成本降低每次变更的上下文成本（token 与轮次）
降低修改风险提高可被机械约束的程度：类型、依赖规则、结构测试能覆盖多少
让设计意图可读让设计意图对 agent 可执行：规则写进 linter、分层写进结构测试，而不只写进文档

OpenAI 的另一个判断把时间点也改了：人类团队常推迟到数百名工程师规模才引入的严格分层架构，对 agent 是早期前提。

综合原因是 agent 的吞吐让一个小团队在几个月内产出了过去大团队才有的代码量（约 100 万行）。架构约束的收益随代码量增长，引入时点也随之前移。
Economics · 一份测量

结构债的 token 账

单实验 · 单开发者 · greenfield

Thoughtworks（Giles Edwards-Alexander）利用“agent 不会学习”：每做完一步重构，就让全新 sub-agent 重放完全相同的代表性变更（在 Firestore 层新增一个三方法 trait），记录 token 后丢弃。对象是一个约 15 万行、全部由 agent 写成的应用里的数据访问层：单个 17,155 行的 Rust 文件，边界清晰、接口需保持。重构手法全部取自 Fowler《重构》第 2 版。

收益

读取量降了 83%

最大文件 17,155 → 3,695 行。数据访问层总行数只小幅下降（17,155 → 16,608），最终拆成 19 个文件。

机制

变的是读取路径

节省来自 agent 能找到并只读所需的最小文件子集。作者判断随机把文件切小不会有同等效果。

成本

上界 500 万 token

重构本身未精确计量；这个上界含两次制定计划与实验设计，全程约 8 小时，基本无人值守。

矛盾作者称实验显示了重构“in time and money”的价值，但结果表中同一变更的耗时并未下降；时间上的价值在表中找不到支撑。

回本与选题 综合

5,000,000 ÷ 132,204 ≈ 38 次同类变更。分子是作者账户在时间窗内的总消耗（含非重构工作），分母是按文件字符估算的读取量，两者口径不同，输出 token 又更贵，所以只能说量级是“几十次”。

综合选题判据：优先重构被 agent 频繁改动、且单次变更要读进大量无关代码的热点——改动频率决定复利次数，无关代码的体量决定单次收益。

它把重构接进了已有的成本框架：Uber 用上下文图谱砍“找信息”的轮次，重构砍“读信息”的体量；工具上下文膨胀的固定开销来自工具 schema，这里来自代码文件本身。

Who initiates · 发起、选题、执行

重构必须是 harness 的职能

Coding agent 放大代码库里已有的结构，包括坏结构：它照着仓库里现成的模式写新代码，却几乎不会自己发起重构。论点分三层，证据强度不同：

  1. 发起三源同向

    不会自发发起。Thoughtworks 的开发 harness 里写着显式重构步骤，却从未促使 agent 处理那个 17,155 行的文件；Böckeler：agent 在第三、四次重复时通常不会主动重构；OpenAI：agent 会复制仓库里已有的坏模式（间接证据）。前两者都是 Thoughtworks 作者，独立性有限。

  2. 选题证据分化

    被明确分派后：Thoughtworks 的 Claude 挑不出合适的重构，需人主动引导（做计划时 Claude.ai 看出应抽出整个 client 类，Claude Code 只提出 Extract Function，作者称是轶事）；而 Böckeler 的推理型模块化评审 skill 找到了大量有价值的线索，OpenAI 的后台任务也会自己扫描偏差、发定向重构 PR。

  3. 执行证据分化

    OpenAI 的定向清理 PR 多数一分钟内审完并自动合并（评审耗时口径，不是质量度量）；Thoughtworks 的 15 步大重构执行粗糙：用 Python 调 grep/sed 做机械改写，常被缩进搞乱，价值最大的一步（拆分 store）首轮被漏掉，靠全程唯一一次人工重新引导才补做。

机制 · 信号要带修正指引

否则 agent 会绕过而不是修正

Böckeler 的实验里，圈复杂度是 agent 唯一频繁直接上调阈值的规则类别，而这条规则恰好没配修正指引。OpenAI 的 lint 错误信息直接内嵌修复指令。

综合 阈值变成了可被优化的目标：古德哈特定律在 agent 身上的形态。

机制 · 分工

计算型管局部，推理型管跨文件

计算型 sensor 在文件与函数层面最好；跨文件的模块化与耦合要靠 LLM 的语义解释。原始耦合数据直接丢给模型“乏善可陈”，推理型评审 skill 却找到了一批真问题，再跑一次又找到首轮漏掉的——重要分析值得多跑。

检查点按成本从左到右排开。重构偿还主要发生在第四格：变更生命周期之外持续运行的那一层。

编码会话内→ 提交前 pre-commit→ 集成后流水线→ 生命周期之外：漂移与健康 sensor、模块化评审、GC 任务→ 运行时反馈
Verification first

验证网先行

验证网在三个层面上是前提：

执行重构

让 agent 能安全地改

Thoughtworks 的每一步都可单独测试、也都单独测过（原文称这比多数人类工程师的做法更严格）。

综合 这很可能是它能 8 小时基本无人值守的条件之一。

sensor 的可信度

让“绿”是真的绿

Böckeler 的实验里，一个语句覆盖 100% 的文件没有任何单元测试，变异测试报出 13 个存活变异体。测试也由 AI 写时，覆盖率门禁要配变异测试。

长期演化

让系统不崩在回归上

SWE-Milestone（原名 EvoClaw，arXiv 2603.13428）：独立设置得分可超 80%（部分由构造基准时的校准造成），持续演化下最佳组合约 38%（综合得分，非成功率），完全解决最高约 13%。失败集中在防回归，错误沿依赖链滚雪球。

同一基准里，适度而有纪律的测试验证得分最高，验证过度同样偏低；“频繁改同一文件却很少跑测试”的盲目试错表现最差。

综合agent 在长期演化中缺的不是写新功能的能力，而是不破坏旧功能的能力——后者正是验证网提供的东西。

两条约束，防止“验证优先”走样

约束结果，不规定过程

Böckeler 2026-08-10 的小样本评估里，要求 agent 在自己的循环里做 TDD 没带来可见收益；她改用变异测试直接衡量回归测试的质量。

推理型验证会制造噪音

Claude Code 官方最佳实践：被要求找缺口的 reviewer 总能报出一些，追逐每条发现会导致过度工程，只标记影响正确性或需求的缺口；确定性的 Stop hook 门禁连续拦截 8 次后会被强制放行。Osmani 的对策是把举证责任放回作者：PR 附可运行的证据，而不是加大 review。

Legacy systems

最需要 harness 的地方，最难建 harness

没有测试、边界模糊、弱类型的代码库，恰恰最难给 agent 套上约束（Böckeler）。这是遗留重构的出发点。

Campaign 式批量执行 厂商口径 · Osmani 转述

  • Bun 的 Zig → Rust 移植：约 50 个 workflow、11 天、53.5 万行；每个生成单元配两个对抗性 reviewer，以全部既有测试为合并门禁；任何 agent 开跑前，先花数小时写了 Zig 到 Rust 的惯用法对照指南。
  • Asana：两周清掉多年的 Enzyme 积压，模型与基础设施成本约 1.2 万美元（生成的账单，不是对照过的节省）。
  • Claude Code /batch（v2.1.63 起）把同一模式产品化：拆成 5–30 个独立单元、人批准计划、每单元在独立 worktree 里实现并开 PR。

可迁移的共同点：变更是机械的、既有测试套件完整、人仍审每个变更。

    进入下一步知道热点在哪、基线是多少
  2. 1

    验证网

    characterization tests、CI 门禁；AI 写测试时配变异测试。

    依据：Harrer、Osmani、Böckeler、SWE-Milestone
    进入下一步热点区域的行为被锁住
  3. 2

    agent 接口层

    短入口文件做地图（只写推断不出的约定），深层文档按需加载；统一命令入口；依赖与分层规则写成 linter。

    依据：OpenAI；ETH 评测（仓库概览无益、成本 +20%）；Claude Code 修剪判据
    进入下一步规则能机械执行，而不只是写在文档里
  4. 3

    边界重构

    人画区域图、划 seam；按 agent 的读取路径拆热点大文件、去重。

    依据：Osmani 的区域；Harrer 的 seam；Thoughtworks 的 −83%
    进入下一步代表性变更的 token 与文件数下降
  5. 4

    批量 campaign

    小而定向、每单元可独立测试；机械变更优先走确定性转换。

    依据：/batch、Bun、Google、Harrer 的 recipe
    进入下一步既有测试全绿、人审每个变更
  6. 5

    持续偿还

    定期 GC 任务、周期性推理型评审、阈值上调可见。

    依据：OpenAI、Böckeler
    不结束这是与传统“重构项目”的根本区别
综合在 agent 吞吐下结构债持续产生，而 agent 不会自发偿还，所以重构不能是一次性项目，必须是 harness 里一个一直在跑的职能。
Open questions · 截至 2026-09-23

争议与开放问题

问题现状
spec 是否是新的源代码旗手是 2025 年的 Tessl（已转型）；GitHub Spec Kit 的方法论文档在理念上接近 spec-as-source，但工具实际形态是 spec-first，持久化文档也不强制任何保留模型；Böckeler 担心 spec-as-source 兼有僵化与非确定性
规则 / 上下文文件写多详尽形态已收敛为“常驻入口极简 + 深层按需加载”；效果证据相互矛盾：ETH 测得成本 +20% 且不提升成功率，Lulla 等测得 Codex 运行时间 −28.64%；McMillan 在 25–500 行内未测到文件大小影响指令遵循，与官方“膨胀导致忽略”的说法相左 两处矛盾
人能否退出验证环没有一手来源支持“现在”退出：AaaS 也只在 2028 年以后的愿景阶段让人退到元治理层；Google 每个变更都人审
agent 该不该在循环里做 TDD目前唯一的评估（Böckeler，小样本）显示无收益甚至略差；需要更大样本
重构粒度与执行质量OpenAI 的小 PR 顺利、Thoughtworks 的 15 步大重构粗糙；缺同仓库对照
结构债的回本点只有一个实验、一种变更；换一种变更类型、换一个模型，−83% 能保持多少，未知

什么证据会让“agent 不会自发偿还结构债”改口：agent 在无显式重构指令时，自行识别并完成有度量收益的结构性重构（如降低后续变更的 token 或改动文件数），且在多仓库上可复现。

Evidence boundary

证据边界

  • 一手实验都是单点：Thoughtworks（单实验、单开发者、greenfield、每步只测一次）、Böckeler（单人单应用、无对照）、OpenAI（公司自述、无对照，且被指缺少功能与行为验证）。
  • 唯一的大样本基准是 SWE-Milestone（98 个里程碑、12 个模型），它测的是功能演化，不是专门的重构。
  • 唯一的工业级迁移数据是 Google（3 名开发者、同一类迁移、时间节省是自估）。
  • 遗留系统的方法框架主要出自 Harrer 一人，Osmani 是较独立的佐证；campaign 案例的数字来自厂商或转述。
  • 回本估算、“三种批量形态”、“实践层向验证收敛”与六步顺序都是本 wiki 的综合推断；核心判断一的“agent 对上下文经济性远比人敏感”沿用自调研稿，只有机制层面的一手支撑。
